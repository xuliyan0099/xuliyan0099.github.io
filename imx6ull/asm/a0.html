为什么非写不可

第 00 章约 18 分钟★ 必读

先说结论：这门手艺不是用来写产品代码的

没人会拿纯汇编去写一个文件系统。手写汇编的真正用途只有三个，而且都很硬：

  1. 读懂反汇编。你在板子上跑一个驱动，内核 panic，串口吐出一段 oops，中间是十几个十六进制数字和一段反汇编。这一段就是现场唯一的证据。认不出来，你只能改代码猜；认得出来，你能指出「它在 r0=0 的时候取了 [r0,#0x10]」。
  2. 读懂启动代码。i.MX6ULL 上电后不是从 C 开始跑。Boot ROM 读 IVT、跳到你的 u-boot，u-boot 的 _start 前几百行全是汇编：关看门狗、设栈、清 BSS、切 CPU 模式、开 MMU、最后才 bl main。看不懂这几百行，启动阶段的问题你只能凭运气。
  3. 看穿寄存器配置。外设配置的本质就是往某个地址的某几位写值。你在 C 里写 writel(0x5, base + 0x10)，编译器忠实地把它变成一条 str——但你对「清掉了哪几位、置了哪几位、哪些位保持原样」是瞎的。手写过 bic / orr / bfi，你才会明白为什么内核到处是「读—改—写」，而不是直接赋值。
一句话记住：C 会骗你，寄存器不会。你在 C 里写的 *p = 3，可能被优化成一条 str，也可能整段被删掉；你写的 delay() 空循环，可能一条指令都不剩。汇编里没有这些中间层。

场景一：一段 oops 里的反汇编

假设串口打出这么一段（节选，地址已简化）：

Unable to handle kernel NULL pointer dereference at virtual address 00000010
PC is at my_led_write+0x28/0x60
LR is at vfs_write+0x1a0/0x2c0

然后 objdump -d 里 my_led_write 附近是这样：

00000000 <my_led_write>:
   0:   push   {r4, lr}
   4:   ldr    r4, [r0, #0x30]      @ r0 = file 指针，取 private_data
   8:   cmp    r4, #0
   c:   beq    0x3c                @ 空指针就跳去报错
  10:   ldr    r3, [r4, #0x10]      @ ← 出事的就是这一条
  14:   str    r3, [r4, #0x14]

对照 oops 里的 virtual address 00000010，结论几乎不用推：r4 是 0，说明 private_data 没被赋值（或者设备没 open 就被写），于是 r4+0x10 = 0x10，正好是出错地址。

这就是手写汇编的实际收益：地址偏移和寄存器名是可读的证据链。你能一眼看出「它在拿一个结构体第 0x10 字节的字段」，而不是「反正崩了」。

场景二：u-boot 的 _start

i.MX6ULL 的 u-boot 第一段代码，结构永远是这几步（顺序不能乱）：

_start:
    @ 1. 把自己搬到一个干净的地址（relocate），因为 DDR 还没跑起来时可能运行在 SRAM
    @ 2. 设栈：sp = 某块确定的内存顶端
    @ 3. 清 BSS、清 cache、关 MMU 与 D-cache（此时还是物理地址直跑）
    @ 4. 保存启动参数（r0/r1/r2 里是 Boot ROM 传进来的机器类型、dtb 地址）
    @ 5. 切到 SVC 模式、开 I-cache
    @ 6. bl board_init_f → 板级初始化 → 重定位 → board_init_r → 进命令行

其中每一步都是「关一个东西 / 开一个东西」。比如关 MMU 的那几行：

    mrc  p15, 0, r0, c1, c0, 0     @ 读 SCTLR
    bic  r0, r0, #0x1              @ 清 M 位：关 MMU
    bic  r0, r0, #0x4              @ 清 C 位：关 D-cache
    mcr  p15, 0, r0, c1, c0, 0     @ 写回
    isb

mrc/mcr 是协处理器访问指令，操作的是 CP15 的系统控制寄存器——这种东西 C 里没法直接表达，只能靠内联汇编或者 .S 文件。你不需要背这些位，但需要能认出「这是在改 SCTLR 的 M/C 位」。

场景三：writel 到底做了什么

C 侧的写法：

writel(0x5, base + 0x68);   /* 想把这个脚的 MUX_MODE 设成 ALT5 */

这句的语义是「把 0x68 偏移处的整个 32 位寄存器写成 5」。如果那个寄存器里别的位正被别人用着（比如 SION、或者相邻功能的选择位），你就把它们一起清成 0 了。

汇编层面看得很清楚：一条 str，一次全覆盖写。

    mov  r1, #5
    str  r1, [r0, #0x68]      @ 整个寄存器 = 5，其余位全变 0

正确的做法是读—改—写，只动 bit[2:0]：

    ldr  r1, [r0, #0x68]      @ 读
    bic  r1, r1, #0x7         @ 清低 3 位
    orr  r1, r1, #0x5         @ 置成 5
    str  r1, [r0, #0x68]      @ 写回

这就是内核里 readl / writel / regmap_update_bits 存在的理由：C 语言里 .field = x 看着像只改字段，实际很可能是一次整寄存器覆盖。手写一遍汇编，这个直觉就长在脑子里了。

那手写汇编不能干什么

  • 不要拿它写业务逻辑。寄存器分配、栈帧维护、调用约定，编译器做得比人稳。
  • 不要以为手写一定更快。现代 GCC -O2 出来的代码，在流水线排布、指令选择上经常比人肉强；只有极少数场景（精确延时、上下文切换、启动 stub、DMA 对齐拷贝）值得人写。
  • 不要在没有 objdump 对照的情况下相信自己的记忆。编码规则一定会记错：立即数范围、移位量上限、哪些指令 Thumb 态没有、条件码哪个对应哪种比较，全靠反汇编验证。

三笔账：成本与收益

你投入你换到
两小时认指令与寻址能读 oops、能读 uboot 入口、能估计一个函数多少条指令
半天认立即数/条件码/位域配寄存器不再「照抄别人的值」，能自己算掩码
一天做完全部 20 道练习敢在驱动里写内联汇编（屏障、CPSR、协处理器）并知道为什么加 volatile
一个周末把点灯跑通完整走一遍「复位 → 时钟 → 引脚 → GPIO → 循环」，这条链是所有外设的模板

学习路径（这一路口怎么走）

十篇是递进的，别跳：

  • 01 先把「写 → 编译 → 反汇编」的闭环打通，你得能看见自己写的字节。
  • 02 撞立即数那道墙，这是后面所有「掩码为什么要移位造」的根。
  • 03 学地址怎么算、栈怎么长，这是函数与中断的地基。
  • 04 学 lr 的生死，这里出错的表现是「跑飞」，最难查。
  • 05 学条件码，特别是「有符号」和「无符号」两套门。
  • 06 把位操作练成肌肉记忆，回到寄存器配置。
  • 07 接回 C 语言，学内联汇编与屏障，这是日常真正会用到的部分。
  • 08 全部压到板子上：纯汇编点灯。
  • 09 二十道题自测，每题都有验收法，别自己觉得对。
