上电到 shell：五段路

按下电源到你能在串口敲命令，中间是一条固定的接力链：电源 → Boot ROM → u-boot → 内核 → 用户空间。每段交接都会在串口留一行字。学会读这条「进度条」，排障就从猜变成定位。

读完这一章，你应该能

  1. 画出五段路，并说出每段「谁在跑、代码从哪来、跑在哪个地址」
  2. 看懂串口输出，凭最后一行判断断在第几段
  3. 解释 SPL 与 u-boot 的关系，以及为什么 DDR 必须先被初始化
  4. 知道内核 panic 的常见原因里，哪些其实是硬件/参数问题

1.4.1五段路总览

先给结论：这段路上，代码执行的位置从「片内 ROM」→「片内 SRAM」→「DDR」，控制权从「硬件固化逻辑」→「u-boot」→「内核」→「init 进程」。理解这三步搬迁，就理解了整个启动。

1.4.2① 电源：最容易被忽略的第一段

按下电源那一刻，板上发生的是有顺序的电气事件，不是「一瞬间全亮」：

  1. 5V 就位。DC 座或 USB 供电进入，经过保险、滤波电容，电压稳定在 5V 附近。
  2. 3.3V 起来。第一级 DC-DC 输出，供电给 IO、外设、存储。
  3. DDR 电压起来（1.35V）。顺序不能反：DDR 供电晚于 IO，SoC 可能锁在异常态。
  4. 内核电压起来（约 1.2V）。有些板子由 PMIC 按固定时序给出。
  5. 复位释放。RESET 脚从低变高，CPU 从 0x00000000 取第一条指令。

这一段没有串口输出，也没有任何提示。所以「一点反应都没有」时，唯一能做的就是拿万用表量电压、看电流。一个实用技巧：把万用表接在 5V 上，眼睛盯表同时按电源键——如果电压瞬间跌到 4.3V 以下再回升，说明供电带载不足或有大电容短路。

电源段最常见的三个坑

USB 口供电。标称 5V/0.5A，启动瞬间不够，表现为「灯闪一下就灭」。

电源线太细/太长。电阻压降，表上看着 5V，进板只剩 4.5V。

用万用表量「平均电压」。要盯上电瞬间的最低点，平均值会骗人。

1.4.3② Boot ROM：芯片自己做的第一件事

i.MX6ULL 片内有一段只读代码（Boot ROM），出厂固化了启动逻辑，改不了。它做的事很朴素：

  1. 读 BOOT_MODE 引脚 / eFuse，决定从哪个介质启动（eMMC、TF、USB、NAND，见下一章）。
  2. 初始化对应的存储控制器（SD1/SD2/NAND 等）到能读第一个扇区的程度。
  3. 读出镜像头（IVT），校验长度、加载地址、入口地址。
  4. 把镜像搬到片内 SRAM（或直接 DDR，视镜像而定），跳转执行。

关键认知：这一刻 DDR 还不能用。所以被 Boot ROM 加载的第一段程序（通常是 SPL）必须小到能装进片内 SRAM（i.MX6ULL 约 128KB 的 OCRAM 可用），它的唯一使命就是「把 DDR 初始化好」。

Boot ROM 期间的串口输出极少，多数板子在 USB 下载模式下才有一行 ROM 提示。所以这一段「沉默」是正常的，不要因为没输出就判定板子坏了。

1.4.4③ SPL 与 u-boot：真正开始说话

SPL（Secondary Program Loader）是 u-boot 编译出来的「精简版」，只做一件事：按板子的 DDR 参数把内存初始化好，然后把完整 u-boot 搬进 DDR 并跳过去。从这里开始，串口才有输出，你才算「能听见板子说话」。

完整 u-boot 干的事就多了：配置时钟树、初始化串口、识别存储、读环境变量、读内核与设备树、组装启动参数（bootargs），最后 bootm 跳进内核。

典型串口输出（各家板厂文字略有差异）：

U-Boot SPL 2018.03 (Oct 11 2023 - 09:12:33 +0800)
DRAM:  512 MiB
Trying to boot from MMC2

U-Boot 2018.03 (Oct 11 2023 - 09:12:33 +0800)

CPU:   Freescale i.MX6ULL rev1.1 528 MHz (running at 396 MHz)
Model: i.MX6ULL 14x14 EVK Board
DRAM:  512 MiB
MMC:   FSL_SDHC: 0, FSL_SDHC: 1
In:    serial
Out:   serial
Err:   serial
Net:   FEC0
Hit any key to stop autoboot:  0
Booting from mmc ...
## Booting kernel from Legacy Image at 80800000 ...
   Loading Kernel Image ... OK
## Flattened Device Tree blob at 83000000
   Booting using the fdt blob at 0x83000000
   Starting kernel ...

读这段输出的方法：看到 DRAM: 512 MiB 说明 DDR 初始化成功（SPL 过了）；看到 Starting kernel ... 说明 u-boot 已把控制权交给内核（u-boot 过了）。这行字之后如果没有任何输出，问题一定在内核侧，而不是电源或存储。

1.4.5④ 内核：接管一切

内核进来先把自己解压（zImage 是压缩的，自解压代码在头部），然后：打开 MMU、建立页表、接管中断、解析设备树、probe 各驱动、挂载根文件系统、启动 init。

这里的卡点非常典型：

串口最后一行说明先查
Starting kernel ... 后无输出内核没跑起来，或串口没被内核接管内核镜像是否匹配板型、设备树是否对、内核里的 earlycon 参数
Uncompressing Linux... 后卡住解压或 DDR 访问异常DDR 时序、内核加载地址、镜像完整性
Unable to mount root fs根文件系统找不到bootargs 里的 root= 设备名、分区是否存在、文件系统类型
Kernel panic - not syncing: VFS...同上，且已判定放弃同上；另外查 eMMC/TF 是否真被识别
mmc0: error -110SD 通信超时卡质量、卡座供电、pin 复用、bus-width
为什么「Starting kernel」之后可能是「完全没输出」

因为内核启动时会重新初始化串口，而它的串口配置来自设备树（chosen/stdout-path）与内核自己的驱动。如果设备树里的调试串口写错、或者内核根本没编进这个 UART 的驱动，就会出现「u-boot 能打印、内核一声不吭」的经典现象。排查时先用 earlycon 参数强行打开早期控制台，能立刻区分是「内核没跑」还是「内核跑了但没话说」。

1.4.6⑤ 用户空间：从 init 到 login

内核完成初始化后，会执行 init（BusyBox、systemd 或自写脚本）。它负责挂载其余分区、启动服务、拉起 getty（就是给你 login 提示符的那个程序）。这一段出问题，表现是「内核日志刷完，但始终没有 login」：

  1. 根文件系统不完整。缺 /sbin/init 或权限不对 → Kernel panic: No init found。
  2. init 脚本语法错。卡在某个服务，无 login；串口还能按回车看到反应。
  3. 串口 getty 没配。系统起来了但没在 UART1 上开登录 → 换个串口或看 /etc/inittab。
五段路诊断器选一个「串口最后一行」，看断在哪、先查什么
一条排障心法

串口是唯一可靠的时间戳。没有输出 = 前三段（电源/ROM/u-boot）；有 u-boot 没内核 = 存储或镜像/设备树；有内核日志但没 login = 根文件系统或 init。永远先问「最后一行是什么」，再决定动哪里。

自测

为什么 SPL 必须很小，而 u-boot 可以很大？
因为 SPL 运行在 DDR 初始化之前，只能待在片内 SRAM（i.MX6ULL 约百 KB 级）；u-boot 是 SPL 初始化完 DDR 之后才被搬进 DDR 运行的，所以不受这个限制。这也是为什么 SPL 只能做「初始化内存 + 搬运」这类最小工作。
串口停在 Starting kernel ...，你会怎么判断是内核问题而不是硬件问题？
因为这一行是 u-boot 打印的，说明电源、DDR、存储、加载全部成功——硬件链路已经通了。之后的沉默属于内核侧：镜像不匹配、设备树串口配错、earlycon 没开、内核卡在解压。可以用 earlycon 或不带设备树的最小启动来二分。
为什么有的板子「u-boot 有输出，内核完全没有」？
最常见是设备树里 stdout-path 指向的串口与实际接线不一致，或者内核没编进该 UART 驱动。u-boot 用的是自己写死的串口配置，不受设备树影响，所以能打印。这也是「u-boot 正常、内核哑巴」这个经典现象的来源。
