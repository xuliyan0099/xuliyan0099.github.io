SPI 子系统：控制器驱动与设备驱动

SPI 只有四根线，却有三层结构：控制器、协议核心、设备驱动。看懂 spi_message 怎么被拆成 transfer，你就懂了这类总线的通用套路。

SPI 只有四根线：SCLK、MOSI、MISO、CS。没有地址线，也没有应答——所以「怎么知道从设备在说什么」全靠**时钟极性与相位**约定，也就是 mode 0–3。

Linux 把这类同步串行总线抽象成三层：控制器驱动（搬字节）、协议核心（排队与加锁）、设备驱动（懂具体芯片的寄存器）。

先玩一下：一次 SPI 读取的时序

这就是你在逻辑分析仪上会看到的东西。注意 CS 在整个 message 期间保持低电平，中间可以有多个 transfer。

注意第 3 步：读的时候主机也得「发」点什么。因为 SPI 是移位寄存器环，时钟一动，主机的位就从 MOSI 出去、从机的位从 MISO 进来。所谓「哑字节」只是内容无意义，作用就是提供时钟。

一、三层结构与两个结构体

spi_controller控制器。提供 transfer_one / transfer_one_message、CS 控制、时钟分频。i.MX6ULL 上是 spi-imx（ECSPI）。
spi_device一个从设备：mode、max_speed_hz、chip_select、bits_per_word。来自设备树子节点。
spi_message + spi_transfer一次原子事务：message 里挂 1..n 个 transfer，全部执行期间 CS 一直有效，中间不释放总线。

设备树里长这样：

&ecspi2 {
    status = "okay";
    cs-gpios = <&gpio1 20 GPIO_ACTIVE_LOW>;
    sensor@0 {
        compatible = "demo,sensor";
        reg = <0>;                    /* 片选编号 */
        spi-max-frequency = <10000000>; /* 10 MHz */
        spi-cpha;                      /* mode 1 或 3 的一半信息 */
        spi-cpol;                      /* 与上一条组合出 mode 3 */
    };
};

二、spi_sync 做了什么

如果一次要搬几百字节，用 spi_async 或让控制器走 DMA；spi_sync 在大数据量下会让出 CPU 等完成，但依然是「一个一个字节移位」，吞吐上限由 SCLK 决定。

三、频率与时间的算术

误解：spi-max-frequency 写多大就跑多大实际频率由控制器分频器取「不超过该值」的最接近档位，还会受板级走线、从设备时序限制。spi_sync 成功不代表数据对——时序不对时，读回来的是 0x00 或 0xFF，而不是报错。
调试顺序先用逻辑分析仪看 CS 是否真的拉低、SCLK 是否有 8/16 个脉冲、MOSI 的命令字节对不对。三者都对而数据错，才轮到怀疑 mode（CPOL/CPHA）或位宽。

动手（可选）：用 spidev 先验证硬件

只在 🔧 实作模式展开需要板子；没有板子也能读懂流程。
  1. 设备树给 spidev 兼容，启动后出现 /dev/spidev2.0。
  2. 用 spi-config 或一段 C 代码设 mode、bits、speed，做 SPI_IOC_MESSAGE 传输。
  3. 先读写一个确定存在的寄存器（WHO_AM_I），拿到固定 ID 才算通了。
  4. 再换到自己的驱动：把同样的 transfer 搬进 spi_sync，对比用户态与内核态的结果。

离开这一篇，你应该能

  • 说出 SPI 四根线的作用，以及为什么读操作也要发数据。
  • 解释 message 与 transfer 的区别，以及 CS 在什么时候释放。
  • 给定 SCLK、字节数、频率，算出一次事务的时间与总线占用率。

SPI 是「小数据、快节奏」。下一类设备完全相反：一次要搬 512 字节以上，还要排队、合并、重排——块设备。
