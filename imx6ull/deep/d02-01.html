ELF 与链接重定位：从符号表到 .rel.text

编译器把 C 变成 .o，链接器把 .o 拼成可执行文件。中间那一步，靠的是「留坑 + 填坑」：符号表记录坑在哪，重定位表记录怎么填。

你一定见过这种报错：undefined reference to 'foo'。它出现在链接阶段，而不是编译阶段。为什么编译器不早说？因为编译器只对自己的这一份 .o 负责，它只知道「这里需要一个叫 foo 的东西」，至于 foo 到底在哪，是链接器的事。

这一篇就讲这一个动作：留坑，然后填坑。理解了它，.o、符号表、重定位表、readelf -r 的输出，全都会变成同一件事的不同侧面。

先玩一下：链接器改写的是哪几个字节

下面这段代码调用了一个「还不知道地址」的函数。点「单步」，看指令字怎么被链接器改掉——注意右侧 PC 与 R0 的变化，它模拟的是 R_ARM_CALL 这一类重定位的填坑过程。

这里有一个容易忽略的点：填进去的往往不是地址本身。ARM 的 bl 编码里只有 24 位立即数，表示的是相对偏移；R_ARM_ABS32 才是往一个 32 位字里写绝对地址。所以「重定位类型」这个字段是必须的——不同的坑，填法不一样。

一、为什么必须留坑

编译一个 .c 时，编译器是单独工作的。它不知道 foo 在哪个文件、最终会被放在哪个地址。它能确定的事情只有三件：

  • 这条指令/这个数据位置需要一个外部符号；
  • 这个坑在段内的偏移是多少；
  • 坑周围还有没有额外修正（比如「再加 4」这种加数）。

于是它把这三件事写进两个表，剩下的交给链接器。这也解释了一个现象：.o 文件里的地址几乎全是 0 或者很小的偏移，因为此时还没有分配最终地址。

符号表 .symtab每个符号一行：名字、值（地址或偏移）、大小、类型（FUNC / OBJECT / SECTION）、绑定（GLOBAL / LOCAL / WEAK）、以及它属于哪个段。
重定位表 .rel.text每个坑一行：坑在哪（r_offset）、要用哪个符号+哪种填法（r_info）、有没有加数（r_addend）。
字符串表 .strtab符号名不是直接存在符号表里的，只存一个下标，名字本体在这张表里——省空间的老办法。

三张表的关系可以用一句话记住：符号表回答「这个符号是谁」，重定位表回答「哪里需要它」。

二、把 .o 摊开看

不需要板子，PC 上就能做。这是纯读也能看懂的版本——命令只是为了让输出现身，你不必真的敲。

# 1. 只编译，不链接
arm-linux-gnueabihf-gcc -c -O0 add.c -o add.o

# 2. 看段和符号
arm-linux-gnueabihf-readelf -S add.o      # 段表：.text .data .bss .rel.text ...
arm-linux-gnueabihf-readelf -s add.o      # 符号表：Bind / Type / Ndx / Value / Size

# 3. 看坑
arm-linux-gnueabihf-readelf -r add.o      # 重定位表：Offset / Info / Type / Sym
arm-linux-gnueabihf-objdump -dr add.o     # 反汇编 + 每条指令对应的重定位

典型的输出长这样（节选，数值是示意）：

OffsetInfoTypeSymbol读法
0x1c0x0b01R_ARM_CALLfoo0x1c 处那条 bl 要跳去 foo，用相对偏移填
0x200x0b02R_ARM_ABS32counter0x20 处一个字要写 counter 的绝对地址
0x240x0b03R_ARM_ABS32.rodata + 0指向只读段里的字符串常量

注意第三行：符号不一定是函数，也可能是「某个段 + 偏移」。C 里写 puts("hello")，字符串进 .rodata，代码里留下的是指向它的地址，于是产生一条针对该段的绝对重定位。

三、链接器按顺序做五件事

第三步容易被低估。layout 不是「随便排一下」，它由链接脚本决定，还要满足对齐：.text 通常按 4 或 16 字节对齐，页对齐的段要按 4 KB 对齐。你在 .o 里看到的偏移是「段内偏移」，经过这一步才变成「虚拟地址」——这是后面讲程序加载时 PT_LOAD 的前提。

四、四种你会遇到的重定位

类型用在哪怎么填常见报错
R_ARM_ABS32函数指针、全局变量地址、字符串地址直接写 32 位绝对地址（+addend）—
R_ARM_CALL / JUMP24bl / b 指令写 PC 相对偏移，范围约 ±32 MBrelocation truncated to fit
R_ARM_PREL31异常处理表（.ARM.exidx）写 31 位相对偏移—
R_ARM_REL32调试信息、部分 PIC 引用写「符号 - 当前位置」—

relocation truncated to fit 这条报错值得单独记：它说明目标地址离得太远，24 位相对偏移装不下。解决办法通常是让链接脚本把相关段排近一点，或者改用绝对跳转的长调用序列（-mlong-calls）。

五、三个常见误解

误解一：反汇编里 call 的目标是 0，说明编译器坏了没有坏。那是还没填的坑。用 objdump -dr（带 -r）才能同时看到指令和它对应的重定位项；只看 -d 就像看一张还没写答案的卷子。
误解二：strip 之后符号表没了，程序就找不到函数了链接完成后符号表对运行没有作用（动态符号表 .dynsym 是另一张，strip 不会删它）。strip 删掉的是「给人看」的调试信息，填坑早已完成。
误解三：重定位是运行时做的静态链接的重定位在链接时完成，运行时一个字节都不会改。运行时才填坑的是动态链接的 GOT——那是下一篇的主角。

动手（可选）：自己造一个坑

只在 🔧 实作模式展开需要：一台 Ubuntu（或 WSL），装 gcc-arm-linux-gnueabihf 或直接用本机 gcc。目的不是编译成功，而是看见重定位项。
  1. 写两个文件：add.c 里定义 int counter; int add(int a,int b){counter++;return a+b;}；main.c 里 extern int add(int,int); 并调用它。
  2. gcc -c add.c main.c，分别 readelf -r。你会看到 main.o 里有 R_ARM_CALL add，add.o 里没有针对 add 的重定位（它就是定义者）。
  3. 把 add.c 改名成 add2.c 但函数名不改，再链接 main.o add2.o——应该能过。这证明链接器只认符号名，不认文件名。
  4. 把函数名改成 add2，再链接，你会得到 undefined reference to 'add'。这条报错的来源就是「重定位表里有一个坑，符号表里找不到对应的定义」。

预期与失败对照：如果 readelf -r 输出为空，通常是开了优化把调用内联掉了，或者函数被声明成 static（那就变成段内重定位，甚至完全消失）。这不是工具坏了，是坑根本不存在。

离开这一篇，你应该能

  • 说出符号表与重定位表各自回答什么问题，以及 .o 里为什么地址几乎都是 0。
  • 拿到一行 R_ARM_CALL foo，解释「填进去的是相对偏移而不是地址」。
  • 解释 undefined reference 为什么属于链接错误，而不是编译错误。
