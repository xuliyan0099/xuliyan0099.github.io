多线程与锁：pthread、条件变量、常见死锁

线程共享地址空间，所以省了拷贝，也带来了竞争。锁不是万能药：粒度、顺序、唤醒丢失，三件事决定你的程序是稳还是玄学。

线程比进程便宜，是因为它共享地址空间——不用切页表，不用复制内存。代价是共享的一切都可能被同时改。

锁不是「加了就安全」，它带来三个新问题：粒度（太粗等于串行）、顺序（互相等就死锁）、唤醒（通知丢了就永久卡住）。这一篇把这三件事说透。

先玩一下：一个线程的一生

点事件按钮，看状态怎么转。注意 BLOCKED 有两种来源：等锁、等条件变量。两者醒来后都要重新检查条件。

单核（i.MX6ULL）也能「并发」：靠时间片轮转与阻塞让出。所以「我这只有一个核，不用加锁」是错的——只要有两个执行流会被调度交错，就有竞争。

一、锁的四个家族

机制等待方式能否睡眠用户态对应
原子操作不等待，硬件指令不涉及stdatomic / __atomic
自旋锁忙等，占 CPU不能睡几乎没有（内核专用）
互斥锁睡等，唤醒后抢能睡pthread_mutex
信号量睡等，可计数能睡sem_t

选择标准很朴素：临界区里有阻塞操作（IO、sleep、等另一个锁）就用互斥锁；纯 CPU 的极短临界区在内核里才考虑自旋锁。用户态几乎没有理由自旋。

二、条件变量：为什么必须配 while

条件变量本身不存「有没有数据」，它只是「等/通知」的通道。所以标准写法一定是：

pthread_mutex_lock(&m);
while (!has_data)                              /* 必须 while，不是 if */
    pthread_cond_wait(&cond, &m);             /* 内部会原子地放锁 + 睡 */
take_data();
pthread_mutex_unlock(&m);

/* 生产者 */
pthread_mutex_lock(&m);
has_data = 1;
pthread_cond_signal(&cond);                    /* 或 broadcast */
pthread_mutex_unlock(&m);

用 if 会踩两种坑：虚假唤醒（系统可能无故唤醒你）与惊群（broadcast 唤醒多个，只有一个能拿到数据，其余必须回去再等）。两者都要求重新检查条件——所以只能是 while。

「先拿锁、再检查、再 wait」这三步的顺序，就是避免丢失唤醒的全部秘密。看起来只是顺序问题，实际上是一类 bug 的总开关。

三、死锁：四个条件与三种破法

死锁需要同时满足四个条件（互斥、持有并等待、不可剥夺、循环等待）。工程上最容易破的是循环等待：给所有锁编号，永远按同一顺序获取。

  • 锁顺序：全局规定 lock A → lock B，禁止反向。代码评审时先看这个。
  • 超时：pthread_mutex_timedlock 可以在拿不到时退出并重试，把死锁降级为「慢」。
  • 缩小临界区：把 IO、日志、回调移出锁外，减少「持有并等待」的窗口。
误解：加锁就一定线程安全锁保护的是「数据」，不是「函数」。同一个对象的读和写若用两把不同的锁，等于没锁。另一个常见错误是返回内部指针，调用方在锁外继续用。

动手（可选）：亲手制造一次死锁

只在 🔧 实作模式展开PC 上即可，几行代码。
  1. 两个线程、两把锁，线程 A 先锁 1 再锁 2，线程 B 反过来。跑几百次几乎必然卡住。
  2. gdb attach 上去，thread apply all bt 看到两个线程各持一把锁——这就是死锁的现场证据。
  3. 改成统一顺序（都先锁 1），问题消失。
  4. 再用 helgrind（valgrind 工具）或 ThreadSanitizer（-fsanitize=thread）扫一遍数据竞争。
