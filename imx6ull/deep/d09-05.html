DMA 与 Cache 一致性：谁负责 flush，谁负责 invalidate

CPU 写进 Cache 的数据，DMA 看不见；DMA 写进内存的数据，CPU 可能还在读旧 Cache。这一类「幽灵 bug」有固定的解法。

DMA 让硬件替你搬数据，代价是它绕过了 CPU，也就绕过了 Cache。于是出现两类只在板子上才复现的怪事：CPU 写的描述符，DMA 读到的是旧的；DMA 写的数据，CPU 读到的是缓存里的旧值。

这两件事的解法是固定的：谁写、给谁看、方向是什么。把这三个问题答对，一致性就不会出错。

先玩一下：一次没有同步的 DMA

点「自动播放」。第 4 步开始出问题：CPU 还在读 Cache 里的旧值，而内存已经被 DMA 改过了。注意修复发生在最后两步。

这类 bug 的典型症状是「加一条 printf 就好了」「换个编译优化等级就坏了」——因为 printf 或优化改变了 Cache 的时序。看到这种描述，第一个怀疑对象就是 DMA 一致性。

一、两种内存，两种 API

类型分配方式是否可缓存适用
一致性内存（coherent）dma_alloc_coherent()通常 uncached，CPU 与设备看到同一份长期存在的描述符环、控制块
流式内存（streaming）普通 kmalloc/页，再用 dma_map_single() 映射可缓存，需显式同步一次性的数据缓冲，性能更好

一致性内存省心但慢（每次 CPU 访问都打到内存）；流式内存快，但你必须自己管同步。不能混用：把 dma_alloc_coherent 拿到的指针再去做 dma_map_single，是典型错误。

如果缓冲要反复用（比如环形队列），不要每次 map/unmap，而是 map 一次、每次传输前后用 dma_sync_single_for_device() / dma_sync_single_for_cpu()。这样避免映射开销，也能精确控制 flush 与 invalidate。

二、Cache line 的代价

Cache 的操作单位是行（Cortex-A7 通常是 64 字节，具体以 TRM 为准），不是字节。所以你要同步 1 个字节，实际可能冲刷 64 字节；缓冲区没对齐时，还会跨两行。

三、四个必须记住的顺序

  • 写方向（CPU → 设备）：先写数据，再 dma_map/sync_for_device（clean），最后启动 DMA。
  • 读方向（设备 → CPU）：DMA 完成后先 sync_for_cpu（invalidate），再读数据。
  • 描述符：描述符在 coherent 内存里最安全；若在可缓存内存，必须每改一次就 clean 一次。
  • 顺序保证：writel() 后加 wmb() 或使用 readl() 回读，防止编译器/CPU 重排导致「先启动、后写地址」。
误解：ARM 是弱一致性，只加 barrier 就够了barrier 管的是 CPU 访问顺序，不负责 Cache 与内存的一致。flush/invalidate 是另一件事，两者都要做。
最快的自证方法把同一段代码在「关闭 D-cache」下跑一遍，如果 bug 消失，就是一致性问题，而不是逻辑问题。裸机阶段可以这样定位；Linux 下则检查你是否漏了 dma_sync_*。

动手（可选）：制造并修掉一次不一致

只在 🔧 实作模式展开需要板子；没有板子可只读上面的时序。
  1. 用 coherent 缓冲做一次 DMA，确认正常。
  2. 换成 kmalloc + dma_map_single，故意在启动 DMA 前不做 clean，把 CPU 刚写的标志位交给设备读。
  3. 观察设备读到旧值（可通过设备回读寄存器或逻辑分析仪确认）。
  4. 补上 dma_sync_single_for_device，bug 消失；再把读方向也补上 invalidate，验证状态字正确。

离开这一篇，你应该能

  • 解释 coherent 与 streaming 两种 DMA 内存的差别与适用场景。
  • 说出「写方向 flush、读方向 invalidate」的原因，以及顺序为什么不能反。
  • 估算未对齐缓冲带来的额外冲刷量。
