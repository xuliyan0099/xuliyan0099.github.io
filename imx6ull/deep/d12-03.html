HAB 安全启动：签名、验签、失败现象

BootROM 是芯片里一段不可改的代码。它只认一件事：这个镜像有没有被正确的私钥签过名。签名链一旦断了，板子连一行串口都不会给你。

i.MX 系列的这套机制叫 HAB（High Assurance Boot）。它的验证发生在 BootROM 里，比你写的任何代码都早。

先玩一下：一次签名镜像的验证链

点「下一步」。注意第 3 站：BootROM 用的是熔丝里烧进去的 SRK 公钥 hash，不是镜像里带的公钥——这是防止「自己签名自己」的关键。

注意第 2 站：HAB 的信任根是熔丝，不是文件。所以「烧熔丝」是一个不可逆的、必须想清楚的操作——烧错了，芯片就再也启动不了未签名的镜像。

一、四个名词

名词是什么谁生成
SRKSuper Root Key，根公钥（通常 3–4 把，对应不同用途）你用自己的私钥生成，hash 烧进熔丝
CSFCommand Sequence File：一段「要校验哪些区域」的命令 + 签名NXP 的 CST 工具生成
CSRTCSF 的模板/描述，声明镜像布局与要签的段手写或工具生成
HAB 状态BootROM 的验证结果，可在运行时读回硬件寄存器 / hab_status

签名流程大致是：生成密钥 → 用 CST 生成 CSRT → 对镜像（IVT+U-Boot 等）算 hash → 用私钥签 CSF → 把 CSF 追加进镜像 → 烧写。运行时 BootROM 反向做一遍。

二、失败时你会看到什么

  • 完全无输出：验签在串口初始化之前，所以最常见的就是「一点反应都没有」。这时只能靠 JTAG 停核看 PC 是否停在 ROM 的失败循环里。
  • U-Boot 里读到 HAB_FAILURE：如果之前有能启动的镜像，可在 U-Boot 命令行 hab_status 看具体失败原因（CSF 缺失、hash 不匹配、签名错）。
  • 日志里出现 HAB Failure：部分 BSP 会在启动时打印。
最危险的操作：烧熔丝烧之前必须确认：签名镜像已经在同一块板子上验证通过、备份了密钥、记录了 SRK hash、并且有一条「救砖」路径（比如能从另一个启动介质进入 U-Boot 重新烧写）。烧错一次，芯片就报废。
误解：签名能防篡改，所以不用管升级包签名保护的是「启动链」，不是「运行中的系统」。rootfs 是否被改，要靠 dm-verity；升级包是否可信，要靠传输层签名。三者是三件事。

三、与双 Bank 的关系

双 Bank 解决「换得安全」，HAB 解决「只跑我签过的」。两者叠加才是产品的完整启动信任链：BootROM → 签名的 SPL → 签名的 U-Boot → 校验内核 → 挂载 verity 的 rootfs。

开发阶段的现实做法先不烧熔丝，用 hab_status 验证签名流程能走通；量产前再做一次「烧熔丝 + 断电重启 + 回滚」的完整演练。顺序反了，代价是板子。

动手（可选）：走一次签名（不烧熔丝）

只在 🔧 实作模式展开需要板子、CST 工具与 U-Boot 源码；风险操作，务必先备份。
  1. 用 CST 生成一对密钥与 SRK hash，保存好私钥（丢了就再也签不出能启动的镜像）。
  2. 按 CSRT 模板对 U-Boot 镜像签名，生成带 CSF 的镜像，烧到板子。
  3. 不烧熔丝，启动后在 U-Boot 里 hab_status，确认显示 HAB_SUCCESS（或开放状态）。
  4. 故意改镜像一个字节，再看 hab_status 变成失败——这就是「验签生效」的证据。

离开这一篇，你应该能

  • 说出 SRK、CSF、CSRT 各自是什么，以及信任根为什么是熔丝。
  • 解释验签失败时为什么通常「串口无输出」。
  • 说明 HAB 与 dm-verity、升级包签名三者的分工。
