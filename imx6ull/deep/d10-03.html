socket 与 epoll：一个能扛住千连接的事件循环

一万个连接不需要一万个线程。线程的成本不在创建，而在每个线程一份栈、一次上下文切换、一把调度锁。事件循环把这三种成本压成一份。

epoll 的全部价值可以用一句话说清：它把「哪些 fd 就绪」这件事，从「每次遍历所有 fd」变成了「内核维护一张就绪链表」。

先玩一下：一个事件循环在干什么

看这条循环：注册 → 等 → 处理 → 再等。注意第 4 步只处理「就绪的」，没就绪的 fd 一个都不碰。

和「一个连接一个线程」相比，差别不在快慢，而在可预测性：线程数随连接数线性增长，内存与切换开销也跟着涨；事件循环的连接数增长几乎只增加内核里的几个结构体。

一、四个调用，三种触发

调用做什么注意
epoll_create1(0)创建 epoll 实例（一个内核对象 + 红黑树 + 就绪链表）用完要 close
epoll_ctl(ADD/MOD/DEL)注册/修改/删除关注的 fd 与事件ADD 同一个 fd 两次会 EEXIST
epoll_wait()取出就绪事件数组返回的是「个数」，不是「所有 fd」
EPOLL_CTL_MOD改关注的事件掩码ET + ONESHOT 常用它重新武装
  • 水平触发（LT，默认）：只要 fd 还有数据，每次 wait 都会返回它。写起来简单，但可能反复空转。
  • 边沿触发（ET）：状态变化才通知一次。必须配非阻塞 fd，并且读到 EAGAIN。
  • EPOLLONESHOT：触发一次后自动失效，处理完要 MOD 重新注册。多线程处理同一连接时用它避免两个线程同时读。

二、一个能跑的骨架

ET 的三个必踩坑1）accept 只调一次 → 漏连接；2）read 只读一次 → 剩余数据永久挂起；3）用阻塞 fd → 最后一次 read 把线程卡死。三个坑都源于同一个误解：把 ET 当成 LT 用。

另一个常见问题是「惊群」：多个线程/进程等同一个 listen fd，新连接到达时全部被唤醒，只有一个 accept 成功。解法是 EPOLLEXCLUSIVE（较新内核）或 SO_REUSEPORT 让每个线程各有一个监听 socket。

三、连接数 × 缓冲 = 内存

动手（可选）：压到一千连接

只在 🔧 实作模式展开PC 上即可，不需要板子。
  1. 写一个 epoll ET 服务端，只回显；用 ulimit -n 4096 提高 fd 上限。
  2. 用一个 Python 脚本开 1000 个非阻塞连接，各发一条消息，统计往返延迟与内存（ps -o rss）。
  3. 把 ET 改成 LT，观察 CPU 占用变化（LT 下空闲 fd 不会空转，但忙时会反复唤醒）。
  4. 故意把 read 只读一次，制造「剩余数据不触发」的现象，再用 strace 看到底卡在哪。
