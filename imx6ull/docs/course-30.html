卷 04·操作系统·第 05 篇

中断

CPU 不可能一直轮询每个外设，那太浪费。它选择被打断：外设有事就拉一根线，CPU 立刻放下手里的事去处理。这一课把链路从「外设置位」走到「你的 handler 执行」，并讲清一条铁律：中断里不能睡觉。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 链路每一步做什么？② 为什么中断里不能睡眠？③ 上半部与下半部怎么分工？④ 中断返回地址为什么要减 4？⑤ 中断风暴怎么产生？

1. 上半部与下半部

static irqreturn_t my_isr(int irq, void *dev)
{
    u32 st = readl(base + STATUS);
    if (!(st & RX_READY)) return IRQ_NONE;
    readl(base + CLEAR);          // 清中断标志，必须做
    schedule_work(&my_work);      // 重活交给 workqueue
    return IRQ_HANDLED;
}

static void my_work_fn(struct work_struct *w)
{
    msleep(10);                   // 这里可以睡眠
    process_big_buffer();
}

2. 为什么中断里不能睡眠

  • 没有 task 可挂起：中断不属于任何进程，谁来恢复它？
  • 可能持锁：若还握着自旋锁睡过去，别的核死等，直接死锁。
  • 栈不独立：在中断栈上，没有 task_struct 支撑恢复。

所以内核 API 分两套：spin_lock（可用在中断上下文）、mutex（只能进程上下文）。在中断里误用 mutex，会立刻报 sleeping function called from invalid context。

3. 那个 sub lr, lr, #4 是干什么的

irq_handler:
    sub  lr, lr, #4        ; 修正返回地址！
    srsdb sp!, #0x13       ; 保存 lr 与 spsr 到 SVC 栈
    ...                    ; 调用 C 语言 handler
    rfeia sp!              ; 恢复并返回

原因：ARM 在中断时保存的是「已取指但未执行」的那条（PC+4 语义），而实际要返回的是「被打断的那条」。所以必须减 4 修正。不修正就会跳过一条指令——那种 bug极难查，因为只在特定时序下出现。

4. 中断风暴

如果 handler 没清中断标志，硬件会立刻再报一次，CPU 就陷入「进中断 → 返回 → 立刻再进」的死循环，用户态完全得不到执行。

现象：系统卡死、top 里 si（软中断）或 hi（硬中断）占用接近 100%、串口打不出字。排查第一步永远是确认「标志清了没有、电平中断是否已释放」。

5. 与 Linux 的接缝：tick 也是一次中断

内核的「时间感」来自周期性中断：i.MX6ULL 用 GPT/EPIT 定时器，每 1/HZ 秒（常见 100~1000Hz）打断一次，更新 jiffies、检查调度、统计时间。

# 看当前 HZ 与中断分布
cat /proc/interrupts        # 每个中断源的计数
grep CONFIG_HZ /boot/config-$(uname -r)

# 若某中断计数疯长，基本就是「没清标志 / 电平没释放」
watch -n1 'cat /proc/interrupts'

/proc/interrupts 是排障时最有用的一个文件：它能立刻告诉你「是哪个中断在发疯」。

7. 自测与动手

1

中断链路里 GIC 的作用？

看答案

汇总多路中断、定优先级、向 CPU 提供中断号（读 IAR），并支持屏蔽与清除。

2

为什么 sub lr, lr, #4 必须做？

看答案

中断保存的返回地址超前了一条指令，减 4 才是被打断那条，否则会跳过指令。

3

softirq 与 workqueue 的关键区别？

看答案

softirq 在中断返回路径执行、不能睡眠；workqueue 由内核线程执行、可以睡眠。

4

中断风暴的典型成因与现象？

看答案

没清标志或电平中断未释放；现象是系统卡死、/proc/interrupts 计数暴涨。

5

共享中断时 handler 返回 IRQ_NONE 意味着什么？

看答案

「这个中断不是我的」，内核会继续调用同一条线上的下一个 handler。

  1. 写一个 GPIO 按键中断驱动，打印时间戳，观察抖动。
  2. 在 handler 里故意不清标志，观察中断风暴。
  3. 用 cat /proc/interrupts 找出你系统里最忙的中断。
  4. 把耗时逻辑改成 workqueue，比较系统响应。
