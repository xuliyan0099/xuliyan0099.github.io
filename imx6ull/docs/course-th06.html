中断、并发与同步（详解）

中断是「硬件主动叫 CPU」的唯一方式，也是驱动正确性的分界线。这一章从 GIC 的一根信号线讲到自旋锁的一条死线：哪些代码可以等、哪些一秒都不能等、为什么「抢锁时还能被中断」会导致死锁。

★ 一读 纯读约 5 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 一个按键怎么在几微秒内通知到 CPU；② 中断入口为什么要保存比系统调用更多的寄存器；③ 上半部与下半部为什么必须分开；④ 内核里到底有几种并发来源；⑤ 自旋锁与互斥锁的分界线在哪。

读完你应该能回答

  • IRQ 进入时，硬件自动关了中断吗？为什么？
  • 为什么中断处理函数里不许 sleep，而 workqueue 里可以？
  • spin_lock_bh() 里的 bh 指的是什么？为什么需要它？
  • 同一条中断线被两个设备共享时，驱动必须做什么？
  • mdelay(1) 和 msleep(1) 差在哪，为什么前者会害死系统？

1. 一次按键中断的硬件全过程

CPU 视角（配合 T18 读） 本章说「中断分上下半部」，硬件侧的完整时序在那一章。 想看清每条指令的位段、流水线与寄存器实际变化，跳 T18 · CPU 是怎么执行一行代码的 第 8、9 节（svc 进内核、时钟中断抢回 CPU）。

假设你按下接在 GPIO1_IO03 上的按键。从电平变化到 CPU 开始执行你的处理函数，中间经过这些硬件环节：

引脚电平变化→GPIO 状态寄存器置位→GPIO 中断使能位判定→GIC 分发器排队→比优先级→拉 CPU 的 IRQ 引脚→CPU 切 IRQ 模式→跳向量表

几个必须知道的硬件事实（以 i.MX6ULL 为例）：

  • 中断控制器是 GIC-400，基址 0x00A0_0000。它分两部分：分发器（Distributor，0x00A0_1000）管「哪个中断能被送给哪个核、优先级多少」；CPU 接口（0x00A0_0100）管「当前核正在处理哪个中断、何时结束」。
  • 每个中断有编号（ID）。i.MX6ULL 上 GPIO1 的组合中断是 66 号（不同手册版本可能不同，务必查你自己的 RM）。编号是软件与硬件对话的钥匙。
  • 优先级可配，数字越小优先级越高（GIC 用 0–255，实际常配 0–31）。高优先级中断可以打断低优先级中断——这叫中断嵌套。
  • GIC 有「活跃状态」概念：一个中断被 CPU 接手后处于 active，直到你写 EOIR 才结束。忘了写 EOIR，这个中断就永远不会再来。

1.1 CPU 进入 IRQ 模式时，硬件做了什么

这一步与 T01 讲的 svc 很像，但有三个关键差别：

项目SVC（系统调用）IRQ（硬件中断）
触发方式软件主动执行指令硬件异步拉信号
发生时机的确定性确定（就在那条指令处）不确定（任意指令边界）
硬件保存SPSR_svc ← CPSR，LR_svc ← PC+4SPSR_irq ← CPSR，LR_irq ← PC+4
中断屏蔽位不变（SVC 不自动关中断）自动置 I 位，关掉 IRQ
入口偏移VBAR + 0x08VBAR + 0x18

「自动关中断」是硬件替你做的最重要一件事：否则中断处理函数还没保存完现场，就被下一个中断打断，现场会乱成一团。但这也意味着「中断处理期间默认不响应新中断」，需要嵌套时必须手动开（enable_irq 或清除 CPSR.I），并付出栈深度与重入的代价。

「时机不确定」是 IRQ 与 SVC 的本质差别：被打断的那一刻，CPU 可能正在算一个复杂的表达式，r0–r3 里全是中间值。所以 IRQ 入口必须保存 r0–r3 也要存（SVC 不需要，因为系统调用是主动发起的，参数是约定好的）。这就是「中断入口比系统调用入口保存更多寄存器」的原因。

2. 中断处理的四个软件层次

从向量表那条 b irq_handler 开始，内核要过四层才到你的代码：

层代码位置干什么
① 入口汇编arch/arm/kernel/entry-armv.S保存 r0–r12/sp/lr/spsr 到栈，形成 pt_regs；切到 SVC 模式栈；调 C 函数
② 中断分发kernel/irq/读 GIC 的 IAR 拿到中断号，找对应的 irq_desc
③ 控制器操作irq-gic.c 里的 irq_chipack（告诉 GIC 我接了）、mask（必要时屏蔽）、eoi（写 EOIR 结束）
④ 具体处理你的驱动 request_irq 注册的 handler判断是不是自己的中断，读状态寄存器，清标志，做最少的事

irq_desc 是每个中断号一个的描述符，里面挂一条 action 链表——这就是「中断共享」的实现方式。多个设备接在同一条中断线上时（比如老式 PCI 中断），链表上会有多个 handler，内核会依次调用每一个，所以每个 handler 都必须自己判断「这次是不是我的中断」，不是就立刻返回 IRQ_NONE。

/* 一个正确的中断处理函数骨架 */ static irqreturn_t my_isr(int irq, void *dev_id) { u32 st = readl(base + ST_REG); if (!(st & MY_BIT)) return IRQ_NONE; /* 不是我的中断，立刻退出 */ writel(MY_BIT, base + ST_REG); /* 清中断标志（写 1 清 0 型） */ /* 只做最少的事：记数据、唤醒下半部 */ return IRQ_HANDLED; }

3. 上半部与下半部：为什么必须切开

中断处理函数有三个先天限制：① 运行时本核默认不再响应同级及更低优先级中断；② 绝对不能睡眠（它没有可被调度的上下文）；③ 它的时间是从所有任务那里偷来的。所以规矩是：上半部只做「必须现在做、且极快」的事，其余全推给下半部。

机制运行上下文能睡眠吗并发性典型延迟适用
softirq软中断上下文（中断返回时执行）不能同一类型可在多核并行几十微秒网络收包、定时器、RCU（数量固定，内核内置）
tasklet基于 softirq不能同一 tasklet 不会并发几十微秒简单的设备延迟处理（旧代码常见）
workqueue内核线程（进程上下文）可以由线程池决定毫秒级需要 IO、需要睡眠、耗时较长
threaded irq专用内核线程可以每中断一个线程毫秒级实时系统、需要阻塞的复杂处理

这张表的用法很直接：如果你在下半部里需要调用任何可能睡眠的函数（msleep、mutex_lock、copy_from_user、I2C/SPI 传输），就必须用 workqueue 或 threaded irq。 在 softirq/tasklet 里睡眠，后果不是「慢一点」，而是「整个核卡死」——因为没有调度器上下文可以把它换出去。

/* threaded irq：上半部只清标志，下半部干活 */ request_threaded_irq(irq, my_isr_fast, my_isr_thread, IRQF_ONESHOT, "mydev", dev); /* 或者：普通中断里只排队 */ static irqreturn_t my_isr(int irq, void *d) { disable_irq_nosync(irq); /* 防重复触发 */ schedule_work(&my_work); /* 剩下的交给工作队列 */ return IRQ_HANDLED; }

顺便解释 IRQF_ONESHOT：它让中断线在处理线程跑完前保持屏蔽，避免「一边处理一边又来中断」把线程淹没。这是 threaded irq 的常用搭配。

4. 内核里到底有几种并发

写驱动时最容易犯的错是「我这颗是单核，不用加锁」。这句话在 Linux 里是错的。并发来源有四种，其中三种在单核上照样存在：

来源单核是否发生典型场景
硬件中断是你的驱动正在改链表，中断来了，handler 也改同一链表
软中断 / tasklet是网络收包在中断返回时执行，可能与进程上下文竞争
内核抢占是（若开 CONFIG_PREEMPT）内核代码执行到一半被更高优先级任务抢占
SMP 多核否两个核同时执行同一段内核代码

由此推出一条工程结论：内核代码默认就必须是「可重入 + 抗并发」的，不需要并发的地方才用「关中断/禁抢占」这类手段显式排除。而用户态程序正好相反：默认单线程顺序执行，需要并发才显式创建线程。

5. 锁的分界线：能不能睡眠

内核里的锁不是按「轻重」分类的，而是按一条硬线分类：持有它的时候，能不能被调度出去。

锁能睡眠吗可用在中断上下文吗典型用途
spinlock不能能极短临界区（改几个变量、链表指针）
mutex能不能可能涉及 IO、可能阻塞的较长临界区
rwlock / seqlock不能能（读侧）读多写少
RCU读侧不能睡（经典 RCU）能读者零开销的链表替换
atomic_t—能单个计数、标志位

5.1 spinlock 的三个版本，为什么要分

这是最容易搞错的一组 API，差别全在「还额外防住谁」：

API防多核禁抢占禁中断禁软中断
spin_lock()是是否否
spin_lock_bh()是是否是
spin_lock_irqsave()是是是（保存原状态）是（附带）
死锁是怎样发生的（单核就能复现）
① 进程上下文拿到 spin_lock(&L)，正在改链表
② 硬件中断到来，CPU 立刻跳进中断处理函数
③ 中断处理函数也需要这把锁，调 spin_lock(&L)
④ 锁已被占，中断函数开始自旋等待
⑤ 但持锁的那个进程已经被中断挂起，根本没法继续执行来释放锁
结果：这台核永远转在④这一步，系统彻底卡死（不是慢，是死）
正确做法：进程侧用 spin_lock_irqsave(&L, flags)，拿锁时就把中断关了

所以规则是：只要中断处理函数可能碰这把锁，进程侧就必须用 _irqsave；只要软中断可能碰，就必须至少用 _bh。 拿不准就用最保险的那个，代价只是稍微多关几十个纳秒的中断。

5.2 mutex 的适用边界

mutex 有「持有者」概念，所以能做优先级继承（见 T02），也能被调试工具检测「谁占着锁不放」。它的代价是：获取可能要睡眠（等别人释放），所以绝对不能在中断上下文里用——中断上下文没有可被调度的实体，一睡就是死机。

还有一条常被忽略的：mutex 允许同一线程重复加锁吗？ 默认不允许（会死锁），除非用 mutex_lock_interruptible 配合自己设计，或明确使用「递归锁」语义（内核里基本不鼓励）。设计上应该避免「同一个函数在持锁时又调用了会拿同一把锁的函数」。

5.3 三条铁律

  1. 锁顺序必须全局一致。A 线程先拿 L1 再拿 L2，B 线程先拿 L2 再拿 L1，必然死锁（ABBA）。多把锁的代码必须写出明确的「层级」并在注释里定死。
  2. spinlock 不可重入。同一执行流重复 spin_lock 同一把锁，会自己等自己。
  3. 持 spinlock 时不许睡眠。不许 kmalloc(GFP_KERNEL)、不许 copy_from_user、不许 mutex_lock、不许 IO 等待。要分配内存就用 GFP_ATOMIC。

6. 时间、延时与定时器

内核的时间基准是 jiffies：一个随定时器中断自增的计数器，频率由 HZ 决定（常见 100、250、1000）。所以 1 jiffy = 10ms / 4ms / 1ms，取决于编译配置。所有老式定时都建立在这个粒度上。

四种「等一会儿」的函数，区别全在「让不让出 CPU」：

函数方式能在中断里用吗精度适用
udelay(n)忙等（空转 CPU）能微秒级，较准等硬件就绪，n < 10 级别
mdelay(n)忙等能毫秒级极短的硬件等待，大数禁用
msleep(n)睡眠（让出 CPU）不能受 HZ 限制，可能多睡进程上下文里等几十毫秒以上
usleep_range(a,b)睡眠不能微秒级，允许范围需要较精度的短延时，且可睡眠
为什么 mdelay 会害死系统 忙等期间这颗核什么也做不了：不能调度、不能响应同级中断。你在驱动里写 mdelay(100)，系统就丢掉 100ms 的实时性；写在循环里调用几十次，就会触发内核的 soft lockup 检测（默认 20 秒无调度就报警），日志里出现 BUG: soft lockup，栈上正是你的驱动。

定时执行的三种工具，按精度和上下文选：

  • timer_list：基于 jiffies，精度到 1 个 tick；回调在软中断上下文，不能睡眠。
  • hrtimer：高精度（纳秒级），实时场景常用；回调同样不能睡眠。
  • delayed_work：延时后跑在工作队列线程里，可以睡眠，是驱动里最常用的「过一会儿再做」。

7. 十个常见误解

误解真相
「中断处理函数里可以随便调用函数」只能调用「不睡眠」的函数。凡涉及 IO、内存分配（GFP_KERNEL）、mutex 的都不能用。
「单核系统不需要考虑并发」中断、软中断、内核抢占在单核上都会造成并发。
「spinlock 一定比 mutex 快」只在极短临界区成立。长期持有时多核都在空转，总吞吐反而更差。
「进程侧用 spin_lock 就够了」若中断 handler 也碰这把锁，必须用 spin_lock_irqsave，否则单核就死锁。
「关中断能解决所有同步问题」关中断只挡住本核；多核之间还要靠锁。而且长时间关中断会毁掉实时性。
「tasklet 可以睡眠」不行，它在软中断上下文。要睡眠只能用 workqueue 或线程化中断。
「softirq 可以自己新增一种」不能，它是编译期固定的十种左右，用户只能用 tasklet 或 workqueue。
「GPIO 号就是中断号」两者完全不同的编号体系，必须查芯片手册的中断映射表。
「清中断标志只是走个形式」不清就再也不会收到下一次中断——这是「只触发一次」类 bug 的头号原因。
「IRQ 和 FIQ 只是名字不同」FIQ 有独立寄存器组、优先级更高、可嵌套更少保存，是给极低延迟场景用的。

8. 自检：能答出来才算懂

1

进入 IRQ 时硬件自动做了什么？和 SVC 相比多了什么、少了什么？

看答案

保存 CPSR→SPSR_irq、PC+4→LR_irq、切 IRQ 模式与栈、自动置位 I 关中断、跳到 VBAR+0x18。相比 SVC 多了「自动关中断」，且发生时点不确定，所以软件要保存更多寄存器（r0–r3 也得存）。

2

中断处理函数为什么不能睡眠？睡了会怎样？

看答案

它没有可被调度的任务上下文（不是某个 task 在执行），调度器无法把它「换出去再换回来」。一旦调用会睡眠的函数，调度器会报 BUG: scheduling while atomic，系统可能直接卡死。

3

为什么要把中断分成上下半部？各自能做什么？

看答案

上半部在中断上下文，期间本核难以响应同级中断、不能睡眠，所以要极短：只清标志、读关键数据、唤醒下半部。下半部（softirq/tasklet/workqueue）承担耗时工作；其中只有 workqueue 与线程化中断可以睡眠。

4

单核系统里有哪三种并发来源？

看答案

硬件中断、软中断/tasklet、内核抢占（若开启）。三者都能在「你的代码正执行到一半」时插进来。

5

复述那个「spin_lock + 中断」的死锁，并给出正确写法。

看答案

进程持锁 → 中断打断 → handler 抢同一把锁 → 自旋等 → 但持锁进程被挂起无法释放 → 死锁。正确写法：进程侧 spin_lock_irqsave(&L, flags)，拿锁时关中断，释放时 spin_lock_irqrestore。

6

spin_lock_bh() 里的 bh 是什么？什么场景必须用它？

看答案

bh = bottom half，指软中断/tasklet 那层。若软中断代码也会拿同一把锁，进程侧必须用 _bh 版本，否则「持锁被软中断打断，软中断抢同一锁」就死锁。

7

mutex 和 spinlock 的选择标准，一句话说清。

看答案

临界区里会不会睡眠（或可能阻塞）。不会 → spinlock（可用在中断）；会 → mutex（只能进程上下文）。

8

同一条中断线被两个设备共享时，驱动必须遵守什么？

看答案

注册时带 IRQF_SHARED；handler 里必须先判断中断是不是自己的，不是就立即返回 IRQ_NONE；且不能假设「中断来了就一定是我的事件」。

9

mdelay(100) 为什么是危险写法？该换成什么？

看答案

它是忙等，100ms 内这颗核既不调度也不响应同级中断，会严重破坏实时性并可能触发 soft lockup。进程上下文里应换 msleep(100) 或 usleep_range。

10

中断「只触发一次」的最常见原因是什么？

看答案

没有清中断标志（或清的方式不对，比如该写 1 清 0 却写了 0，或清了外设但没写 GIC 的 EOIR）。硬件认为这次中断还没被处理完，就不再上报。

9. 这一章要动手的命令

  1. cat /proc/interrupts —— 看每个中断号在每颗核上的计数，多按几次按键看数字涨没涨。
  2. watch -n1 'grep gpio /proc/interrupts' —— 实时观察某个外设的中断频率。
  3. cat /proc/softirqs —— 看各类软中断的分布，判断系统负载类型。
  4. dmesg | grep -i -E "irq|interrupt" —— 找中断申请失败、共享冲突的痕迹。
  5. 在驱动里故意写 mdelay(500) 并循环 10 次，观察 dmesg 里的 soft lockup 报警。
  6. trace-cmd record -e irq_handler_entry 或 perf record -e irq:irq_handler_entry —— 看中断处理耗时。
  7. 开启 CONFIG_DEBUG_ATOMIC_SLEEP 后跑自己的驱动 —— 它会直接抓出「在原子上下文里睡眠」的调用栈。
