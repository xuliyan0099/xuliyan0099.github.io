ARM 架构与 Cortex-A7

读启动代码时，你会看到一堆 mcr p15、movs pc, lr、dsb 这样的指令。它们不是玄学，每一条都对应一个明确的硬件动作。这一章把 Cortex-A7 的寄存器、异常、协处理器、缓存与内存映射讲透，之后 T08 的启动链路就能一句一句读懂。

★ 一读 纯读约 5 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① Cortex-A7 到底有哪些寄存器、哪些是每个模式私有的；② 七种异常怎么进入、怎么返回；③ mcr p15 在配什么；④ 缓存与 DMA 为什么会打架；⑤ 三种屏障指令各管什么。

读完你应该能回答

  • 为什么 IRQ 返回要用 subs pc, lr, #4 而不是 movs pc, lr？
  • SCTLR 的 M 位和 I 位分别控制什么？打开它们的顺序有讲究吗？
  • 一条 cache line 多少字节？DMA 收完数据为什么要 invalidate？
  • DMB、DSB、ISB 三者最核心的区别是什么？
  • i.MX6ULL 的 DDR 从哪个物理地址开始，内核把它映射到哪个虚拟地址？

1. 为什么不能跳过硬件细节

CPU 视角（配合 T18 读） 本章讲 CPSR 与异常向量，那张位段图在 T18 有逐位拆解。 想看清每条指令的位段、流水线与寄存器实际变化，跳 T18 · CPU 是怎么执行一行代码的 第 2、8 节（机器码位段、异常进入的三件事）。

裸机/内核启动代码里有几类东西，不懂硬件就完全读不下去：

代码里看到的背后的硬件概念在哪一章会用到
mcr p15, 0, r0, c1, c0, 0写 CP15 的 SCTLR，开 MMU/cacheT08 启动、T03 页表
msr cpsr_c, #0xD3切到 SVC 模式并关中断T08 head.S
ldr sp, =0x...给当前模式的栈指针赋值T08 启动
dsb / isb等内存访问完成 / 清流水线T03、T06、驱动
b vector异常向量表T06、T08

所以这一章不是「补充知识」，而是后面三章的前置条件。

2. Cortex-A7 是什么水平的一颗核

i.MX6ULL 里是单核 Cortex-A7（A7 本身支持多核簇，但这颗芯片只放了一个）。它的关键参数：

项目规格工程含义
架构ARMv7-A，32 位虚拟地址 4GB，两级页表（无 LPAE 时）
流水线8 级，顺序双发射分支误预测代价大，代码布局影响性能
主频i.MX6ULL 常见 528MHz（可超到 800+）算力有限，别指望跑重负载
L1 缓存32KB 指令 + 32KB 数据，4 路组相联cache line 64 字节
L2 缓存i.MX6ULL 集成 128KB多核共享（此处单核）
NEON有（SIMD/FPU）可做向量运算，但要注意上下文保存开销
MMU有，支持 4KB/64KB/1MB 页T03 讲的页表就基于它

「顺序双发射」意味着它不能像 A15/A72 那样乱序执行多条指令，所以依赖链和 cache miss 的代价更直接地反映在性能上。这也是为什么在 A7 上「把热数据放一起、少用指针追逐」这类优化效果特别明显。

3. 寄存器组：16 个通用 + 状态寄存器 + 影子寄存器

ARMv7-A 有 16 个 32 位通用寄存器（r0–r15）和两个状态寄存器（CPSR、SPSR）。其中几个有特殊身份：

寄存器别名特殊用途
r13SP栈指针，每个模式各有一个
r14LR链接寄存器，存返回地址，异常进入时硬件写它
r15PC程序计数器（读它得到的是当前指令地址 + 8，这是流水线造成的）
r7—ARM EABI 里专门放系统调用号（见 T01）
r11FP帧指针（编译器可选）

「影子寄存器」（banked registers）是 ARM 的一个精巧设计：不同模式下，同一编号的寄存器指向不同的物理寄存器。比如 SVC 模式有自己的一份 r13/r14，IRQ 模式也有自己的一份。这样异常进入时，硬件只要切换模式，SP 和 LR 自动就是「这个模式专用的」，不需要软件保存——这是 ARM 能快速响应中断的关键。

User 模式： r0..r12, sp_usr, lr_usr, pc, cpsr SVC 模式： r0..r12, sp_svc, lr_svc, pc, cpsr, spsr_svc IRQ 模式： r0..r12, sp_irq, lr_irq, pc, cpsr, spsr_irq FIQ 模式： r8..r12 也有私有副本（共 5 个额外影子寄存器，响应最快）

注意 FIQ 特殊在哪：它除了 sp/lr，还有 r8–r12 的私有副本。所以 FIQ 处理函数几乎不用保存寄存器，延迟可以做到极低。代价是它能用的寄存器少、且通常只给一个中断源用。

CPSR 的关键位（记住这几位就够用）：

位名字作用
[4:0]M当前模式（0x10=User、0x13=SVC、0x12=IRQ…）
[7]IIRQ 屏蔽位，1 = 关
[6]FFIQ 屏蔽位，1 = 关
[9]A非对齐访问陷阱（调试用）
[28:31]N/Z/C/V条件标志，比较与跳转依赖它们

4. 七种异常：进入、返回，以及为什么返回要减 4

ARM 把「打断正常执行、跳到固定地址」的所有情况统称异常。七种，向量表里占八项（第 8 项保留）：

异常向量偏移触发原因进入时 LR 保存的是返回指令
Reset0x00上电 / 复位无（不需要返回）—
Undefined0x04执行了非法指令非法指令的下一条地址movs pc, lr
SVC0x08svc 指令（系统调用）svc 的下一条movs pc, lr
Prefetch Abort0x0C取指时 MMU 拒绝（代码页不可执行/未映射）出错指令的下一条subs pc, lr, #4
Data Abort0x10读/写数据时 MMU 拒绝（缺页、越权）出错指令的下下条（+8）subs pc, lr, #8
IRQ0x18普通中断被打断指令的下一条subs pc, lr, #4
FIQ0x1C快速中断同上subs pc, lr, #4

为什么 IRQ 返回要 subs pc, lr, #4？ 因为中断可能在任意一条指令执行到一半时到来（实际上是在指令边界，但「边界」指的是取下一条指令之前）。硬件存的 LR 是「被打断那条指令的下一条」，而我们想回去执行的是「被打断的那一条」。所以返回时要减 4（一条 ARM 指令 4 字节）。

为什么 Data Abort 要减 8？ 因为 ARM 的流水线预取了指令，Data Abort 发生时 PC 已经跑到出错指令之后两条的位置，硬件存 LR 时又加了一层偏移。这是历史包袱，记住结论就行：Data Abort 用 subs pc, lr, #8，Prefetch Abort 与 IRQ/FIQ 用 #4，SVC/Undefined 直接 movs pc, lr。

movs pc, lr 那一串 s（suffix）是关键：它不只是「跳回」，还会把 SPSR 恢复到 CPSR，也就是把模式从异常模式切回原来的模式。所以异常返回一条指令就完成了「恢复状态 + 跳转」两件事。

向量表本身很小，每项只有 4 字节，放不下处理代码，所以通常写成「跳转」：

_vectors: b reset_handler @ 0x00 b undef_handler @ 0x04 b svc_handler @ 0x08 b prefetch_handler @ 0x0C b data_handler @ 0x10 b reserved @ 0x14（ARMv7 保留） b irq_handler @ 0x18 b fiq_handler @ 0x1C

这张表放在哪由 SCTLR.V（bit13）或 VBAR（CP15 c12）决定：老方式是 V=0 放 0x0000_0000、V=1 放 0xFFFF_0000；Cortex-A7 支持 VBAR，可以放任意对齐地址。Linux 启动早期就靠它把向量表迁到高地址。

5. CP15：配 MMU、缓存、向量表的那个协处理器

协处理器 15（CP15）是 ARM 的「系统控制单元」。它的寄存器不叫 r0–r15，而是用 cN 编号，访问必须用两条指令：

MRC p15, opc1, Rt, CRn, CRm, opc2 @ 读 CP15 到通用寄存器 MCR p15, opc1, Rt, CRn, CRm, opc2 @ 写通用寄存器到 CP15 @ 例：读 SCTLR 到 r0 MRC p15, 0, r0, c1, c0, 0 @ 例：把 r0 写进 SCTLR（比如开 MMU） MCR p15, 0, r0, c1, c0, 0

起名规律：MCR 是「从处理器（r）到协处理器（c）」，MRC 反过来。记不住就记「MCR = Move to Coprocessor Register」。

最关键的几个寄存器：

寄存器名字管什么
c1SCTLR总开关：MMU、D cache、I cache、对齐检查、向量表基址模式
c2TTBR0 / TTBR1两张页表的物理基址（低地址/高地址），含 ASID
c3DACR域访问控制（Linux 用它管理页的访问权限）
c12VBAR异常向量表基址（Cortex-A7 支持）
c13FCSE / ASID进程地址空间标识
c15CBAR告诉软件「GIC 在这个地址」，Linux 用它找中断控制器

SCTLR（c1）的关键位，看启动代码时会反复遇到：

位名字含义
[0]MMMU 总开关，1 = 开
[1]A地址对齐检查
[2]C数据缓存（D cache）开关
[12]I指令缓存（I cache）开关
[13]V向量表基址：0 = 0x0000_0000，1 = 0xFFFF_0000
[23]XP扩展页表（用于 TEX 重映射）
[28]TRETEX 重映射使能
/* 打开 MMU 的标准顺序（顺序错了会当场死机） */ 1. 建好页表，把页表物理基址写入 TTBR0 2. 写 DACR（通常先全 client 权限） 3. 无效化 TLB 与 cache（TLB 里可能还留着旧映射） 4. DSB + ISB（确保写操作真的生效） 5. 读 SCTLR → 置位 M=1、I=1、C=1 → 写回 6. ISB（清流水线，下一条指令就用新映射取指）

第 4 步和第 6 步为什么必须有？因为 ARM 是流水线 + 缓存架构：你写进去的配置值不一定立刻生效，正在预取的指令也可能是旧地址的。没有这两条屏障，你会遇到「MMU 明明开了，但跑到某条指令就飞」这类最折磨人的问题。

6. 缓存与 DMA：为什么会读到旧数据

Cortex-A7 的 L1 数据缓存是 32KB、4 路组相联，cache line 为 64 字节。CPU 的每次读写都先经过 cache：读到就命中（极快），没读到就整行（64 字节）从内存搬进来。

问题在于：DMA 引擎和外设不经过 CPU 的 cache，它们直接读写物理内存。于是两个方向都可能出错：

方向发生了什么症状正确操作
设备写内存（收数据）cache 里还留着这块内存的旧副本，设备已经更新了内存CPU 读到的永远是旧数据invalidate（丢弃 cache line，强制下次从内存读）
设备读内存（发数据）CPU 写的数据还在 cache 里（脏行），没落到内存设备读到的是旧内容clean（把脏行写回内存）
一个真实的踩坑：串口 DMA 收到乱码
① 驱动准备缓冲 buf[256]，先 memset 清零 → 这 256 字节进了 cache
② 启动 DMA 接收，CPU 去干别的
③ DMA 把收到的 20 字节直接写进内存，但 cache 里的旧副本还是 0
④ CPU 读 buf → 命中 cache → 读到全 0，看起来「什么都没收到」
正确做法：DMA 启动前对 buf 做 clean + invalidate；DMA 完成后对 buf 做 invalidate（或用内核的 dma_map/dma_sync API）

要强调一个陷阱：缓存操作的最小单位是 cache line（64 字节），不是字节。如果你的 DMA 缓冲只有 20 字节，而它和别的变量共享同一条 64 字节 cache line，那么一次 invalidate 会把相邻变量的缓存也丢掉（数据本身没坏，但可能丢掉了未写回的脏数据）。所以 DMA 缓冲必须按 cache line 对齐，并独占整条 line。这也是内核 dma_alloc_coherent() 会返回对齐内存的原因。

在 Linux 驱动里，不要自己写 mcr p15 来管 cache，要用 DMA API：dma_map_single()（准备给设备用）、dma_sync_single_for_cpu()（拿回给 CPU 用）、dma_unmap_single()（用完解映射）。这些 API 在带 cache 的 ARM 上会插入正确的 clean/invalidate，在没有 cache 一致性问题或带 IOMMU 的平台上则自动退化为空操作。

7. 三种屏障：DMB、DSB、ISB

这是 ARM 上最抽象的一组指令，但它们的用途可以用一句话区分：

指令保证什么不保证什么典型场景
DMB它前后的内存访问，在别的观察者看来顺序正确不保证前面的访问已经完成多核共享数据、DMA 描述符发布
DSB前面的所有内存访问已真正完成（对系统可见）不清流水线写外设寄存器后必须等它生效；改页表后
ISB清空流水线，让后面的指令按新状态取指不等内存完成改完 CP15 配置、改完代码、切换 MMU

三条记忆锚点：

  • DSB 最重：它真的「等」，代价最大，只在必须确认硬件收到时才用。
  • DMB 管顺序：写两个变量，想让另一个核看到时「先 A 后 B」，就在中间插 DMB。
  • ISB 管代码：只要「我改的东西会影响后面指令的执行」（配置寄存器、自修改代码、MMU），就必须 ISB。

启动代码里最常见的组合是 DSB 紧跟 ISB：先确保配置写进去了（DSB），再清流水线让新配置生效（ISB）。这个组合在 T08 的 MMU 使能、cache 使能处会反复出现。

内核启动后建立的「直接映射」把 DDR 从物理 0x8000_0000 映射到虚拟 0xC000_0000 起，所以有 virt = phys - 0x80000000 + 0xC0000000 这个换算（见 T03）。而外设区（0x0200_0000 一带）不在直接映射里，必须 ioremap 才能访问。

提醒 上表的地址请以你手上的《i.MX6ULL 参考手册》第 2 章 Memory Map 为准。不同封装/型号的地址会有差异，尤其是 GPIO5、UART 编号与 OCRAM 大小。写驱动前先抄手册，不要抄博客。

9. 十个常见误解

误解真相
「ARM 是精简指令集，所以每条指令都一样快」流水线、cache、分支预测都会造成差异；load/store、cache miss 的代价远高于算术指令。
「r15 读出来就是当前指令地址」读到的是「当前指令 + 8」（流水线预取），写 PC 才是跳转。
「所有模式的 r13 是同一个」每个异常模式有独立的影子 SP/LR，这正是异常能快速进入的原因。
「异常返回就是普通跳转」movs pc, lr 同时恢复 SPSR 到 CPSR，即切回原模式。
「IRQ 返回不用减 4」必须减，否则会跳过一条指令（或重复执行错位）。
「MMU 和 cache 可以一起开」要按顺序：页表 → DACR → 无效化 TLB → DSB/ISB → SCTLR → ISB。顺序错会死机。
「cache 一致性由硬件自动保证」Cortex-A7 不维护与 DMA 的自动一致，必须手动 clean/invalidate 或用 DMA API。
「DMB 就是等所有操作完成」那是 DSB。DMB 只保证顺序可见。
「cache line 是 32 字节」A7 是 64 字节。算 DMA 对齐时用错会踩相邻数据。
「FIQ 只是更快的 IRQ」它有独立寄存器组（r8–r12 影子），几乎不用保存现场，是为极低延迟设计的。

10. 自检：能答出来才算懂

1

IRQ 进入时硬件保存了哪两个寄存器？为什么返回要 subs pc, lr, #4？

看答案

保存 CPSR→SPSR_irq、PC+4→LR_irq。LR 存的是「被打断指令的下一条」，而要回去执行的是被打断的那条，所以减 4。

2

为什么每个模式有自己的 SP？这对异常响应有什么好处？

看答案

影子寄存器让异常一进入就自动拥有独立的栈指针，不需要软件先把用户 SP 存起来再换栈，省掉了关键的前几条指令，缩短响应延迟。

3

SCTLR 的 M、C、I 三位各是什么？打开顺序有讲究吗？

看答案

M=MMU、C=D cache、I=I cache。必须先建页表并写 TTBR0、清 TLB、DSB/ISB，再一起置位；顺序颠倒会在「MMU 开了但页表没准备好」时立刻取指失败。

4

DMA 往内存写数据后，CPU 读到旧值，该做 clean 还是 invalidate？

看答案

invalidate（丢弃 cache line）。clean 是把 CPU 的脏数据写回内存，方向相反。

5

DMB、DSB、ISB 各保证什么？各举一个使用场景。

看答案

DMB 保证顺序（多核共享数据发布）；DSB 保证完成（写外设寄存器后等生效）；ISB 清流水线（改 CP15 配置或改代码后）。

6

cache line 多大？为什么 DMA 缓冲要独占一条 line？

看答案

A7 上是 64 字节。缓存操作以整行为单位，若缓冲与别的变量共享一行，invalidate 会连带丢弃对方的缓存内容（可能丢脏数据）。所以要按 64 字节对齐并独占。

7

MRC p15, 0, r0, c1, c0, 0 在做什么？

看答案

把 CP15 的 c1（SCTLR，系统控制寄存器）读进 r0。这是「先读出来、改几位、再写回」这种配置方式的第一步。

8

向量表可以放在哪？由谁决定？

看答案

老方式由 SCTLR.V 决定（0x0000_0000 或 0xFFFF_0000）；Cortex-A7 支持 VBAR（CP15 c12），可放任意对齐地址，Linux 启动早期会把它迁到内核空间。

9

为什么 movs pc, lr 能同时「跳回」和「切模式」？

看答案

因为 s 后缀让它把 SPSR 恢复到 CPSR。CPSR 里有模式位，所以模式随之切回，而 PC 被写入 lr 完成跳转。

10

i.MX6ULL 的 DDR 物理地址与内核虚拟地址怎么换算？

看答案

物理 0x8000_0000 对应虚拟 0xC000_0000，所以 virt = phys - 0x80000000 + 0xC0000000，即 __va/__pa。只适用于直接映射区，外设区要走 ioremap。

11. 这一章要动手的命令

  1. 写一段裸机（或 U-Boot 里）读 SCTLR 的代码：MRC p15,0,r0,c1,c0,0，打印出来对照第 5 节的位表。
  2. 反汇编任意一个 ARM 程序：arm-linux-gnueabihf-objdump -d demo，找 svc、push {r4,lr}，理解调用约定。
  3. cat /proc/cpuinfo —— 看 processor/Features，确认你的板子实际开了哪些特性。
  4. dmesg | grep -i -E "cache|mmu|Memory" —— 看内核启动时报告的 cache 与内存布局。
  5. cat /proc/iomem —— 看内核视角的物理地址分配表，对照第 8 节。
  6. 在驱动里故意省掉 DMA 前的 clean，观察数据错乱（理解第 6 节）。
