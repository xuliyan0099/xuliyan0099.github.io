虚拟内存与地址翻译（详解）

这一章是「内存」这条线的地基：硬件怎么把一个虚地址拆成三段、页表里每个位代表什么权限、缺页时有几种完全不同的处理、为什么你 malloc 了 1MB 却几乎不占物理内存。不把这一章啃下来，后面所有「段错误」「OOM」「内存泄漏」都只能是猜。

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

▶ 动手看它怎么翻译：MMU 页表互动台

输入任意虚拟地址，实时看它被拆成 10/10/12 三段，逐级扫过一级页表和二级页表，最后拼出物理地址；还可以对比 TLB 命中、关掉 MMU、空指针触发 abort 三种情况。

本章要解决的问题

① 为什么必须有虚拟地址，物理地址直接用会死在哪；② 一个 32 位地址怎么被拆开去查表；③ 页表描述符的每个位是什么意思；④ 缺页到底分几种，各走什么路径；⑤ 页表的空间开销有多大，大页为什么能救 TLB。

读完你应该能回答

  • 一个 4KB 页表项（PTE）里，权限位、缓存位、有效位分别在管什么？
  • 进程切换后为什么 TLB 不必全刷？靠什么区分不同进程的条目？
  • malloc(1MB) 返回了地址，为什么 RSS 几乎没涨？
  • 为什么访问一个没映射的地址是 SIGSEGV，而访问一个已映射但没调入的页只是变慢？
  • 用 1MB 大页和 4KB 小页，TLB 能覆盖的范围差多少倍？

1. 三个死结：为什么非虚拟地址不可

假设没有 MMU，程序直接操作物理地址，会立刻撞上三堵墙：

第一堵：互相踩踏。 你的程序算出一个越界下标，写到了 0x8000_1000，那里正好是另一个程序的变量。对方算错了，你根本不知道是自己干的。没有任何机制能拦住你——因为物理地址是「公共场所」。

第二堵：地址写死。 程序编译时函数地址就定了。如果这个程序被加载到物理地址 0x8000_0000，那没问题；换一台机器加载到 0x8100_0000，所有绝对地址全错。你不可能为每个加载地址编一份程序。

第三堵：装不下。 物理内存 512MB，你要跑 3 个各需 300MB 的程序，直接用物理地址就绝无可能。但其中两个程序大部分时间在睡觉，它们的代码页其实可以不在内存里。

虚拟内存一次解决三个：每个进程有自己独立的地址世界（第一堵）、程序永远认为自己从固定地址开始（第二堵）、虚拟页可以不在物理内存里（第三堵）。代价是每次访存都要多一次（或几次）地址翻译——这个代价由硬件 MMU 承担。

2. MMU 怎么翻译一个地址（ARMv7 细节）

以最常见的 4KB 页 + 两级页表（ARMv7 短描述符格式）为例。一个 32 位虚拟地址被切成三段：

31 20 19 12 11 0 ┌──────────────────┬────────────┬─────────────┐ │ L1 索引（12位） │ L2 索引(8位)│ 页内偏移(12位) │ │ 0..4095 │ 0..255 │ 0..4095 │ └──────────────────┴────────────┴─────────────┘ ↓ 查第一级表 ↓ 查第二级表 ↓ 直接用作偏移

三步走：

  1. 用 L1 索引查一级表：一级表有 4096 项、每项 4 字节，所以它必须 16KB 对齐，基址放在 TTBR0（低地址）或 TTBR1（高地址）。
  2. 拿到 L2 表的基址，用 L2 索引查二级表：二级表 256 项、每项 4 字节，共 1KB，1KB 对齐。
  3. 拿到物理页基址，加上 12 位页内偏移，得到最终物理地址。

所以「一个 4KB 页的映射」在内存里要花掉 4 字节（L2 表项），而它依赖的那张 1KB 的二级表，会被同一 1MB 区间内的所有页共享。

2.1 页表项里到底有哪些位

一个 L2 小页描述符（4 字节）的关键位：

位名字作用
[1:0]类型0b10 = 小页（4KB）；0b01 = 大页（64KB）；0b00 = 无效（访问即触发缺页）
[11:10]AP访问权限：00 仅内核读写；01 全可读写；10 内核读写/用户只读；11 全只读
[3:2]C / BCache 与写缓冲策略：写通、写回、强序。直接影响外设寄存器访问是否正确
[8:5]domain域，用于把一组页的权限整体切换（Linux 用得很克制）
[0]（第二字）XN执行禁止。标了它，这块页只能读写不能取指——这是防「数据被当代码执行」的关键
为什么驱动里访问寄存器要专门 ioremap 因为普通内存映射的 C/B 位是「可缓存」，CPU 可能把你的读操作合并、把你的写操作延后。而外设寄存器要求「每次访问都真的到硬件」。所以 ioremap() 会给你一块标为「强序、不缓存」的映射。用普通指针去访问寄存器地址，症状是「写没生效」「读到的值不变」。

2.2 TLB：翻译结果的缓存

如果每次访存都走上面三步，程序会慢到无法接受（每次要 2~3 次额外内存访问）。所以 MMU 里有一小块缓存叫 TLB，存「虚页号 → 物理页号 + 权限」的翻译结果。

问题来了：进程切换时，另一个进程的虚地址含义完全不同，TLB 里的旧条目必须失效。如果每次都全刷，切换代价高得离谱。ARM 的解法是给每个 TLB 条目打上 ASID（地址空间标识），切换进程时只改 ASID 寄存器，TLB 里不同 ASID 的条目天然互不干扰。这就是「进程切换不必刷 TLB」的技术基础。

还有一个必须知道的点：改了页表之后必须让对应 TLB 条目失效。内核为此提供 flush_tlb_* 一族函数。你在驱动里动态改映射却忘了刷 TLB，症状是「代码明明改了，行为还是旧的」——这种 bug 极难查。

3. 缺页：同名不同命的三种情况

「缺页」这个词容易误导，以为只有一种。实际上 CPU 只报告一件极简的事：「这次访问，我没法完成」。内核拿到这个报告后，必须自己判断原因，可能是完全不同的三件事：

类型根本原因内核动作用户态看到耗时量级
无效访问（bad area）这个地址根本不在任何 VMA 里，或权限不符（写只读页）给进程发 SIGSEGV段错误，进程被杀微秒
次要缺页（minor）地址合法，页也已在内存里，只是页表项还没建（如 COW、匿名页首次写）分配/复用物理页，填页表项，刷 TLB毫无感觉几微秒
主要缺页（major）页不在内存：要么在 swap，要么在文件里还没读进来发起 IO 读入、可能要先回收一页明显卡顿（几十毫秒到几百毫秒）毫秒级

内核的处理路径（ARM 上从异常向量进 do_page_fault）大致是：

MMU 报 Abort→读 FAR（出错地址）→查 VMA 树→落在 VMA 内？→handle_mm_fault→建页表项→返回重试该指令

注意最后一句：内核不是「跳过」那条指令，而是返回用户态重新执行它。所以「缺页」对程序是透明的——只要这次能修好，程序根本不知道发生过。

同一个地址，三次不同的结局
① 访问 0x0000_0000（NULL 附近）：不在任何 VMA → SIGSEGV，进程死
② 访问刚 malloc 的地址：VMA 有，页表项空 → minor fault，分配 4KB 页，继续跑
③ 访问被换出到 eMMC 的页：VMA 有，页在磁盘 → major fault，读盘（几毫秒），继续跑
差别不在「地址」本身，而在页表和 VMA 的状态

由此可以解释一个很常见的困惑：为什么「空指针」几乎总是崩在 0 附近？ 因为内核刻意让低地址区间（通常是前 4KB 到 128KB，由 mmap_min_addr 控制）没有任何映射。这是故意的：如果 0 地址可访问，那么「结构体指针为 NULL 但访问其成员」这种经典 bug 就不会崩，而是悄悄读到垃圾数据，后果更难查。

4. malloc 的真相：虚拟内存的「空头支票」

malloc(1024*1024) 立刻返回一个合法指针，但这时物理内存一个字节都没给。它只做了两件事：

  1. 让内核在进程的 VMA 链表里加一段「这段虚拟地址归你用」的登记（若是大块，走 mmap；小块走 brk 抬高堆顶）。
  2. 返回这段虚拟地址的起始位置。

页表项呢？没建。所以真正第一次写这 1MB 里的某个字节时，才会触发 minor fault，内核才分配一个 4KB 物理页、填一个页表项。这个「用多少给多少」的策略叫延迟分配（demand paging）。

算一笔：malloc 1MB，只写第一个字节
malloc 之后：VSS（虚拟大小）+1MB，RSS（常驻）几乎不变
写第一个字节：触发 1 次 minor fault，分配 1 个 4KB 页
RSS 增加：4KB（不是 1MB）
若之后逐页写满：再触发 255 次 minor fault，RSS 才涨到 1MB
结论：VSS 是「许愿」，RSS 是「兑现」，PSS 是「按共享比例分摊后的兑现」

这三个指标必须分清，否则内存排查全错：

  • VSS（Virtual Set Size）：虚拟地址空间总量。虚高是正常的，不代表真占内存。
  • RSS（Resident Set Size）：真正在物理内存里的页。但它会重复计算共享页（比如 10 个进程共用一份 libc，每个进程的 RSS 都算上那几 MB）。
  • PSS（Proportional Set Size）：把共享页按使用进程数平摊。多进程环境下用它判断真实占用更准。

还有一个高频疑问：为什么 free 之后 RSS 不降？ 因为 glibc 的分配器（arena）把内存留在自己手里，方便下次复用，不还给内核。只有大块（默认 >128KB，由 M_MMAP_THRESHOLD 控制）才走 mmap/munmap 真正归还。

5. 页表的成本，与大页为什么存在

页表本身也要占内存，而且可能占得惊人。算两个具体数：

算一：把 1GB 虚拟空间用 4KB 页映射满
1 张 L2 表覆盖 1 个 1MB 区间（256 项 × 4KB）
1GB = 1024 个 1MB 区间 → 需要 1024 张 L2 表
每张 L2 表 = 256 × 4 字节 = 1KB
页表总开销 = 1024 × 1KB = 1MB（还没算 L1 那 16KB）
占被映射内存的 0.1% —— 可以接受，但 TLB 会受不了
算二：同样 1GB，改用 1MB 段（大页）
一段 = 直接在 L1 表里写一项，不需要 L2 表
1GB = 1024 项 L1 → 占 1024 × 4 字节 = 4KB
相比 4KB 页方案，省下约 1MB 页表内存
代价：映射粒度粗，1MB 里只要有一小块要不同权限，就整段拆开

比省内存更重要的是省 TLB。TLB 条目数是固定的（Cortex-A7 一级 TLB 约 64 项），能覆盖的地址范围直接由页大小决定：

页大小TLB 项数能覆盖的范围
4KB64256KB
64KB644MB
1MB（段）6464MB

这就是内核为什么用 1MB 段映射 DDR：512MB 的物理内存用 4KB 页映射要 512 张 L2 表、TLB 覆盖率只有 256KB，几乎每次访存都 TLB miss；用 1MB 段只需要 512 个 L1 项，TLB 一次命中覆盖 64MB。对大块连续内存（DDR、显存、DMA 缓冲），大页是唯一合理选择。

6. 三种地址必须分清：虚拟、物理、总线

这是嵌入式 Linux 最容易搞混的一组概念，混错了就会写出「在 x86 能跑、在 ARM 上崩」的代码：

名字给谁用例子（i.MX6ULL）注意
虚拟地址CPU 执行指令时用的地址内核直接映射区 0xC000_0000 起（3G）所有指针都是这个
物理地址内存控制器看到的地址DDR 0x8000_0000；OCRAM 0x0090_0000；CCM 0x020C_4000MMU 关掉时 CPU 直接用它
总线地址DMA 控制器、外设主设备用的地址多数 ARM SoC 上与物理地址相同，但不保证不能假设相等，要走 DMA API

几个具体事实（对照 i.MX6ULL 手册的 memory map）：

  • DDR 起始 0x8000_0000，i.MX6ULL 通常 512MB，到 0x9FFF_FFFF。
  • 内部 OCRAM 0x0090_0000，128KB，U-Boot 常把栈、关键变量放这里。
  • BootROM 在 0x0000_0000，只读，复位后 CPU 从这里取第一条指令。
  • AIPS1 外设区 0x0200_0000 起：CCM（时钟）0x020C_4000、GPIO1 0x0209_C000、UART1 0x0202_0000 都在这一带。
  • GIC 中断控制器 0x00A0_0000。

内核启动后打开 MMU，从此 CPU 眼里只有虚拟地址。你要访问 0x020C_4000 这个时钟寄存器，必须先用 ioremap(0x020C4000, size) 拿到一个虚拟地址，再用它访问。若你直接把 0x020C4000 赋给指针，在 MMU 开启后会访问到一块完全无关的内存（通常是直接映射区里某个偏移），轻则读垃圾，重则改坏内核数据。

另外两条必须记的换算规则：

① 直接映射区的换算：内核把物理 0x8000_0000 起的 DDR 直接映射到虚拟 0xC000_0000 起，所以 virt = phys - 0x80000000 + 0xC0000000。宏 __va() / __pa() 干的就是这个（只在直接映射区成立）。

② DMA 必须给物理地址：外设的 DMA 引擎不懂虚拟地址。所以你要用 dma_map_single() 把虚拟地址转成设备能用的地址，用完 dma_unmap_single()。直接 __pa() 在简单 SoC 上能凑合，在有 IOMMU 或多级总线的系统上就是错的。

7. 十个常见误解

误解真相
「虚拟地址是假的，访问它要额外时间」TLB 命中时翻译几乎零开销，与物理地址访问同速。只有 TLB miss 才需要走表（多几次内存访问）。
「页表只有一张，全系统共用」每个进程一张用户页表；内核页表是所有进程共享的那一半。
「段错误都是野指针造成的」还可能是：写只读页（代码段、字符串常量）、栈溢出、访问已 munmap 的地址、非对齐访问。
「free 之后内存就还给系统了」glibc 保留 arena 复用；只有大块 mmap 才真还。
「RSS 大就是内存泄漏」RSS 含共享库页且重复计数。要看 PSS 或 smaps 里的私有部分。
「4KB 页一定最好」大块内存用大页能省页表和 TLB；4KB 只在细粒度权限/共享时有优势。
「ioremap 只是把地址加个偏移」它建立新映射并设置「不缓存、强序」属性，还会占用 vmalloc 虚拟空间。
「物理地址等于总线地址」多数 ARM SoC 恰好相等，但有 IOMMU 的系统不等。规范做法是走 DMA API。
「缺页一定很慢」minor fault 几微秒，major fault 才毫秒级，性能影响差上千倍。
「栈不会缺页」栈是自动增长的 VMA，每次大幅下探都会触发缺页；栈溢出则是越过 VMA 边界触发 SIGSEGV。

8. 自检：能答出来才算懂

1

一个 32 位虚拟地址在两级页表下被切成哪三段？各多少位？

看答案

L1 索引 12 位（bit 31–20）、L2 索引 8 位（bit 19–12）、页内偏移 12 位（bit 11–0）。对应 4096 项一级表、256 项二级表、4KB 页。

2

L1 表为什么必须 16KB 对齐？L2 表为什么 1KB 对齐？

看答案

L1 是 4096 项 × 4 字节 = 16KB，L2 是 256 项 × 4 字节 = 1KB。硬件把地址高位直接替换低位来定位表基址，所以要求表按自身大小对齐。

3

页表项里的 C/B 位如果配错，会看到什么现象？

看答案

访问外设寄存器时「写不进去」「读到的值不变」或「连续写只生效最后一次」。因为缓存与写缓冲把多次访问合并或延后了。正确做法是 ioremap 得到不缓存、强序的映射。

4

进程切换后为什么可以不刷整个 TLB？

看答案

靠 ASID。每个 TLB 条目带 ASID 标记，切换时只改 ASID 寄存器，不同进程的条目互不干扰，无需整表刷。

5

minor fault 与 major fault 的本质区别是什么？

看答案

minor：页已在物理内存，只缺页表项，纯内存操作，几微秒。major：页不在内存，要从 eMMC/swap 读入，涉及块设备 IO，毫秒级。差 1000 倍源于「内存 vs 存储」的量级差。

6

为什么 malloc 1MB 之后 RSS 几乎不变？什么时候才会涨？

看答案

malloc 只登记 VMA，不建页表、不给物理页（延迟分配）。第一次写某个页时才触发 minor fault 分配 4KB，RSS 按页增长，写满 1MB 才涨满。

7

1GB 空间用 4KB 页映射，页表要多少内存？改用 1MB 段呢？

看答案

4KB 页：1024 张 L2 表 × 1KB = 1MB。1MB 段：1024 个 L1 项 × 4 字节 = 4KB。更重要的是 TLB 覆盖率从 256KB 变成 64MB。

8

为什么内核要在 0 地址附近留一块「绝不允许映射」的区域？

看答案

为了让「NULL 指针解引用」立刻崩溃，而不是悄悄读到合法数据。这是用「保证故障可见」换「故障难查」，由 mmap_min_addr 控制。

9

举一个「物理地址 ≠ 总线地址」会出问题的场景。

看答案

带 IOMMU 的系统，或某些 SoC 的 PCIe 窗口、多级总线桥。CPU 视角的物理地址与设备发起 DMA 时的地址需要经过翻译，直接用 __pa() 会写错位置。正确做法是 dma_map_single()。

10

写只读页为什么会 SIGSEGV，而 COW 写只读页却不会？

看答案

因为 COW 页在 VMA 里被标为「可写、但当前共享」，缺页处理发现是 COW 就复制一份并授权写；而代码段/常量区的 VMA 本身标为不可写，缺页处理判为非法访问，直接发 SIGSEGV。区别在 VMA 的语义，不在页表当下的只读位。

9. 这一章要动手的命令

  1. cat /proc/self/maps —— 看自己地址空间的各段区间与权限。
  2. pmap -x <pid> 或 cat /proc/<pid>/smaps —— 逐段看 RSS/PSS/私有/共享，找出「看起来很大其实没占」的那段。
  3. cat /proc/meminfo | head -20 —— PageTables 就是本章第 5 节那笔开销。
  4. vmstat 1 —— si/so 是换入换出（major fault 的直接体现）。
  5. 写一个 malloc(100MB) 但只写 1 字节的程序，看 RSS 验证延迟分配。
  6. echo 3 > /proc/sys/vm/drop_caches 后读大文件，用 time 观察 major fault 的代价。
  7. slabtop -o —— 看内核对象缓存占了多少，排查「内核内存去哪了」。
