IP、路由与网卡驱动：包怎么出了门又回来

★ 一读 纯读约 2 小时 左侧是本卷目录 理论为主 · 实作可跳

一个包出门要过四道关：查路由、找 MAC、排队、交给网卡。回来时要过相反的关，还要多一道「中断 → 软中断 → 协议栈」。这一篇把这条链走完，顺便解释为什么 ping 通不代表端口通。

先玩一下：出门的四道关

把卡片拖成正确顺序。注意「查路由」在「找 MAC」之前——路由决定从哪张网卡出去，邻居子系统才知道该问谁的 MAC。

一、路由：不是「查表」，是「最长前缀匹配」

ip route 打印出来的每一行都是「网络/掩码 → 出口」。查表时内核不是线性扫，而是找匹配位数最多的那一条：192.168.1.0/24 与 0.0.0.0/0 同时匹配时，选前者。

路由类型含义典型输出
local本机地址，包不进网卡，直接回环local 127.0.0.1 dev lo
unicast普通单播，走某张网卡192.168.1.0/24 dev eth0
default兜底，前缀长度 0default via 192.168.1.1
unreachable / blackhole明确拒绝，用于策略blackhole 10.0.0.0/8

路由结果不是一个 IP，而是一个 struct dst_entry：它记着出口设备、下一跳、MTU、以及一组输出函数（output 指针）。所以「路由缓存」缓存的不是表项，而是这个已经准备好的「出行方案」。

二、邻居：知道 IP，但不知道 MAC

以太网发帧需要 6 字节 MAC。IP 层只知道下一跳的 IP，于是要向邻居子系统要 MAC。它维护一张 ARP 缓存，条目有状态：

INCOMPLETE刚发出 ARP 请求，还没人回答。此时 skb 被挂在这个邻居项的等待队列里。
REACHABLE确认可用，正常发包。有超时，超时后转 STALE。
STALE可能过期，但还能用。下次发包时先发一个探测，不阻塞。
FAILED问了几次没人答。后续包直接返回「主机不可达」。

ip neigh 看的就是这张表。板子上「能 ping 网关、不能 ping 同网段设备」时，先看这里有没有 FAILED，再看交换机/网线——比怀疑驱动快得多。

三、qdisc：交通管制，也是丢包的第一现场

驱动发送环很小（i.MX6ULL 的 FEC 只有几十个描述符）。上层发得比网卡快，就必须排队，这就是 qdisc（queue discipline）。默认是 fq_codel（较新内核）或 pfifo_fast。

  • 队列满时的默认动作是 drop tail：丢掉最新来的包。TCP 会因此重传，行为上表现为「吞吐上不去、延迟抖」。
  • tc -s qdisc show dev eth0 能看到 dropped 计数。这个数字持续增长，说明瓶颈在出口，不在应用。
  • 想优先保障某类流量，用 tc 建 class + filter；嵌入式产品里更常见的做法是「把非关键流量限速」，而不是做复杂调度。

四、出门与回来：完整的一条链

这条链上最容易被忽略的是第 6–7 站的分工：硬中断只负责「叫醒」，真正的收包在软中断里批量做。原因很直接：千兆线速下每秒上百万个包，每个包一次完整中断会让 CPU 完全陷在中断上下文里，应用没机会跑。

NAPI 的 budget（默认 300 个包/轮，netdev_budget）就是「一次最多处理多少」，处理不完就把软中断交给 ksoftirqd 线程，让出 CPU。你在 top 里看到的 ksoftirqd 占用高，往往就是收包压力的直接体现。

五、MTU 与开销：小包为什么贵

以太网 MTU 1500，IPv4 头 20，TCP 头 20，于是 MSS 通常 1460。每个包固定背 40 字节头，包越小，头的占比越高。

六、三个常见误判

「ping 通，端口就一定通」ping 走 ICMP，端口走 TCP/UDP，可能被防火墙、可能没有监听、也可能 backlog 满了。四件事要分开查：路由（ip route）、邻居（ip neigh）、监听（ss -lntp）、队列丢弃（ss -lnt 的 Send-Q 与 nstat）。
「MTU 调大一定更快」路径上任何一跳 MTU 更小都会导致分片或 PMTUD 黑洞。看到「小包能过、大包卡住」，先怀疑 MTU，而不是应用。
板子上的顺序网卡不通时按这个顺序查：ip link（PHY 是否 link up）→ ethtool -S eth0（错误计数）→ ip addr → ip route → ip neigh → ping → tcpdump。这条顺序能把「驱动没起来」和「网络配错」分开。

动手（可选）：看一次真实的收包

只在 🔧 实作模式展开PC 上做，或板子上做，结论一致。
  1. nstat -az | head -30 先记一份基线（尤其 IpInReceives、TcpInErrs、UdpInErrors）。
  2. tcpdump -i any -n -c 100 port 22 抓 100 个包，再 nstat -az 对比增量。
  3. tc -s qdisc show dev eth0 看 dropped；用 iperf3 打满出口再看一次。
  4. 板子上用 cat /proc/interrupts | grep eth 看中断计数，配合 top 看 ksoftirqd——这就是 NAPI 在工作的证据。

离开这一篇，你应该能

  • 按顺序说出出包的六步，并指出哪一步会丢包。
  • 解释「最长前缀匹配」与 dst_entry 的关系。
  • 说清硬中断与 NAPI 的分工，以及 ksoftirqd 高占用意味着什么。
