Buildroot 到 Yocto：定制镜像、裁剪包、产出固件

★ 一读 纯读约 6 小时 左侧是本卷目录 理论为主 · 实作可跳

「能跑 demo」和「能交产品」之间隔着一条沟：构建要可重复、镜像要可裁剪、升级要能回滚。这一篇讲构建系统，下一篇讲升级与分区。

Buildroot 与 Yocto 不是两个发行版，而是两种组织方式：一个用 Makefile 一把梭，一个用分层与配方（recipe）做长期维护。

先玩一下：一次构建的六步

把卡片拖成正确顺序。注意「先编工具链、再编包」——交叉工具链是所有后续步骤的前提。

一、Buildroot：适合一个人维护的产品

它的工作目录很直白：output/build/ 是各包的源码与编译产物，output/host/ 是交叉工具链与主机工具，output/target/ 是即将成为 rootfs 的目录树，output/images/ 是最终镜像。

    <
  • defconfig：把配置固化成文件（make imx6ull_defconfig），保证换台机器也能复现。
  • 外部树（BR2_EXTERNAL）：把自己的板级包、补丁、overlay 放在独立目录，不污染上游。
  • 增量：make 只重建变化的包；make <pkg>-rebuild 强制重编单个包。
  • overlay：把 /etc 配置、启动脚本直接叠进 target，不用改包。

二、Yocto：适合一个团队维护三年

Yocto 的核心概念只有四个：layer（分层）、recipe（配方）、task（步骤）、sstate（共享状态缓存）。

概念是什么对应文件
Layer一组相关的配方与配置，可叠加、可复用meta-*/conf/layer.conf
Recipe「怎么拿到源码、怎么编、装什么」xxx_1.0.bb
Taskdo_fetch/do_configure/do_compile/do_install由 bitbake 调度
sstate-cache任务级缓存，命中就不重编SSTATE_DIR
SDK给应用开发者用的工具链 + 库bitbake -c populate_sdk

Yocto 的代价是学习曲线与磁盘：一个完整的 poky 构建动辄几十 GB。收益是可审计、可复现、可长期维护：每个包的来源、补丁、许可证都记录在案，适合有合规要求的量产项目。

选型的一条硬标准只有你一个人维护、需求半年内定型 → Buildroot；有团队、要维护三年以上、要做 SDK 给第三方 → Yocto。混着用（Buildroot 起步、后期转 Yocto）往往付出双倍代价。

三、构建产物到手之后

一次构建会产出四类东西：bootloader（SPL + U-Boot）、内核（zImage/uImage）、设备树（dtb）、根文件系统（tar/ext4/squashfs）。它们最终被写进不同的分区，这就是下一篇的主题。

误解：构建成功就等于镜像能启动构建只保证「文件生成了」。能不能启动取决于分区位置、启动参数（bootargs）、设备树是否匹配板子、rootfs 里是否有 init。四者任何一处错，串口都会停在某个固定位置——这也是排障时「看停在哪一级」的价值。

动手（可选）：产出一个最小镜像

只在 🔧 实作模式展开PC 上做，需要网络与 20 GB 空间。
  1. git clone Buildroot，make imx6ull_defconfig（或 qemu_arm_vexpress_defconfig 先练手）。
  2. make -j$(nproc)，观察 output/images/ 里出现了哪些文件。
  3. 用 qemu-system-arm -M vexpress-a9 -kernel zImage -dtb vexpress-v2p-ca9.dtb -rootfs ... 起一次，确认能到 shell。
  4. 改 board/.../rootfs_overlay/etc/inittab，重新 make，验证 overlay 生效。
