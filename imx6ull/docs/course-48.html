中断的上半部与下半部

按键按下去，芯片的电平变了，可 CPU 不会自己知道——它要么不停轮询（浪费），要么等一个中断。中断处理有三条铁律：不能睡、要快、不能丢事件。这一课把「硬件触发 → GIC → 上半部 → 下半部 → 你的业务」这条链走一遍，并用一个带防抖的按键驱动收尾。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 中断和异常有什么区别？② 为什么中断处理里不能睡眠？③ 上半部该做哪几件事、不该做哪几件？④ tasklet、工作队列、threaded IRQ 三者怎么选？⑤ 按键为什么会「按一次触发十几次」？

1. 直觉：门铃与开门

中断像门铃：按下去铃响，你去开门——不用一直站在门口看。但门铃响了不代表人还在（可能已经走了），所以开门这件事要「等一等再确认」，这个「等一等」就是下半部。

类比失效处：门铃一次只响一下，中断会「攒」——如果你在开门时又按了三次，硬件可能只记一次（边沿触发丢事件）或记很多次（电平触发重复进入）。所以真实驱动必须处理「重复进入」与「漏掉」两种情况。

2. 硬件：从引脚到向量表

按键引脚配置成双边沿触发 → GIC 记录挂起 → CPU 在指令边界检查 IRQ 线 → 保存现场、跳到向量表 IRQ 入口 → 内核按中断号找到你 request_irq 时登记的那个函数。整个过程里，中断号是唯一的关键字：设备树里 interrupts 描述的号，必须和你 request_irq 用的号一致。

3. 软件：一个带防抖的按键驱动

#include <linux/interrupt.h>
#include <linux/input.h>

static irqreturn_t key_hard(int irq, void *dev)      /* 上半部 */
{
    struct key *k = dev;
    /* 只做最急的：确认是自己的中断、把它清掉 */
    disable_irq_nosync(irq);                          /* 暂时关掉，避免抖动洪泛 */
    schedule_delayed_work(&k->dwork, msecs_to_jiffies(20));
    return IRQ_HANDLED;
}

static void key_soft(struct work_struct *w)          /* 下半部 */
{
    struct key *k = container_of(w, struct key, dwork.work);
    int v = gpiod_get_value(k->gpio);
    if (v == 0) {                                     /* 仍被按住，才算真按下 */
        input_report_key(k->input, KEY_ENTER, 1);
        input_report_key(k->input, KEY_ENTER, 0);
        input_sync(k->input);
    }
    enable_irq(k->irq);
}

static int key_probe(struct platform_device *pdev)
{
    ...
    ret = devm_request_irq(&pdev->dev, irq, key_hard,
            IRQF_TRIGGER_FALLING | IRQF_ONESHOT, "mykey", k);
    ...
}

三处关键：disable_irq_nosync 在上半部立刻关中断，防住 20ms 内的十几次抖动；20ms 后再读电平，仍低才算有效按下；IRQF_ONESHOT 保证下半部跑完之前不放开这条中断。少了任何一处，你会看到「按一次出十个字符」。

4. 三条误解

  • 「中断处理越短越好，所以什么都丢给下半部」：上下半部之间也有调度延迟。把「清中断」这种必须立刻做的活丢到下半部，会导致中断源一直拉着线，形成中断风暴。
  • 「/proc/interrupts 里的计数就是按键次数」：那是「进入中断的次数」，抖动会让它一次按键涨十几。它是排障工具，不是业务计数。
  • 「共享中断线可以随便挂」：共享线上每个 handler 都会被调用，必须能判断「这次是不是我的」，否则会误报。

5. 五题自测

1

为什么中断处理函数里不能 msleep？

看答案

中断上下文没有「当前任务」，调度器无法切走再切回；调用会直接报 BUG: scheduling while atomic，严重时整机卡死。

2

边沿触发与电平触发，哪个更容易丢事件？为什么按键仍常用边沿？

看答案

边沿触发在「中断被屏蔽期间又来一次」时会丢；但按键抖动会产生大量边沿，若用电平触发会持续重复进入。所以用「边沿 + 上半部关中断 + 延时确认」这套组合。

3

IRQF_ONESHOT 解决什么问题？

看答案

它保证下半部执行完之前中断线保持屏蔽，避免同一次抖动反复进入上半部；threaded IRQ 必须带它。

4

request_irq 返回 -EBUSY 意味着什么？

看答案

这条中断号已被别人占用且没标共享。要么换号，要么双方都加 IRQF_SHARED 并各自能识别自己的中断。

5

驱动里忘了 free_irq 就卸载模块，会发生什么？

看答案

中断表里还留着指向已卸载代码的指针，下一次中断直接 oops；正确做法是用 devm_request_irq 让内核自动回收。

6. 动手（40 分钟）

1. cat /proc/interrupts 找到按键那一行，按住键不放，看计数是否只涨 1（说明防抖有效）。

2. 把 20ms 改成 1ms，再按一次，观察「一次按键涨好几下」的现象。

3. 把下半部改成 tasklet 并在里面调用 i2c_transfer，看 dmesg 里的报错——亲手踩一次比背十条规则有用。

4. 用 evtest 查看上报的 KEY_ENTER 事件，确认从「电平变化」到「应用收到事件」的链路通了。
