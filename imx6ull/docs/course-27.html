进程、线程与 task_struct

Linux 在这件事上有个非常「反教科书」的设计：它根本不区分进程和线程。内核里只有一种东西——task。所谓「进程」只是「有自己地址空间的 task」，而「线程」是「和别人共享地址空间的 task」。这一课讲清这个统一模型，以及描述它的那个巨大结构体。

1. task_struct：一个几 KB 的「任务身份证」

2. 四个状态，看 /proc 就能对上

state/proc 里的字母含义能不能被信号唤醒
TASK_RUNNINGR正在跑或就绪排队—
TASK_INTERRUPTIBLES可中断睡眠（等事件）能
TASK_UNINTERRUPTIBLED不可中断睡眠（等 IO）不能（kill -9 也杀不掉）
EXIT_ZOMBIEZ已退出，等父进程回收—

看到 D 状态且长期不消失，通常意味着 IO 卡住（磁盘、NFS、驱动等待）。这是嵌入式排障里非常关键的一个信号：D 状态的进程连 kill -9 都无效，只能修 IO。

3. 内核栈：每个任务 8KB

用户态的栈在进程自己的地址空间里（默认 8MB），内核态的栈是另一块内存，通常 8KB，随 task_struct 一起分配。

// 内核代码运行在这个 8KB 栈上
// 所以：
//   - 不能放大数组（第 17 课讲过）
//   - 递归深度极其有限
//   - 中断上下文用同一个栈（或独立 IRQ 栈）

// 查当前任务的内核栈使用：
cat /proc//stack        # 内核栈回溯
# 编译时开启 CONFIG_DEBUG_STACK_USAGE 可在 panic 时打印余量

4. TGID 与 PID：线程组的两个视角

创建线程（clone 时带 CLONE_THREAD）后：

  • 每个线程有自己的 PID（内核调度单位）。
  • 它们共享同一个 TGID（即「进程 ID」，用户看到的那个）。
  • getpid() 返回 TGID，gettid() 返回自己的 PID。
ls /proc//task/          # 列出该进程的所有线程
cat /proc//status | grep -E "Pid|Tgid|Threads"
ps -eLf                       # 显示线程
top -H                        # 按线程显示

这条知识在调试死锁时很有用：你看到的「进程卡住」往往是某个线程卡住，而线程才是调度与 CPU 占用的真实单位。

5. 三条常见误解

6. 实验：观察一个任务的内部

# 造一个多线程程序
#include <pthread.h>
void *worker(void *a) { while (1) sleep(1); }
int main(void) {
    pthread_t t[3];
    for (int i = 0; i < 3; i++) pthread_create(&t[i], 0, worker, 0);
    while (1) sleep(1);
}

# 观察
PID=$(pgrep -f a.out | head -1)
cat /proc/$PID/status | grep -E "Pid|Tgid|Threads|VmRSS"
ls /proc/$PID/task/
cat /proc/$PID/task/*/stat | awk '{print $1, $2, $3}'   # pid, comm, state

你会看到 4 个 task（1 主 + 3 线程），同一个 Tgid，各自的 Pid。这就是「Linux 统一任务模型」最直白的证据。

7. 自测与动手

1

Linux 区分进程与线程吗？靠什么区分？

看答案

不区分，都是 task。靠是否共享 mm_struct（与 files 等）来体现「线程」语义。

2

D 状态为什么 kill -9 也杀不掉？

看答案

不可中断睡眠不响应信号，必须等内核里的等待完成（通常是被 IO 卡住）。

3

内核栈多大？为什么不能放大数组？

看答案

通常 8KB，与用户态 8MB 栈完全不同；一个大数组加调用链就会溢出。

4

getpid 与 gettid 返回什么？

看答案

getpid 返回 TGID（进程号），gettid 返回线程自己的 PID。

5

为什么说「线程共享内存」不是约定而是事实？

看答案

它们共用同一个 mm_struct，同一张页表，访问的就是同一块物理内存——硬件层面没有隔离。

  1. 跑多线程程序，观察 /proc/pid/task/ 下的目录数量。
  2. 看 status 里的 Threads 与 Tgid。
  3. 制造一个 D 状态（如读一个卡住的设备），确认 kill -9 无效。
  4. 读一份 task_struct 的源码片段，标出 mm、files、stack 三个字段。
