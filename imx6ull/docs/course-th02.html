卷 04·操作系统·第 09 篇

进程、线程与调度（详解）

「进程」是操作系统里最容易被说滥的概念。这一章把它落到结构体和寄存器上：一个进程由哪几块内存组成、fork 到底复制了什么、切换时哪 12 个寄存器必须搬走、调度器凭什么算「谁该跑」。

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 进程在内核里长什么样；② fork 为什么「瞬间」完成，写时才拷贝；③ 上下文切换具体保存了哪些寄存器；④ CFS 的 vruntime 到底怎么算，nice 值如何变成 CPU 份额；⑤ 实时任务为什么会被普通任务「卡住」。

读完你应该能回答

  • 一个进程的地址空间里，至少有几样东西是「独占」的？
  • fork 之后父子进程的页表项是什么权限？谁把它改回来的？
  • ARM 上下文切换保存 r4–r11 而不保存 r0–r3，为什么合理？
  • 两个任务 nice 0 和 nice 5，CPU 时间大约按什么比例分？
  • 僵尸进程占的是什么资源，为什么不能自动回收？

1. 进程在内核里就是一个结构体

CPU 视角（配合 T18 读） 本章说「切换就是保存 12 个值」，那 12 个值在硬件上就是几条 stmia/ldmia。 想看清每条指令的位段、流水线与寄存器实际变化，跳 T18 · CPU 是怎么执行一行代码的 第 10 节（一次线程切换，CPU 动了哪些寄存器）。

内核用 struct task_struct（在 include/linux/sched.h）描述一个进程。这个结构体有几百个字段，但对理解原理真正关键的是下面这十几个：

字段存什么缺了它会怎样
state运行 / 可中断睡眠 / 不可中断睡眠 / 停止 / 僵尸调度器不知道该不该叫醒它
stack内核栈指针（ARM 上通常 8KB，2 个页）无法保存陷入内核时的现场
mm指向 mm_struct：页表、VMA 链表、代码/数据/堆/栈区间没有独立地址空间，就和线程没区别了
active_mm当前实际在用的地址空间（内核线程借用上一个进程的）内核线程切换时会丢掉页表基址
pid / tgid线程 id / 线程组 id（用户看到的「进程号」其实是 tgid）无法区分「进程」和「进程里的线程」
parent / children父子关系链表无法回收僵尸、无法做进程组信号
files打开文件表（fd → file 结构）fd 无法跨 fork 继承
fs当前工作目录、根目录相对路径无法解析
signal / sighand待处理信号、信号处理函数表信号机制失效
creduid/gid/能力集（权限的真正依据）无法判断能不能打开某个设备
threadcpu_context：切换时要保存的寄存器快照无法恢复执行
prio / se动态优先级、调度实体（含 vruntime）调度器找不到排序依据
一句话总结进程的构成 一个内核栈 + 一份 task_struct + 一张页表（mm）+ 一张文件表和信号表。「线程」和「进程」的区别只在于：哪些东西是共享的。

2. 进程和线程：差别就在 clone 的几个标志位

Linux 内核里没有独立的「线程」概念，只有任务（task）。所谓线程，是共享了地址空间和若干资源的任务。这个「共享哪些」由 clone() 的标志位精确控制：

标志共享的东西不共享时
CLONE_VM同一张页表、同一份地址空间各自独立地址空间（进程）
CLONE_FILES同一张 fd 表（一个线程关 fd，别的线程也看不到）fd 表各自复制一份
CLONE_FS共享当前目录 / 根目录各进程可 chdir 到不同地方
CLONE_SIGHAND共享信号处理函数表各进程可注册不同处理函数
CLONE_THREAD放进同一个线程组，共享 tgidpid == tgid，独立的「进程」
/* pthread_create 在内核看来就是这一串 flag */ clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS | CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID, ...)

由此能推出一串实用结论：线程崩溃会拖死整个进程（因为共享地址空间，一个线程写坏堆，别的线程也用同一份堆）；线程间切换比进程间便宜（不用换页表、不用刷 TLB）；一个线程调 exit() 会让所有线程退出（因为它杀的是线程组），必须用 pthread_exit()。

3. fork 到底复制了什么

教科书说「fork 复制父进程的地址空间」，这句话在实现上其实不成立。真实的 fork 分两步：

  1. 复制结构，不复制内容：新 task_struct、新内核栈、新 mm_struct、新页表（页表本身的页要复制），但页表里指向的物理页一页都不复制。
  2. 把所有可写页表项改成只读，并打上「写时复制（COW）」标记，父子双方共享同一批物理页。

然后等着「谁写谁分配」：任一进程写某个页时，MMU 发现该页只读 → 触发 Abort（缺页）→ 内核缺页处理发现是 COW 页 → 分配一个新物理页、把原内容拷进去、把当前进程的页表项改回可写并指向新页。

算一笔：fork 一个 100MB 的进程，真正花了多少内存带宽？
若真复制数据：100MB 内存拷贝 → 约 100MB 的读 + 100MB 的写
实际 fork 只复制页表：100MB ÷ 4KB = 25600 个页表项
每个 PTE 4 字节 → 约 100KB 的页表数据要写
比率：100MB vs 100KB ≈ 1000 倍
结论：fork 便宜不是因为「聪明」，是因为它把成本推迟到真正写的时候

这解释了两个经典现象：① fork 之后父子进程各自改自己的变量，互不影响（因为已经分了页）；② 一个进程 fork 后只读不写，实际内存占用几乎不增加（ps 里的 RSS 会因共享页而偏低，这是正常的）。

把 fork 拆开看，copy_process() 的主要步骤是：dup_task_struct（复制结构体和栈）→ 检查资源限制 → sched_fork（设置调度参数）→ copy_mm（复制页表或共享）→ copy_files / copy_fs / copy_sighand → 分配 pid → wake_up_new_task。任何一步失败都要原路回滚，这是个很长的错误处理链，也是 fork 相关 bug 的高发区。

4. 五个状态：进程到底「在干什么」

内核里进程只有五种基本状态，每个状态对应「它现在能不能被选中运行」这一个问题：

状态含义怎么进怎么出
TASK_RUNNING可运行（在跑或在就绪队列里等）被创建、被唤醒、时间片用完仍可运行被抢占 / 主动睡眠
TASK_INTERRUPTIBLE可中断睡眠：等事件，能被信号打断wait_event_interruptible 之类事件到达 / 收到信号
TASK_UNINTERRUPTIBLE不可中断睡眠：等硬件，连 kill 都不理等 IO 完成、等锁只有事件到达
TASK_STOPPED被暂停（收到 SIGSTOP）SIGSTOP / 调试器 attachSIGCONT
TASK_ZOMBIE已退出，等父进程收尸进程调用 exit父进程 wait 回收

两个最常被问的点：

为什么有「不可中断睡眠」这种杀人都不管的状态？ 因为它等的东西不能半途而废。典型例子是等磁盘 IO 或等某个硬件寄存器就绪——如果这时响应信号强行退出，可能留下半个写坏的文件或半个配置好的外设。代价是你偶尔会看到进程卡在 D 状态、kill -9 无效，此时只能等硬件返回或重启。

僵尸进程占什么？为什么不能自动回收？ 它已经释放了地址空间、文件表、大部分内存，只剩两样：task_struct（含退出码、资源统计）和一个 pid。之所以内核不敢自动删，是因为父进程有权知道子进程是怎么死的（退出码、被哪个信号杀死、用了多少 CPU）。这些信息只能存在 task_struct 里等父进程来取。父进程一旦 wait()，内核就把这块内存释放。父进程先死了怎么办？子进程会被 init（或 systemd）收养，由它负责收尸——这就是为什么孤儿进程不会变成永久僵尸。

5. 上下文切换：凭什么只保存 12 个寄存器

「上下文」就是「CPU 此刻的全部可见状态」：通用寄存器、程序计数器、栈指针、状态寄存器。切换的本质是把这一整套存进旧任务的存储区，再从新任务的存储区装回来。

ARM 上的切换核心是这么一段（arch/arm/kernel/entry-armv.S 的 __switch_to）：

/* 简化示意 */ stmia prev_thread, {r4-r11, sp, lr} /* 存 10 个值到 prev->thread.cpu_context */ ldmia next_thread, {r4-r11, sp, lr} /* 从 next 的同一位置装回来 */ /* 再写 CP15 c2（TTBR0）换成 next 的页表，DSB + ISB 保证生效 */

问题来了：为什么不保存 r0–r3 和 CPSR？ 两个理由：

  • r0–r3 是「调用者保存」寄存器。ARM 的调用约定规定：函数调用后 r0–r3 可以被随意改。而切换一定发生在一次函数调用内部，所以被切走的那一刻，编译器早就认为 r0–r3 是「已经不需要了」的。切回来接着执行，它也不会去读 r0–r3 的旧值。
  • CPSR 在切换时本来就是内核态。被切走的任务是在内核里（可能刚处理完中断或刚进系统调用）被切走的，CPSR 待会儿恢复时还是内核态；用户态的 CPSR 早就存在 pt_regs 的 SPSR 槽里了。
要保存的 12 个值分别是：r4–r11（被调用者保存，8 个）+ sp + lr。 这 12 个值全放在 task_struct.thread.cpu_context 里。所以「上下文切换」在内核里就是十几次内存访问，这也是它能做到微秒级的原因。

还有两个必须提的细节：

① 页表切换的时机。 换 TTBR0 之后必须执行 DSB（等前面的写完成）+ ISB（清流水线），否则 CPU 可能还在用旧页表取指。这类「屏障指令」在驱动里也常出现，原因相同：CPU 和内存不是同步的。

② 内核线程的页表问题。 内核线程没有自己的 mm，它借用上一个用户进程的 active_mm。如果这时不做特殊处理，内核线程一跑就可能把某个进程的页表当成自己的用；更糟的是如果那个进程刚好退出，页表就没了。所以内核用 active_mm 的引用计数来兜住这个生命周期。

6. CFS：用「虚拟运行时间」排队

普通进程（SCHED_NORMAL）由 CFS（完全公平调度器）管。它的核心不是「时间片」，而是一个虚拟时钟：

vruntime += 本次实际运行时间 × (NICE_0_WEIGHT / 该任务的权重) 其中 NICE_0_WEIGHT = 1024，权重 = 1024 / 1.25^nice

直觉解释：vruntime 跑得越快，说明这个任务「占便宜」越多，应该少给它机会。 调度器永远挑 vruntime 最小的那个跑（用红黑树维护，取最左节点，O(log n)）。

nice 值就是权重档位。几个关键值：

nice权重相对 nice 0 的 CPU 份额
-53121约 3.05 倍
010241 倍（基准）
5335约 0.327 倍
10110约 0.107 倍
1915约 0.015 倍
算一遍：nice 0 与 nice 5 两个任务抢一个核
权重：1024 与 335，总权重 = 1359
CPU 份额：1024/1359 = 75.3%；335/1359 = 24.7%
调度周期 sched_latency 默认 6ms → 分别得 4.52ms 和 1.48ms
反推 vruntime：nice 5 每真跑 1ms，账面扣 1024/335 ≈ 3.06ms
所以它「账面跑得快」，很快变成最左节点被切走——公平由此实现

还有三个机制要知道，否则你会对观测结果困惑：

  • min_vruntime 单调递增：所有新任务的 vruntime 起点被抬到不低于它，防止「睡很久的老任务」回来时账面太低、一把抢走 CPU 很久。
  • 最小粒度：即使份额算出来只有 0.2ms，也不能真给这么短（切换开销会吃掉收益），所以有 sched_min_granularity（默认 0.75ms）兜底。
  • 6.6 起换成 EEVDF：把「虚拟时间」换成「lag（应得与已得的差）」模型，允许任务申请指定时间片（sched_setattr），并显式处理延迟敏感任务。原理相通，细节不同——你只要记住「按应得份额排队」这个不变的内核。

7. 实时调度与优先级反转

实时任务（SCHED_FIFO / SCHED_RR）的优先级是 1–99，普通任务是 0。规则残酷而简单：只要有任何一个实时任务处于可运行状态，普通任务就永远拿不到 CPU。

  • SCHED_FIFO：同优先级先进先出，除非它自己阻塞、退出或被更高优先级抢占，否则一直跑。写错就是「一个死循环卡死整机」。
  • SCHED_RR：同优先级按时间片轮转，时间片用完排到队尾。

这解释了嵌入式里最常见的故障现象：系统看起来「卡死了」，但串口还能响应中断。因为中断照常进（硬件中断优先级高于任何任务），而所有普通进程（包括 shell、看门狗喂狗线程）都饿死了。

7.1 优先级反转：一个真实的翻车模型

假设三个任务，优先级 H > M > L，共用一把互斥锁：

L 拿到锁→M 抢占 L（M 优先级更高）→H 就绪，需要这把锁→H 阻塞等 L→M 继续跑，L 拿不到 CPU

结果是：最高优先级的 H 被最低优先级的 L 拖住，而 L 又被中优先级的 M 拖住。 H 的实际等待时间取决于 M 跑多久，跟 H 自己毫无关系。这就是优先级反转。

1997 年火星探路者的重启事故就是它：低优先级的气象任务持有总线锁，被中优先级的通信任务抢占，高优先级的总线管理任务等锁超时，看门狗判定系统失效并重启。

7.2 解法：优先级继承与优先级天花板

优先级继承（PI）：当高优先级任务 H 因等锁被阻塞时，内核临时把持锁任务 L 的优先级提升到 H 的级别。这样 M（中间优先级）就无法抢占 L，L 能尽快跑完临界区放锁，H 立刻得到锁并恢复自己的优先级。

优先级天花板：另一种做法是把锁的优先级一开始就定死为「所有可能用它的任务中最高的那个」，只要拿到锁就升到那个级别。开销更小，但要求你事先知道谁会用这把锁。

Linux 里的使用门槛要注意：

  • 内核的 rt_mutex 默认就带优先级继承，是内核里实时锁的基础。
  • 用户态的 pthread_mutex_t 默认不带 PI，必须创建时指定属性 PTHREAD_PRIO_INHERIT，否则你自己写的实时程序仍然会发生反转。
  • Spinlock 不能睡眠，所以它无法参与 PI，实时场景要用 rt_mutex 替代。
一个常被混淆的点 优先级反转 ≠ 死锁。反转是「临时被拖延」，只要中间任务跑完就会恢复；死锁是「互相等对方放锁」，永远不恢复。两者都会让系统「看起来卡住」，但排查手段完全不同：反转看优先级和持锁时间，死锁看循环等待链。

8. 十个常见误解

误解真相
「fork 会复制父进程全部内存」只复制页表并做 COW 标记，物理页共享，写时才真正复制。
「线程是内核里另一种对象」内核只有 task，线程 = 带 CLONE_VM|CLONE_THREAD 等标志的 task。
「pid 就是进程号」用户看到的「进程号」是 tgid，pid 在主线里是线程号。
「nice 值是绝对优先级」它是权重档位，只影响相对份额；两个任务都 nice 0 就是 50/50，谈不上「优先级」。
「CFS 有时间片」CFS 没有固定时间片，只有「按 vruntime 排队 + 最小粒度兜底」。
「实时任务一定准时」它只保证「优先被调度」，不保证「无延迟」。关中断、关抢占的内核临界区一样会让你晚到。
「kill -9 一定能杀进程」处于不可中断睡眠的进程杀不掉，只能等硬件事件返回。
「僵尸进程占很多内存」只剩 task_struct 和一个 pid，几 KB 量级；但 pid 会被耗尽，这是真危害。
「上下文切换只保存通用寄存器」ARM 上还要换 TTBR0、刷 TLB 相关状态，代价远不止 12 个寄存器。
「多线程一定比多进程快」省的是切换与共享成本，代价是锁竞争与缓存伪共享，未必更快。

9. 自检：能答出来才算懂

1

一个进程最少由哪几块「独占资源」构成？线程共享了其中哪几块？

看答案

独占：内核栈 + task_struct + 地址空间（mm）+ 寄存器上下文。线程共享地址空间、fd 表、当前目录、信号处理表（取决于 clone 标志）；但内核栈和 task_struct 永远是各自独立的，这就是线程也能独立被调度、独立陷入内核的原因。

2

fork 之后，父子进程对同一全局变量的修改为什么互不影响？

看答案

因为写之前两者共享同一物理页；一旦某一方写入，MMU 因该页只读触发缺页，内核为它分配新物理页并复制内容，从此两边指向不同页。所以「互不影响」是 COW 的结果，不是 fork 时就复制了。

3

ARM 上下文切换为什么只保存 r4–r11、sp、lr？r0–r3 去哪了？

看答案

r0–r3 是调用者保存寄存器，切换发生在函数调用内部，编译器已认定它们可被破坏，恢复后也不会读旧值。r4–r11 是被调用者保存寄存器，必须由内核负责保存。CPSR 则因为在切换时本就在内核态，用户态的那份早存在 pt_regs 的 SPSR 里。

4

nice 0 和 nice 5 抢一个核，CPU 大约怎么分？为什么不是 1024:335 以外的比例？

看答案

约 75% 与 25%（1024/1359 与 335/1359）。因为 CFS 按「权重占比」分配时间，权重由 1024/1.25^nice 决定，所以比例是权重的直接比值。

5

进程卡在 D 状态，kill -9 无效，为什么？怎么办？

看答案

因为它处于 TASK_UNINTERRUPTIBLE，内核故意忽略信号，避免在硬件操作中途被打断留下不一致状态。只能等事件返回（IO 完成、驱动超时），或者排查驱动问题、重启。若频繁出现，通常是驱动或存储介质有问题。

6

僵尸进程到底占什么资源？父进程不 wait 会怎样？

看答案

占一个 task_struct 和一个 pid。父进程不 wait，它就一直挂着；数量多了会耗尽 pid（默认几万到几十万），新进程无法创建。父进程先退出的话，子进程被 init/systemd 收养并自动收尸。

7

为什么一个死循环的 SCHED_FIFO 任务能让系统「假死」但串口仍有反应？

看答案

实时任务优先级高于所有普通任务，只要它不阻塞就一直占 CPU，普通任务（shell、日志、喂狗线程）全部饿死；但硬件中断仍能进入（中断不受任务调度影响），所以串口这类中断驱动的外设还能响应。

8

用一句话说清优先级反转，再说清它与死锁的区别。

看答案

反转：高优先级任务被低优先级任务持有的锁挡住，而低优先级任务又被中优先级任务抢占，导致高优先级任务的等待时间与它自身无关。死锁：两个以上任务互相等待对方持有的资源，永远不恢复。反转是「拖延但会好」，死锁是「永久卡住」。

9

pthread 互斥锁默认能防优先级反转吗？要怎么改？

看答案

不能。默认属性没有优先级继承，必须用 pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT) 创建带 PI 的互斥锁。内核里的 rt_mutex 则默认支持。

10

EEVDF 相比 CFS，改的到底是什么？

看答案

把「累积虚拟运行时间」换成「lag（应得与已得的差）」作为排序依据，并允许任务显式申请时间片；同时把「延迟敏感」从隐式的唤醒抢占变成显式的资格判断。核心目标没变：按权重公平分配，但延迟控制更可控。

10. 这一章要动手的命令

  1. ps -eo pid,tgid,stat,pri,ni,comm —— 一次看清 pid 与 tgid 的区别（多线程进程里 tgid 相同）。
  2. cat /proc/<pid>/sched —— 直接读该任务的 vruntime、切换次数、在 CPU 上的累计时间。
  3. chrt -f 50 ./busy & 再 top —— 亲眼看到普通进程被饿死、系统「假死」。
  4. taskset -c 0 ./busy —— 把进程钉在 CPU0，观察单核争抢时的份额分配。
  5. nice -n 5 ./busy & 与 nice -n 0 ./busy & 同时跑，配合 top 验证 75:25。
  6. pidstat -w 1 —— 看每秒的上下文切换次数（cswch/s 与 nvcswch/s 的区别值得查清）。
  7. perf sched record -- sleep 5 然后 perf sched latency —— 看真实的调度延迟分布。
