上下文切换

调度器决定「该换 B 了」，但真正执行「换人」的是 switch_to 里那几行汇编：保存 callee-saved、换栈、把返回地址指向 B 上次离开的地方。这一课把它拆开，再算清真实代价——你会发现大头根本不在寄存器保存上。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① switch_to 保存哪些寄存器，为什么只这些？② 为什么它「调用一次、返回两次」？③ 换页表与 TLB 的代价？④ 一次切换多少纳秒？⑤ 线程切换为什么更便宜？

1. 那几行汇编

__switch_to:
    add   r0, r0, #TI_CPU_SAVE
    stmia r0, {r4-r11}        ; 保存 callee-saved 到 prev 的 task_struct
    add   r1, r1, #TI_CPU_SAVE
    ldmia r1, {r4-r11}        ; 从 next 恢复
    mov   sp, r1              ; 换栈指针（关键一步）
    mov   pc, lr              ; 返回

只有四类动作：存、取、换 sp、跳。没有「保存 16 个寄存器」的豪举——其余寄存器已由上层 C 代码放在 A 的栈上了。

2. 「调用一次，返回两次」

A 执行 bl __switch_to 时，lr 指向 A 的返回点。这个 lr 被存进 A 的栈上（C 代码 push 过的），而 switch_to 里换 sp 之后，mov pc, lr 用的是 B 栈上对应的那个返回地址——于是「返回」进了 B 的世界。

所以同一个函数调用，在 A 的视角是「我切出去，稍后回来」；在 B 的视角是「我上次切出去，现在回来了」。这就是「一次调用两次返回」的真实含义。它不是魔法，只是栈换了。

3. 真正的开销在哪

实测数字（Ubuntu 上）：一次进程切换约 2~5 微秒，线程切换约 1~2 微秒。换算成 528MHz 的周期数，大约是 1000~2600 拍。

# 自己测：两个进程通过管道互相 ping-pong，测往返时间
# 或用 perf
perf stat -e context-switches,cpu-migrations ./prog

# 内核工具
perf sched record ./prog
perf sched latency          # 每个任务的调度延迟分布

4. 线程切换为什么更便宜

线程共享同一个 mm_struct，所以切换时：

  • 不用换页表（同一个页表寄存器值）。
  • 不用刷 TLB（地址空间没变，翻译仍然有效）。
  • Cache 的工作集可能仍然有效（同一份数据）。

这就是「线程轻」的真正含义：不是创建快，而是切换后不需要重建内存上下文。这也是为什么用线程池做高并发比 fork 每请求一个进程划算得多。

5. 实验：把切换量出来

// 两个线程 ping-pong（用两个原子变量 + 自旋）
// 循环 100 万次，测总时间 → 除以次数得到切换延迟
// 若线程绑到同一个核，测的是「纯切换」；
// 若绑到不同核，测的是「跨核通信延迟」

#include <pthread.h>
volatile int turn = 0;
void *a(void *x) { for (int i=0;i<1000000;i++){ while(turn!=0); turn=1; } return 0; }
void *b(void *x) { for (int i=0;i<1000000;i++){ while(turn!=1); turn=0; } return 0; }

注意：纯自旋不切线程，测不到切换。要真测切换，得用 sched_yield() 或 futex 唤醒。这个实验的意义在于让你体会「切换 vs 自旋」的取舍——短临界区自旋，长等待睡眠。

6. 三条常见误解

7. 自测与动手

1

switch_to 为什么不保存 r0-r3？

看答案

它们是 caller-saved，调用者若需要早已自己存到栈上；ABI 允许被调用者随意破坏。

2

「换 sp」为什么是切换的核心动作？

看答案

每个任务的现场都存在自己栈上；把 sp 指过去，就等于「接上了」那个任务的全部上下文。

3

一次进程切换的真实大头是什么？

看答案

切换后的 TLB 与 Cache 冷启动（新任务的工作集不在缓存里），可达几百拍以上。

4

线程切换省了哪几步？

看答案

不换页表、不刷 TLB、地址空间不变，缓存可能仍有效。

5

短临界区该自旋还是睡眠？

看答案

短（几微秒内）自旋；长等待睡眠。自旋浪费 CPU，睡眠付出切换开销。

  1. 用 perf 测一个多线程程序的 context-switches 数。
  2. 把线程数从 2 加到 32，观察切换次数与总耗时的关系。
  3. 读一段 switch_to 的真实源码，找出那五行。
  4. 用 cyclictest 观察高负载下的调度延迟。
