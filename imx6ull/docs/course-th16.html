BSP 与设备树原理

这一章讲「Linux 怎么知道你这块板子上焊了什么」。答案是设备树——一份用文本写成、编译成二进制的硬件描述。学会它，你就能在不改内核一行代码的前提下支持一块新板子。这是嵌入式 Linux 与单片机开发最大的分水岭。

★ 一读 纯读约 6 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① BSP 到底是哪几样东西；② 为什么内核不再用 board 文件写死硬件；③ dts、dtsi、dtb 三者怎么转换；④ 设备树里的节点凭什么能匹配到某个驱动；⑤ 自己画一块 i.MX6ULL 板，要改哪些地方。

读完你应该能回答

  • 同一份内核镜像怎么支持两种不同外设配置的板子？
  • compatible = "fsl,mx6ull-evk" 这个字符串在哪一侧被比较？
  • pinctrl 的 &iomuxc 引用在编译后变成了什么？
  • reg = <0x02190000 0x4000> 这两个数字分别是什么？
  • 改完 dts 要重新编译哪个文件、放在哪、谁去读它？

1. BSP 是什么：一整套「让板子能跑」的东西

BSP（Board Support Package）不是单个文件，而是五件套。缺任何一件，板子都跑不起来：

组成内容典型来源
BootloaderU-Boot（含 SPL）与该板的配置U-Boot 主线 + 厂商补丁
内核zImage + 该板的设备树 dtb厂商 BSP 内核分支
设备树imx6ull-xxx.dts 与其引用的 dtsi从 EVK 的 dts 改出来
根文件系统busybox / buildroot / Yocto 产物自建或用厂商镜像
工具链交叉编译器、sysroot、调试工具Linaro / 厂商提供
BSP 与「驱动」不是一回事 驱动是内核里通用的代码（如 drivers/mmc/host/sdhci-esdhc-imx.c 这种），BSP 是针对某块板的配置集合。同一份驱动代码，配不同的设备树，就服务不同的板子。

2. 设备树的由来：从「代码里写死」到「数据描述」

2011 年之前，ARM Linux 的做法是给每块板子写一个 board-xxx.c，里面用 C 代码写死「我的串口在哪个地址、我的 I2C 上挂了什么芯片」。结果是 arch/arm/mach-* 目录塞满上千个板级文件，内核越来越大，Linus 在邮件列表上公开发火。

设备树的思路正好相反：硬件信息从代码里剥离，变成一份数据。内核只保留「怎么驱动这类设备」的知识，具体地址、引脚、中断号全部来自设备树。

board 文件时代设备树时代
硬件信息位置C 代码里独立的 dts 文本
换一块板重新编译内核只换 dtb 文件
一份内核只能对应一种配置可配多个 dtb，启动时选一个
维护成本板级代码爆炸新增板只加 dts

这就是为什么现在的嵌入式内核「一个 zImage + 十几个 dtb」就能覆盖一整条产品线——dtb 是运行时选择的，不是编译期决定的。

3. dts / dtsi / dtb 的关系

soc.dtsi（芯片级）→board.dts（板级）→dtc 编译→board.dtb→U-Boot 加载并传给内核→内核展开成 device_node 树
文件内容谁维护
.dtsi芯片级公共描述（CPU、中断控制器、各外设寄存器基址）SoC 厂商，如 imx6ull.dtsi
.dts板级差异（内存大小、外设使能、引脚、挂载的芯片）板厂或你自己
.dtb编译后的二进制（FDT 格式）由 dtc 生成

编译命令就一条：

dtc -I dts -O dtb -o board.dtb board.dts # 内核构建系统里更常用： make ARCH=arm imx6ull_xxx.dtb

U-Boot 通过 bootz zImage - dtb 的第三个参数把 dtb 地址传给内核，内核启动时把它展开成 device_node 与 property 组成的内存树。

4. 语法要点：节点与属性

设备树的语法只有三层：节点（用花括号包住的一块）、属性（键值对）、cell（属性值里的 32 位数字）。

/ { // 根节点 model = "My i.MX6ULL Board"; // 字符串属性 compatible = "fsl,imx6ull", "fsl,imx6ull-evk"; // 字符串列表，按优先级 memory@80000000 { // 节点名@地址 device_type = "memory"; reg = <0x80000000 0x20000000>; // 起始地址 大小（两个 cell） }; leds { compatible = "gpio-leds"; led0: led { // label:led0 便于被引用 gpios = <&gpio1 3 GPIO_ACTIVE_LOW>; // phandle 引用 + 引脚号 + 极性 linux,default-trigger = "heartbeat"; }; }; };

几个必须掌握的语法点：

  • label 与 phandle：led0: 是标签，编译后变成唯一的 32 位 phandle 数字，&led0 就是引用它。
  • &node 追加：在 dts 里写 &uart1 { status = "okay"; }; 表示「往 dtsi 里已有的 uart1 节点里补属性」。
  • status："okay" 启用、"disabled" 不启用。这是板级文件里出现频率最高的属性。
  • #address-cells / #size-cells：决定子节点 reg 里地址与长度各占几个 cell。
  • ranges：把子总线的地址映射到父总线地址空间。
算一笔：reg = <0x02190000 0x4000> 是什么
第一个 cell 0x02190000 是起始物理地址（uSDHC1 控制器基址）
第二个 cell 0x4000 是长度（16KB 寄存器空间）
驱动 probe 时 platform_get_resource 拿到的就是这对值，再 ioremap 成虚拟地址
若 #address-cells = <2>，则地址要用两个 cell 拼成 64 位，写成一个 32 位数就是错的

5. compatible 如何把节点和驱动配上

这是设备树最核心的机制。一句话：内核遍历所有已注册驱动的 match 表，逐个和节点里的 compatible 字符串比较，第一个匹配上的驱动去 probe 这个节点。

// 设备树一侧 uart1: serial@021a0000 { compatible = "fsl,imx6ull-uart", "fsl,imx21-uart"; reg = <0x021a0000 0x4000>; interrupts = <GIC_SPI 26 IRQ_TYPE_LEVEL_HIGH>; status = "okay"; }; // 驱动一侧 static const struct of_device_id imx_uart_dt_ids[] = { { .compatible = "fsl,imx6ull-uart" }, { .compatible = "fsl,imx21-uart" }, { /* sentinel */ } }; static struct platform_driver imx_uart_driver = { .probe = imx_uart_probe, .driver = { .name = "imx-uart", .of_match_table = imx_uart_dt_ids }, };

匹配规则里有三个细节，容易踩：

  1. 字符串必须完全一致，包括逗号、大小写。"fsl,imx6ull-uart" 与 "fsl,IMX6ULL-uart" 不匹配。
  2. 按顺序匹配：节点里写了两个 compatible，驱动表里只要命中任意一个即可，但节点第一个通常是最具体的型号。
  3. 匹配不到不会报错：节点就静静躺在那里，没有驱动绑定。查 /sys/firmware/devicetree/base/ 能看到它存在，但设备不会工作。
「设备树写了但设备不工作」的标准排查三步 ① ls /sys/firmware/devicetree/base/ 确认节点在不在；② 看 status 是不是 "okay"；③ dmesg | grep -i <驱动名> 看有没有 probe 记录。三步下来基本能定位到「没写 / 没启用 / 没匹配」。

6. 从设备树到硬件：一条完整链路

以「设备树里挂了一个 I2C 上的 RTC 芯片」为例，走完全程：

dts 写节点→dtc 编译成 dtb→U-Boot 传给内核→内核建 device_node→I2C 子系统扫子节点→compatible 匹配驱动→probe 执行→i2c_transfer 读芯片→注册 rtc_device→/dev/rtc0 出现
// 设备树片段 &i2c1 { status = "okay"; clock-frequency = <100000>; rtc@68 { compatible = "nxp,pcf8563"; reg = <0x68>; // I2C 从机地址（7 位） }; }; // 驱动 probe 里做三件事 1. 用 reg 里的地址作为 i2c_client 的 addr 2. 申请中断（如果有 interrupts 属性） 3. 向 RTC 子系统注册 rtc_device，暴露 /dev/rtc0
算一笔：I2C 地址为什么是 0x68 而不是 0xD0
7 位地址 0x68 = 二进制 1101000
总线上实际先发 8 位：(0x68 << 1) | R/W，写 = 0xD0，读 = 0xD1
设备树里写的是 7 位地址，驱动里也按 7 位存
把 0xD0 写进设备树 → 内核会再左移一位变成 0x1A0，溢出 8 位 → 通信彻底失败

7. 自己画一块板：BSP 要改哪几处

从 EVK 的 dts 复制一份改名，是最省力的起点。然后逐项核对下面这张清单——漏一项，板子就在某个阶段停住：

要改的地方具体内容漏了会怎样
model / compatible（根节点）改成你板子的名字只是标识不对，不影响启动，但会影响某些匹配逻辑
memory 节点reg 的地址与大小要跟你实际 DDR 容量一致内存被少报或越界，内核可能启动到一半崩
启动介质uSDHC 或 NAND 的 status 与总线宽度找不到根文件系统，卡在 VFS: Unable to mount root
串口调试串口的 status 与 pinctrl没有任何输出，等于黑屏调试
pinctrl每个外设引脚的 mux 与电气属性引脚功能不对，设备注册成功但收发全错
I2C / SPI 子节点挂载的芯片型号与地址对应设备不存在，相关功能全废
GPIO（LED、按键）gpios 属性与极性灯不亮、按键没反应
网卡 PHYPHY 地址、复位 GPIO、RMII 时钟Link 不通
regulator（电源）各路的 GPIO 使能脚与电压外设不上电，表现为「驱动 probe 失败」
bootargsconsole、root=、rootwait 等启动参数错，找不到根文件系统或没有控制台
pinctrl 是新手最容易漏的一项 dtsi 里通常只定义了外设节点，引脚复用写在板级 dts 的 iomuxc 子节点里。只开 status = "okay" 不配 pinctrl，驱动会 probe 成功但引脚还是默认功能。

8. 常见误解

误解真相
「设备树是驱动」设备树只是数据描述，驱动仍是 C 代码；两者靠 compatible 结合。
「改 dts 要重新编译内核」只需重新编译 dtb，内核不用动（除非驱动也改了）。
「status = okay 就一定能工作」还要 pinctrl、时钟、regulator、中断都对，缺一项就不工作。
「compatible 随便写都行」必须与驱动 of_match_table 完全一致，否则永不匹配。
「reg 里两个数一个是地址一个是中断号」是「起始地址 + 长度」，中断在 interrupts 属性里。
「I2C 地址按 8 位写更直观」设备树与驱动统一用 7 位，写 8 位会溢出。
「一份 dtb 能适配所有板子」dtb 是板级描述，一块板一个；一份内核可以配多个 dtb。
「设备树写在 dtsi 里更省事」dtsi 是芯片级公共描述，板级差异必须写在 dts，否则会污染所有板。

9. 自检：能答出来才算懂

1

BSP 五件套是哪五样？

看答案

Bootloader、内核、设备树、根文件系统、工具链。

2

设备树解决了 board 文件时代的什么问题？

看答案

硬件信息写死在 C 代码导致板级文件爆炸、一份内核只能配一种板。设备树把硬件变成数据，换板只换 dtb。

3

dts、dtsi、dtb 分别是什么，谁生成谁？

看答案

dtsi 是芯片级公共描述，dts 是板级描述（include dtsi），dtc 把 dts 编译成 dtb。

4

&uart1 { status = "okay"; }; 这一句做了什么？

看答案

往 dtsi 里已定义的 uart1 节点追加属性，把它启用。这叫「引用并追加」，不是新建节点。

5

compatible 匹配发生在内核的哪一侧，匹配不到会报错吗？

看答案

在内核侧，遍历驱动的 of_match_table 与节点 compatible 比较。匹配不到不报错，节点保持未绑定状态。

6

reg = <0x02190000 0x4000> 两个数分别是什么？

看答案

起始物理地址与长度（16KB 寄存器空间）。中断号在 interrupts 里，不是这里。

7

设备树里 I2C 从机地址该写 0x68 还是 0xD0，为什么？

看答案

写 7 位的 0x68。驱动会左移一位加读写位，写 0xD0 会溢出成错误地址。

8

只写 status = "okay" 不配 pinctrl，会发生什么？

看答案

驱动 probe 成功、设备注册成功，但引脚仍是默认功能，实际收发全错或无输出。

10. 这一章要动手的命令

  1. ls /sys/firmware/devicetree/base/ —— 看内核实际拿到的设备树节点树。
  2. cat /sys/firmware/devicetree/base/model —— 读当前板子的 model。
  3. ls /sys/bus/platform/drivers/ —— 看哪些平台驱动已注册。
  4. ls /sys/bus/platform/devices/ —— 看哪些设备已被识别。
  5. dmesg | grep -i "of_" 或 grep -i deferred /sys/kernel/debug/devices_deferred —— 查未匹配/延迟 probe 的设备。
  6. dtc -I dtb -O dts /boot/xxx.dtb | head -60 —— 把 dtb 反编译回文本，验证是否是你写的那份。
  7. U-Boot 里 fdt addr $fdt_addr_r; fdt print / —— 看 bootloader 传给内核的树。
