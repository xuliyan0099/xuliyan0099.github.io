交叉编译与工具链原理

你在 x86 电脑上敲 gcc hello.c，出来的是 x86 程序，拷到 i.MX6ULL 上根本跑不起来。交叉编译就是「在 A 机器上生成 B 机器的代码」。这一章把工具链拆到底：名字里每段是什么意思、四步编译各产出什么、链接为什么最容易出错。

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 为什么不能在板子上直接编译；② arm-linux-gnueabihf-gcc 这串名字怎么读；③ .c 到可执行文件经历了哪四步，每步产生什么文件；④ 静态库与动态库该选哪个；⑤ 「GLIBC_2.29 not found」这类错误到底什么原因。

读完你应该能回答

  • 编译、汇编、链接各自由哪个工具完成，产物后缀是什么？
  • gnueabi 与 gnueabihf 差一个字母，差的是什么？
  • 为什么交叉编译时绝对不能把 /usr/include 加进搜索路径？
  • .a 与 .so 的本质区别，GOT/PLT 是干什么的？
  • ELF 里 .text、.data、.bss 分别放什么？

1. 为什么必须交叉编译

程序是「机器指令序列」，指令集不同就不能互相执行。x86 的机器码在 ARM 核上是一条条非法指令；ARM 的机器码在 x86 上也一样。所以有两种做法：

方式做法问题
本地编译（native）在目标板上跑 gcc，直接生成 ARM 码板子 CPU 弱、内存小，编译一个内核要几小时甚至几天；工具链本身也占几十 MB
交叉编译（cross）在 PC 上跑「能生成 ARM 码的 gcc」需要一套专门的工具链，且要小心别把主机的东西混进来

嵌入式 99% 用交叉编译。工具链本身也是一个「程序」，它跑在 x86 上，但它的输出是 ARM 代码——这个「跑在 A、产出 B」的特性，是靠 gcc 内部的 target 描述（指令模板、寄存器约束、ABI 规则）实现的。

工具链从哪来 三条路：① 直接下载 Linaro / ARM 官方预编译包；② 用 Buildroot / Yocto 自己构建（可定制 libc、可复现）；③ 用 crosstool-NG 从源码构建。厂商 BSP 一般会提供一份，优先用厂商那份，因为内核与驱动是按它验证的。

2. 工具链的组成

「工具链」不是单个 gcc，而是一整套协作的程序：

组件作用典型命令
binutils汇编器、链接器、目标文件工具as、ld、objcopy、objdump、readelf、nm、strip
gcc编译器驱动：调度预处理、编译、汇编、链接arm-linux-gnueabihf-gcc
C 库提供 printf、malloc 等运行时glibc / musl / uClibc
sysroot目标机的头文件与库的「影子根目录」--sysroot=/opt/arm-sysroot
调试器源码级调试（配合 gdbserver）arm-linux-gnueabihf-gdb
内核头文件编译驱动/内核模块时需要来自内核源码的 include/
sysroot 是交叉编译的核心概念 它是一份「按目标机目录结构摆放」的头文件与库集合（如 sysroot/usr/include、sysroot/usr/lib）。编译器默认只在这个影子根里找，这样就不会误用主机的 x86 头文件。

3. 名字里的三个约定

arm-linux-gnueabihf-gcc 可以拆成四段（常被说成「三元组」，实际多为四段）：

段值含义
archarm目标指令集：32 位 ARM
vendor / oslinux目标操作系统：Linux（要有系统调用、ELF 格式）
abignueabihfGNU EABI + hard float：浮点参数通过 VFP 寄存器传递

同族名字的对比，能看清每个字母的作用：

名字目标区别
arm-none-eabi-gcc裸机（无 OS）没有 Linux 系统调用，生成的是裸 ELF/HEX，常用于 STM32
arm-linux-gnueabi-gccARM Linux 软浮点浮点参数用整数寄存器传，靠软件模拟浮点运算
arm-linux-gnueabihf-gccARM Linux 硬浮点浮点参数用 VFP 寄存器传，i.MX6ULL（有 VFP）用这个
aarch64-linux-gnu-gccARM6464 位指令集，与 arm 完全不兼容
软硬浮点混用是隐形炸弹 gnueabi 编译的库 + gnueabihf 编译的程序链接在一起，编译期可能不报错，运行时浮点参数全乱。整个项目（含第三方库）必须统一 ABI。

4. 从 .c 到可执行文件：四步

很多人以为「编译」是一个动作，其实是四步，每步都可以单独执行、单独观察产物：

步骤做什么命令产物
预处理展开 #include、宏、条件编译，删注释gcc -E hello.c -o hello.i纯展开后的 C 文本
编译把 C 翻译成汇编gcc -S hello.i -o hello.s汇编文本（人类可读）
汇编把汇编翻成机器码，生成目标文件gcc -c hello.s -o hello.o.o（ELF 可重定位文件）
链接合并多个 .o、解析符号、接上库gcc hello.o -o hello可执行 ELF
算一笔：一次「看不见的」编译链
arm-linux-gnueabihf-gcc hello.c -o hello 这一条命令内部依次调用
cpp（预处理）→ cc1（编译成汇编）→ as（汇编成 .o）→ collect2/ld（链接 libc 与启动代码）
加上 -v 就能看到它实际调用的每个子程序与完整命令行
调试「头文件找不到」「链接找不到库」时，第一步永远是加 -v

链接阶段是所有交叉编译问题的集中地，因为要同时解决三件事：

  1. 符号解析：printf 在哪个文件里？找不到就报 undefined reference。
  2. 地址重定位：各段最终放在哪个虚拟地址，跳转指令要按最终地址改写。
  3. 指定入口与解释器：可执行文件要告诉内核「从哪开始执行」，动态链接还要指定 ld-linux 路径。

4.1 ELF 文件里有什么

段内容是否占文件空间
.text机器指令是
.rodata只读数据（字符串常量、const 表）是
.data已初始化的全局/静态变量是
.bss未初始化或初始为 0 的全局/静态变量否，只记大小，运行时清零
.symtab符号表（调试与链接用）是，可被 strip 删掉
.dynamic动态链接信息（依赖库、GOT/PLT 位置）是
.bss 不占文件空间的原因 一个 10MB 的全局数组如果初始化为 0，ELF 里只记录「需要 10MB 的零」，不真的存 10MB 个 0。加载时内核给一块清零的匿名页即可。这就是为什么 int buf[1000000]; 不会让程序体积变大。

5. 静态库与动态库

静态库 .a动态库 .so
本质多个 .o 打包（ar 归档）独立的 ELF，运行时被加载
链接时机编译期，代码直接复制进可执行文件运行时，由动态链接器装载
体积每个程序都带一份多个程序共享一份
升级库必须重新编译程序换 .so 即可
启动速度快（无装载与符号解析开销）慢一点
嵌入式适用推荐（依赖少、可控）系统里多程序共用时才划算

动态库为了「代码段共享、数据段独立」，需要两个表：

  • GOT（全局偏移表）：存外部符号的地址，代码通过它间接访问，这样代码段本身不用改。
  • PLT（过程链接表）：函数调用的跳板，第一次调用时解析真实地址（懒绑定），之后直接跳。
算一笔：strip 能省多少
未 strip 的可执行文件含 .symtab 与调试信息，常见可占总体积的 30%–70%
假设程序 2.0MB，strip 后 700KB，省下 65%
代价：gdb 失去符号与行号，只能看地址
正确做法：保留未 strip 的版本用于调试，strip 版本用于出厂

6. 常见坑与判断方法

现象真正原因怎么确认
undefined reference to 'xxx'链接时缺少对应的 .o 或库按顺序检查 -l 与 -L；库之间有依赖时顺序很关键
xxx.h: No such filesysroot 不对或 -I 指向了主机路径-v 看它真正搜索了哪些目录
运行时 GLIBC_2.29 not found工具链的 glibc 版本高于目标板上的strings /lib/libc.so.6 | grep GLIBC_ 对比
编译通过，运行 Illegal instruction用了目标 CPU 不支持的指令（如 NEON、硬浮点指令但板子无 VFP）看编译选项 -march、-mfpu 是否超出 SoC 能力
浮点结果离谱软/硬浮点 ABI 混用readelf -A 看 Tag_ABI_VFP_args
程序在板子上「找不到文件」但路径没错动态链接器路径不对（/lib/ld-linux-armhf.so.3 不存在）readelf -l 看 INTERP 段
静态链接后 DNS 不工作glibc 的 NSS 需要动态加载模块改用 musl，或改用动态链接
最常见的根因只有一个 把头文件路径写成了主机的（/usr/include、/usr/local/include）。一旦这样，编译器会拿 x86 环境里的头文件去生成 ARM 代码，类型宽度、结构体布局、宏定义全可能不对，编出来的程序行为诡异且极难查。交叉编译时 -I 只指向 sysroot 里的路径。

7. 常见误解

误解真相
「交叉编译就是换个 gcc」还要配套 binutils、目标 libc、sysroot、调试器，一整套才完整。
「gnueabi 和 gnueabihf 差不多」浮点参数传递方式不同，混用会让浮点值全错。
「编译就是一步」预处理、编译、汇编、链接四步，每步都能单独跑。
「.bss 占文件体积」只记录大小，运行时清零，不占文件空间。
「静态库更省内存」静态库每个程序各带一份，多程序场景下动态库才省。
「strip 越狠越好」strip 掉符号就没法源码级调试，必须保留未 strip 版本。
「-O2 一定比 -O0 好」调试时 -O2 会打乱行号与变量，定位问题反而更难。
「工具链版本越新越好」新版 glibc 编译出的程序在老板上可能直接跑不起来。

8. 自检：能答出来才算懂

1

为什么不在板子上直接编译？

看答案

板子 CPU 弱、内存小，编译内核要数小时；工具链本身也占几十 MB，不划算。所以用 PC 交叉编译。

2

arm-linux-gnueabihf-gcc 里 hf 代表什么？

看答案

hard float：浮点参数通过 VFP 寄存器传递，而不是用整数寄存器 + 软件模拟。

3

预处理、编译、汇编、链接各产出什么？

看答案

展开后的 .i 文本 → 汇编 .s → 可重定位目标文件 .o → 可执行 ELF（或 .so/.a）。

4

sysroot 是什么，为什么必须有？

看答案

目标机头文件与库的影子根目录。没有它，编译器会去主机路径找 x86 头文件，编出的 ARM 程序布局错误。

5

.a 与 .so 在链接时机上有什么区别？

看答案

.a 在编译期把代码复制进可执行文件；.so 在运行时由动态链接器加载，可被多程序共享。

6

GOT 与 PLT 各解决什么问题？

看答案

GOT 存外部符号地址，让代码段不必重写；PLT 是函数跳板，首次调用解析地址（懒绑定）。

7

为什么 int buf[1000000]; 不增加文件体积？

看答案

它在 .bss 段，ELF 只记录需要的大小，不存实际零字节，运行时由内核分配清零页。

8

运行时报 GLIBC_2.29 not found，怎么查、怎么修？

看答案

用 strings /lib/libc.so.6 | grep GLIBC_ 看板上实际版本；改用与板上 glibc 匹配的工具链，或静态链接/换 musl。

9. 这一章要动手的命令

  1. arm-linux-gnueabihf-gcc -v —— 看工具链版本、target、配置与 sysroot。
  2. arm-linux-gnueabihf-gcc -E hello.c -o hello.i —— 亲眼看预处理展开的结果。
  3. arm-linux-gnueabihf-gcc -S hello.c -o hello.s —— 看生成的 ARM 汇编。
  4. file hello —— 确认产物是 ELF 32-bit LSB executable, ARM 而不是 x86。
  5. readelf -h hello 与 readelf -l hello —— 看入口地址、段表、INTERP。
  6. nm hello | head 与 arm-linux-gnueabihf-objdump -d hello | head -40 —— 看符号与反汇编。
  7. arm-linux-gnueabihf-strip hello -o hello_stripped; ls -l hello hello_stripped —— 量 strip 前后的体积差。
