platform 总线模型：probe、匹配、资源与设备树

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

SoC 内部的外设不在 PCI 上，也不在 USB 上。它们挂在地址总线的固定位置上，没有「枚举」这回事。于是 Linux 用一条假总线把它们管起来：platform 总线。

它解决的问题只有一个：设备与驱动要能互相找到，但谁都不该硬编码对方。设备树说「我这里有一个 UART，寄存器在 0x2020000，中断是 26」；驱动说「我支持 compatible = fsl,imx-uart」；platform 总线负责配对。

先玩一下：从 insmod 到 probe 被调用

点「单步」。注意 EPROBE_DEFER 那一步：驱动不是失败，而是「我要的时钟还没准备好，等会儿再来」——这是 probe 可能被调用多次的原因，也是新手最常踩的坑。

这台状态机里最重要的不是「成功」，而是失败路径。probe 里任何一步失败都必须把前面已经申请的东西退回去（goto 分级错误处理），否则下次 probe 会撞上「中断已被占用」「ioremap 泄漏」。这是驱动代码审查的第一眼。

一、三个名字，一条匹配规则

  • platform_device：描述「有什么」。来自设备树的 of_platform_populate，或老式的板级文件静态注册。
  • platform_driver：描述「我会什么」。包含 probe、remove、id_table、of_match_table。
  • platform_bus_type：把两者配对。匹配优先级：of_match_table（设备树 compatible）→ id_table → name 字符串相等。

设备树里的节点长这样（i.MX6ULL 的 UART 为例，节选）：

uart2: serial@21e8000 {
    compatible = "fsl,imx6ul-uart", "fsl,imx6q-uart";
    reg = <0x021e8000 0x4000>;
    interrupts = <GIC_SPI 27 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&clks IMX6UL_CLK_UART2_IPG>, <&clks IMX6UL_CLK_UART2_SERIAL>;
    status = "okay";
};

驱动的匹配表就是这段 compatible 的镜像。两边字符串必须完全一致，多一个空格都不行——这是最常见的一类「驱动不 probe」。

二、probe 里到底该做什么

这里有个容易被忽略的设计：驱动不该自己去找寄存器地址。地址、中断号、时钟全来自描述信息（设备树），驱动只消费。这样同一份驱动代码可以服务 i.MX6ULL、i.MX6UL、甚至别的 SoC，只要 compatible 与资源描述对得上。

误解：probe 只调用一次只要返回 -EPROBE_DEFER，或者设备被 unbind/bind，probe 会再次执行。所以 probe 必须可重入、必须能清理干净，不能假设「全局变量只初始化一次」。
排障第一现场/sys/bus/platform/devices/ 看设备在不在；/sys/bus/platform/drivers/<drv>/ 看有没有软链指向设备。没有软链就是没匹配上，先 diff compatible，别怀疑硬件。

动手（可选）：写一个最小 platform 驱动

只在 🔧 实作模式展开需要板子与内核源码树；只想懂理论可跳过。
  1. 在设备树里加一个节点 mydev@0 { compatible="demo,mydev"; reg=<0x02000000 0x1000>; status="okay"; };（地址要用你板子上确实空着的区域）。
  2. 驱动里写 of_match_table 与 probe，probe 里只 dev_info 打印 base 与 irq。
  3. insmod 后 dmesg | tail 看到打印，说明匹配与资源解析通了。
  4. 故意把 compatible 改错一个字符，重新编译 dtb，观察不再 probe——这就是「驱动不加载」的最常见原因。

离开这一篇，你应该能

  • 画出 device / driver / bus 的三角关系，说出匹配的三种依据。
  • 解释 -EPROBE_DEFER 为什么存在，以及它对 probe 代码的要求。
  • 列出 probe 里至少五件必须做的事，以及失败时怎么退。

驱动挂上总线之后，就要面对用户态最朴素的需求：read 的时候数据还没来怎么办。下一篇专门讲「等」这件事。
