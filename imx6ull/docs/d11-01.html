oops 现场还原：寄存器、栈回溯、反汇编定位到行

★ 一读 纯读约 3 小时 左侧是本卷目录 理论为主 · 实作可跳

内核崩了不会给你断点，只给你一段文字：Unable to handle kernel NULL pointer dereference at virtual address 00000000，加一串 PC is at ...、LR is at ...、几行 [<addr>] func+0x..，最后一行 Code: e5900000 ...。

这段文字足够定位到「源文件第几行、哪个指针是空的」——前提是你会按顺序读它。

先玩一下：把 oops 的寄存器搬到反汇编上

点「单步」。右侧寄存器会随每一行变化，PC 指到哪一行，那一行就是出事的地方。

上面这段是「读法演示」，地址与指令是示意的。真实的流程是：PC 值 → 在 vmlinux 里 addr2line → 得到 file:line → 回去看那一行的变量。

一、oops 的六段，各有用途

字段含义怎么用
故障描述NULL deref / paging request / alignment 等先判断是「访问了不该访问的地址」还是「指令本身非法」
virtual address出错时访问的地址0x0 → 空指针；0xfffffff0 之类 → 野指针/负偏移
PC is at出错指令地址 + 符号 + 偏移定位「哪一行代码」
LR is at调用者返回地址回溯上一层
Call trace栈回溯（函数 + 偏移）还原调用链，找「谁传了空指针」
Code:出错指令前后的机器码反汇编对照；也可用 scripts/decodecode

一个实用细节：func+0x1c/0x2a0 这种偏移是相对函数入口的，addr2line -f -e vmlinux 0xbf0421a0 能直接给出行号；如果没有调试信息，就只剩函数名与偏移，只能靠反汇编硬看。所以产品必须保留一份带符号的 vmlinux，与固件版本一一对应。

二、常见四类根因

  • 空指针：dev 还没赋值就用了；probe 失败路径没清理；of_node 为空。
  • 野指针 / use-after-free：kfree 后继续用；并发下对象被另一个线程释放。开启 CONFIG_DEBUG_KMEMLEGS/KASAN 能提前抓到。
  • 栈溢出：内核栈通常 8 KB（ARM 32 位可能是 8 KB），大数组 + 深递归就爆。症状常是「随机在某处崩溃」，回溯看起来毫无关联。
  • 硬件访问：时钟没开就读写寄存器 → 总线错误（External abort），这类 oops 的地址往往是正常的寄存器地址，但硬件没响应。
oops ≠ panicoops 通常只杀死当前进程（panic_on_oops=0 时），系统还能跑；panic 会停住或重启。所以「崩溃后系统还在，但某个功能不工作了」也是 oops，别以为没日志就没问题，去 dmesg 里翻。
掉电前最后的日志配置 pstore/ramoops 后，崩溃前的 dmesg 会留在内存里，重启后从 /sys/fs/pstore/ 读出。panic_timeout 配合看门狗，能把「死机无日志」变成「有现场」。

动手（可选）：故意造一次 oops

只在 🔧 实作模式展开需要板子；没有板子可只读上面的读法。
  1. 写一个模块，在 open 里 *(int *)0 = 1;，insmod 后 cat /dev/xxx。
  2. dmesg 里拿到 PC 与 Call trace，用 addr2line 定位到你写的那一行。
  3. 把空指针改成 dev->field（dev 未初始化），看故障地址从 0x0 变成一个小偏移——这就是「结构体成员偏移」的线索。
  4. 再写一个栈上 16 KB 数组的函数，观察 stack overflow 或莫名其妙的崩溃。

离开这一篇，你应该能

  • 按六段读一份 oops，并说出 PC is at 与 Code: 各自的用途。
  • 用 addr2line 把地址换成行号，并说明为什么需要保留 vmlinux。
  • 区分空指针、UAF、栈溢出、总线错误四类根因的典型症状。

如果崩溃发生在「串口还没输出」的极早期，oops 根本不会出现。这时候只能靠 JTAG 把 CPU 按停——下一篇。
