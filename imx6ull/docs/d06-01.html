卷 06·网络栈·第 01 篇

从 socket 到协议栈：套接字、sock、传输层入口

★ 一读 纯读约 2 小时 左侧是本卷目录 理论为主 · 实作可跳

socket() 返回的那个整数，和 open() 返回的没有任何区别：它只是进程 fd 表里的一个下标。真正干活的东西藏在三层结构后面——struct file、struct socket、struct sock。

把这三层理清，你就能回答一个很实际的问题：write 返回成功的时候，数据到底到哪了？答案是：到内核的发送队列里，还没上 wire。

先玩一下：write 之后数据经过谁的手

点「下一步」看这条链。注意第 5 站之后数据已经不在你的进程里了——这也是「write 返回 ≠ 对方收到」的原因。

所谓「两次拷贝」就是这么来的：一次 CPU 拷贝（用户 → skb），一次 DMA（内存 → 网卡）。零拷贝技术（sendfile、splice、MSG_ZEROCOPY）省掉的是第一次，或者把第一次也变成页的引用。

一、三层结构，各管一件事

结构谁创建管什么你能在哪看到
struct fileopen/socket 时由 VFS 建fd 表项、引用计数、f_op 函数表/proc/<pid>/fd 的软链
struct socket__sock_create类型（STREAM/DGRAM）、状态、ops（proto_ops）基本只在代码里
struct sockinet_create → 协议族创建协议状态机、收发队列、定时器、选项ss 命令读的就是它

proto_ops 是「通用套接字接口」，proto 是「具体协议实现」。同一个 sendmsg 调用，先进 sock_sendmsg（通用层，处理等待、信号、超时），再到 inet_sendmsg（地址族层），最后由 tcp_sendmsg（协议层）真正干活。分层的目的很实际：让 AF_INET 和 AF_INET6 共用一套套接字语义，却各用各的地址处理。

二、listen 与 accept 到底发生了什么

很多人对 accept 有误解，以为它「建立连接」。实际上：

  • listen(fd, backlog)：把 sock 状态改为 TCP_LISTEN，并准备两个队列——半连接队列（收到 SYN、还没完成握手）与全连接队列（握手完成、等待被 accept）。backlog 影响的是后者（还有 somaxconn 上限）。
  • 三次握手的最后一步 ACK 到达时，内核自己创建一个新的 sock，挂进全连接队列。你还没调 accept，连接已经建好了。
  • accept 只是从这个队列里取一个出来，包一层新的 struct socket + file，返回新 fd。

所以「服务端 accept 慢一点会不会丢连接」的答案是：只要队列没满就不会；满了之后新来的 SYN 会被丢弃或忽略（取决于 tcp_abort_on_overflow），客户端表现为超时重传。这是生产环境最常见的一类「玄学连接失败」。

三、发送队列与「写完就算成功」

tcp_sendmsg 会把数据切成不超过 MSS 的段，逐个塞进 sk_write_queue。这个队列有上限，由 SO_SNDBUF（以及 net.ipv4.tcp_wmem 的自动调优）决定。write 返回成功，只表示「成功放进队列」，不代表对端 ACK。

要确认对端真的收到，只有两条路：应用层协议自己回 ACK（HTTP 响应、RPC 返回值），或者用 TCP_INFO 查 tcpi_unacked（能看到还有多少字节没被确认）。这也是为什么「发完就 close」的程序容易丢数据：close 会触发 FIN，但队列里没发完的数据仍会继续发，只是你再也拿不到错误通知了。

四、四个容易混的点

「socket 就是文件」对，但不完整fd 层面它确实是文件；但它没有磁盘 inode，也没有页缓存。它的「读写」走的是 proto_ops，不是 file_operations 里那套常规实现。
阻塞与非阻塞的差别不在 socket，而在等待方式非阻塞时，队列满就返回 EAGAIN；阻塞时，进程挂到 sock 的等待队列上睡过去，直到有空间或被信号打断。同一个 tcp_sendmsg，两条分支。
一个能立刻用的观察ss -m -i 能看到每个连接的 skmem（rmem/wmem 的分配量）与 cwnd/rtt。当 wmem 一直贴着上限，说明瓶颈在发送侧（对端窗口小或本机队列小），不是「网卡不行」。

动手（可选）：看见 sk_buff 在涨

只在 🔧 实作模式展开PC 上即可；板子上结论一样。
  1. 起一个 nc -l 9000 当服务端（或者干脆连一个不读对端）。
  2. 客户端用 Python 连续 send 大量数据但不读响应，用 ss -m 观察 wmem 一路涨到 sndbuf 上限。
  3. 把 SO_SNDBUF 设成 4 KB 再试，send 会开始阻塞或返回 EAGAIN——你就亲手摸到了发送队列的边界。
  4. 用 bpftrace（或 perf trace）挂 tcp_sendmsg 的返回值，能看到每次实际拷贝了多少字节。

离开这一篇，你应该能

  • 画出 fd → file → socket → sock 的包含关系，并说出 proto_ops 与 proto 的分工。
  • 解释 write 返回成功时数据在哪，以及怎么确认对端收到。
  • 说清 listen 的两个队列、accept 真正做的事，以及「连接失败」可能来自哪。
