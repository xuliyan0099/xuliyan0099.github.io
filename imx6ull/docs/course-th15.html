卷 04·操作系统·第 11 篇

内核全貌：子系统如何协作

前面几章是「竖着切」——把进程、内存、文件、中断一个个挖到底。这一章「横着切」：一次最简单的 read 到底穿过了哪几层，一个网络包要走多少站，以及你怎么用自己的眼睛看见这些过程。

◆ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 内核到底由哪几块组成，边界在哪；② 读一个文件，从系统调用到磁盘，中间有几次拷贝；③ 发一个网络包，经过哪些队列与回调；④ 出问题时不加 printk，靠什么定位；⑤ 嵌入式为什么要裁内核，裁错了会怎样。

读完你应该能回答

  • 六大子系统各自负责什么，互相之间靠哪些接口通信？
  • 一次 read 的完整调用链，页缓存命中与未命中差在哪？
  • 网络收包为什么分「硬中断 + 软中断」两段？
  • ftrace 的 function_graph 怎么用，能看什么？
  • 裁剪内核时哪些东西绝对不能关？

1. 六大子系统与它们的边界

Linux 内核不是一个「程序」，而是六个互相咬合的子系统。理解分工比背函数名重要得多：

子系统核心职责关键数据结构和谁打交道
进程调度谁在什么时候用 CPU、用多久task_struct、rq、sched_entity中断（唤醒）、内存（栈）、文件（fd 表）
内存管理虚拟地址、物理页、分配与回收mm_struct、vma、page调度（切页表）、文件（页缓存）、驱动（DMA）
虚拟文件系统统一「文件」抽象，屏蔽具体文件系统super_block、inode、dentry、file块层、驱动、内存（页缓存）
网络协议栈TCP/IP 与套接字sk_buff、sock、net_device驱动（网卡）、内存（skb 分配）
进程间通信管道、消息队列、共享内存、信号pipe_inode_info、shmid_kernel调度（阻塞唤醒）、内存（共享页）
设备驱动把硬件能力暴露成统一接口device、driver、file_operations中断、时钟、电源与上述所有子系统
边界靠「接口」而不是「代码位置」 源码目录 kernel/、mm/、fs/、net/、ipc/、drivers/ 大致对应这六块，但真正的边界是接口：调度器通过 wake_up_process 被中断唤醒，内存管理通过 alloc_pages 被所有人调用。看代码先找接口，别按目录硬切。

2. 一次 read 文件的完整路径

假设应用执行 read(fd, buf, 4096)。这一条语句背后有十几个环节：

用户态 read→svc 进入内核→sys_read→vfs_read→f_op->read→页缓存查找→命中直接拷贝→未命中读盘→DMA 填页→中断唤醒→copy_to_user

逐段说明，重点看「数据被拷贝了几次」：

阶段关键动作数据拷贝
系统调用入口保存寄存器、切内核栈、查 fd 表拿到 struct file无
VFS 层检查权限、可读性、偏移合法性无
页缓存查找按 inode 与页号在 xarray 里找页无
命中直接 copy_to_user 拷贝到用户缓冲1 次
未命中提交 bio 给块层，驱动 DMA 把数据写进页缓存DMA 不经 CPU
返回再 copy_to_user总计 1 次 CPU 拷贝
算一笔：为什么「零拷贝」有意义
普通路径：磁盘 → 页缓存（DMA）→ 用户缓冲（CPU 拷）→ 网卡（CPU 拷）= 2 次 CPU 拷贝
sendfile 路径：磁盘 → 页缓存（DMA）→ 网卡（DMA）= 0 次 CPU 拷贝
1GB 数据、拷贝带宽 2GB/s，省下约 1 秒；高吞吐服务上是数量级差异
嵌入式更在意「省 CPU」而不是「省时间」：CPU 空出来能跑业务
页缓存是「隐形的加速器」 第二次读同一个文件几乎不碰磁盘，因为页还在缓存里。这也是 free 显示内存总「很少」的原因——内核把空闲内存全拿去做缓存，需要时随时归还。

3. 一个网络包的旅程

发送与接收路径完全不对称，这不对称是故意的：收包发生在中断上下文，不能久留，所以必须拆成两段。

3.1 发送方向

应用 send→socket 层→TCP 分段→IP 加头→邻居/路由→qdisc 排队→驱动 tx→DMA 到网卡→发送完成中断→释放 skb
  • skb（sk_buff）：网络子系统里所有数据的载体，头部指针可以在同一块内存上前后移动，避免反复拷贝。
  • qdisc：排队规则。默认 pfifo_fast，按优先级分三条队列；流量整形（tc）也在这里生效。
  • 发送完成中断：驱动把 skb 交给网卡后并不立刻释放，等硬件确实发完才回收，否则会出现「数据还没出去就被改写」。

3.2 接收方向：两段式

网卡收到帧→硬中断（上半部）→关中断，登记到 poll 列表→软中断 NET_RX→驱动 poll 收包→协议栈解析→放入 socket 队列→唤醒应用

为什么必须两段：

阶段做什么为什么不能合并
硬中断确认是哪路中断、清标志、把网卡加入 poll 列表中断里不能长时间关中断，否则丢包、影响其他设备
软中断真正把帧从网卡 FIFO 读到内存、跑协议栈耗时长，必须允许被更高优先级中断打断
NAPI 机制 高流量下如果每个包都产生一次硬中断，CPU 会被中断淹没。NAPI 的做法是：第一个包来时关中断并登记，之后改用轮询批量收包，收完再开中断。这就是「中断 + 轮询」混合，是中高负载下的标准做法。

4. 怎样看见内核在做什么

不看代码、不加 printk 也能定位问题，靠这五样工具：

工具看什么典型用法
dmesg内核日志（printk 输出）dmesg -T | tail -50 看启动或报错
/proc内核状态的文本快照buddyinfo、interrupts、meminfo、stat
/sys设备模型与驱动的可读写属性改 GPIO、看时钟、调驱动参数
ftrace函数级调用轨迹、耗时function_graph 看一次系统调用的完整调用树
perf采样分析、热点函数perf top、perf record -g
// ftrace 最基本的三步（不需要重新编译内核） cd /sys/kernel/debug/tracing echo function_graph > current_tracer echo 1 > tracing_on cat trace | head -50 echo 0 > tracing_on // 只看某个进程 echo $$ > set_ftrace_pid

5. 为什么嵌入式必须裁剪内核

一块 i.MX6ULL 板子的存储往往是 512MB NAND 或 8GB eMMC，内存 256–512MB。内核全量编译出来的镜像能到 10MB 以上，加上根文件系统就吃紧，而且启动要几十秒。裁剪带来三个直接收益：

收益量级原因
镜像变小10MB → 2–3MB去掉不用的驱动、文件系统、调试设施
启动变快几十秒 → 2–5 秒少加载模块、少探测设备、少初始化子系统
攻击面变小—不编译进去的代码不可能被利用

裁剪的机制是 Kconfig + .config：每个目录下的 Kconfig 定义「有哪些选项、依赖谁」，make menuconfig 生成 .config，编译时按它决定哪些代码进镜像。

// 裁剪的典型流程 make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- mx6ull_defconfig // 先拿基线 make ARCH=arm menuconfig // 进去逐项关 make ARCH=arm -j8 zImage modules dtbs // 编译 ls -lh arch/arm/boot/zImage // 看体积变化
这几项绝对不能关 ① 你的启动介质驱动（MMC/NAND）；② 根文件系统类型（ext4/squashfs/ubifs）；③ 串口驱动（关了就没有任何输出，等于自断手脚）；④ 中断控制器与定时器；⑤ 你板子的机器类型（CONFIG_MACH_*）与设备树支持。只裁「确定用不到的驱动」，别裁机制。

裁完必须验证三件事：能启动到 shell、各外设仍可用、断电重启后仍正常。前两项容易过，第三项常暴露「某个驱动被编成模块但没放进去」。

6. 内核版本：别乱追新

版本号有三段：主版本.次版本.修订号，例如 5.10.120。选版本的原则是看 SoC 厂商的 BSP 用什么，就用什么：

类型特点适用
LTS（长期支持）维护 2–6 年，修 bug 与安全漏洞产品项目首选，如 5.10、5.15、6.1
稳定版短期维护，功能较新需要新特性且能自己扛维护
厂商 BSP 内核NXP/瑞芯微等打了几百个补丁i.MX6ULL 上用 NXP 的 4.1.15 或 5.10 分支
主线 mainline社区维护，i.MX6ULL 支持较完整想长期可维护、愿意自己补驱动
为什么不能随便升级大版本 内核内部接口（如 file_operations 的某些成员、设备树绑定、GPIO 子系统 API）在大版本间会变。厂商 BSP 的驱动是按特定版本写的，跨版本移植要改代码。产品上「能跑就别动」，除非有安全漏洞必须修。

7. 常见误解

误解真相
「内核就是一个大程序」是六个子系统的协作体，靠接口耦合，不是单一模块。
「read 会把数据从磁盘拷两次」普通路径只有 1 次 CPU 拷贝，磁盘到页缓存是 DMA。
「free 内存少说明内存泄漏」空闲内存被用作页缓存，看 available 才准。
「收包应该一次中断处理完」中断里不能久留，必须拆上下半部，否则丢包并影响其他设备。
「有 printk 就够了」printk 会扰动时序，定位性能问题要用 ftrace/perf。
「内核越小越好」裁掉机制类选项（中断、定时器、串口）会让系统直接起不来。
「版本越新越好」驱动与 BSP 是按版本适配的，升级大版本要改代码。
「oops 只要看最后一行」要看 PC、调用栈、寄存器三处，最后一往往只是表象。

8. 自检：能答出来才算懂

1

六大子系统里，哪个负责把硬件能力暴露给用户态？

看答案

设备驱动。它把硬件寄存器操作包装成 file_operations，再通过 VFS 暴露成 /dev 下的文件。

2

一次 read 的主路径，函数依次经过哪几个关键节点？

看答案

sys_read → vfs_read → file->f_op->read → 页缓存查找 → 命中 copy_to_user / 未命中提交 bio。

3

页缓存命中时，一次 read 有几次 CPU 拷贝？

看答案

1 次（内核页 → 用户缓冲）。磁盘到页缓存那一步是 DMA，不经 CPU。

4

为什么收包要拆硬中断与软中断？

看答案

硬中断必须极短，否则影响其他设备并丢包；协议栈处理耗时长，只能放到软中断里做。

5

NAPI 解决的是什么问题，怎么实现？

看答案

高流量下中断风暴。做法是首个包来时关中断并登记，之后轮询批量收包，收完再开中断。

6

ftrace 的 function_graph 能看什么，怎么开？

看答案

看函数级调用树与耗时。在 /sys/kernel/debug/tracing 里 echo function_graph > current_tracer，再 echo 1 > tracing_on。

7

裁剪内核时哪五类东西不能关？

看答案

启动介质驱动、根文件系统类型、串口、中断控制器与定时器、机器类型与设备树支持。

8

为什么 i.MX6ULL 项目更推荐厂商 BSP 内核而不是最新主线？

看答案

BSP 已针对该 SoC 打了大量补丁并适配驱动，主线需要自己补很多东西，且内部接口跨版本会变。

9. 这一章要动手的命令

  1. uname -a 与 cat /proc/version —— 确认版本与编译工具链。
  2. cat /proc/interrupts —— 看所有中断的实际分布，理解「子系统协作」的证据。
  3. strace -c cat /etc/hostname —— 从用户态看系统调用次数与耗时。
  4. cat /sys/kernel/debug/tracing/available_tracers —— 看可用 tracer 列表。
  5. perf top -g —— 采样看当前热点函数。
  6. dmesg -T | head -60 —— 按时间读启动日志，对照第 1 节的子系统顺序。
  7. ls -lh /boot/ 或 ls -lh arch/arm/boot/zImage —— 看内核镜像体积。
