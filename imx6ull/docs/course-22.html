内存墙与局部性

Cache 之所以有用，是因为程序不是随机的：它反复用同一批数据（时间局部性），也倾向用相邻的数据（空间局部性）。这两条「局部性原理」是把程序性能拉回 CPU 侧的唯一杠杆。不懂局部性，就只能靠堆硬件；懂了局部性，一行代码顺序的调换就能让程序快 10 倍。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 时间局部性与空间局部性分别是什么？② 为什么「大 O 相同」实测能差 10 倍？③ 分块（tiling）怎么用？④ 内核为什么大量用链表而不是数组？⑤ 内存墙还会越来越糟吗？

1. 两条局部性

类型定义典型来源受益的机制
时间局部性刚访问过的，很快还会再访问循环变量、热函数、栈顶Cache 保留 + 寄存器分配
空间局部性访问了 A，很可能访问 A+4数组、结构体、顺序代码按行搬运 + 预取

程序的真实行为高度符合这两条：90% 的时间花在 10% 的代码上（时间局部性），且这 10% 的代码通常访问少量集中的数据（空间局部性）。这就是 Cache 能生效的根本原因。

2. 分块：把「大」切成「小到能装进 Cache」

矩阵乘法是经典案例：朴素三重循环对 B 的访问是「按列跳」，局部性极差。分块后，每块数据在 Cache 里被反复使用，未命中骤降。

// 朴素：B 按列访问，每步跳 N*4 字节
for (i) for (j) for (k) C[i][j] += A[i][k] * B[k][j];

// 分块：一次只处理 TS×TS 的小块（TS 取 16~64，约等于 Cache 行数）
for (ii += TS) for (jj += TS) for (kk += TS)
    for (i in ii..ii+TS) for (j in jj..jj+TS) for (k in kk..kk+TS)
        C[i][j] += A[i][k] * B[k][j];

实测提升常常是 3~10 倍，而算法复杂度完全没变。这就是「懂硬件」带来的、纯算法视角看不到的优化空间。

3. 为什么内核大量用链表

这看起来违背局部性：链表节点分散、遍历慢。但内核的选择理由是「增删的代价」而不是「遍历的速度」：

  • 进程、文件、socket 都在动态创建销毁，数组要预留或搬移，链表 O(1) 插入删除。
  • 内核的遍历次数远少于用户态的数据处理，局部性损失可以接受。
  • 现代内核已经在改：hlist（单指针头）、xarray（基数树，适合稀疏大索引）、list_lru（按 NUMA 节点分桶）都在减少跳转。

这条对比很值得记住：数据结构的选择是「访问模式 + 更新模式」的联合优化，不是单一指标的最优。

4. 内存墙的未来

# 三十年的大致趋势（量级示意）
# CPU 每周期性能：×1000 以上
# DRAM 延迟（ns）：从 ~100ns 降到 ~50ns，改进不到 2 倍
# → 相对差距扩大了几百倍
# 缓解手段：多级 Cache、预取、乱序执行、SIMD、多核、近存计算

这也是为什么「数据局部性」正在成为比「算法复杂度」更重要的工程指标：AI 推理、图计算、数据库，最后都在拼内存带宽与访问模式。

5. 实验：量化局部性的价值

# 板子上（C 程序）
perf stat -e cache-references,cache-misses,cycles,instructions ./matmul

# 关注两个比值：
#   cache-misses / cache-references   → 未命中率
#   instructions / cycles             → IPC
# 分块前后各跑一次，你会看到未命中率明显下降、IPC 上升

# 也可以用 valgrind --tool=cachegrind 在 PC 上做详细模拟
valgrind --tool=cachegrind ./matmul

Cachegrind 会给出「D1 miss rate、LL miss rate」，并可按源码行定位。它是你在没有硬件计数器时，理解局部性最方便的工具。

7. 自测与动手

1

举一个只有时间局部性、没有空间局部性的例子。

看答案

反复读同一个全局变量（如计数器），地址固定，不涉及相邻数据。

2

分块大小怎么选？

看答案

让「同时活跃的几块数据」合计不超过 Cache 容量（常取一半留余量），且是行大小的整数倍。

3

为什么链表的遍历慢但内核还用它？

看答案

内核更看重 O(1) 插入删除与无需连续大块内存；遍历不是最热路径，且已有 hlist/xarray 等改良结构。

4

内存墙的本质是什么？

看答案

CPU 性能提升速度远超 DRAM 延迟改进速度，导致「每次未命中的相对代价」逐年增大。

5

cache-misses / cache-references 这个比值说明什么？

看答案

未命中率。它高说明访问模式差或工作集太大；优化方向是改布局、分块、减少随机访问。

  1. 实现朴素与分块的矩阵乘法，在板子上各跑一次 perf stat。
  2. 用 cachegrind 定位你程序里未命中最多的一行源码。
  3. 把一个链表改成数组（或反过来），实测两种场景的耗时。
  4. 把一个大结构体数组拆成两个（SoA），看是否变快。
