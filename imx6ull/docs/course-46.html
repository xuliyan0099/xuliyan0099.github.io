pinctrl 与 GPIO

新手的第一个困境往往不是写不出驱动，而是「代码没错，灯就是不亮」。九成原因是这颗引脚根本没被交给 GPIO——它可能还归 UART1，可能被拉成了开漏，可能电源域没开。这一课把「复用（pinmux）→ 配置（pinconf）→ 驱动（gpiod）」这三关拆开讲，每关都给出你在设备树和代码里的具体落点

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 一颗 SoC 的 100 多个引脚，凭什么能当 UART、I2C、GPIO 用？② IOMUXC 里到底存了什么？③ 设备树里的 pinctrl-0 是谁在什么时候写进寄存器的？④ gpiod_get 和老的 gpio_request 差在哪？⑤ 内核里已经有 GPIO 驱动了，我的 LED 驱动还要不要自己写寄存器？

1. 直觉：引脚是一个多功能插孔，同一时刻只能插一个插头

芯片内部每个焊盘都连着一条「选择器」，外面接了七八个功能模块（UART、I2C、PWM、GPIO…）。你写 MUX_MODE 就是拨动这个选择器。拨错档位，你后面怎么拉高都没用——因为信号根本没接到 GPIO 模块上。

类比失效处：插孔拨错还能换，寄存器拨错会让两个模块同时驱动一条线（比如 UART 的 TX 和 GPIO 都在推），出现「电压只有 1.6V」这种诡异现象。这不是软件 bug，是电气冲突。

2. 硬件：IOMUXC 里存的是两样东西

以 i.MX6ULL 为例，每个焊盘对应两个寄存器：MUX（4 位，选功能）与 PAD（16 位，选电气属性）。PAD 里典型字段：HYS 施密特触发、PUS 上下拉强度、PUE 保持/上下拉、PKE 是否启用、ODE 开漏、SPEED 速率、DSE 驱动能力。

// 头文件里一个宏就代表「焊盘 + 功能」这一对数
#define MX6UL_PAD_UART1_TX_DATA__GPIO1_IO16  0x0084 0x02E8 5 0x0 0x10B0
//                                     ↑mux寄存器 ↑pad寄存器 ↑mux值 ↑pad值 ↑输入选择

这串数字的含义是：把 0x02E8 处的 MUX 写成 5（ALT5 = GPIO1_IO16），把 0x0084 处的 PAD 写成 0x10B0（上下拉、驱动强度等）。设备树里的 fsl,pins 就是在写这张表，内核的 pinctrl 驱动在 probe 时把它翻译成寄存器写入。

3. 软件：设备树申请，驱动只管「拉」

// 设备树：前两关写在这里
led_gpio: led-gpio {
    fsl,pins = <MX6UL_PAD_UART1_TX_DATA__GPIO1_IO16 0x10B0>;
};

myled {
    compatible = "demo,myled";
    led-gpios = <&gpio1 16 GPIO_ACTIVE_HIGH>;   /* 控制器 + 编号 + 极性 */
    pinctrl-names = "default";
    pinctrl-0 = <&led_gpio>;
};
#include <linux/gpio/consumer.h>

struct gpio_desc *led;

static int my_probe(struct platform_device *pdev)
{
    led = devm_gpiod_get(&pdev->dev, "led", GPIOD_OUT_LOW);
    if (IS_ERR(led)) return PTR_ERR(led);
    gpiod_set_value(led, 1);      /* 天亮 */
    gpiod_set_value(led, 0);      /* 天灭 */
    return 0;
}

注意 devm_ 前缀：它把资源绑定到设备生命周期，卸载时自动释放。没有 devm 的版本必须手写 gpiod_put，忘了就泄漏——泄漏几十次之后你会开始怀疑人生。

4. 三条误解

  • 「设备树里写了就生效」：只有被 compatible 匹配上的设备、且 pinctrl 驱动确实实现了 set_mux，这段才生效。引脚名拼错（比如把 PAD_UART1_TX_DATA 写成 PAD_UART1_TX）编译期不报错，运行期静默失败。
  • 「gpiod_set_value 能当延时用」：可以，但忙等很浪费；gpiod_set_value_cansleep 用于可能休眠的 I2C/SPI 扩展 GPIO（如 9555），在中断上下文里调它会睡死。
  • 「极性不重要」：GPIO_ACTIVE_LOW 表示「低电平算点亮」。很多底板 LED 是灌电流接法，写 1 反而灭。设备树里把极性写对，代码里就永远写「1=亮」，不用记硬件接法。

5. 五题自测

1

为什么「代码没错灯不亮」，先查复用而不是先查代码？

看答案

因为复用错了，GPIO 模块的输出根本没接到焊盘，后面所有操作都是「对着空气拉高」。用 devmem2 读一下 MUX 寄存器的值最快确认。

2

pinctrl-0 和 led-gpios 各自负责什么？

看答案

pinctrl-0 管「复用 + 电气属性」，led-gpios 管「哪个控制器的第几号、什么极性」。前者在设备初始化阶段生效，后者在驱动取用时解析。

3

同一颗引脚被两个设备树节点同时申请，会发生什么？

看答案

谁先 probe 谁先占；后者 gpiod_get 会拿到 -EBUSY。日志里能看到 gpio 16 is already requested——这是很典型的「两个驱动抢一个引脚」。

4

GPIO_ACTIVE_LOW 下 gpiod_set_value(led,1) 输出什么电平？

看答案

低电平。内核在 gpiod 层做了取反，所以软件语义永远是「1 = 有效（点亮）」，与硬件高低无关。

5

为什么推荐 devm_gpiod_get 而不是 gpio_request？

看答案

gpio_request 是旧的整数编号 API，还要手动 gpio_free；devm_gpiod_get 用描述符、自动释放、支持极性抽象，且 probe 失败时不会泄漏。

6. 动手（40 分钟）

1. 用 cat /sys/kernel/debug/gpio 看当前哪些 GPIO 已被占用，找到你板子上 LED 的编号。

2. 用 devmem2 读该引脚的 MUX 寄存器，确认它是否真在 GPIO 模式（ALT5）。

3. 在设备树里加 led-gpios 节点，重新编译 dtb，启动后用 gpioset 手动拉高，确认灯亮。

4. 再把它改成 GPIO_ACTIVE_LOW，观察「写 1 反而灭」——这是极性写错的经典复现。
