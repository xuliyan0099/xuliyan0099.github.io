设备模型与驱动框架

这一章解释三件在嵌入式开发里天天遇到但很少有人讲清的事：/dev 下那个设备节点凭什么能打开、插上 U 盘内核怎么「自动」知道该用哪个驱动、为什么你的驱动 probe 总是不执行。答案都在设备模型这套机制里。

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 用户 open("/dev/xxx") 时内核怎么找到你的驱动；② major/minor 到底编码了什么；③ 设备、驱动、总线三者怎么互相发现；④ 设备树怎么取代了静态设备表；⑤ 为什么 probe 会被延迟甚至不执行。

读完你应该能回答

  • 字符设备的主设备号和次设备号各能表示多少个设备？
  • 一个驱动文件里，file_operations 是怎么被「挂」到某个 inode 上的？
  • 为什么网络设备在 /dev 下没有节点？
  • -EPROBE_DEFER 是什么机制，解决什么问题？
  • 同一个驱动能不能同时管理两个同型号设备？靠什么区分？

1. 从 open("/dev/led") 说起

用户在 /dev 下看到一个叫 led 的东西，open 它就能控制 LED。这中间发生了什么？关键在于：/dev/led 不是一个普通文件，它只是一个「带设备号的特殊 inode」。

Linux 用 dev_t（32 位无符号数）编码设备身份：

dev_t（32 位） = major(12 位) | minor(20 位) 主设备号 次设备号 MKDEV(major, minor) = (major << 20) | minor MAJOR(dev) = dev >> 20 MINOR(dev) = dev & 0xFFFFF

两者的分工是老传统：主设备号决定「用哪个驱动」，次设备号决定「驱动里的第几个设备」。所以一个串口驱动注册主设备号 4，然后主设备 4 + 次设备 0/1/2 分别对应 ttyS0/ttyS1/ttyS2——一个驱动管多个实例。

打开流程是这样的：

open("/dev/led")→路径解析到 inode→发现是字符设备→取 inode->i_rdev→按主设备号查 cdev 表→得到 file_operations→调 f_op->open

这里有两个必须记的结构：

  • struct cdev：驱动注册时创建，内部记录「我的主次设备号范围」和「我的 file_operations」。内核用一张全局表（cdev 哈希/映射）按设备号找它。
  • struct file_operations：一堆函数指针（open/read/write/ioctl/mmap/release）。这是驱动与 VFS 的唯一接口。
为什么用户态只认设备号 因为 /dev/led 这个名字是「用户态约定」，内核并不在乎它叫什么。真正决定行为的，是它的 inode 里存的 i_rdev（主次设备号）。你甚至可以 mknod /tmp/myled c 240 0 造一个同设备号的节点，照样能打开同一个驱动。

1.1 主设备号怎么来的

两种注册方式，选择哪一种是新手第一个坑：

方式函数特点适用
静态指定register_chrdev_region(dev, count, name)你写死主设备号，冲突就失败沿用标准号（如 4=tty、1=mem）
动态分配alloc_chrdev_region(&dev, 0, count, name)内核挑一个空闲主设备号给你自定义驱动首选

静态指定的风险很实际：主设备号是被全系统共享的资源，你写死 240，另一个驱动也写死 240，两个就打架。生产驱动一律用动态分配，然后在 /proc/devices 里查自己拿到了什么号。

2. 设备模型：kobject / device / driver / bus

Linux 2.6 之后引入了「设备模型」，目的不是好看，而是解决三个真问题：① 系统里几千个设备怎么统一管理生命周期；② 设备与驱动的匹配怎么自动化；③ 电源管理与热插拔怎么广播。它的实现就是 /sys 那棵目录树。

对象代表在 /sys 里的样子
kobject一切模型对象的基类，管引用计数与名字一个目录 + 里面的 uevent 等属性
device一个具体硬件/sys/devices/... 下的目录
driver一段能管理某类设备的代码/sys/bus/xxx/drivers/yyy/
bus设备与驱动相遇的「场所」（platform、i2c、spi、usb…）/sys/bus/xxx/
class按功能归类（gpio、tty、leds、block…）/sys/class/xxx/ 下全是符号链接

/sys/class/gpio/gpio12 是个符号链接，指向 ../../devices/platform/soc/.../gpio12。class 是「视角」，devices 是「实体」，一个实体可以出现在多个 class 视角里。这就是为什么同一个 GPIO 既能从 /sys/class/gpio 看到，也能从 /sys/class/leds 看到。

2.1 匹配是怎么发生的

「设备」和「驱动」是两拨独立注册的东西，内核必须把它们配上对。配对规则由总线决定（bus->match 回调），常见三种：

  1. 名字匹配：设备名 == 驱动名（老式 platform 设备）。
  2. ID 表匹配：驱动里带一张 of_device_id 表，比对设备树节点的 compatible 字符串。
  3. 总线协议匹配：I2C/SPI 用设备地址 + 厂商 ID 匹配（如 I2C 的 i2c_device_id）。

一旦某侧注册，总线就把该侧所有「还没配对」的对象遍历一遍，逐个试 match，成功就调用驱动的 probe()。所以 probe 的调用时机是不确定的：可能驱动先注册（等设备），也可能设备先注册（等驱动），只要配对成功就会调一次。

/* 典型 platform 驱动的匹配表 */ static const struct of_device_id led_of_match[] = { { .compatible = "myvendor,myled" }, /* 必须与 dts 里一致 */ { } }; MODULE_DEVICE_TABLE(of, led_of_match); static struct platform_driver led_driver = { .probe = led_probe, .remove = led_remove, .driver = { .name = "myled", .of_match_table = led_of_match, }, };

对照设备树里的节点：

myled: led { compatible = "myvendor,myled"; /* 与上面字符串完全一致才匹配 */ reg = <0x0209C000 0x4000>; /* GPIO1 寄存器基址与长度 */ led-gpios = <&gpio1 3 GPIO_ACTIVE_LOW>; };
最常见的「probe 不执行」原因 compatible 字符串错一个字（比如 myvendor,myLed 大写、或逗号写成下划线），匹配就永远不成立，而且内核不会报错——它只是「没找到匹配」。排查方法：/sys/bus/platform/drivers/<你的驱动名>/ 下如果空着，就是没匹配上。

3. 设备树：把硬件描述从代码里搬出来

在设备树出现之前（ARM 老内核），每块开发板都要在 arch/arm/mach-xxx/ 下写一个 board 文件，里面全是这样：

static struct resource led_res[] = { { .start = 0x0209C000, .end = 0x0209C3FF, .flags = IORESOURCE_MEM }, }; static struct platform_device led_dev = { .name = "myled", .id = -1, .resource = led_res, .num_resources = 1, };

问题很明显：几千块板就有几千个 C 文件，同一个 SoC 的重复描述占满内核源码，改一个引脚要重编内核。设备树的解法是把这些「硬件长什么样」的信息搬到独立的文本文件里，编译成 .dtb，由 bootloader 传给内核：

board.dts→dtc 编译→board.dtb→U-Boot 加载→内核解析→of_platform_populate→生成 platform_device→触发匹配

内核启动时解析 DT，遍历每个带 compatible 属性的节点，为它创建一个 platform_device 并注册到 platform 总线。剩下的匹配流程和静态表时代完全一样。所以设备树并没有改变驱动机制，它只是把「设备清单」从代码变成了数据。

这条分界必须理解清楚：

谁负责写什么例子
设备树（dts）硬件事实：地址、引脚、时钟源、中断号、极性led-gpios = <&gpio1 3 GPIO_ACTIVE_LOW>
驱动（.c）行为逻辑：怎么初始化、怎么读写、怎么响应中断gpiod_set_value(led, 1)

所以「换个引脚」只改 dts 重启就行，不用重编内核；「改驱动逻辑」才需要重编。这条规则也是评审时最常被挑的：把硬件参数写进驱动代码里（比如 #define LED_GPIO 3）就是违反了设备树的设计意图。

实用命令：dtc -I dtb -O dts board.dtb > board.dts 可以把板子上现成的 dtb 反编译成文本，这是逆向别人板子最快的方法。运行时看内核实际解析出的树在 /proc/device-tree/（或 /sys/firmware/devicetree/）。

4. probe 为什么会被「延迟」

真实系统里驱动是有依赖的：LED 驱动需要 GPIO 控制器，GPIO 控制器需要 pinctrl，pinctrl 需要时钟，时钟需要 PMIC。而 probe 的调用顺序由注册顺序和链接顺序决定，无法人为保证。如果 LED 驱动先 probe，而 GPIO 控制器还没准备好，怎么办？

老的写法是「返回失败，等下次」。但这会留下一个隐患：失败之后内核可能就不再试了。-EPROBE_DEFER 就是为此设计的正式机制：

static int led_probe(struct platform_device *pdev) { struct gpio_desc *g = devm_gpiod_get(&pdev->dev, "led", GPIOD_OUT_LOW); if (IS_ERR(g)) { if (PTR_ERR(g) == -EPROBE_DEFER) return -EPROBE_DEFER; /* 告诉内核：我依赖的东西还没好，稍后再试 */ return PTR_ERR(g); } ... }

内核收到 -EPROBE_DEFER 后，把这个驱动放进「延迟探测队列」，等有新驱动注册成功时再整队重试。由此推出三条实践要求：

  • probe 必须可重入：可能被调用多次，所以每次失败都要把自己申请的资源释放干净（用 devm_* 系列函数最省心，它会在 probe 失败时自动回收）。
  • 不要把所有错误都当成 DEFER：只有「依赖未就绪」才返回它。真错误（参数非法）返 DEFER 会导致无限重试。
  • 一直 defer 就是死循环：如果依赖的驱动永远不会注册（比如 dts 里漏了节点），这个设备就永远 probe 不了，日志里会反复出现 defer 提示。cat /sys/kernel/debug/devices_deferred 可以直接列出所有卡住的设备。
一条排障口诀 设备不工作 → 先看驱动有没有 probe（ls /sys/bus/platform/drivers/<name>/ 有没有设备符号链接）→ 没有就看匹配（compatible 对不对）→ 匹配上了但没 probe 成功，就看 dmesg 里 probe 的报错 → 报 -517（即 -EPROBE_DEFER）就是依赖没就绪，去查依赖链。

5. 一个字符设备的注册骨架

概念讲完，看一个最小但完整的注册流程。写驱动时按这六步走，一步都不能少，每步的作用都很明确：

static int my_open(struct inode *in, struct file *f) { return 0; } static ssize_t my_read(struct file *f, char __user *buf, size_t n, loff_t *off) { ... return 0; } static const struct file_operations my_fops = { .owner = THIS_MODULE, .open = my_open, .read = my_read, .write = my_write, .unlocked_ioctl = my_ioctl, }; static dev_t my_dev; static struct cdev my_cdev; static struct class *my_class; static int __init my_init(void) { alloc_chrdev_region(&my_dev, 0, 1, "mydev"); /* ① 要设备号 */ cdev_init(&my_cdev, &my_fops); /* ② 绑定操作表 */ cdev_add(&my_cdev, my_dev, 1); /* ③ 注册进内核 */ my_class = class_create("mydev"); /* ④ 建 /sys/class/mydev */ device_create(my_class, NULL, my_dev, NULL, "mydev0"); /* ⑤ 建 /dev/mydev0 */ return 0; }

逐条对应到前面讲过的机制：

步骤做了什么少了它会怎样
① 分配设备号拿到一组 major:minor后面全部无号可用
② cdev_init把 fops 挂到 cdev 上打开时找不到操作表
③ cdev_add把 cdev 注册进全局表，与设备号建立映射open 报 ENODEV
④ class_create在 /sys/class 下建目录不影响功能，但 udev 规则无从挂
⑤ device_create触发 devtmpfs 自动创建 /dev/mydev0设备能工作，但用户找不到节点，得手动 mknod

第 ⑤ 步是最容易漏的。很多人调试时发现「驱动加载了、/proc/devices 里也有我的主设备号，但 /dev 下什么都没有」——就是漏了 device_create，或者没开 CONFIG_DEVTMPFS。

6. 三种设备类型，本质是三种「访问模型」

类型设备节点访问单位缓存典型
字符设备有，/dev/xxx字节流，无固定块一般无页缓存串口、LED、按键、I2C 从设备
块设备有，/dev/mmcblk0固定大小的块（512B 起）有页缓存 + IO 调度eMMC、SD、U 盘、硬盘
网络设备没有数据包有自己的队列eth0、wlan0、can0

网络设备为什么没有设备节点？这是个很值得想的问题。因为它的数据模型和文件流根本不同：文件是「有位置的字节序列」（可以 seek、可以重复读），网络是「一次性的包」（来了就消费掉，无法回退）。硬塞进 read/write 模型会非常别扭，所以内核给它单独一套 socket 接口，用 ip/ifconfig 管理。

块设备与字符设备的区别也不是「大 vs 小」，而是有没有页缓存和调度。块设备的读写先经过页缓存（见 T04），再由 IO 调度器合并排序后下发；字符设备通常是「直接操作寄存器」，每次 read 就是一次真实的硬件交互。这也解释了为什么读 /dev/ttyS0 会真的等串口来数据，而读 /dev/mmcblk0 会被缓存加速。

7. 十个常见误解

误解真相
「/dev 下的节点就是驱动」节点只是一个带设备号的 inode，驱动在内核里，与节点名无关。
「一个主设备号只能给一个驱动」可以共享。misc 设备就是所有杂项共用主设备号 10，靠次设备号区分。
「insmod 成功设备就能用了」还要与设备匹配并成功 probe。模块加载只证明代码进了内核。
「probe 只会调用一次」可能多次：延迟探测重试、设备热插拔、驱动卸载重载都会再调。
「设备树是内核的一部分」独立文件，由 bootloader 传给内核；同一内核可配不同 dtb 支持不同板子。
「compatible 随便写」它是驱动与 dts 之间的契约，必须逐字符一致，且应按 vendor,device 规范命名。
「主设备号越大越高级」纯编号，12 位上限（0–4095），与能力无关。
「字符设备不能有缓存」可以自己实现缓冲，只是内核不替你做。
「/sys 和 /proc 是一回事」sysfs 是结构化的设备模型树；proc 是进程与内核参数的投影，两者用途不同。
「驱动里写死 GPIO 号没关系」违反设备树设计意图：换板子就要重编内核，且无法一内核多板。

8. 自检：能答出来才算懂

1

dev_t 里 major 和 minor 各多少位？各能表示多少？

看答案

major 12 位（0–4095），minor 20 位（0–1048575）。内核用 MKDEV/MAJOR/MINOR 三个宏做编解码。

2

open("/dev/led") 时，内核靠什么找到你的驱动？

看答案

靠 inode 里的 i_rdev（主次设备号），按主设备号在 cdev 映射里找到你注册的 cdev，再取它绑定的 file_operations，调用其中的 open。

3

cdev_add 漏了会怎样？device_create 漏了会怎样？

看答案

漏 cdev_add：设备号没有映射，open 直接 ENODEV，功能完全不可用。漏 device_create：内核功能其实是通的，但 devtmpfs 不会自动建节点，用户得手动 mknod。

4

为什么网络设备没有 /dev 节点？

看答案

因为网络的数据模型是「一次性数据包」，不支持定位与重读，塞进 read/write 的字节流模型很别扭。内核用 socket 接口 + 独立的 net_device 结构管理它。

5

块设备与字符设备的核心差别是什么？

看答案

块设备按固定块访问，读写要过页缓存与 IO 调度器；字符设备是字节流，通常直接操作硬件，没有内核代管的缓存与调度。

6

-EPROBE_DEFER 是干什么的？返回值是多少？

看答案

表示「我依赖的资源还没准备好」，请内核稍后重试。数值是 -517。内核会把它放进延迟探测队列，等新驱动注册时统一重试。

7

probe 里为什么必须保证「可重入 / 失败可回滚」？

看答案

因为它可能被调用多次（延迟重试、热插拔、重载）。若失败时留下半成品资源（申请了中断却没释放），下次重试就会冲突或泄漏。用 devm_* 系列可自动回收。

8

设备树到底改变了什么、没改变什么？

看答案

改变了「硬件描述从 C 代码变成 dts 数据」；没改变「驱动匹配与 probe 的机制」——内核仍是解析出 platform_device，再走同一套 bus->match。

9

怎么快速判断「设备存在但驱动没工作」？

看答案

看 ls /sys/bus/platform/drivers/<驱动名>/：有设备符号链接说明匹配成功；同时看 dmesg 是否有 probe 相关报错；再看 /sys/kernel/debug/devices_deferred 是否列着它。

10

一个内核能支持两块不同的板子吗？靠什么？

看答案

能。内核不编译板级信息，只编译驱动；板子的硬件差异全在各自的 dtb 里，启动时由 U-Boot 选对应 dtb 传给内核即可。

9. 这一章要动手的命令

  1. cat /proc/devices —— 列出所有已注册的字符/块设备主设备号，找你自己驱动的号。
  2. ls -l /dev | head -30 —— 看设备节点的类型（c/b）与主次设备号。
  3. mknod /tmp/t c 1 3 && head -c 10 /tmp/t —— 亲手造一个指向 /dev/null 的节点，验证「节点只是设备号入口」。
  4. ls /sys/bus/platform/drivers/ 再进去看某个驱动目录 —— 有符号链接就是匹配到了设备。
  5. cat /sys/kernel/debug/devices_deferred —— 看哪些设备卡在延迟探测。
  6. ls /proc/device-tree/ 与 cat /proc/device-tree/model —— 看内核运行时实际拿到的设备树。
  7. udevadm info -a -n /dev/mmcblk0 —— 看一个真实设备的完整属性链（从 class 到 devices 到 bus）。
