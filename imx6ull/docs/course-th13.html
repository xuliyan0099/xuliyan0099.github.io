卷 07·芯片与硬件底座·07.10

最小系统必需外设（下）：存储、DMA、以太网、USB

上一章讲的是「让 CPU 能跑、能说话、会数时间」的外设。这一章讲存得住、搬得动、连得上的那一类：SD/eMMC/NAND 三种存储、DMA 引擎、以太网、USB。它们的共同特点是都有自己的协议与状态机，不像 GPIO 那样寄存器一写就到。

★ 一读 纯读约 5 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① SD 卡、eMMC、NAND 到底该选哪个；② NAND 为什么必须有 ECC，坏块怎么标记；③ DMA 到底是 CPU 的帮手还是新的麻烦；④ 网口不通时先查 PHY 还是先查 MAC；⑤ USB 为什么同一根线既当主又当从。

读完你应该能回答

  • eMMC 与 NAND 在 Linux 里为什么是两套完全不同的驱动？
  • 一页 2KB + 64B OOB 的 NAND，ECC 怎么放、坏块标记放哪？
  • DMA 传完数据后为什么要和 cache 打交道，操作方向搞反会怎样？
  • RMII 与 MII 的区别是什么，50MHz 参考时钟谁给？
  • OTG 口在设备树里怎么写才能既当主又当从？

1. 三种存储：SD、eMMC、NAND

三者都能「存住代码和数据」，但在 Linux 眼里是完全不同的三条路径：

SD / microSDeMMCNAND（裸片）
控制器uSDHC1 0x0219_0000同一控制器，MMC 模式GPMI 0x0180_0000 + BCH
接口4 线 DAT + CMD + CLK8 线 DAT，可选 HS200/HS4008/16 位并行 IO，ALE/CLE/WE/RE
有内部控制器吗有，卡内自带有，芯片内有 FTL没有，全靠 SoC 管
坏块管理卡自己管芯片自己管软件必须管
Linux 子系统MMC 子系统MMC 子系统MTD 子系统
能不能直接执行代码不能，要走文件系统不能不能，NOR 才可以 XIP
为什么 eMMC 比裸 NAND 好写驱动 eMMC 芯片内部自带闪存转换层（FTL），对外表现得像一块「按块读写的硬盘」，你只要发 CMD17/CMD18 这类标准命令。裸 NAND 则要你自己处理页编程、块擦除、ECC、坏块表、磨损均衡——所以它走 MTD 而不是块设备。

1.1 uSDHC 初始化的关键步骤

  1. 给 uSDHC 供时钟（CCGR 里打开，频率通常 198MHz 或 52MHz 分档）。
  2. 配 IOMUXC：CLK、CMD、DAT0–DAT3（或 DAT0–DAT7）全部切到 uSDHC 功能，DAT 线上拉。
  3. 写 SYSCTL 的 SDCLKFS 与 DVS 得到卡时钟：识别阶段必须 ≤ 400kHz。
  4. 发 CMD0 复位 → CMD8 查电压 → ACMD41 等卡退出 idle → CMD2 取 CID → CMD3 取 RCA。
  5. 切高速时钟（25/50MHz），CMD7 选中卡，ACMD6 设 4 位总线。
  6. Linux 下这些由 MMC 子系统自动完成，设备树里只要写对总线宽度与 no-1-8-v 等属性。
「卡不识别」九成是这三件事 ① 时钟没开或分频错；② IOMUXC 没配或上拉没开；③ 1.8V/3.3V 电平切换配错。用示波器看 CLK 有没有波形，是最快判据。

2. NAND 与 ECC：为什么它这么难伺候

NAND 的物理特性决定了它必须「按页读写、按块擦除」，而且写入会出错。所以每写一页，硬件都要算一份校验码一起存进去，读的时候再校验——这就是 ECC。

一页 NAND 的典型布局（2KB 页 + 64B 备用区）：

区域大小放什么
主数据区2048 B真正的数据（文件系统块或内核镜像）
OOB 备用区64 BECC 校验码 + 坏块标记 + 文件系统元数据
算一笔：BCH40 的 ECC 要占多少 OOB
BCH40 表示「每 512 字节数据能纠正 40 bit 错误」
2048 B = 4 个 512B 扇区，每扇区 40 bit ≈ 5 字节，按 7 字节对齐
ECC 总量 ≈ 4 × 7 = 28 字节，加坏块标记 2 字节与文件系统标记，64B OOB 够用
若选 BCH8（每 512B 纠 8 bit），ECC 约 8 字节，余量大但纠错力弱
坏块标记的位置是约定俗成的 厂商约定：块内第一页的 OOB 第一个字节（或前两个字节）非 0xFF 即坏块。所以 OOB 布局不能随便改，改了以后坏块表读不出来，量产时会「莫名其妙丢数据」。

3. DMA：把「搬数据」从 CPU 手里拿走

i.MX6ULL 里的 DMA 引擎叫 SDMA（Smart DMA，基址 0x0209_0000），它本质是一个独立的小处理器：你给它一串「脚本」（channel control block），它按脚本自己搬运数据，完成后发中断。NAND 另有 APBH-DMA 专门配合 GPMI 用。

三种传数据方式的成本完全不同：

方式CPU 占用适用场景
CPU 逐字节拷贝100% 全程占用几十字节以内的小数据
CPU 循环读 FIFO与数据量成正比几百字节，无 DMA 可用时
DMA 搬运只剩配置与中断开销音频流、网络包、SD 大块读写

3.1 DMA 与 cache 的冲突（这一段最重要）

CPU 有 cache，DMA 没有。这导致两个方向的问题，方向搞反就是「数据凭空丢失」：

// 方向 1：CPU 写 → DMA 读（发送方向） CPU 写完 buf，数据可能还在 cache 里没进内存 必须先 clean（把 cache 刷回内存），DMA 才能读到正确内容 漏了 → DMA 读到旧数据 // 方向 2：DMA 写 → CPU 读（接收方向） DMA 把数据写进内存，但 cache 里可能还留着旧副本 必须先 invalidate（作废 cache 行），CPU 才能看到新数据 漏了 → CPU 读到旧数据 // 关键约束：操作粒度是 cache line（ARM Cortex-A7 为 64 字节） 若 buf 与相邻变量共享一个 cache line，invalidate 会顺手把邻居的脏数据作废

工程上三条保命规则：

  1. DMA 缓冲区用 dma_alloc_coherent() 分配，它返回的是一致性内存（通常不开 cache），省掉全部手工同步。
  2. 若必须用普通内存，缓冲区大小取 cache line 整数倍，且地址对齐。
  3. 同步函数成对使用：dma_map_single() 之后一定 dma_unmap_single()，否则平台代码里的同步不会执行。

4. 以太网：MAC 与 PHY 的分工

一个网口是两颗芯片：SoC 内的 MAC（ENET1 基址 0x0218_8000）负责组帧、CRC、DMA 收发描述符；板上的 PHY（如 KSZ8081）负责电气层：编码、自协商、双绞线驱动。

应用→TCP/IP→MAC 组帧→RMII/MII→PHY→网线

两者靠两组信号连起来：

接口线数特点
MII约 16 根收发数据各 4 位，需要 25MHz 时钟，引脚多
RMII约 9 根收发各 2 位，需要 50MHz 参考时钟，省引脚，板上最常用
MDIO/MDC2 根管理通道，读 PHY 内部寄存器（自协商状态、链路速率）
算一笔：RMII 为什么必须是 50MHz
RMII 每根数据线 2 bit，两个方向共 4 bit 并行
100Mbps 需要每秒传 100M bit，2 bit 一组 → 需要 50M 组/秒
所以参考时钟 = 50MHz，由 SoC 输出或 PHY 晶振提供，二者只能有一个给
若时钟给成 25MHz，链路会「自协商成功但收发包全错」

网口不通时的排查顺序（照这个走，别乱猜）：

  1. 先看 PHY 的复位与供电，量 50MHz 时钟有没有。
  2. ethtool eth0 看 Link detected 与速率：有 Link 说明 PHY 与对端协商成功，问题在 MAC 以上。
  3. ethtool -S eth0 看 rx/tx 错误计数，能区分是物理层噪声还是驱动丢包。
  4. ip link 看接口是否 up、MAC 地址是否读到（MAC 地址读不到说明设备树里没配 mac-address 或 OTP 未烧）。
  5. 最后才怀疑 TCP/IP 配置——物理层没通，上层怎么配都没用。

5. USB：主从结构决定了驱动怎么写

USB 是严格的主从总线：一条总线上只能有一个 Host，所有通信都由 Host 发起。i.MX6ULL 的 USB 控制器是 Chipidea 的 OTG 控制器，一根 USB 线可以扮演两种角色：

角色谁发起通信Linux 里的驱动框架典型场景
Host（主）板子USB Host 子系统 + 各类 class 驱动插 U 盘、键盘、4G 模块
Device / Gadget（从）PCGadget 框架 + function（如 mass_storage、rndis）板子当 U 盘、当网卡给 PC 用

角色由 OTG 的 ID 引脚决定：ID 接地 → Host；ID 悬空 → Device。设备树里用 dr_mode 属性覆盖这个自动判断：

usbotg1: usb@2184000 { dr_mode = "otg"; // "host" / "peripheral" / "otg" 三选一 vbus-supply = <®_usb_otg1_vbus>; // Host 模式才需要供电 };

USB 枚举的四个步骤（Host 视角）：

  1. 总线复位：D+/D− 拉低一段时间，让设备回到默认状态（地址 0）。
  2. 分配地址：SET_ADDRESS，之后设备只响应新地址。
  3. 读描述符：先读 8 字节设备描述符拿 bMaxPacketSize0，再读完整描述符、配置描述符、接口与端点描述符。
  4. 选择配置：SET_CONFIGURATION，设备进入工作状态，驱动开始绑定接口。
Host 模式不供 VBUS 是最常见的「插 U 盘没反应」 很多开发板的 OTG 口 VBUS 由一颗 MOSFET 控制，需要设备树里配 vbus-supply 并在驱动里拉高。只配 dr_mode 不配供电，设备根本没上电。

6. 其余常用外设速览

下面这些不属于「最小系统」，但几乎每个项目都会用到。它们的坑高度相似：协议简单、时序细节多。

外设关键点最常见故障
I2C开漏 + 上拉电阻、7 位地址、时钟延展上拉没焊/阻值过大，总线拉不高；地址写错（7 位左移一位）
SPICPOL/CPHA 四种模式、CS 有效电平、时钟频率模式配错读回全 0xFF 或全 0x00
PWM周期与占空比两个寄存器、时钟源分频输出频率算错，占空比 100% 时引脚恒定不翻转
ADC参考电压、采样时间、通道选择参考电压没接或接错，读数整体偏移
看门狗见 T11，使能后通常不可关闭调试时反复复位，误以为程序跑飞
LCD / eLCDIF像素时钟、时序参数（HSW/HBP/HFP）、帧缓冲地址像素时钟算错导致图像偏移或花屏
一条通用规律 凡是「总线型」外设（I2C、SPI、SD、USB），故障首先怀疑电气与时钟；凡是「寄存器型」外设（GPIO、PWM、定时器），故障首先怀疑复用与门控。按这个顺序查，命中率很高。

7. 常见误解

误解真相
「NAND 和 eMMC 都是 flash，驱动可以复用」eMMC 有内部 FTL，走 MMC 子系统；裸 NAND 走 MTD，两套完全不同的框架。
「NAND 不用 ECC 也能读写」短时间可能「看起来正常」，但出厂就有坏位，长时间使用必然丢数据，几乎没有例外。
「坏块标记放哪都行」位置是厂商与文件系统共同约定，改了坏块表就读不出来。
「DMA 一定比 CPU 拷贝快」小数据量下 DMA 的配置与中断开销更大，几十字节用 DMA 反而更慢。
「DMA 缓冲区直接 malloc 就行」普通内存开 cache，必须手工 clean/invalidate，否则数据错乱；推荐 dma_alloc_coherent。
「网口不通先查 IP 配置」先看 Link 与 50MHz 时钟，物理层没通，上层怎么配都白搭。
「RMII 与 MII 可以随便换」引脚数与参考时钟频率都不同，混接必然不通。
「USB 插上就能识别」Host 模式必须供 VBUS，OTG 的 ID 引脚与 dr_mode 也要匹配。

8. 自检：能答出来才算懂

1

eMMC 与裸 NAND 在 Linux 里分别走哪个子系统，为什么？

看答案

eMMC 走 MMC 子系统（内部有 FTL，对外像块设备）；裸 NAND 走 MTD（需要软件管坏块、ECC、磨损均衡）。

2

2KB 页 + 64B OOB、BCH40，ECC 大约占多少字节？

看答案

4 个 512B 扇区，每扇区约 7 字节 → 约 28 字节，加坏块与文件系统标记，64B 够用。

3

识别 SD 卡时为什么要先把时钟降到 400kHz 以下？

看答案

协议规定初始化阶段必须低速，保证各种电压/时序的卡都能可靠通信；识别完成后再切高速。

4

DMA 发送方向（CPU 写、DMA 读）该做 clean 还是 invalidate？

看答案

clean：把 cache 里的新数据刷回内存，让 DMA 读到正确内容。接收方向才是 invalidate。

5

ARM Cortex-A7 的 cache line 是多少字节，为什么这个数字重要？

看答案

64 字节。cache 维护按整行操作，缓冲区若不是整行对齐，一次 invalidate 会把邻居的脏数据一起丢掉。

6

RMII 需要多少 MHz 参考时钟，为什么？

看答案

50MHz。RMII 每方向 2 bit 并行，100Mbps 需要每秒 50M 组，故 50MHz。

7

USB 枚举的四个步骤是什么？

看答案

总线复位 → SET_ADDRESS 分配地址 → 读设备/配置/接口/端点描述符 → SET_CONFIGURATION。

8

插 U 盘不识别，除了 dr_mode 还要检查什么？

看答案

VBUS 供电（vbus-supply 与 MOSFET 控制），以及 OTG 的 ID 引脚电平。

9. 这一章要动手的命令

  1. ls /sys/class/mmc_host/ 与 cat /sys/block/mmcblk0/size —— 确认卡被识别与容量。
  2. cat /proc/mtd —— 看 MTD 分区表（裸 NAND/NOR 才有）。
  3. dmesg | grep -i -E "mmc|nand|mtd|dma" —— 看存储与 DMA 初始化日志。
  4. ethtool eth0 —— 看链路状态、速率、双工。
  5. ethtool -S eth0 —— 看收发错误计数，区分物理层与协议层问题。
  6. lsusb 与 ls /sys/bus/usb/devices/ —— 确认 Host 模式枚举到设备。
  7. cat /sys/kernel/debug/dma/ 或 dmesg | grep -i sdma —— 看 DMA 通道占用情况。
