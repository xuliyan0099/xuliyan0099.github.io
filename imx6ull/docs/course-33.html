同步

counter++ 看起来是一条语句，实际是「读、加、写」三步。两个核同时做，结果少加一次。这个「丢失更新」是并发 bug 的祖型。这一课从硬件的原子指令讲起，一路到自旋锁、互斥量、优先级反转与死锁——这些东西不是软件发明的，是硬件只提供了有限原语。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

1. 丢失更新：一步步看

# 两个核，counter 初始 0，各执行 counter++

时刻 核A                核B                counter
 t1 读 counter = 0                         0
 t2                     读 counter = 0     0
 t3 写回 0+1 = 1                           1
 t4                     写回 0+1 = 1       1   ← 只加了 1 次

# 期望 2，实际 1。这就是「丢失更新」

解决办法不是「小心点」，而是让「读-改-写」成为一个不可分割的整体。而软件做不到这件事，必须硬件支持。

2. 从原子指令到锁

硬件只给一个原语：ldrex/strex（或 x86 的 lock cmpxchg）。在此之上，软件可以构造出：

  • 原子计数：atomic_inc，循环重试 ldrex/strex。
  • 自旋锁：用一个整数的 0/1 表示锁，抢不到就循环重试。
  • 互斥量：抢不到就睡眠排队（要内核调度参与）。

3. 优先级反转：一个真实事故

1970 年代火星探路者就栽在这上面。三段场景：

  1. 低优先级任务 L 拿着锁。
  2. 高优先级任务 H 要这把锁，被阻塞。
  3. 中优先级任务 M 就绪，抢走了 L 的 CPU（因为 M 比 L 高）。
  4. 于是 H 在等 L，L 在等 M，而 M 在跑——H 的优先级被「反转」成了最低。

解法：优先级继承——L 持有锁期间临时提升到 H 的优先级，让它尽快跑完释放。rt_mutex 就实现了这个。另一条解法是优先级天花板。

5. 内存序：比锁更隐蔽的一层

即使每个变量都加了锁，编译器与 CPU 仍可能重排指令。所以内核有屏障：

原语作用典型场景
barrier()编译器屏障，只防编译器重排循环里防止被优化掉
smp_mb()CPU 全屏障多核共享数据
smp_wmb() / rmb()写/读屏障生产者-消费者
readl() / writel()含设备 IO 屏障外设寄存器

「屏障」不是「同步」，它只保证顺序，不保证互斥。两者必须配合使用。

6. 实验：亲眼看到数据竞争

// 造一个必然出错的程序
#include <pthread.h>
int counter = 0;
void *worker(void *a) {
    for (int i = 0; i < 1000000; i++) counter++;
    return 0;
}
int main(void) {
    pthread_t t[4];
    for (int i = 0; i < 4; i++) pthread_create(&t[i], 0, worker, 0);
    for (int i = 0; i < 4; i++) pthread_join(t[i], 0);
    printf("expect 4000000, got %d\n", counter);
}

// 编译：gcc -O2 -pthread race.c
// 输出往往小于 4000000
// 加上 -fsanitize=thread 会直接报 data race

// 修法一：原子
//   __atomic_add_fetch(&counter, 1, __ATOMIC_RELAXED)
// 修法二：互斥量
//   pthread_mutex_lock/unlock

加上 -fsanitize=thread（TSan）后再跑，你会看到精确的「哪个线程读了哪个地址、与谁冲突」。这是排查并发 bug 最有效的工具。

7. 三条常见误解

8. 自测与动手

1

为什么 counter++ 不是原子的？

看答案

它是「load → add → store」三条指令，中间可被打断或插入另一个核的操作。

2

ldrex/strex 的「监视器」机制解决什么问题？

看答案

保证「读之后没人改过」才允许写，从而让读-改-写整体不可分割。

3

中断上下文里为什么只能用自旋锁？

看答案

互斥量会睡眠，而中断上下文不能睡眠。

4

优先级反转怎么破？

看答案

优先级继承（持锁者临时提升）或优先级天花板协议。

5

死锁四条件里，工程上最容易破坏哪个？

看答案

循环等待：统一加锁顺序；其次是持有并等待：一次性申请全部。

  1. 跑数据竞争程序，对比有/无原子操作的结果。
  2. 加 -fsanitize=thread 复现并读 TSan 的报告。
  3. 写一个必然死锁的程序（两把锁反序），用 gdb 看两个线程卡在哪。
  4. 在驱动里用 spin_lock_irqsave，说明为什么要保存中断状态。
