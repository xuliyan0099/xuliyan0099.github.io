卷 11·调试与可观测·第 02 篇

调试与排障工具箱

嵌入式开发 70% 的时间在查问题。工具不多，但要熟到形成条件反射：先看日志、再看状态、最后才动代码。

★ 一读 纯读约 8 小时 左侧是本卷目录 理论为主 · 实作可跳

本章目标

① 会用串口日志 + dmesg 定位内核与驱动问题；② 用 strace 看清程序卡在哪个系统调用；③ 用 core dump + addr2line 定位段错误行号；④ 会用 ftrace 粗看内核函数调用；⑤ 有一张自己的报错速查表。

13.1 排障的正确顺序

① 现象到底哪里不对
不亮？没输出？重启？
→
② 日志串口 / dmesg / journalctl
→
③ 状态/proc /sys / lsmod
→
④ 定位strace / gdb / 反汇编
→
⑤ 验证改一处，重测

新手最大的毛病是直接跳到第 ⑤ 步：猜一个原因就改代码，改完还是不行，再猜下一个。正确做法是让日志告诉你原因，改之前先确认假设。

13.2 内核日志：dmesg 与 printk 级别

$ dmesg | tail -50
$ dmesg -w                     # 实时跟随（插拔设备时用）
$ dmesg | grep -i -E "error|fail|denied"
$ dmesg -T | tail -20         # 带人类可读时间戳
$ cat /proc/sys/kernel/printk  # 当前控制台日志级别
级别宏用途
0KERN_EMERG系统要挂了
3KERN_ERR错误，必看
4KERN_WARNING警告
6KERN_INFO普通信息（默认常被过滤）
7KERN_DEBUG调试
 
# 让所有级别都打到串口（调试期）
# echo 8 > /proc/sys/kernel/printk
# 或改 bootargs 加 loglevel=7
驱动打印看不到？ 多半是 printk(KERN_INFO ...) 被默认级别 4 过滤了。临时 echo 8 > /proc/sys/kernel/printk 就能看到；或直接用 pr_err()/dev_err()。

13.3 运行时状态：/proc 和 /sys

$ cat /proc/cpuinfo | grep -E "model|Processor"
$ cat /proc/meminfo | head -3
$ cat /proc/interrupts          # 中断有没有触发
$ cat /proc/devices             # 已注册的主设备号
$ cat /proc/modules             # 已加载模块
$ cat /proc/device-tree/model

$ ls /sys/class/leds/           # LED 设备
$ ls /sys/class/gpio/           # GPIO 导出
$ cat /sys/class/net/eth0/address
$ ls /sys/bus/platform/drivers/ # 平台驱动与已绑定设备
判断驱动有没有 probe 成功 ls /sys/bus/platform/drivers/你的驱动名/，里面出现设备名 = 绑定成功。只 lsmod 看到模块在，不代表 probe 跑了。

13.4 strace：程序卡在哪

程序「跑着没反应」「打开文件失败但没报错」，用 strace 看它到底调了哪些系统调用、在哪一步返回错误。

$ strace ./app
$ strace -f ./app              # 跟子进程
$ strace -e trace=open,read,write ./app
$ strace -p 1234               # 附到运行中的进程
$ strace -c ./app              # 统计各系统调用耗时

典型输出：open("/dev/myled", O_RDWR) = -1 ENOENT —— 一眼看出设备节点不存在，比猜半小时快。

13.5 段错误：从崩溃到代码行

# 1. 编带符号的程序
$ arm-linux-gnueabihf-gcc -g -O0 app.c -o app

# 2. 板子上开启 core dump
# ulimit -c unlimited
# ./app
Segmentation fault (core dumped)

# 3. PC 上用 gdb 打开 core
$ gdb-multiarch app core
(gdb) bt                  # 看调用栈，定位到函数与行号
(gdb) info registers
(gdb) x/8i $pc            # 看崩溃处的指令

# 没有 core 时：用 addr2line 把地址翻译成行号
$ arm-linux-gnueabihf-addr2line -e app -f 0x000104f0
$ arm-linux-gnueabihf-objdump -d app | less   # 反汇编
段错误三大来源 ① 空指针/野指针解引用 ② 数组越界写到只读段 ③ 栈溢出（大数组放局部变量）。先看 bt 的最上面那一帧，别从 main 开始读。

13.6 ftrace：内核里发生了什么

怀疑某驱动没被调用、中断没进、调度延迟，用 ftrace 看内核函数调用，不需要重新编译内核。

# cd /sys/kernel/debug/tracing
# echo function > current_tracer
# echo gpio_set_value > set_ftrace_filter
# echo 1 > tracing_on
# …执行你的操作…
# echo 0 > tracing_on
# cat trace | head -30

没有 /sys/kernel/debug？先 mount -t debugfs none /sys/kernel/debug，并确认内核配置里开了 CONFIG_FUNCTION_TRACER。

13.7 报错速查表

现象 / 报错方向
Permission denied权限位、属主、dialout 组、只读文件系统
No such file or directory（文件明明在）动态链接器缺失、架构不对（用 file 查）
Text file busy程序正在运行，不能覆盖写
cannot execute binary fileABI 不匹配（x86 程序拿到 ARM 上跑）
insmod: invalid module format.ko 与内核版本/配置不一致，必须用同一份内核源码编
Unknown symbol in module依赖的符号没导出，检查 Module.symvers 与依赖模块
驱动加载但无反应compatible 不匹配、probe 未执行、GPIO 被占用、pinctrl 没配
Kernel panic - not syncing根文件系统挂不上 / init 缺失 / 内存越界
NFS 挂载超时IP 网段、exports 权限、防火墙、nfsvers

13.8 动手任务

  • 写一个故意空指针解引用的程序，编译运行，拿到 core，用 gdb 的 bt 定位到行号。
  • 写一个打开不存在文件的程序，用 strace 找到 ENOENT 那一行。
  • 用 strace -c 统计一个程序最耗时的系统调用。
  • 驱动里加一条 printk(KERN_INFO)，先看不到，echo 8 > /proc/sys/kernel/printk 后再看到。
  • 用 ls /sys/bus/platform/drivers/ 确认你的驱动是否绑定成功。
  • 用 ftrace 跟踪一次 gpio_set_value，确认应用写 /dev 时内核里确实被调用。

13.9 验收标准

  • 遇到问题第一反应是看日志，而不是改代码
  • 能用 dmesg + printk 级别解决「驱动没打印」
  • 能用 strace 定位「程序卡住/文件打不开」
  • 能用 core + gdb bt 定位段错误到具体行
  • 能判断驱动是否 probe 成功（不是只看 lsmod）
  • 手上有一份自己的报错速查表，遇到新问题会往里加
