页表与 MMU

虚拟地址能翻译成物理地址，靠的是一张表。这张表不仅记「映射到哪」，还记「能不能写、能不能执行、有没有被改过」。所以 MMU 不只是翻译器，它是整个系统的权限闸门——SIGSEGV、只读段保护、W^X 安全策略，全在这张表的几个比特里。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 页表项里有什么？② 为什么要分级页表？③ 段映射解决什么？④ 改页权限为什么要刷 TLB？⑤ ASID 解决了什么？

1. 两级页表：为什么要分级

平表需要 4GB / 4KB = 100 万项，每项 4 字节 = 4MB——每个进程光页表就 4MB，不可接受。分级的好处是未使用的区域可以不建表：只用几十 MB 的进程，页表可能只有几十 KB。

2. 段映射：少查一级

ARM 支持「段」（1MB）映射：一级页表项直接给 1MB 物理基址，省掉二级查表。内核里给 DDR 做线性映射时就用段，好处是 TLB 只需缓存一级，翻译更快。

代价是粒度粗：1MB 内无法单独设权限。所以「代码段只读」这类保护要用 4KB 页。

3. 改权限为什么要刷 TLB

// 典型场景：修改自身代码（JIT、动态补丁）
// 1) 代码页本来是「只读可执行」
// 2) 想改：先改成「可写不可执行」
// 3) 写入新指令
// 4) 改回「只读可执行」
// 5) 必须刷 TLB，因为 TLB 里还存着旧的权限！

所以内核提供 flush_tlb_range() / flush_icache_range()。忘记刷就会遇到「我明明改了页表，为什么还是 SIGSEGV」——这在写自修改代码、热补丁、内核模块加载时非常常见。

4. ASID：为什么切换进程不必全刷 TLB

没有 ASID 时，切换进程必须把整个 TLB 清空（因为不同进程的同名虚拟地址指向不同物理页）。有了 ASID（Address Space ID），每个 TLB 项带上「属于哪个地址空间」的标记，不同进程的项可以共存。

无 ASID有 ASID
切换时全表 flush只写新 ASID 寄存器
切换后开销大量 TLB 未命中旧项仍有效，命中率高
典型代价几十~几百周期几个周期

这条优化让「上下文切换」从「昂贵到难以承受」变成「可接受」。第 32 课会再回来看它的具体实现。

5. 实验：看到页表

# 用户态：看映射与权限
cat /proc/self/maps
# 每行末尾的 r-xp / rw-p / r--p 就是页权限

# 看某个地址是否已映射到物理页（需 root）
# 读 /proc/self/pagemap 的 64 位项，低 55 位是物理页帧号

# 内核里：
cat /proc/vmallocinfo
cat /sys/kernel/debug/kernel_page_tables   # 部分平台提供

# 崩溃时的典型输出：
#   Segmentation fault (core dumped)   ← 有效位=0 或权限不符

/proc/self/maps 是理解「进程地址空间」最快的一扇窗。把它的每一行与第 19 课的段布局对照，你会发现完全一致。

6. 三条常见误解

7. 自测与动手

1

为什么平表不可行？

看答案

4GB/4KB = 100 万项 × 4 字节 = 4MB/进程，几十个进程就吃光内存；且大部分地址根本没用到。

2

段映射的粒度与优缺点？

看答案

1MB，少一级查表、TLB 更省；但无法在 1MB 内细分权限。

3

改代码页权限后忘了刷 TLB 会怎样？

看答案

CPU 仍用旧的 TLB 项（旧权限），可能出现「明明可写却 SIGSEGV」或「明明只读却能写」。

4

ASID 解决什么问题？

看答案

让不同进程的 TLB 项共存，切换时不必全刷，大幅降低上下文切换成本。

5

XN 位有什么用？

看答案

标记「不可执行」，防止数据区被当作代码执行——这是抵御缓冲区溢出攻击的核心硬件机制（W^X）。

  1. 在 Ubuntu 上 cat /proc/self/maps，标出哪些段是 r-xp、哪些是 rw-p。
  2. 写一个程序往自己的 .text 写入，观察 SIGSEGV（说明只读生效）。
  3. 在驱动里改一处 PTE 的权限位，故意不刷 TLB，观察「改了却不生效」的现象。
  4. 查 A7 的 ASID 位宽（8 位还是 16 位），算一下最多能同时容纳多少地址空间。
