I2C 设备驱动

GPIO 是一个引脚管一件事，I2C 是两根线管一串设备——靠 7 位地址点名。这一课把「总线 → 控制器 → 设备 → 驱动」这条链拆开，讲清 i2c_client 是谁创建的、probe 里第一个寄存器该读什么、为什么老手都用 regmap、以及接上传感器后 i2cdetect 扫不到地址时该怎

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 地址 0x68 是谁分配的？② 为什么设备树里写 reg = <0x68> 就够了，不用写「怎么发开始位」？③ i2c_client 和 i2c_driver 谁先谁后？④ 为什么推荐 regmap？⑤ i2cdetect -y 1 扫不到设备时，先怀疑什么？

1. 直觉：一条只有两根线的「广播总线」

SCL 打拍子，SDA 传数据。主机先说「我要找 0x68」，然后读写。所有设备都听得到，但只有地址对上的那个应答。地址是芯片出厂定的（有的可由 ADDR 引脚改 2 档）。

类比失效处：广播这个比喻会让人以为「可以同时发」。实际是一条线一个时刻只能有一个主设备在驱动，两个主机同时发就是总线冲突，波形会糊掉——I2C 没有冲突检测，只能事后发现数据不对。

2. 硬件：上拉电阻不是可选项

I2C 是开漏输出，只能拉低不能拉高。总线空闲时靠两个上拉电阻（常见 4.7k）把线拉回高电平。没有上拉，波形永远起不来；上拉太小（如 1k）会增加功耗并让低电平拉不下去；线太长（>30cm）分布电容会把上升沿拖成斜坡，表现为「偶尔读到全 0xFF」。

3. 软件：设备树给「设备」，驱动给「行为」

&i2c1 {
    clock-frequency = <400000>;          /* 400kHz 快速模式 */
    status = "okay";

    myaccel: accel@1e {
        compatible = "demo,myaccel";
        reg = <0x1e>;                     /* 7 位地址，不写读写位 */
        interrupt-parent = <&gpio1>;
        interrupts = <9 IRQ_TYPE_EDGE_FALLING>;
    };
};
#include <linux/i2c.h>
#include <linux/regmap.h>

static const struct regmap_config cfg = {
    .reg_bits = 8, .val_bits = 8, .max_register = 0x7F,
};

static int my_probe(struct i2c_client *cli)
{
    struct regmap *map = devm_regmap_init_i2c(cli, &cfg);
    int id;
    if (IS_ERR(map)) return PTR_ERR(map);
    regmap_read(map, 0x0F, &id);          /* WHO_AM_I */
    dev_info(&cli->dev, "chip id = 0x%02x\n", id);
    return 0;
}

static const struct of_device_id my_of[] = {
    { .compatible = "demo,myaccel" }, { }
};
MODULE_DEVICE_TABLE(of, my_of);

static struct i2c_driver my_drv = {
    .driver = { .name = "myaccel", .of_match_table = my_of },
    .probe = my_probe,
    .id_table = NULL,
};
module_i2c_driver(my_drv);

顺序是：i2c 控制器先注册 → 解析设备树时创建 i2c_client（带地址）→ 驱动模块加载时用 compatible 匹配 → 匹配成功才调 probe。所以「驱动加载了但 probe 没跑」几乎总是 compatible 字符串不一致，不是地址错。

4. 三条误解

  • 「reg 要写 8 位地址」：设备树里 reg 是 7 位地址（0x1E），读写位由控制器自动加。写成 0x3C（8 位形式）会扫不到。
  • 「i2cdetect 扫不到就是驱动问题」：扫描发生在应用层，跟你的驱动无关。扫不到先查硬件：上拉电阻、供电、ADDR 引脚、地址是否被别的设备占用。
  • 「probe 里可以随便忙等」：probe 在进程上下文，可以 msleep；但如果你在中断上下文调 i2c 传输，必须用 i2c_transfer 的非睡眠版本或干脆挪到工作队列。

5. 五题自测

1

设备树里 reg = <0x1e> 和驱动里的 compatible 各决定什么？

看答案

reg 决定「跟哪个地址通信」，compatible 决定「由哪个驱动接管」。两者独立：地址对但 compatible 不匹配，probe 不会跑。

2

为什么读一个 8 位寄存器要两轮传输？

看答案

第一轮写「地址 + 寄存器号」，第二轮用重复 START 切到读模式取数据。芯片不会记住上一次的寄存器号，除非它支持 auto-increment 且你连续读。

3

i2cdetect -y 1 全是 --，可能原因按概率排序？

看答案

① 没上拉电阻或没供电 ② 总线号用错（i2c-1 未必是板上的 I2C1）③ 设备地址是 8 位写法 ④ SDA/SCL 接反 ⑤ 引脚没复用成 I2C 功能。

4

regmap_read 返回负值，通常是什么？

看答案

-ENXIO/--EREMOTEIO 表示设备没应答（NAK），多半是地址错或设备没上电；-ETIMEDOUT 是总线被拉死（某个设备把 SDA 拉低不放）。

5

设备树里 clock-frequency 改了 400k，为什么有的从设备反而不工作？

看答案

老器件只支持 100k；另外上拉电阻与线长在 400k 下更容易造成上升沿过慢。降回 100k 一试就知道。

6. 动手（40 分钟）

1. i2cdetect -l 列出总线，i2cdetect -y <n> 扫地址，把扫到的表贴出来。

2. 用 i2cget -y <n> 0x1e 0x0F 读 WHO_AM_I，和手册比对。

3. 写一个最小 i2c 驱动，probe 里打印芯片 ID，确认 dmesg 里出现你那一行。

4. 故意把设备树 compatible 改错一个字母，重新启动，确认「驱动在、probe 不在」——这是最常见的一种静默失败。
