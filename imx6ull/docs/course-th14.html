卷 03·存储与地址·第 09 篇

内存管理进阶：分页、回收与 OOM

T03 讲清了「为什么要有页表」。这一章往下钻一层：一次访存失败之后，内核到底做了哪 12 件事；物理页怎么按「伙伴」凑块；内存不够时谁先被杀。看得懂这一章，你就能回答嵌入式面试里 80% 的内存问题。

◆ 一读 纯读约 5 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 一个虚拟地址到物理地址，中间究竟经过几次查表、谁会失败；② malloc 返回成功但第一次写就崩，为什么；③ 内核怎么知道哪块内存该回收；④ OOM killer 凭什么选中某个进程；⑤ kmalloc 与 vmalloc 到底差在哪。

读完你应该能回答

  • ARMv7 的 L1 段描述符与 L2 页描述符，各是哪几位决定属性？
  • 缺页中断由谁接手，要走哪几步才能回到用户态继续执行？
  • 伙伴系统的 order 是什么，为什么它能防外部碎片？
  • 水位 watermark 的 min/low/high 三级分别触发什么行为？
  • OOM 分数 oom_score 由什么构成，怎么保护关键进程？

1. 为什么必须分页

不分页的世界是这样的：进程 A 认为自己从 0 地址开始，进程 B 也认为自己从 0 地址开始，两个 0 指向同一块物理内存，立刻互相覆盖。分页解决的就是这个矛盾：每个进程一套独立的虚拟地址空间，由页表翻译到各自的物理页。

分页带来的四个能力，每一个都不可替代：

  • 隔离：进程 A 写不到 B 的内存，因为页表里根本没映射。
  • 按需分配：申请 1MB 不必立刻给 1MB 物理页，第一次写才给。
  • 可换出：不常用的页可以写到磁盘/swap，腾出物理内存。
  • 共享：多个进程的同一虚拟页可以指向同一物理页（如 libc 的代码段）。
代价也要说清 每次访存多一次（或两次）内存访问来查页表，所以必须有 TLB 缓存；页表本身也要占内存（1GB 空间用 4KB 页要 1MB 页表）。分页不是免费的，是用「硬件复杂度 + 内存开销」换「隔离 + 灵活性」。

2. 一次地址翻译的全过程

ARMv7（Cortex-A7）用两级页表：

虚拟地址→TTBR0/TTBR1 选基址→L1 表（16KB 对齐）→L2 表（1KB 对齐）→物理地址

32 位虚拟地址被切成三段，位段划分决定了表的大小：

位段位宽含多少项作用
[31:20]12 位4096 项L1 索引（每项 4 字节 → 表 16KB）
[19:12]8 位256 项L2 索引（每项 4 字节 → 表 1KB）
[11:0]12 位4096 字节页内偏移，不参与翻译

两级描述符里，属性位藏在固定位置。这是必须背下来的：

位字段含义
[1:0]类型0b10 = 段/页描述符，0b00 = 无效，0b01 = 粗页表
[11:10]AP访问权限：00 只内核、01 内核读写/用户读、11 全可读写
[3]C可 cache（write-back）
[2]B可 buffer（write-through）
[0]（L2 的 bit0）XN禁止执行，置 1 则该页不可取指
[11]（L1 段）nG非全局，切换进程时刷新 TLB 项
算一笔：一次访存的开销
TLB 命中：查 TLB 约 1 个周期，直接得到物理地址
TLB 未命中：L1 查表 1 次内存访问 + L2 查表 1 次内存访问 = 多花 2 次内存访问
主存延迟按 100 周期算，未命中一次的成本 ≈ 200 周期
所以 TLB 覆盖率极其关键：4KB 页的 TLB 覆盖范围小，2MB 大页能把覆盖范围放大 512 倍

3. 用户空间与内核空间

32 位 Linux 把虚拟地址空间按 3:1 劈开：0x0000_0000–0xBFFF_FFFF 给用户，0xC000_0000–0xFFFF_FFFF 给内核。这条分界线由 TTBR0（用户页表基址）与 TTBR1（内核页表基址）两个寄存器实现——切换进程只改 TTBR0，内核映射不动。

区域典型内容谁有权访问
用户区低端代码段、数据段、堆（向上长）仅该进程
用户区高端栈（向下长）、mmap 区、共享库仅该进程
内核区直接映射区（物理内存线性映射）、vmalloc 区、内核栈仅内核态（用户态访问立刻异常）
// 一次「用户态访问内核地址」会发生什么 用户态执行 LDR r0, [0xC0000000] → MMU 查到该页 AP 位为「仅内核」 → 触发 Data Abort（权限错误） → 内核 do_page_fault 判定为非法访问 → 给进程发 SIGSEGV（段错误） → 进程被终止，dmesg 里打印 segfault 与出错地址

这就是为什么「段错误」几乎总是「指针指向了不该指的地方」，而不是「内存不够」。内存不够的表现是 malloc 返回 NULL 或 OOM 杀进程，不是 SIGSEGV。

4. 缺页：内存是「用的时候才给」

进程 malloc 1MB 时，内核只做两件事：在 VMA（虚拟内存区域）链表里加一条记录，返回一个虚拟地址。物理页一个都没给。真正给页是在第一次访问时——这就是缺页（page fault）。

缺页的完整路径（这是本章最该记住的一张流程图）：

CPU 访存失败→Data Abort 异常→保存现场，进内核→读 DFSR/DFAR 判断原因→查 VMA 是否合法→handle_mm_fault→分配页或读文件或换入→填页表→刷 TLB→返回用户态重试指令

三种缺页，处理方式完全不同：

类型触发场景内核动作成本
匿名页缺页第一次写 malloc 的内存从 buddy 取一页，清零，填入页表低（微秒级）
文件页缺页第一次读 mmap 的文件/可执行文件从页缓存取，没有则读磁盘可能很高（要等 IO）
写时复制（COW）fork 后子进程写共享页复制一页，改子进程页表指向新页中等
交换缺页访问已被换出的页从 swap 读回很高
算一笔：为什么 fork 很快，写却变慢
父进程 100MB，fork 后子进程页表全部指向同一批物理页（只读）
fork 本身成本：复制页表项，约 100MB/4KB = 25,600 项，几毫秒
子进程写其中 1MB：触发 256 次 COW 缺页，每次复制 4KB
结论：fork 的成本被推迟到「真正写」的时候，这就是 COW 的全部意义

5. 内存不够时：回收与 OOM

内核手里有一条水位线（watermark），它决定「什么时候开始着急」：

水位含义触发行为
high富余线kswapd 停止回收，恢复正常
low警戒线唤醒 kswapd 后台回收
min红线分配者自己同步回收（direct reclaim），进程被卡住

回收的优先级由 LRU 链表决定：内核把页分成 active 与 inactive 两条链，先在 inactive 尾部找「最近没被访问」的页。回收顺序是：

  1. 丢弃干净的文件页（有副本在磁盘上，直接扔，零成本）。
  2. 把脏文件页写回磁盘后再丢（有 IO 成本）。
  3. 把匿名页写到 swap 后再丢（有 IO 成本，且嵌入式常无 swap）。
  4. 以上都不够 → 触发 OOM killer。

OOM killer 选谁杀，靠 oom_score：

因素影响
占用内存（RSS + swap）越大分数越高，越容易被杀
oom_score_adj（-1000 ~ 1000）手工调节，-1000 表示永不杀
是否 root / 是否有 CAP_SYS_ADMIN有特权则分数下调
运行时间长短刚启动的进程更容易被选中
嵌入式设备的实用做法 把关键服务（如通信守护进程）的 oom_score_adj 设为 −1000，把可能吃内存的业务设为正数。这样内存耗尽时，被杀的是业务进程而不是系统守护进程。

6. 分配器：从整页到几字节

内核里有两层分配器，职责完全不同：

层分配单位解决的问题典型接口
伙伴系统（buddy）页（4KB）的 2 的幂大块物理内存管理、防外部碎片alloc_pages
SLUB / slab几十字节到几 KB小对象复用、防内部碎片kmalloc、kmem_cache_alloc

6.1 伙伴系统：order 是关键

物理页按 2^order 分组：order=0 是 1 页（4KB），order=1 是 2 页（8KB），order=10 是 1024 页（4MB）。分配时如果目标 order 没有空闲块，就从更高 order 切一半下来，另一半留在对应 order 的空闲链上——这就是「伙伴」的含义，合并时也只和这一半合并。

算一笔：要 8KB，但只有 32KB 的块
目标 order=1（8KB），当前最大空闲块 order=3（32KB）
32KB 切成 2 个 16KB → 一个给下级，一个留在 order=2
16KB 再切成 2 个 8KB → 一个返回给调用者，一个留在 order=1
释放时若 order=1 的伙伴也空闲 → 合并成 order=2，再逐级向上合并

cat /proc/buddyinfo 能看到每个 order 的空闲块数。这一行数字是判断「内存碎片严重程度」的最直接证据：如果 order 高的块几乎全为 0，说明虽然总空闲内存不少，但已经拿不出连续大块了。

6.2 SLUB：小对象怎么复用

内核里大量对象是几十字节的（如 task_struct 外的各种小结构）。若每次都给一整页，浪费惊人。SLUB 的做法是：从伙伴系统拿一页或多页，切成固定大小的槽位，同类对象共用。

算一笔：96 字节的对象一页能放几个
页 4096 B，对象 96 B → 4096 / 96 = 42.6
减去 slab 管理头（约 32B）→ (4096 − 32) / 96 = 42 个
利用率 42 × 96 / 4096 = 98.4%，几乎无浪费
若换成 100 字节对象：(4096−32)/100 = 40 个，浪费 64B，仍可接受

kmalloc 的尺寸不是任意值，内核只提供固定档位（8、16、32、64、96、128、192、256、512、1024…）。申请 100 字节实际拿到 128 字节的槽——所以 kmalloc 的实际占用总是比你要的多。

6.3 vmalloc 与 kmalloc 的区别

kmallocvmalloc
物理连续性要求连续不要求，靠页表拼出连续虚拟地址
大小上限受 order 限制，通常几 MB 就难可到几百 MB
性能快，无额外页表开销慢，要逐页建映射，且 TLB 压力大
可否给 DMA 用可以（物理连续）不可以（物理不连续）
典型用途驱动里的小缓冲、结构体模块加载区、超大缓冲
用户态的 malloc 是第三套东西 glibc 的 malloc 在用户空间自己管内存：小的用 brk 扩展堆并按块切分，大的（>128KB）直接用 mmap。它和内核的 slab 没有关系，只是最终都会落到「缺页 → 内核给页」这一步。

7. 常见误解

误解真相
「malloc 成功就有内存了」只是拿到了虚拟地址，物理页在第一次写时才给；这也是 Linux 允许 overcommit 的原因。
「内存不够会返回 NULL」用户态可能因 overcommit 拿到地址，随后被 OOM killer 杀掉；内核态则可能直接 panic 或触发 OOM。
「段错误就是内存不足」段错误是非法地址或权限错误，和内存余量无关。
「free 内存少就是内存泄漏」Linux 会把空闲内存拿去做页缓存，free 少是正常的；要看 available 与 slab 增长。
「伙伴系统只按页分配，不会有碎片」它能防外部碎片，但长期高低 order 混用后仍会出现「大块拿不出」。
「vmalloc 和 kmalloc 可以互换」vmalloc 物理不连续，不能给 DMA；性能也差一截。
「大页一定更快」大页省 TLB，但分配难、浪费大，小内存设备上反而更容易失败。
「OOM 杀的是占内存最多的」是综合 oom_score，包含 adj、特权、运行时长等因素。

8. 自检：能答出来才算懂

1

ARMv7 两级页表，32 位地址的 [31:20]、[19:12]、[11:0] 分别做什么？

看答案

[31:20] L1 索引（4096 项，表 16KB）；[19:12] L2 索引（256 项，表 1KB）；[11:0] 页内偏移，不参与翻译。

2

L1 段描述符里 AP 位、C/B 位、XN 位各控制什么？

看答案

AP[11:10] 控制访问权限（内核/用户可读可写）；C/B 控制 cache 与 buffer 策略；XN 置 1 表示该页不可取指。

3

用户态读 0xC0000000 会发生什么，为什么？

看答案

该地址属内核区，页表 AP 位标为仅内核访问 → Data Abort → 内核判为非法 → 给进程发 SIGSEGV。

4

缺页处理的完整路径有哪几个关键步骤？

看答案

访存失败 → Data Abort → 读 DFSR/DFAR → 查 VMA 合法性 → handle_mm_fault → 分配/读文件/换入 → 填页表 → 刷 TLB → 返回重试。

5

fork 为什么快？子进程写内存时发生了什么？

看答案

fork 只复制页表并全部标只读，物理页共享；子进程写时触发 COW 缺页，才真正复制对应的页。

6

watermark 的 min/low/high 三级分别对应什么行为？

看答案

high：kswapd 停止回收；low：唤醒 kswapd 后台回收；min：分配者自己同步回收（direct reclaim）。

7

只有 32KB 空闲块，要 8KB，伙伴系统会怎么切？

看答案

32KB 切两半 16KB，留一半在 order=2；16KB 再切两半 8KB，返回一个、留一个在 order=1。

8

kmalloc(100) 实际会占用多少，为什么？

看答案

会落到 128 字节档位。因为 SLUB 只提供固定尺寸，按档位向上取整。

9. 这一章要动手的命令

  1. cat /proc/buddyinfo —— 看每个 order 的空闲块数，判断碎片程度。
  2. cat /proc/meminfo —— 看 MemFree、MemAvailable、Slab、SReclaimable、Cached 的差异。
  3. cat /proc/pagetypeinfo —— 看可迁移/不可迁移类型的分布。
  4. slabtop —— 实时看哪个内核对象占用最多。
  5. cat /proc/<pid>/smaps | head -40 —— 看某进程各段的 VSS/RSS/PSS。
  6. cat /proc/<pid>/oom_score 与 oom_score_adj —— 验证第 5 节的评分规则。
  7. dmesg | grep -i -E "oom|page allocation failure" —— 查找历史的内存告急记录。
