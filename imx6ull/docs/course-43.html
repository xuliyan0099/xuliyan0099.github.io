排障方法论

嵌入式排障最容易犯的错是「乱试」：改个参数、重启、还是不行、再改一个。十分钟过去，你既不知道改了什么有效，也不知道问题还在不在。这一课给一套可复用的流程：先分层，再二分，最后只改一个变量。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

1. 现象 → 层次对照表

现象最可能的层第一个动作
完全无输出硬件量电源、晶振、启动引脚
串口乱码时钟核对晶振与波特率
设备不识别设备树 / 驱动dmesg、/proc/device-tree
读写数据错时序 / 电平示波器看波形
偶发卡顿中断 / 内存/proc/interrupts、perf
程序崩用户态strace、gdb、core dump

这张表的用法：先确定「最可能的层」，再只在该层取证。跨层乱查是效率最低的做法。

2. 三个必看的信息源

# 1) dmesg：内核说过的每一句话
dmesg | grep -i "error\|fail\|timeout"
dmesg -w            # 实时跟踪（复现时用）

# 2) /proc/interrupts：中断是否在正常工作
watch -n1 'cat /proc/interrupts'
# 计数不动 → 硬件没产生中断（引脚/时钟/使能）
# 计数暴涨 → 没清标志，或电平没释放

# 3) strace：用户态到底在做什么
strace -f -e trace=open,read,write,ioctl ./prog
# 卡在哪个系统调用，就是问题的位置

这三条几乎能覆盖「软件侧」的全部问题。排查顺序建议就是 dmesg → interrupts → strace，从底往上。

3. 二分法：把范围砍半

  • 代码二分：git bisect 找出引入问题的提交。
  • 配置二分：注释掉一半设备树节点，看是否恢复。
  • 硬件二分：换一块板/换一根线/换一个电源，看现象是否跟随。
  • 时序二分：降低频率/加大延时，看是否复现。

「换一块板试试」是最快的二分：如果问题跟着板走，是代码/配置；如果不跟着走，是这块板的硬件个体问题。这一句话能省掉几小时的纠结。

6. 自测与动手

1

串口乱码最先查什么？

看答案

晶振频率与波特率配置，其次是接线与电平。

2

中断计数不动说明什么？

看答案

硬件根本没产生中断：引脚复用、时钟未开、中断未使能，或外设没配置。

3

换板测试能区分什么？

看答案

问题跟着板走 = 代码/配置问题；不跟着走 = 这块板的硬件个体问题。

4

为什么加 sleep 有时「修好」了？

看答案

它只是改变了竞态窗口，问题并未消除，属于掩盖而非修复。

5

一次只改一个变量的理由？

看答案

否则无法归因：你不知道哪个改动有效，也无法确认问题是否真的消失。

  1. 拿一个你遇到过的问题，按五步重写一遍过程。
  2. 练习用 dmesg -w 实时抓一次错误。
  3. 用 git bisect 定位一次历史 bug。
  4. 建立一份自己的「现象 → 层次 → 动作」速查表。
