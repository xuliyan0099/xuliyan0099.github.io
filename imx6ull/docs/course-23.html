用 perf 量化

性能优化最大的坑是「凭感觉改」。你以为是 CPU 算得慢，其实是内存没命中。这一课用 perf 建立一条硬规矩：先量出瓶颈属于哪类资源，再动手。这条习惯比任何技巧都值钱。

💻 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 六个核心指标各说明什么？② CPI 高说明什么？③ 怎么区分 CPU 慢与内存慢？④ 火焰图怎么看？⑤ 板子上 perf 跑不起来怎么办？

1. 六个指标，一张判据表

指标含义异常时的解读
cycles消耗的时钟周期基线，用来算 CPI
instructions执行的指令数与 cycles 之比即 IPC
IPCinstructions / cycles低于 1 一般有停顿；高于 1 说明多发射生效
cache-misses缓存未命中高 → 访问模式差或工作集大
branch-misses分支预测失败高 → 分支密集、模式随机
context-switches上下文切换高 → 锁竞争或调度频繁

2. 判据：三步定性

# 第一步：看整体
perf stat -e cycles,instructions,cache-misses,branch-misses ./prog

# 判据
#   IPC < 0.5 且 cache-miss 高   → 内存 bound
#   IPC < 1   且 branch-miss 高  → 分支 bound
#   IPC 1~2   且 cycles 高       → CPU bound（该优化算法了）
#   IPC 低但 miss 都低            → 依赖链 / 停顿

# 第二步：采样，找热点函数
perf record -g -F 999 ./prog
perf report --stdio | head -40

# 第三步：定位到行
perf annotate --stdio

第四行「IPC 低但 miss 都低」常被忽略，实际很常见：连续 a = a * b + c 形成长依赖链，每步都在等上一步，CPU 的并行能力用不上。

3. 火焰图：时间花在哪个调用栈上

perf record -F 99 -g -- sleep 30
perf script > out.perf
# 用 FlameGraph 工具折叠并生成 SVG
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > flame.svg

读法：横轴是「出现次数占比」（不是时间轴），纵向是调用栈。最宽的那一条就是热点；如果一条很宽的栈却对应很浅的函数，说明它自己就慢；如果宽在底部而顶部很窄，说明时间分散在很多小函数里。

4. 板子上 perf 起不来怎么办

嵌入式内核常没开 CONFIG_PERF_EVENTS，或没有 PMU 支持。三条替代路径：

  • ftrace：echo function > /sys/kernel/debug/tracing/current_tracer，看函数调用。
  • trace-cmd / kernelshark：ftrace 的友好前端。
  • 自己打点：用 ktime_get() 取时间戳，做粗粒度测量——有时比全套工具更实用。

另外，很多工程师会用 cyclictest 测实时延迟抖动，用 lmbench 测内存带宽——这些是嵌入式性能的两个常用基准。

5. 实验：一次完整的优化闭环

# 1) 基线
perf stat -e cycles,instructions,cache-misses ./matmul_naive

# 2) 记录基线 /tmp/base.txt
# 3) 只改一处：把列遍历改行遍历
# 4) 再测，写入 /tmp/opt.txt
# 5) diff 两个文件，确认只有目标指标变化

# 6) 如果收益不明显，回退，换下一个假设
#    绝不保留「看起来可能有用的改动」

这个闭环做三遍，你就会形成「假设 → 测量 → 结论」的肌肉记忆。以后遇到「程序变慢了」，你不会再盲改。

6. 三条常见误解

7. 自测与动手

1

IPC = 0.3、cache-misses 很高，瓶颈在哪？

看答案

内存 bound：CPU 大部分时间在等数据。方向是改访问模式、分块、缩小工作集。

2

IPC 很高（如 2.0）说明什么？

看答案

多发射/超标量生效，CPU 并行度用得好；此时再优化要靠减少指令数或 SIMD。

3

火焰图横轴代表什么？

看答案

采样占比（相当于「时间比例」），不是时间顺序。最宽的一列就是最耗时的路径。

4

板子上没有 perf，可以用什么替代？

看答案

ftrace / trace-cmd 看函数级耗时；或用 ktime_get 自己打点；也可用 cyclictest 测延迟。

5

为什么对比测试要固定 CPU 频率？

看答案

DVFS 会让同一次运行跑在不同频率上，周期数与耗时都会漂移，比较失去意义。

  1. 对一个程序跑 baseline，记录六个指标。
  2. 只改一处（访问顺序），再跑一次，比较差异。
  3. 生成一张火焰图并指出最宽的一条栈。
  4. 在板子上用 ftrace 看一次函数调用序列。
