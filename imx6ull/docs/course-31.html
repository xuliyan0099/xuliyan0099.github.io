调度

只有一个 CPU 核，却有几十个任务想跑。切得太多，切换开销吃掉性能；切得太少，用户感觉卡。调度器就是在这两个极端之间做决策的东西。这一课讲 Linux 的主调度器 CFS——它到底在「公平」什么，以及实时任务为什么能插队。

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① CFS 的「公平」公平在哪？② vruntime 怎么算？③ nice 值怎么影响权重？④ 实时任务为什么能插队？⑤ 为什么内核也要能被抢占？

1. 核心思想：按权重分配时间

CFS 不用「时间片轮转」，而是记录每个任务的虚拟运行时间 vruntime：

vruntime += 实际运行时间 × (基准权重 / 本任务权重)

# nice = 0  → 权重 1024（基准），跑 1ms 算 1ms
# nice = -5 → 权重更大，跑 1ms 只算 0.6ms（更「抗饿」）
# nice = 10 → 权重更小，跑 1ms 算 2ms（很快欠账）

调度器总是挑 vruntime 最小的那个跑。于是权重高的任务跑得更频繁、但 vruntime 增长得更慢，最终达到「按权重比例分摊 CPU」的效果。

2. 实时任务：完全另一套规则

类策略特点典型用途
实时SCHED_FIFO / SCHED_RR优先级 1~99，永远压过普通任务电机控制、音频、工业 IO
普通SCHED_NORMAL（CFS）按权重公平分配绝大多数进程
空闲SCHED_IDLE只在没别的事时跑后台清理

实时任务的危险：如果它死循环，普通任务永远得不到 CPU，系统看起来「死机」。所以内核留了 5% 的「给非实时任务的保底」（sched_rt_runtime_us），防止实时任务锁死系统。

chrt -f 50 ./motor_ctrl       # 以 FIFO 优先级 50 运行
chrt -p $$                    # 查看当前策略
taskset -c 0 ./prog           # 绑到 CPU0（单核时无意义，多核有用）
ionice -c1 -n0 ./io_heavy     # 调整 IO 优先级

3. 抢占：内核也要能被切

早期 Linux 内核不可抢占：一个系统调用跑长循环，别的任务只能等。现在（CONFIG_PREEMPT）内核在多数位置可被抢占，这让「桌面响应」明显改善。

但即使在可抢占内核里，也有「不可抢占区」：持自旋锁、关中断、中断上下文。这些区域必须短——这正是「中断上半部要短」的另一半理由（第 30 课）。

4. 观察调度行为

# 每个任务的调度统计
cat /proc//sched
cat /proc/sched_debug | head -40

# 看唤醒与迁移
perf stat -e sched:sched_switch,sched:sched_wakeup ./prog
perf sched record ./prog && perf sched latency

# 实时性抖动测试（工业场景常用）
cyclictest -m -p 80 -i 1000 -l 10000

cyclictest 测的是「我要求 1ms 后醒来，实际晚了多少」。这个「晚了多少」就是实时系统的核心指标，嵌入式 Linux 上常在几十到几百微秒。

5. 三条常见误解

6. 自测与动手

1

vruntime 增长得快说明什么？

看答案

该任务权重低（nice 高），「欠账」累积快，会更晚被调度。

2

为什么 CFS 用红黑树而不是链表？

看答案

要频繁取最小、插入、删除，红黑树 O(log n) 且最左节点即最小，链表 O(n) 太慢。

3

实时任务死循环会怎样？内核怎么防？

看答案

普通任务饿死、系统像死机；内核对 RT 任务限流（默认留约 5% 给非 RT 任务）。

4

cyclictest 测的是什么？

看答案

期望唤醒时刻与实际唤醒时刻的差值（延迟抖动），是实时性核心指标。

5

哪些区域不可抢占？

看答案

持自旋锁、关中断、中断上下文、部分原子操作区——所以这些区域必须短。

  1. 用 nice -n 19 跑一个忙循环，再用 top 看它的 CPU 占比。
  2. 用 chrt -f 50 跑同样的循环，观察系统响应变差。
  3. 读 /proc/<pid>/sched，找出 vruntime 与切换次数。
  4. 在板子上跑 cyclictest，记录最大延迟。
