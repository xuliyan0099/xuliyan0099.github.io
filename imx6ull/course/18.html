第 18 课 · 从 C 到汇编：编译器到底做了什么

C 常被称为「高级的汇编语言」，因为它离硬件足够近：一个 i++ 对应一条 add，一次 a[i] 对应一条带移位的 ldr。但 -O2 之后，它又完全不像你写的那样。这一课把同一段 C 在不同优化级别下的汇编摆在一起，让你看清「编译器在替你做哪些决定」。

这一课要回答的问题

① 编译器在哪一步优化？② 为什么 -O0 的代码那么「笨」？③ 局部变量到底在寄存器还是栈上？④ 未定义行为为什么会被优化成「怪物」？⑤ volatile 到底阻止了什么？

1. 同一段 C，三个优化级别

int sum_to(int n) {
    int s = 0;
    for (int i = 1; i <= n; i++) s += i;
    return s;
}
; -O0（几乎逐句翻译，每个变量都在栈上）
sum_to:
    push {r7, lr}
    sub  sp, sp, #16
    add  r7, sp, #0
    str  r0, [r7, #12]     ; n 存栈
    movs r3, #0
    str  r3, [r7, #8]      ; s = 0 存栈
    movs r3, #1
    str  r3, [r7, #4]      ; i = 1 存栈
.L3:
    ldr  r3, [r7, #4]      ; 每次循环都从栈读 i
    ldr  r2, [r7, #12]     ; 读 n
    cmp  r3, r2
    bgt  .L4
    ldr  r3, [r7, #8]      ; 读 s
    ldr  r2, [r7, #4]      ; 读 i
    add  r3, r3, r2
    str  r3, [r7, #8]      ; 写回 s
    ldr  r3, [r7, #4]
    adds r3, r3, #1
    str  r3, [r7, #4]      ; 写回 i
    b    .L3

; -O2（寄存器化 + 强度削减 + 循环优化）
sum_to:
    cmp   r0, #0
    ble   .L2
    add   r1, r0, #1
    mul   r0, r0, r1       ; n(n+1)
    lsr   r0, r0, #1       ; /2  —— 直接算出解析解！
.L2:
    mov   r0, #0
    bx    lr

看懂这个对比，你就理解了两件事：-O0 是「忠实翻译」，方便调试；-O2 是「重新发明你的算法」。前者每条语句都能对应到代码行，后者已经认不出原样了——这也是为什么 -O2 下 gdb 单步会「跳来跳去」。

2. 局部变量在哪：寄存器优先

ARM 有 16 个寄存器，其中约 12 个可用作通用。编译器会把最热的变量放进 r4-r11，只有「取地址了、太多、或跨函数调用要保留」的才落到栈上。

这解释了一个常见困惑：「我加了局部变量，为什么没有栈帧？」——因为它在寄存器里。也解释了 -O0 为什么慢：它把每个变量都赶回栈，每个 i++ 变成「load-add-store」三步。

3. 未定义行为：编译器的「合法乱来」

// 经典例子：有符号溢出是 UB
int f(int x) { return x + 1 > x; }

// -O2 直接优化成：return 1;
// 理由：如果溢出是 UB，编译器可以假设「不会溢出」，
//       那么 x+1 必然 > x，恒为真。

// 另一个：空指针解引用是 UB
int g(int *p) { int v = *p; if (!p) return 0; return v; }
// -O2 会把 if 删掉：既然已经解引用了 p，p 就不可能是 NULL

// 这不是 bug，是标准赋予编译器的自由

这条知识在嵌入式里极其重要：很多「只在 -O2 下出现」的诡异 bug，根源是 UB。解法不是降优化级别，而是修掉 UB（用无符号、加判空、避免严格别名冲突）。

4. volatile：只阻止一部分优化

volatile 只保证「每次访问都真的去读/写」，它不保证原子性、不保证顺序、不保证与其他线程的可见性。

场景volatile 够吗正确做法
读写硬件寄存器够readl/writel（内含 volatile + 屏障）
中断里改的标志位基本够（单核）多核要加 smp_mb() 或原子变量
多线程共享计数不够atomic_t / 互斥锁

「volatile 不等于线程安全」是嵌入式面试与实战里最常见的坑。

5. 实验：自己看四个阶段

gcc -E t.c -o t.i        # 只看预处理（宏展开后，往往几万行）
gcc -S t.c -o t.s        # 只看汇编
gcc -c t.s -o t.o        # 只到目标文件
gcc t.o -o t             # 链接

# 看符号表与重定位
nm t.o
readelf -r t.o
objdump -d t.o

# 三个优化级别对比
for o in 0 1 2 s; do
  gcc -O$o -S t.c -o t_O$o.s
  echo "=== -O$o 行数: $(wc -l < t_O$o.s)"
done

跑完你会看到：-O0 的汇编往往有 100 多行，-O2 可能只有 10 行。这个行数差，就是「编译器替你做了多少事」的量化证据。

7. 自测与动手

1

undefined reference 是哪个阶段的错误？

看答案

链接阶段（ld）。编译阶段只知道「有个外部符号」，链接时找不到定义才报。

2

为什么 -O0 下每个变量都在栈上？

看答案

为了保证调试时每个变量都有确定的内存地址、可被 gdb 修改；寄存器变量无法稳定映射到源码行。

3

x + 1 > x 被优化成恒真，为什么？

看答案

有符号溢出是 UB，编译器可假设不发生溢出，于是 x+1 必然大于 x。

4

volatile 保证了什么，没保证什么？

看答案

保证每次访问都真实发生；不保证原子性、不保证内存序、不保证多核可见性。

5

-Os 与 -O2 的核心差别？

看答案

-Os 以体积为优先，关闭部分增大代码的优化（如激进内联、展开），适合 Flash 受限的 MCU。

  1. 用四个阶段命令跑一遍，记录每个中间文件的大小。
  2. 把 sum_to 在 -O0/-O2/-Os 下对比行数与指令数。
  3. 写一个 UB 例子，观察 -O0 与 -O2 的行为差异。
  4. 用 readelf -r 看一个 .o 的重定位表，找出它引用了哪些外部符号。
