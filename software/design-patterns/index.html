设计模式全书/三篇 10 章/C 与 C++ 双实现

设计模式：从一张函数表，到一个可替换的对象

这套东西不背定义。每个模式都走同一条线：先看它在真实代码里长什么样（通常是坏的），再画清结构，然后给两份实现——一份 C 的（结构体首成员放函数表指针，手工虚表），一份 C++ 的（虚函数 + unique_ptr/shared_ptr）。两份代码用 gcc/g++ -Wall -Wextra 零警告编译，页面上的 RUN 输出就是实际跑出来的结果。场景全部来自车载与嵌入式：CAN 调度、ECU 状态机、报文过滤、驱动注册、传感器适配。

这套书的基准

  • C 版统一写法：静态存储 + 函数指针表（ops / 手工 vtable），不依赖第三方库，单个 .c 就能编译。
  • C++ 版统一写法：虚函数、override、unique_ptr/shared_ptr，同样单文件、-std=c++17。
  • 每章六节：问题 → 结构图（点方框看职责）→ 两份实现 → 真实 RUN 输出 → 纯 JS 交互演示 → 角色对照与代价。
  • 不承诺“最佳实践”：每章最后一节都写清这个模式带来的间接层、分配、生命周期与可测性代价。

0　三篇的关系

第一篇不是模式，是地基：1.1 给一条“按症状找模式”的路，1.2 把 C 的多态拆开——对象首字节放函数表指针，调用先取表、再按偏移取地址、最后把对象自己当第一个参数。后面每一章的 C 版，都是这三步的变体。

第二篇五个模式解决同一类问题：把“变化的那一段”从流程里拿出来。第三篇三个模式换的是对象本身——接口怎么接（适配器）、对象怎么造（工厂）、全局只留一个（单例）。建议顺序读；赶时间就按症状跳，导读页第一张表就是入口。

怎么读：每章先看第 1 节的“坏代码”，确认自己踩过这个坑；第 3 节两份实现对照着看，差异就在“谁持有那张表”；第 4 节的 RUN 输出逐行对；第 6 节的代价表决定项目里到底该不该用。

源码在哪：每章代码块的文件名就是 src/ 里的文件，页面代码与源码逐字一致，改完直接 gcc/g++ 编译即可复现。
