单例模式SINGLETON

配置、日志、诊断会话这类东西，一个进程里只能有一份。单例解决的是“唯一”和“第一次访问才构造”，不是“全局变量很方便”。它同时也是最难测的模式——因为所有测试共享同一份状态。

三次访问 · 一次初始化 C++ 局部静态天然线程安全 测试之间会互相污染

01问题：要么到处传，要么到处复制

假设有一份运行配置：超时 500 ms、日志级别 2。不做单例，通常只有两种下场：

  • 一路往下传。从 main 传到业务、再传到驱动，每个函数多一个 config_t* 参数；中间某个模块为了省事，自己抄了一份副本，从此两份配置各自演化。
  • 到处放全局变量。extern config_t g_cfg; 写进头文件，任何文件都能改；初始化顺序没人管，某处读到的是全零。

单例把这两件事合起来解决：入口只有一个 instance()，第一次调用时完成初始化，之后都返回同一个地址。它没有消灭全局状态，只是把全局状态收进一个可被追踪的入口——这一点很重要，因为单例的代价几乎都来自“它是全局的”。

02结构：一个入口，一个对象

三个调用点（a / b / c）走同一扇门，门后只有一个对象；拷贝构造被删掉，所以“再造一个”在编译期就不成立。点方框看各自边界。

Meyers singletoninstance() + 局部静态
职责点方框：唯一性由谁保证，析构为什么容易出问题。

03两份实现

C 版是“静态结构 + ready 标志”，写法最省但完全没有并发保护；C++ 版是函数内局部静态，构造与访问同一处完成，且拷贝构造被显式删除。

Csingleton.c
/* 单例模式 · C 实现：进程内唯一的配置对象
 * 编译：gcc -std=c11 -Wall -Wextra singleton.c -o singleton
 * 注意：这段只保证「唯一」，不保证「多线程安全」，线程版见页面说明。
 */
#include <stdio.h>

typedef struct { int timeout_ms; int log_level; } config_t;

static config_t g_cfg;
static int      g_ready = 0;
static unsigned g_calls = 0;
static unsigned g_inits = 0;

config_t *config_instance(void)
{
    g_calls++;
    if (!g_ready) {
        g_cfg.timeout_ms = 500;
        g_cfg.log_level  = 2;
        g_ready = 1;
        g_inits++;
    }
    return &g_cfg;
}

void config_reset_for_test(void)
{
    g_ready = 0;
    printf("  reset：下次访问会重新初始化\n");
}

unsigned config_calls(void) { return g_calls; }
unsigned config_inits(void) { return g_inits; }

int main(void)
{
    config_t *a = config_instance();
    config_t *b = config_instance();
    config_t *c = config_instance();

    printf("三次取实例是同一个对象：%s\n", (a == b && b == c) ? "是" : "否");
    printf("访问 %u 次，只初始化 %u 次\n", config_calls(), config_inits());

    a->timeout_ms = 800;
    printf("通过 a 改，通过 b 读：timeout=%d\n", b->timeout_ms);

    config_reset_for_test();
    printf("reset 后 timeout=%d（测试用例之间互相污染）\n", config_instance()->timeout_ms);
    printf("reset 后初始化次数=%u\n", config_inits());
    return 0;
}
C++singleton.cpp
// 单例模式 · C++ 实现：Meyers singleton（C++11 起初始化线程安全）
// 编译：g++ -std=c++17 -Wall -Wextra singleton.cpp -o singleton_cpp
#include <cstdio>

class Config {
public:
    static Config& instance() {
        static Config c;          // 局部静态：首次调用时构造，C++11 保证线程安全
        return c;
    }

    int timeout_ms = 500;
    int log_level  = 2;

private:
    Config() = default;
    Config(const Config&) = delete;
    Config& operator=(const Config&) = delete;
};

int main() {
    Config& a = Config::instance();
    Config& b = Config::instance();
    Config& c = Config::instance();

    std::printf("三次取实例是同一个对象：%s\n", (&a == &b && &b == &c) ? "是" : "否");

    a.timeout_ms = 800;
    std::printf("通过 a 改，通过 b 读：timeout=%d\n", b.timeout_ms);
    std::printf("a 与 b 是同一块内存：%s\n", (&a == &b) ? "是" : "否");
    // 拷贝构造已 delete：写 `Config copy = a;` 会在编译期失败，而不是运行时多一个实例
    return 0;
}

C 版多了“访问次数 / 初始化次数”两个计数器，是因为它需要证明“只初始化一次”；C++ 版由局部静态的语义直接保证，静态构造函数只跑一次，不需要额外标志位。

05C 与 C++：同一份唯一，两种保证

角色C 版C++ 版差别意味着什么
唯一存储文件级 static config_t g_cfg函数内 static Config c都在静态存储区，地址全程不变
初始化时机首次调用 + ready 标志首次调用时构造C 版必须自己维护“是否已初始化”
并发无保护，可能双初始化C++11 起局部静态初始化线程安全C 版要补 pthread_once / 原子 CAS
禁止复制做不到，memcpy 随时能造第二份delete 拷贝构造与赋值这是 C++ 版真正的结构优势
析构进程结束时随静态区回收main 返回后析构，顺序不确定析构里若打日志，日志系统可能已经没了
测试重置ready = 0 即可没有官方办法，得自己写 resetForTest()两者都在“为测试开后门”

06代价与坑

  • 单例是带门脸的全局变量。它没消除耦合，只把耦合藏进 instance() 调用里。结果是：依赖关系在签名上看不出来，测试只能靠 reset 硬掰。
  • C 版并不线程安全。两个线程同时看到 !ready，会各自初始化一次，后写的覆盖先写的。要真线程安全，用 pthread_once、原子 CAS，或干脆把初始化挪到启动单线程阶段。
  • 双检锁不是随手能写的。先判空、再加锁、再判空，如果没有原子变量与内存序，编译器/CPU 重排会让你拿到“指针已赋值但对象还没构造完”的实例。别手写，用局部静态或 std::call_once。
  • 析构顺序是隐雷。静态对象在 main 返回之后才析构，此时其他静态对象（日志、内存池）可能已经销毁。工程上常见的做法是“故意不析构”（指针 new 出来永不 delete），换确定性。
  • 跨模块就不是单例了。每个 .so / .dll 若各自编译进一份静态实例，进程里就有多份。要跨模块唯一，得把实例放到主程序并通过接口传出去。
  • 头文件里别定义变量。config_t g_cfg; 写在头文件、被两个 .c include，就是重复定义（C 里链接期报错，C++ 里 ODR 违规）。头文件只放 extern 声明与函数原型。
  • reset 要清干净。演示里 reset 只把 ready 归零，下次访问重新赋初值，看起来“干净”；真实项目里若 reset 漏清某个字段，测试就会带着上个用例的残留跑，而且只在特定顺序下失败。
  • 能注入就别单例。把配置作为构造参数传进模块，测试时可以随手造两份不同的配置并发跑。单例留给真正进程级唯一的东西：日志、诊断会话、硬件管理器。
