理论 T09 · 内核怎么起来

U-Boot 跳过来之后，内核的第一条指令在 head.S 里。这一段代码在「没有栈、没有页表、没有 C 环境」的条件下把机器改造成能跑 C 的状态，然后交给 start_kernel()。这一章把这两段之间的每一步说清，包括为什么早期日志会「丢」。

本章要解决的问题

① 内核第一条指令在做什么；② 没有页表时怎么建页表、怎么开 MMU；③ start_kernel 里几十个初始化为什么顺序不能乱；④ 驱动是靠什么机制「自动」被初始化的；⑤ 为什么启动早期的 printk 看不到。

读完你应该能回答

  • head.S 里最先做的是哪三件检查？
  • 早期页表为什么用 1MB 段而不是 4KB 页？
  • initcall 分几级，谁的优先级最高？
  • 内核线程和用户态 init 进程是什么关系？
  • 没有 earlycon，启动早期的日志去哪了？

1. head.S：在没有 C 环境的情况下开局

内核入口（arch/arm/kernel/head.S）运行时，条件是极端的：MMU 关、缓存关、栈指针不可信、不能调用任何 C 函数、连 printf 都没有。它必须按顺序完成下面这些，每一步都为下一步创造条件：

步骤做什么为什么必须现在做
① 校验 CPU__lookup_processor_type 读 CPU ID，查内核是否支持这颗核不支持的核上跑下去毫无意义，早点死掉比乱跑好
② 校验启动参数检查 r2 指向的 DTB/ATAGS 是否合法后面解析硬件全靠它，坏了必须立刻报
③ 建初始页表__create_page_tables，映射内核自身 + DTB + 串口不开 MMU 就没法用虚拟地址，也没法开缓存
④ 使能 MMU__enable_mmu：写 TTBR0、DACR、置 SCTLR 的 M/C/I之后的代码按虚拟地址链接，必须能翻译
⑤ 设栈SP 指向 init_thread_union 的栈顶C 函数需要栈才能跑
⑥ 清 BSS把 __bss_start 到 __bss_stop 清零C 语言规定未初始化全局变量为 0
⑦ 跳到 Cb start_kernel正式进入内核主体

其中第 ③ 步是这一章的技术核心。它必须在「MMU 还关着」的时候完成，所以它用的是物理地址；而且它只能用最小的代价建最少的映射：

  • 映射内核代码与数据（否则开了 MMU 立刻取指失败）；
  • 映射 DTB（后面要用它解析硬件）；
  • 映射串口寄存器（earlycon 要用，否则早期日志一个字都出不来）。

为什么用 1MB 段而不是 4KB 页？因为此时还没有内存分配器、没有 L2 表的空间，而段映射只需要在 L1 表里写一项就能覆盖 1MB。这是「用精度换可行性」的典型取舍（T03 讲过段的开销优势）。

这里有一个隐蔽的坑 早期页表必须把「内核正在执行的这段代码」映射到它链接时假定的虚拟地址（0xC000_8000 附近），同时还要保证「开 MMU 的那条指令本身」不会因为地址翻译而失效。这就是为什么开 MMU 的那几条指令要放在「同一段映射内」——启动代码里的位置安排不是随意写的。

2. start_kernel：一场严格排序的初始化

start_kernel() 是内核的「main 函数」，它按顺序调用几十个初始化函数。顺序不是随意的：后面依赖前面的成果，动一处就可能全盘崩。关键调用按序如下：

调用建立什么依赖谁
setup_arch()解析 DTB、建立内存布局、识别 CPU、初始化早期控制台head.S 给的 DTB 指针
mm_init()伙伴系统、slab 分配器可用（终于能 kmalloc）setup_arch 报出的内存范围
sched_init()调度器、运行队列、idle 任务mm_init（任务结构要内存）
irq_init() 系列中断控制器（GIC）驱动、中断描述符setup_arch 的 DT 解析
time_init()定时器、时钟源、jiffies 开始走中断可用
console_init()真正注册控制台，printk 的日志终于能输出串口驱动已 probe
rest_init()创建内核线程，转入「多任务世界」以上全部

注意 mm_init 在 sched_init 之前、console_init 很靠后。这两条顺序解释了新手最常遇到的两个现象：

① 「为什么启动早期不能 kmalloc？」 因为在 mm_init 之前分配器还没建立，只能用静态数组或 memblock 这类早期分配器。

② 「为什么启动早期的 printk 看不到？」 因为在 console_init 之前，控制台还没注册，日志只是被塞进内核的环形缓冲区（log_buf）。等控制台就绪后，这些日志会被「刷」出来——所以你在 dmesg 里能看到它们，但在串口实时输出里看不到。

earlycon 是唯一的例外 内核支持用 bootargs 里的 earlycon 参数，在 setup_arch 阶段就用「裸寄存器写」的方式驱动串口。它不依赖驱动框架、不依赖中断、不依赖内存分配，就是几个 writel。这就是「板子起不来时，加上 earlycon 能看到第一行日志」的原因。

3. initcall：驱动「自动被初始化」的机制

你有没有想过：你写驱动时只用了 module_init(my_init)，谁在什么时候调用了它？答案就是 initcall 机制。内核把所有初始化函数收集到一张表里，按级别顺序依次调用。

级别宏执行时机典型用途
0pure_initcall最早纯计算、无依赖的常量初始化
1core_initcall核心内存、调度等最基础的设施
2postcore_initcall核心之后总线（platform）、基础框架
3arch_initcall架构相关SoC 特有初始化
4subsys_initcall子系统class、gpio、pinctrl、clock 框架
5fs_initcall文件系统VFS、proc、sysfs
6device_initcall设备驱动（默认）绝大多数驱动（module_init 就是它）
7late_initcall最后依赖前面全部就绪的功能

三条必须记住的规则：

  • 级别决定大顺序，链接顺序决定同级别内的小顺序。 同一级别里，谁在 Makefile 里排前面谁先执行——这就是为什么改 obj-y 的顺序能改变初始化顺序（也是某些「玄学 bug」的来源）。
  • 级别错了就是全错。 一个 device 级别的驱动要用 gpio 框架，而 gpio 框架是 subsys 级别（4 < 6），所以它一定已经就绪。
  • 依赖没就绪就返回 -EPROBE_DEFER（见 T05），不要靠「调高级别」硬解决。

还有一条容易误解的：module_init 对「编译进内核」和「编译成模块」都有效——编进内核时它等价于 device_initcall；编成模块时它变成 insmod 时的入口函数。所以你在源码里看不到它出现在启动顺序里，但内建时确实会跑。

4. rest_init：从单线程内核到多任务世界

start_kernel 的最后一步是 rest_init()，它做三件事，然后「原来的执行流」自己变成 idle：

  1. 创建 kernel_init 线程（最终成为 PID 1）：它负责跑完所有 initcall、挂载根文件系统、执行用户态 init。
  2. 创建 kthreadd（PID 2）：所有后续内核线程的父进程，负责「生」各种内核线程（工作队列线程、迁移线程等）。
  3. 自己进入 cpu_idle：此时主启动流变成 idle 任务（每个核一个），只在没别的事时运行。

所以「PID 1」不是一个神秘的存在，它就是启动流程最后的那个内核线程转身变成的用户态进程。它的关键步骤是：

kernel_init→do_basic_setup（跑 initcall）→挂 rootfs→exec /sbin/init→变成用户态 PID 1

挂 rootfs 的来源优先级：initramfs（若编进内核）→ bootargs 的 root= 指定设备 → NFS 根。如果最后找不到可执行的 /sbin/init（以及 /etc/init、/bin/sh 等备选），内核会打印 No working init found 并 panic。这是嵌入式最常见的启动失败之一：rootfs 挂了但里面没有 init，或者设备号写错。

算一笔：启动为什么「看起来卡住」几秒
do_basic_setup 里要跑几百个 initcall，其中很多会去探测硬件
I2C 探测超时、SD 卡初始化、以太网 PHY 自协商，每项几十到几百毫秒
累计起来 2–5 秒很正常，日志上表现为「最后一行之后没动静」
判断方式：dmesg 带时间戳，看哪两项之间跨度大；或加 initcall_debug 启动参数，它会逐个打印每个 initcall 的耗时

5. 八个常见误解

误解真相
「内核第一条指令在 C 代码里」在 head.S 的汇编里。C 环境（栈、BSS、MMU）是它造出来的。
「MMU 一开始就是开的」一开始是关的。head.S 建好页表后才开，且开的那一刻地址翻译规则就变了。
「早期页表映射了全部内存」只映射内核、DTB、串口寄存器等最小集合，其余靠后面 setup_arch 补齐。
「printk 一直能用」console_init 之前只进环形缓冲，不输出。要看早期日志必须 earlycon。
「initcall 就是按源码出现顺序执行」先按级别（0–7），同级别才按链接顺序。
「module_init 只对模块有效」编进内核时等价于 device_initcall，同样会在启动时被调用。
「PID 1 是内核创建的普通进程」它是内核线程 kernel_init 执行 exec 后变成的用户态进程，之前一直是内核线程。
「启动慢一定是硬件问题」大量 initcall 的探测超时也会造成数秒延迟，用 initcall_debug 能定位到具体函数。

6. 自检：能答出来才算懂

1

head.S 里最先做的三件事是什么？

看答案

校验 CPU ID（是否支持这颗核）、校验启动参数（DTB/ATAGS 是否合法）、创建初始页表（内核 + DTB + 串口）。

2

为什么早期页表用 1MB 段而不是 4KB 页？

看答案

此时没有内存分配器、没有 L2 表空间；段映射只需在 L1 表里写一项就能覆盖 1MB，代价最小、可行性最高。

3

为什么 mm_init 必须在 sched_init 之前？

看答案

因为调度器要创建任务结构、运行队列等对象，这些都依赖内存分配器可用。分配器没起来，调度器无处落腳。

4

启动早期的 printk 日志去哪了？怎么才能实时看到？

看答案

进了内核的环形缓冲区 log_buf，console_init 后统一刷出。要实时看到必须在 bootargs 加 earlycon（配合正确的串口地址/波特率）。

5

initcall 共几级？module_init 属于哪一级？

看答案

0–7 共八级（pure/core/postcore/arch/subsys/fs/device/late）。module_init 等价于 device_initcall（第 6 级）。

6

同级别的 initcall 谁先执行？由什么决定？

看答案

由链接顺序决定，也就是 Makefile 里 obj-y 的排列顺序。改顺序会影响初始化次序。

7

PID 1 是怎么产生的？它和 kthreadd 是什么关系？

看答案

rest_init 创建 kernel_init 线程，它跑完 initcall、挂 rootfs 后 exec 用户态 init，成为 PID 1。kthreadd 是 PID 2，所有内核线程的父，两者是兄弟线程。

8

打印 No working init found 并 panic，通常是什么原因？

看答案

根文件系统挂上了但里面没有可执行的 init（或 root= 设备写错、rootfs 格式不被支持、init 缺少执行权限/动态库）。

7. 这一章要动手的命令

  1. 在 bootargs 里加 earlycon，重启，观察最早出现的日志行（通常能看到「Booting Linux on physical CPU 0x0」）。
  2. 加 initcall_debug 启动，dmesg | grep initcall —— 看每个初始化函数的耗时，找启动慢的真凶。
  3. dmesg | grep -E "Memory:|On node|Kernel command line" —— 确认内核看到的内存大小与 bootargs。
  4. cat /proc/cmdline —— 确认 earlycon/root/console 真的传进来了。
  5. 在 init/main.c 的 start_kernel 里加一行 pr_info，重编内核，验证自己的第一行内核日志。
  6. grep -c initcall /proc/kallsyms 或读 System.map 里 __initcall_* 段，看初始化函数表有多大。
  7. 故意给一个不存在的 root=，观察 panic 信息与「init 找不到」的完整提示。
