文件系统与 VFS（详解）

Linux 同时支持几十种文件系统，却只需要一份 open() 代码——这是 VFS（虚拟文件系统）的功劳。这一章把 open("a.txt") 拆成十几步，说清 inode、dentry、file 三个对象各管什么，以及「文件删了空间还在占」的真正原因。

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 一个 open 怎么从字符串走到磁盘块；② inode 与 dentry 到底谁缓存了什么；③ 硬链接与软链接的本质区别；④ 删除文件为什么有时不释放空间；⑤ 为什么 /proc 里的「文件」根本不是文件。

读完你应该能回答

  • 打开一个文件，内核里会创建几个对象？哪个是「全系统唯一」的？
  • 为什么同一文件被两个进程打开时，一个进程的读位置不影响另一个？
  • 为什么 rm 掉一个大文件，df 却显示磁盘还是满的？
  • dentry 缓存为什么必须有「负条目」？
  • 没有文件系统，字符设备还能用 open 打开吗？

1. VFS 要解决的核心矛盾

磁盘上有几十种「怎么存文件」的方案：ext4 用 inode + 块位图，FAT32 用簇链，NFS 的文件在另一台机器上，tmpfs 干脆在内存里。它们的实现毫无共同点，但用户程序只想调 open/read/write/close 这四个函数。

VFS 的做法是抽象出四个对象，让每种文件系统都实现同一套操作函数（函数指针表），上层只调抽象接口：

对象代表什么生命周期典型字段
super_block一个「已挂载的文件系统实例」挂载到卸载块大小、操作表 s_op、根 inode、设备号
inode一个「文件本体」的元数据（与名字无关）被引用时存在，可缓存可回收大小、权限、时间戳、块指针、i_op / i_fop
dentry一个「名字 → inode」的目录项被查找过就进缓存名字、父目录、指向的 inode、d_op
file一个「打开的文件实例」（进程视角）open 到 close读写位置 f_pos、打开标志、f_op、私有数据
理解这四者的关系，一句话就够 super_block 管一片存储；inode 管一个文件的内容与属性；dentry 管「路径上的一个名字」；file 管「一次打开」。 一个 inode 可以被多个 dentry 指向（硬链接），也可以被多个 file 打开（多进程同时读），但全系统只有一份 inode。

2. open 的完整路径

以 open("/home/u/a.txt", O_RDONLY) 为例，别看它简单，内核里要过十来道关：

系统调用入口→拷贝路径名→取一个空 fd→逐段解析路径→查 dentry 缓存→取 inode→权限检查→调 fs 的 open→绑定 fd 与 file

逐步说明几个关键点：

  1. 拷贝路径名：路径在用户空间，内核先用 getname() 拷进内核缓冲。原因见 T01：内核不能直接信用户指针。
  2. 取空 fd：get_unused_fd_flags() 在进程的 fd 表里找最小空位。这就是为什么你总是拿到 3（0/1/2 已被占）。
  3. 逐段解析：link_path_walk() 把 /home/u/a.txt 按 / 切开，一段一段往下走。每段先查 dentry 缓存（这是性能关键），命中就直接拿到 inode；不命中才调具体文件系统的 lookup 去读目录块。
  4. 权限检查：inode_permission() 检查 uid/gid 与权限位，还要过 LSM（SELinux/AppArmor）那一层。
  5. 调 fs 的 open：真正打开动作在 f_op->open() 里，比如 ext4 可能在这里做日志恢复检查。
  6. 绑定：fd_install(fd, file) 把新 file 对象挂到进程 fd 表的第 fd 格。

注意第 3 步的代价：路径解析是文件操作里最贵的部分。一段很深的路径要逐段查缓存，每段还可能触发磁盘 IO。这也是为什么「打开文件比读文件慢」、为什么长路径、大量小文件会显著拖慢系统。

2.1 一个文件被两个进程打开，为什么读位置互不影响

因为 file 对象是「每次 open 一份」，而 inode 是共享的。f_pos（读写位置）存在 file 里，所以：

  • 进程 A、B 各自 open 同一文件 → 两个 file 对象 → 两个独立的 f_pos，各读各的。
  • 进程 fork 后，父子共享同一个 file 对象（fd 表被复制但指向同一 file）→ f_pos 共享，会互相干扰。这是脚本里「父子进程读同一文件跳字节」的经典坑。

顺便解释 lseek 的本质：它只是改 file->f_pos 这个整数，不涉及任何磁盘操作。所以它几乎零开销，也是「seek 后再读」不必然比顺序读慢的原因。

3. inode 与 dentry 缓存：性能的真正战场

如果每次 open 都要读磁盘上的目录块、再读 inode 块，系统会慢到不能忍。所以内核做了两级缓存，它们的失效策略不同，理解差别很关键。

3.1 inode 缓存（icache）

键是「哪个文件系统 + 哪个 inode 号」。一个 inode 被读进内存后：

  • i_count > 0（有 dentry 或 file 引用它）：不能被回收，动了系统就崩。
  • i_count = 0：进 LRU 链表，内存紧张时优先回收。回收前如果它是脏的（有未写回的元数据），必须先写回磁盘。

所以「inode 缓存占满了内存」是正常且有益的：那意味着你的目录结构、文件属性都在内存里，ls -l 不需要碰磁盘。这也是 /proc/meminfo 里 Cached 数字很大的原因——它不该被当成「内存泄漏」。

3.2 dentry 缓存（dcache）

键是「父目录 dentry + 名字字符串」。dentry 有四种状态，其中一种特别重要：

状态含义用途
已使用（used）指向有效 inode，被引用中正常查找命中
未使用（unused）还在缓存里，但没人引用下次查找还能命中，内存紧张可回收
负条目（negative）d_inode == NULL，表示「这个名字不存在」避免反复查磁盘
正在查找查找进行中并发控制
算一笔：负条目到底省了多少
场景：脚本循环 1000 次 stat("cache/not_exist.txt")
没有负缓存：每次都读目录块 → 1000 次磁盘（或页缓存）查找
有负缓存：第一次之后全命中内存 → 1000 次纯内存哈希查找
实测差距常在 10 倍以上（机械盘更多）
代价：负条目也要占内存，且「新建同名文件」时必须让它失效

还有一条工程上很重要的事实：dentry 查找有无锁快速路径（RCU walk）。在读多写少的场景（绝大多数程序），路径解析可以不加锁并发进行，这是 Linux 文件系统吞吐高的关键设计之一。它带来的副作用是「查找过程中可能看到中间状态」，所以内核代码要严格遵守引用计数规则。

4. 硬链接与软链接：本质是「几个名字」还是「另一个文件」

这是最容易被面试官抓住的问题，但真正理解的人不多。区别在于它们操作的对象不同：

维度硬链接（ln a b）软链接（ln -s a b）
本质新增一个 dentry，指向同一个 inode新建一个独立的 inode，内容是「目标路径字符串」
inode 号相同不同
占用空间几乎为 0（只多一个目录项）至少一个块（存路径字符串）+ 一个 inode
跨文件系统不行（inode 号只在单个 fs 内有意义）可以
指向目录不行（会造成循环遍历灾难）可以
删除原文件后另一个名字照常可用（数据还在）链接变成「断链」，访问报错
计数i_nlink 记录有几个名字不涉及 i_nlink

硬链接为什么不能跨文件系统？因为 inode 号是文件系统内部的编号——ext4 的 inode 42 和 FAT32 的 inode 42 完全无关。硬链接本质是「在同一个 fs 的目录树里再加一个名字指向这个 inode」，跨 fs 就无处落脚。

为什么不能硬链接目录？因为目录树必须是一棵没有环的树：路径解析、find、备份工具都假设「顺着走一定能走完」。允许目录硬链接就能造出环，遍历会死循环，删除时引用计数也会算不清。

5. 删了文件空间没释放：三个计数在打架

这是运维和嵌入式现场最常见的一个「灵异现象」。要解释它，必须区分 inode 上的两个完全不同的计数：

计数含义谁改它
i_nlink磁盘上有几个目录项指向这个 inodelink() 加一，unlink() 减一
i_count内存里有几个对象引用它（dentry、打开的文件、正在执行的系统调用）内核自动维护，随引用增减

rm 的本质是 unlink()：它只删掉「名字」，把 i_nlink 减一。数据块什么时候真正释放？必须同时满足：

i_nlink == 0 （没有任何名字指向它了） 且 i_count == 0 （没有任何进程还打开着它）

第二个条件就是「删了不释放」的全部原因：只要还有进程持有这个文件的 fd，数据块就必须留着——否则那个进程后续的 read 会读到不存在的块。

算一笔：一个 20GB 日志的「假删除」
14:00 服务在写 /var/log/app.log，同时有人 tail -f 看着
14:05 rm app.log → i_nlink 变 0，但服务与 tail 都还开着 fd → 数据块全部保留
df 显示磁盘依旧占着 20GB，ls 却看不到这个文件
14:06 重启服务与 tail → 最后一个 fd 关闭 → i_count 归零 → 20GB 立刻释放
正确做法：truncate -s 0 app.log（清空但不删名字），或 : > app.log

排查命令：lsof +L1 专门列出「link 数为 0 但仍被打开」的文件，输出里带 (deleted) 标记。嵌入式设备上 Flash 空间被莫名吃掉时，先跑这一条。

另外两个常被误判为「删了不释放」的情况也要分清：① ext4 出厂保留 5% 空间给 root（tune2fs -m 可调），普通用户看到的是「可用」而不是「总容量」；② inode 用尽——df -i 显示 100% 时，即使还有空间也创建不了新文件（大量小文件场景常见）。

6. 页缓存：read 和 write 都不直接碰磁盘

很多人以为 read() 就是「从磁盘读」，write() 就是「写到磁盘」。真实路径完全不同，这也是系统性能与数据安全的关键。

6.1 read 的真实路径

read(fd)→查页缓存→命中？→是：拷到用户缓冲→否：触发预读→提交块 IO→等完成→拷到用户缓冲

页缓存（page cache）以「inode + 页号」为键。命中时 read 只是内存拷贝，几微秒；未命中时内核不仅读你要的那一页，还会预读后面的若干页（默认几十到 128KB，由 read_ahead_kb 控制）。这就是「顺序读大文件比随机读快得多」的原因——预读把零散的小 IO 合并成了连续大 IO。

6.2 write 的真实路径与丢数据风险

write() 返回成功，只代表数据进了页缓存并被标为「脏」，一个字都没到磁盘。真正的落盘由内核的回写线程批量完成：

参数默认值含义
dirty_writeback_centisecs500（5 秒）回写线程多久醒一次
dirty_expire_centisecs3000（30 秒）脏页超过多久必须写
dirty_ratio20%脏页占内存超过这个比例，写操作开始同步阻塞

所以直接断电，最多会丢最近 30 秒的写入。要保证落盘必须显式调用：

  • fsync(fd)：把这个文件的数据 + 元数据刷到存储，并等它真的写完。
  • fdatasync(fd)：只刷数据，不刷不影响读取的元数据（如 mtime），更快。
  • O_SYNC / O_DSYNC：打开时就要求每次写都同步。
  • O_DIRECT：绕过页缓存直接读写设备，数据库常用（自己管缓存）。
嵌入式必记的一条 掉电敏感的场景（配置、计量数据、日志），写完必须 fsync。只 write 就断电，重启后文件内容可能是旧的、甚至出现「长度对但中间是 0」的诡异现象（ext4 延迟分配 + 元数据先落盘的副作用）。

7. 那些「不是文件的文件」

「一切皆文件」是 Linux 最著名的口号，但它常被误解成「所有东西都存在磁盘上」。真相是：「文件」只是一个接口抽象——只要有 open/read/write/close 这套操作，内核就把它挂进目录树。下面这几个挂载点全是这种「假文件」：

文件系统挂载点内容来自能写吗
proc/proc内核内部数据结构（进程、内存、参数）/proc/sys 下可写，其余只读
sysfs/sys设备模型：每个设备一个目录、每个属性一个文件部分属性可写（如 GPIO 导出）
devtmpfs/dev内核探测到的设备节点（major:minor）不能随意创建，由驱动决定
tmpfs/tmp、/run内存（可换出到 swap）能写，断电全丢
debugfs/sys/kernel/debug内核调试信息（需挂载）部分可写，仅调试用

这类文件系统的实现方式是：它们的「读」不是从块设备取数据，而是调用一个内核函数把当前状态格式化成文本。所以你会看到两个「反常」现象：

  • ls -l /proc/cpuinfo 显示大小 0，但 cat 出来几十行。因为大小是动态生成的，stat 时并不知道将来会有多少内容。
  • 同一个 /proc/meminfo，连续读两次内容不同。因为每次读都重新采样当前内存状态。
这条认知决定你怎么用 /sys 和 /proc echo 1 > /sys/class/gpio/gpio12/value 不是在「写文件」，而是在调用内核里对应的属性写函数，这个函数会去操作 GPIO 寄存器。所以这里的 echo 失败可能意味着硬件没配好，而不是「文件权限不对」。

8. 十个常见误解

误解真相
「inode 就是文件」inode 是文件的元数据，不含名字。名字在 dentry / 目录项里。
「一个文件只有一个 inode」对，但可以有多个 dentry 指向它（硬链接）。反过来说「一个 dentry 一定对应一个 inode」也不对——负条目就没有 inode。
「删文件就是删数据」rm 只删名字。数据块在引用计数归零后才释放。
「write 成功就安全了」只到页缓存。断电会丢；必须 fsync 才算落盘。
「read 一定读磁盘」命中页缓存时纯内存拷贝；只有未命中才触发 IO，且会预读。
「Cached 内存是浪费」页缓存可随时回收，它是性能来源，不是泄漏。
「/proc 里的文件大小是 0 说明坏了」动态生成的内容，大小无意义。
「软链接就是快捷方式，等价于原文件」它是独立 inode，内容是路径字符串；原文件删了就断链。
「ext4 一定能防断电丢数据」日志只保证元数据一致性，不保证数据不丢。要保数据必须 fsync。
「目录也是文件，所以可以硬链接」目录是文件，但硬链接目录被禁止，因为它会破坏树的「无环」性质。

9. 自检：能答出来才算懂

1

VFS 的四个核心对象是什么？哪个是「全系统唯一」的？

看答案

super_block（文件系统实例）、inode（文件元数据）、dentry（名字 → inode）、file（一次打开）。inode 在一个文件系统内唯一（同一文件不会有两份）；file 是每次 open 一份；dentry 与硬链接数量相关。

2

open() 里最贵的一步是什么？为什么？

看答案

路径解析（link_path_walk）。长路径要逐段查 dcache，未命中还要读目录块；深度目录 + 冷缓存时，一次 open 可能触发多次磁盘 IO。

3

两个进程各自 open 同一文件，一个读了一半，另一个从哪开始读？

看答案

从各自的位置开始——因为 f_pos 在 file 对象里，每次 open 一份。但如果是 fork 出来的父子进程，共享同一 file，位置就会互相影响。

4

负 dentry 是什么？没有它会怎样？

看答案

d_inode == NULL 的缓存项，记录「这个名字不存在」。没有它，每次访问不存在的路径都要真实查一次目录，脚本循环里会放大成大量 IO。

5

硬链接为什么不能跨文件系统？为什么不能链目录？

看答案

跨 fs 不行：inode 号只在单个文件系统内有意义，硬链接本质是「同一 fs 内新增一个指向该 inode 的目录项」。链目录不行：会让目录树出现环，遍历与引用计数都会崩。

6

rm 一个大文件后 df 没变化，列出两种可能原因。

看答案

① 还有进程打开着它（i_count > 0），数据块保留，用 lsof +L1 找；② 不是空间问题而是 inode 用尽（df -i 100%），或者是 ext4 给 root 保留的 5% 让普通用户看不到。三者现象相似，原因完全不同。

7

write() 返回成功，数据在哪？断电会怎样？

看答案

在页缓存里，标记为脏。断电最多丢最近 30 秒（dirty_expire_centisecs 默认 3000）。必须 fsync 才算真正落盘。

8

为什么顺序读大文件比随机读快很多？两个原因。

看答案

① 预读把后续页一起读进缓存，把多个小请求合并成大请求；② 顺序访问符合存储介质的物理特性（eMMC/机械盘连续块更快）。随机读则每次都可能是 major fault。

9

为什么 ls -l /proc/cpuinfo 显示大小是 0？

看答案

因为它不是磁盘文件，内容在 read 时由内核函数实时生成，stat 阶段没有「大小」这个概念。

10

echo 1 > /sys/class/gpio/gpio12/value 实际发生了什么？

看答案

写这个「文件」触发了 sysfs 属性的 store 回调，该回调调用 GPIO 驱动的代码，最终写 GPIO 数据寄存器。所以这里的「写文件」= 调内核函数 = 操作硬件。

10. 这一章要动手的命令

  1. stat a.txt —— 一次看清 inode 号、链接数、三个时间戳、块数。
  2. ln a.txt b.txt && ls -li a.txt b.txt —— 验证硬链接 inode 号相同。
  3. ln -s a.txt c.txt && ls -li c.txt && rm a.txt && cat c.txt —— 验证软链接断链。
  4. lsof +L1 —— 找「已删除但仍被打开」的文件，复现第 5 节的 20GB 场景。
  5. df -i 与 df -h 一起看 —— 区分「空间满」和「inode 满」。
  6. 写 100MB 后立刻 cat /proc/meminfo | grep Dirty，再 sync，观察脏页清零。
  7. echo 3 > /proc/sys/vm/drop_caches 后 time cat bigfile，再读第二次 time cat bigfile，对比页缓存的效果。
