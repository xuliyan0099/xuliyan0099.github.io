卷 08·启动链·第 06 篇

内核裁剪与设备树

一个内核镜像里面装着几千个驱动，但你的板子只需要几十个。裁剪是减法；设备树是「告诉内核这块板子上到底有什么」的那份说明书。

★ 一读 纯读约 18 小时 左侧是本卷目录 理论为主 · 实作可跳

本章目标

① 会配置、编译内核并产出 zImage；② 知道 defconfig / menuconfig / .config 的关系；③ 读懂 .dts 的节点与属性；④ 能改设备树点亮一个 LED；⑤ 会用 dtc 反编译现成的 .dtb。

10.1 内核源码长什么样

目录内容你会碰到的场景
arch/arm/ARM 架构相关代码、boot/dts/ 设备树、configs/ 默认配置改 dts、选 defconfig
drivers/所有驱动：gpio、leds、mmc、net、tty第 12 章写驱动
fs/文件系统实现：ext4、nfs、ubifs挂根文件系统
kernel/进程调度、时间、中断后期深挖
mm/内存管理后期深挖
init/启动入口 main.c，start_kernel 在这想看启动流程
net/TCP/IP 协议栈网络问题
Documentation/官方文档，含设备树绑定说明查 compatible 怎么写

10.2 配置：三件套的关系

arch/arm/configs/imx6ull_defconfig   ← 厂商给的「默认配置模板」
                ↓ make imx6ull_defconfig
              .config                ← 当前生效的完整配置（几千项）
                ↓ make menuconfig
              .config 被修改         ← 你勾选/取消的每一项都写在这
                ↓ make zImage
        arch/arm/boot/zImage         ← 最终产物

make savedefconfig 可以把你改过的 .config 精简回一个 defconfig 文件，方便保存和复用——这是团队协作里最该有的习惯，而不是把 .config 直接发给别人。

10.3 编译内核

$ export ARCH=arm
$ export CROSS_COMPILE=arm-linux-gnueabihf-
$ make imx6ull_defconfig        # 载入默认配置（名字以 arch/arm/configs/ 下实际文件为准）
$ make menuconfig               # 图形化勾选，可选
$ make zImage -j4               # 编内核
$ make dtbs                     # 编设备树
$ make modules                  # 编模块（写驱动用）
产物路径
内核镜像arch/arm/boot/zImage
设备树arch/arm/boot/dts/xxx.dtb
模块散落在各驱动目录下的 .ko
符号表vmlinux、System.map（调试用）
编不过的三大原因 ① 工具链版本太新（换厂商那套）；② 缺依赖包（bison flex libssl-dev bc libncurses-dev）；③ 源码目录含中文或空格。第三点最隐蔽，路径一律用英文。

10.4 设备树：一句话讲清

老内核把板子信息硬编码在 C 里，一块板子一份代码，几百份重复。设备树把这些信息抽成一个文本文件（.dts），编译成二进制 .dtb，启动时交给内核解析。同一个内核 + 不同 dtb = 支持不同板子。

/ {                                  /* 根节点 */
    model = "Freescale i.MX6ULL 14x14 EVK";
    compatible = "fsl,imx6ull-14x14-evk", "fsl,imx6ull";

    memory@80000000 {                 /* 内存：起始 0x80000000，长度 512MB */
        device_type = "memory";
        reg = <0x80000000 0x20000000>;  /* 起始地址 长度 */
    };

    chosen {
        bootargs = "console=ttymxc0,115200";
    };
};

&iomuxc {                           /* 引用已有节点，往里加内容 */
    pinctrl_led: ledgrp {
        fsl,pins = <
            MX6UL_PAD_GPIO1_IO03__GPIO1_IO03  0x10B0
        >;
    };
};

leds {
    compatible = "gpio-leds";
    led0 {
        label = "sys-led";
        gpios = <&gpio1 3 GPIO_ACTIVE_LOW>;
        pinctrl-0 = <&pinctrl_led>;
        default-state = "on";
    };
};
概念含义
节点 node { }一个设备或一组配置
compatible最关键的属性：驱动靠它匹配设备。格式是 "厂商,型号"
reg地址与长度，<起始 长度>
status"okay" 启用 / "disabled" 关闭
&节点名引用别处定义的节点（label 引用）
pinctrl-0指定这组引脚怎么复用、电气参数如何
gpios = <&gpio1 3 ...>用 gpio1 控制器的第 3 号引脚
引脚复用是硬件的地基 一个引脚可能同时是 UART_TX、PWM、GPIO。给哪个功能用，由 IOMUXC 寄存器决定，设备树里通过 fsl,pins 配置。配错了，代码再对也没反应——这是第 12 章最常见的「驱动加载成功但灯不亮」。

10.5 dtc：编译与反编译

# .dts → .dtb（内核 make dtbs 会自动做，也可手工）
$ dtc -I dts -O dtb -o my.dtb my.dts

# .dtb → .dts（拿到板子/别人的 dtb 时，反编译看里面到底写了什么）
$ dtc -I dtb -O dts -o dump.dts /boot/xxx.dtb

# 板子上直接看当前生效的设备树
# ls /proc/device-tree/
# cat /proc/device-tree/model
# find /proc/device-tree -name compatible
调试设备树最快的办法 板子起来后 cat /proc/device-tree/model，确认内核用的是不是你编的那份 dtb。「我改了 dts 却没效果」90% 是因为板子加载的是旧 dtb。

10.6 改设备树点亮 LED 的完整流程

  • 在原理图上找到 LED 接的引脚（如 GPIO1_IO03），记下网络名和有效电平（高亮还是低亮）。
  • 在 arch/arm/boot/dts/ 找到你板子的 dts，在 &iomuxc 里加一组 pinctrl。
  • 加一个 gpio-leds 节点，写 gpios、pinctrl-0、default-state。
  • make dtbs，把新 dtb 传到板子（或 NFS/TFTP），改 bootargs 让它加载新 dtb。
  • 启动后看 /sys/class/leds/ 下有没有你的 label；echo 1 > brightness 测试。
  • 没反应就 dmesg | grep -i led，看驱动是否匹配失败。

10.7 动手任务

  • 编一次内核，记录从 make 开始到结束的耗时和产物大小。
  • 用 menuconfig 关掉一个明显用不到的功能（如某个文件系统），重编，对比 zImage 体积变化。
  • 把板子上现成的 .dtb 反编译成 .dts，找出 memory、chosen、leds 三个节点。
  • 按 10.6 的流程改 dts，让一个 LED 开机常亮，再改成常灭，各验证一次。
  • 故意把 gpios 里的引脚号改错，观察 dmesg 报什么错，再改回来。

10.8 验收标准

  • 能独立配置并编译出 zImage 与 dtb
  • 能解释 defconfig、.config、menuconfig 三者关系
  • 能读懂一个 dts 节点，说出 compatible、reg、status 的作用
  • 能用 dtc 反编译 dtb 并找到关键节点
  • 能改设备树控制一个 LED，并知道失败时怎么查
  • 能说出 pinctrl 配错会导致什么现象
