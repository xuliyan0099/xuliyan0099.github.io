卷 07·芯片与硬件底座·第 03 篇

总线体系：AXI / AHB / APB 与 I2C / SPI / CAN

「地址对了却读不到」「写寄存器没反应」「I2C 一直 NACK」——这些现象几乎都出在总线层。这一章从 SoC 内部的三级互连讲到板上的两根线，把「一次寄存器读」和「一次 I2C 传输」的物理过程讲完。

★ 一读 纯读约 4 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① CPU 读写一个外设寄存器，信号在路上经过什么；② AXI/AHB/APB 为什么要分三级；③ 为什么访问外设前必须先开时钟，不开会「挂死」；④ I2C、SPI、CAN 的时序差在哪；⑤ 寄存器位域为什么不能直接赋值。

读完你应该能回答

  • 一次 32 位寄存器读，从 CPU 发出地址到拿到数据，经过哪几级？
  • CCGR 寄存器是干什么的？漏开时钟会有什么现象？
  • I2C 的 ACK 是谁发的？为什么上拉电阻不能省？
  • SPI 的四种模式由哪两个参数决定？
  • 「写 1 清 0」和「读清」两种标志位，操作方式差在哪？

1. SoC 内部的三级互连

芯片内部不是「所有外设都挂在一条总线上」，而是按速度分层。i.MX6ULL 用的是 ARM 的 NIC（Network Interconnect）架构，概念上分三级：

层级全称特点挂什么
AXIAdvanced eXtensible Interface高性能、可乱序、多通道（读写分离）、支持突发传输CPU、DDR 控制器、DMA、显示控制器
AHBAdvanced High-performance Bus中等性能、单时钟沿、突发有限USB、SD/eMMC、以太网 MAC
APBAdvanced Peripheral Bus低速、简单、每次一笔传输UART、I2C、SPI、GPIO、定时器、看门狗

分层的原因很现实：DDR 需要每次搬 64 字节甚至更多，而 UART 的一个寄存器只要 4 字节。如果全用最高速的总线，面积和功耗都浪费；如果全用最低速的，CPU 取指都会被拖慢。所以中间用「桥」（bridge）把不同速度的域隔开：CPU 访问 APB 外设时，请求要经过 AXI→AHB→APB 两级桥，每次桥都增加几个周期延迟。

这也解释了一个实际现象：访问 GPIO 寄存器比访问 DDR 慢。不是因为 GPIO 本身慢，而是路径长（多两级桥）+ 通常 uncached（每次都要真的走到硬件）。

2. 一次寄存器读的物理过程

以 readl(GPIO1_BASE + DR) 为例，信号层面发生的是：

CPU 发地址→AXI 主机端口→地址译码→桥转发到 APB→从设备选中→寄存器值上数据线→沿原路返回
  1. 地址译码：互连里有一张地址映射表，判断这个地址属于哪个从设备（比如 0x0209_C000 落在 GPIO1 的窗口）。不属于任何设备，就会返回总线错误（在 ARM 上表现为 Abort，内核里可能直接 panic）。
  2. 桥转换：AXI 的协议（含 ID、突发长度、QoS）要翻译成 APB 的简单「地址+选通+读写」。这一步会插入等待周期。
  3. 从设备响应：外设可能「还没准备好」，它会拉低 HREADY/插入 wait state，总线就停在那里等。这就是为什么慢外设会拖慢 CPU。
  4. 返回数据：32 位值沿原路回到 CPU 寄存器。
关键认知：总线是「同步握手」的 主设备发请求后必须等从设备回应，不是发出去就完事。所以一次外设访问的耗时不由 CPU 主频决定，而由最慢的那个环节决定（桥延迟 + 外设等待周期）。

3. 时钟门控：不开时钟，总线会「挂死」

这是 i.MX6ULL 上最容易踩的坑。SoC 里每个外设的时钟都是单独门控的（为了省电），由 CCM 的 CCGR 寄存器组控制。时钟没开时访问该外设会发生什么？

不是「读到 0」，而是总线永远等不到响应：从设备没有时钟就不会拉 HREADY，主设备就一直等，最终 CPU 卡死在这一条 load 指令上。现象是：

  • 系统看起来「死机」，串口也不打印（因为串口自己的时钟可能也受影响）。
  • 用 JTAG 挂上去看，PC 停在某条 ldr 上，且该地址正是你访问的外设。

所以裸机/U-Boot 阶段的铁律是：先开时钟，再碰寄存器。顺序反了就是硬挂死，不是软件报错。这也是 T11 要把时钟树单独讲一章的原因。

算一笔：为什么「先开时钟」能救命
不开时钟：访问 → 从设备无响应 → 主设备等待 → 无超时机制 → CPU 永久停在该指令
开了时钟：访问 → 从设备 1–3 个周期响应 → 正常返回
代价对比：多写一个寄存器（几纳秒）vs 整机挂死（只能复位）
所以在驱动 probe 的依赖链里，clk_prepare_enable() 永远排在寄存器访问之前

Linux 里这件事由 clock framework 代管：你在 dts 里写 clocks = <&clks IMX6UL_CLK_GPIO1>，驱动里 clk_prepare_enable()，内核会自动去操作 CCGR。所以「设备树写对了但时钟没配」是常见的一类 probe 失败。

4. 板级总线：四根线以内的世界

SoC 内部靠并行总线，芯片之间靠串行总线。嵌入式最常打交道的四种，行为差别很大：

总线线数速率（典型）拓扑典型器件
I2C2（SCL/SDA）100k / 400k / 1M多主多从，靠地址区分EEPROM、PMIC、传感器、触摸屏
SPI4（SCK/MOSI/MISO/CS）几 MHz – 几十 MHz一主多从，靠片选区分Flash、LCD、ADC、无线模块
CAN2（CANH/CANL，差分）125k – 1M多主，报文 ID 仲裁汽车电子、电机控制器
USB2（D+/D-）12M / 480M主机–从机（星型）U 盘、摄像头、串口转换

4.1 I2C：两根线怎么谈成一笔交易

I2C 只有 SCL（时钟）与 SDA（数据），且两者都是开漏输出，必须外接上拉电阻。这个硬件细节直接决定了协议行为：

  • 线与逻辑：任何设备都可以把线拉低，但只有所有设备都放手时线才为高。所以「拉低」代表「有人在说话」。
  • ACK：主机发完 8 位（7 位地址 + 1 位读写方向）后释放 SDA，从机如果存在就把 SDA 拉低一个时钟——这就是 ACK。没拉低就是 NACK，含义是「这个地址没人」或「我不收了」。
  • 时钟拉伸：从机忙不过来时可以一直拉低 SCL，主机就会等——这是 I2C 唯一的流控手段。
  • 没有上拉或阻值过大：上升沿变慢，高速下波形变成「圆角」，表现为随机 NACK、数据错位。这是 I2C 调试最常见的硬件问题。

一次典型的「读寄存器」交易（以常见的传感器为例）分两段：写寄存器地址（NACK 前结束）→ 重复起始 → 读数据。Linux 的 i2c_smbus_read_byte_data() 就是这两段的封装。

4.2 SPI：四个参数决定能不能通

SPI 是全双工、无地址、无 ACK 的总线。它的「配置」几乎全在时序上，四个关键参数：

参数含义配错了会怎样
CPOL空闲时 SCK 是高还是低采错边沿，收到全 0 或全 1
CPHA在第一个还是第二个边沿采样数据整体移位一位，值全错
位宽8 位 / 16 位 / 32 位字节序与对齐全乱
速率SCK 频率超过从设备上限就随机出错

CPOL 与 CPHA 组合出四种模式（Mode 0–3）。Mode 0（CPOL=0, CPHA=0）最常见：空闲低电平，上升沿采样。设备手册一定会写它用哪个模式，抄错就完全读不出数据，而且现象往往是「读回 0x00 或 0xFF」——这时候先查模式，不要怀疑接线。

片选（CS）也常出问题：有些器件要求 CS 在整个传输期间保持低电平，如果驱动在每次读写之间把 CS 抬高，器件会把它当成两笔独立命令，行为就错乱了。

5. 寄存器操作的五个陷阱

寄存器不是普通内存，它有「写进去不一定立刻生效」「读出来会清掉」这些硬件语义。五条必须记住的规则：

  1. 不要直接赋值，要读-改-写。 writel(1, base+CTRL) 会把整个寄存器其他位清零，关掉别人的功能。正确做法：先 readl，再置位/清位，最后写回。
  2. 写 1 清 0 型标志位：写 0 没效果。典型是中断状态寄存器。若你写 writel(0, p) 想「清零」，只会什么都不发生，中断永远不清。
  3. 读清型标志位：读完自动清零。这类位不能「先读一遍看状态，再决定要不要处理」——你一读就已经清掉了。
  4. 自清型动作位：写 1 触发一次动作，硬件做完自己清 0。不要「写完再读回来确认」（可能已经被清掉）。
  5. 写完可能要 dsb()：若后续动作依赖这次写已生效（例如打开时钟后再访问外设），中间要有屏障，否则流水线可能让后一条访问先到（见 T07）。

6. 八个常见误解

误解真相
「所有外设都挂在一根总线上」是分级的互连：AXI / AHB / APB，中间有桥，访问不同外设延迟不同。
「地址对就能访问」还要地址译码命中、设备时钟开启、总线没被占用、权限允许。
「时钟没开最多读到 0」更可能是总线永久等待、CPU 硬挂死，只能复位。
「I2C 的 ACK 是主机发的」写操作时 ACK 由从机发；读操作的最后一个字节由主机发 NACK 表示结束。
「I2C 不需要上拉电阻」开漏输出必须上拉，否则线永远浮空，波形无法成形。
「SPI 只要有线就能通」CPOL/CPHA 模式必须与器件手册一致，错了读回 0x00 或 0xFF。
「寄存器可以直接赋值」会误清其他位，必须读-改-写。
「总线速度由 CPU 主频决定」外设访问速度由最慢环节决定：桥延迟 + 从设备等待周期。

7. 自检：能答出来才算懂

1

AXI、AHB、APB 各挂什么？为什么要分三级？

看答案

AXI 挂 CPU/DDR/DMA/显示；AHB 挂 USB/SD/以太网；APB 挂 UART/I2C/SPI/GPIO/定时器。分级是为了在「带宽」和「面积功耗」之间取舍，并用桥隔离速度域。

2

一次寄存器读，路上经过哪几个环节？哪一步最可能变慢？

看答案

地址译码 → 桥转换（AXI→AHB→APB）→ 从设备响应 → 数据回传。最慢的通常是桥延迟与从设备的 wait state。

3

没开外设时钟就访问它的寄存器，会发生什么？

看答案

从设备无法响应握手，总线永久等待，CPU 卡在那条 load/store 上，表现为整机假死，通常只能复位。

4

I2C 的 ACK 是谁发的？NACK 有哪几种常见含义？

看答案

写方向由从机发 ACK；读方向的最后一位由主机发 NACK 表示结束。NACK 常见含义：该地址无器件、器件忙、器件不接收该命令、上拉/波形问题。

5

SPI 读回全 0x00 或全 0xFF，最先该查什么？

看答案

先查 CPOL/CPHA 模式是否与器件一致，再查 CS 是否在整个传输期间保持有效、位宽与速率是否匹配。模式错是最常见原因。

6

「写 1 清 0」和「读清」操作方式差在哪？各举一个坑。

看答案

写 1 清 0：必须写 1 才清，写 0 无效（坑：以为写 0 能清）。读清：一读就清（坑：想先读看状态，读掉之后就处理不了）。

7

为什么访问外设寄存器不能用 memcpy 那套优化？

看答案

因为排序、合并、预读都会改变「实际访问硬件的次数与顺序」。寄存器要求每次访问都真实到达，所以要用 readl/writel（内部含 volatile 与屏障）。

8

CAN 为什么不需要「地址」？多节点怎么避免冲突？

看答案

CAN 用报文 ID 标识内容而非节点，靠「ID 越小优先级越高」的非破坏性仲裁：多个节点同时发时，发 0 的赢，发 1 的自动退让稍后重发，不丢数据。

8. 这一章要动手的命令

  1. busybox devmem 0x0209C000 32 —— 直接读 GPIO1 数据寄存器，验证「地址 + 空指针」就能访问硬件。
  2. cat /sys/kernel/debug/clk/clk_summary | head -30 —— 看各时钟频率与使能状态（需 debugfs）。
  3. i2cdetect -y 0 —— 扫描 I2C 总线上的地址，快速判断器件是否在线。
  4. i2cget -y 0 0x50 0x00 —— 读 EEPROM 第一个字节，验证 I2C 通路。
  5. ls /sys/bus/i2c/devices/ —— 看内核识别到的 I2C 设备与地址。
  6. cat /proc/interrupts | grep -i i2c —— 确认 I2C 中断在工作。
  7. dmesg | grep -i -E "bus|i2c|spi" —— 找总线初始化失败、NACK 报错的痕迹。
