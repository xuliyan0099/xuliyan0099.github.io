卷 04·操作系统·第 01 篇

操作系统与 Linux 的分层

这一章要把「操作系统」拆到指令级：一条用户态指令怎么被硬件拦住、它怎么求内核办事、内核办事用的是谁的内存、回来时凭什么能接着跑。读完这章，strace 的输出在你眼里不再是符号，而是一次次真实的现场切换。

★ 一读 纯读约 3 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 没有操作系统，一个 C 程序缺什么；② 用户态与内核态在硬件上如何实现；③ 一条 write() 从用户代码走到磁盘驱动要穿过哪些层；④ 为什么内核在所有进程里「地址相同」；⑤ Linux 为什么坚持宏内核，代价是什么。

读完你应该能回答

  • ARM 上一次系统调用，硬件自动保存了哪两个寄存器，软件还必须保存什么？
  • 系统调用的参数与返回值分别放在哪几个寄存器，错误码为什么用负数？
  • copy_from_user() 除了「查权限」，还在防什么？
  • 进程切换时页表基址寄存器换了几个，为什么可以只换一个？
  • 驱动里一个野指针，为什么能让整机重启而不是只崩一个进程？

1. 先把抽象拆掉：一条指令的一生

CPU 的工作循环只有三步：取指 → 译码 → 执行。它认识的东西只有三样：

  • 寄存器：几十个，读写零延迟，装着当前正在算的数。
  • 内存：一大片可按地址访问的存储，一次访问要几十到上百周期。
  • 指令：加减、比较、跳转、读写内存，就这些。

它不认识文件、进程、网络、键盘输入。这些概念全部是软件造出来的。操作系统就是那个「造概念」的软件：把「一块内存 + 一个 CPU」包装成「文件、进程、网络连接」。

所以「学 Linux」本质是两件事：它造了哪些概念（进程、虚拟地址、inode、socket），以及这些概念靠什么硬件机制撑住（MMU、中断、特权级）。只有前者，你只会用命令；只有后者，你写不出能上板子的代码。

2. 没有操作系统，一个 C 程序缺什么

假设在一块裸板（i.MX6ULL，没 U-Boot、没内核）上要跑这段代码：

int main(void) { int buf[1024]; /* 栈上 4KB */ printf("hello\n"); /* 要串口驱动 */ FILE *f = fopen("a.txt"); /* 要文件系统 */ return 0; }

它至少缺六样东西，每一样都对应操作系统的一个子系统：

缺什么裸机上会发生什么谁提供
栈指针复位后 SP 是随机值，第一条压栈就写飞启动代码（内核 head.S 也做这件事）
BSS 清零未初始化全局变量是垃圾值，逻辑随机出错启动代码 / C 运行库
内存分配malloc 没有堆可给内存管理子系统
输出通道printf 不知道往哪写驱动 + 系统调用
文件概念fopen 无从谈起，得自己管闪存块VFS + 文件系统
多任务只能一件事干到底，没法「等串口的同时算别的」进程管理 + 中断
记住这个视角 后面每章都在回答同一个问题：这个能力是靠什么机制做出来的。当你能把「printf 为什么能在没屏幕的板子上出字」一路追到「串口寄存器 + 中断 + 系统调用」，原理就通了。

3. 四个必须解决的矛盾

操作系统不是「为了方便」才出现的，是被四个硬矛盾逼出来的。每条给出具体灾难与对应机制：

矛盾具体灾难OS 的解法所属子系统
程序之间要隔离A 越界写坏了 B 的数据，B 算错，还查不出是谁干的每进程独立虚拟地址空间 + 页表权限位内存管理
地址不能固定程序每次加载到不同物理地址，编译期无法确定函数地址虚拟地址 + MMU 重定位内存管理
物理内存装不下同时开 5 个程序就 OOM按需分配、换出、回收内存管理
硬件要被复用两个程序同时用串口，字节互相穿插，谁都发不完整统一设备抽象 + 互斥 + 缓冲队列设备 / 驱动

这四条把「内存管理」和「设备抽象」推到核心位置。你以后遇到的诡异问题大多能归到某一格：地址错乱看第一格，随机崩溃看第一或第三格，外设行为怪看第四格。

4. 用户态与内核态的硬件实现（ARM 实例）

「内核态」不是一个抽象说法，它是 CPU 里一个状态位。ARM 的当前程序状态寄存器 CPSR 有一个 5 位的模式字段 M[4:0]，它决定两件事：你能执行哪些指令、你访问内存时按哪套权限判。

CPSR 低 5 位（模式字段）常见取值 0b10000 User 用户态，PL0，绝大多数指令可执行，特权指令被拦 0b10011 SVC 内核态主体，复位后默认进入 0b10010 IRQ 普通中断 0b10001 FIQ 快速中断 0b10111 Abort 访存异常（缺页、越权） 0b11011 Undefined 未定义指令 0b11111 System 与 User 共享寄存器视图，但特权级是 PL1

哪些操作在 User 模式下会被硬件直接拒绝？记四类就够用：

  • 改 CPSR 的模式位（MRS/MSR 访问特权字段）——不然你可以自己升到内核态。
  • 开关中断（cpsid 一类）——不然你能让系统永远收不到时钟。
  • 访问协处理器（MCR/MRC）——MMU、Cache、时钟配置全走协处理器指令。
  • 访问被页表标为「仅内核」的内存——这条由 MMU 在每次访问时判，不是指令级拦截。

如果用户态程序硬要执行 MCR p15（比如想自己配 MMU），CPU 会抛 Undefined Instruction 异常，跳进内核的异常向量，内核一看是用户态来的非法指令，直接给这个进程发 SIGILL 杀掉。这就是「非法指令」错误的技术来源。

所以用户态想干特权事，唯一合法通道是：主动触发一个异常，让硬件把自己切进内核态。ARM 上这条指令叫 SVC（Supervisor Call，旧称 SWI）。

5. 一次系统调用的完整现场

拿最常见的一句 write(fd, buf, n) 从头走到尾。这条链路你走通一次，所有系统调用都一样。

5.1 用户侧：glibc 只做三件事

C 库函数 write() 并不是内核函数，它是一小段汇编包装（ARM EABI 约定）：

寄存器装什么
r0第 1 个参数：fd
r1第 2 个参数：buf（用户空间地址）
r2第 3 个参数：n（字节数）
r3–r6第 4–7 个参数（大多数调用用不到）
r7系统调用号，write 是 4
r0（返回时）返回值：成功是字节数，失败是负的 errno
/* glibc 里 write 的实质（示意） */ mov r7, #4 /* __NR_write */ svc #0 /* 触发异常，切内核态 */ bx lr /* 回来后继续执行，r0 已有返回值 */

也就是说：系统调用号放在 r7，参数放在 r0–r6，用一条 svc 触发。这三条约定你必须记死，因为内核入口就是照这个读的。

5.2 硬件：自动保存两个寄存器，切栈，跳向量

svc 执行的那一瞬间，CPU 硬件替你做了四件事（不需要软件参与）：

  1. 把当前 CPSR 复制到 SPSR_svc（保存「回来时该是什么模式」）。
  2. 把 下一条指令地址（PC + 4）放进 LR_svc（保存回来从哪继续）。
  3. 把 CPSR 的模式位改成 SVC，同时切到 SVC 模式自己的 SP（每个模式有独立的栈指针备份）。
  4. 把 PC 跳到异常向量表的 SVC 那一格（基址由 VBAR 决定，SVC 通常是基址 + 0x08）。
硬件只救两个寄存器，剩下的必须软件救 r0–r12 里的值、以及「用户态当时用的那个 SP」都在原处没动。所以内核入口第一件事就是把 r0–r12、SP、LR、SPSR 全部压进内核栈，形成一个叫 struct pt_regs 的结构。以后所有「保存现场 / 恢复现场」说的就是它。

5.3 内核：查表、分派、干活

svc 指令→向量表 SVC→保存 pt_regs→读 r7 取号→sys_call_table[4]→sys_write()→VFS → 驱动

关键代码在 arch/arm/kernel/entry-common.S：它做的事朴素到令人意外——用 r7 作为下标，去一张函数指针数组里取地址，然后跳过去。这张表叫 sys_call_table，几百个系统调用就是几百个表项。

sys_write(fd, buf, count) 拿到的是用户空间的地址。内核不能直接解引用它（那是别人进程的地址空间，且可能根本没映射），所以要走 copy_from_user() 把数据拷进内核缓冲，再交给 VFS 往下走。这一步是「用户数据」和「内核数据」的法定边界。

5.4 返回：一个寄存器同时表达值与错误

内核干完活，把结果写进 pt_regs 里的 r0 槽位，恢复 r0–r12 和 CPSR，跳回 LR 指向的用户态指令。约定是这样的：

返回值含义用户态看到
≥ 0成功，具体数值（字节数、fd、0）直接就是返回值
负值（-1 ~ -4095）失败，绝对值是错误码（-EINVAL、-ENOENT）libc 转成 return -1 + 设置 errno

为什么用负数？因为合法的成功返回值永远是非负的（字节数不会为负、fd 不会为负）。这样一个寄存器就同时承载了「值」和「是否出错」两件事，省掉一次额外的输出参数。而用户态看到的 errno 是 libc 帮你从负值里翻译出来的——内核里根本没有 errno 这个全局变量。

算一遍：write 失败的完整数据流
用户调用：write(-1, buf, 10)
glibc：r7 = 4，r0 = -1，r1 = buf，r2 = 10，执行 svc 0
内核 sys_write：fd 非法 → 返回 -EBADF（-9）
返回：r0 = -9
glibc：r0 落在 -1 ~ -4095 → errno = 9（EBADF），返回值改成 -1
用户看到：write 返回 -1，errno == EBADF

6. 用 strace 亲眼看这些切换

理论讲完，用一条命令验证。写一个最小程序，只做「打开文件、读 5 字节、往屏幕打印」：

$ cat demo.c #include <stdio.h> #include <fcntl.h> #include <unistd.h> int main(void){ char b[8]={0}; int fd=open("a.txt",O_RDONLY); read(fd,b,5); write(1,"hello\n",6); return 0; } $ gcc -o demo demo.c && strace ./demo

你会看到类似这样的输出（已精简）：

execve("./demo", ["./demo"], 0x7ffd...) = 0 openat(AT_FDCWD, "a.txt", O_RDONLY) = 3 read(3, "hello", 5) = 5 write(1, "hello\n", 6) = 6 exit_group(0) = ?

逐行拆：

  • 格式：系统调用名(参数…) = 返回值。每一行背后都是「切内核 → 干活 → 切回来」一整套现场。
  • openat(...) = 3：为什么是 3？因为 0/1/2 已经分别被标准输入、输出、错误占用，新 fd 从 3 开始分配。
  • read(3, "hello", 5) = 5：内核把文件内容从页缓存拷到用户缓冲，返回实际读到的字节数（可能少于请求值，这很正常）。
  • write(1, ...) = 6：fd 1 是 stdout，最终落到终端设备驱动。
  • exit_group(0) = ?：没有返回值，因为进程已经没了。

再补两个实用观察：strace -c ./demo 会给出每个系统调用的次数与耗时占比，你能立刻看出「程序时间都花在哪」；strace -e trace=openat,read ./demo 只盯你关心的调用，输出立刻清爽。

7. 内核空间与用户空间：为什么切进程只换一个寄存器

32 位 ARM 上虚拟地址空间共 4GB，Linux 把它切成两半（俗称 3G/1G）：

区域范围谁可见谁管理
用户空间低 3GB每个进程各自一份，互不可见进程自己的页表
内核空间高 1GB所有进程看到的是同一份全局页表，不随进程变

这个效果靠 ARM 的两个页表基址寄存器实现：TTBR0 管低地址，TTBR1 管高地址。于是：

  • 进程切换：只改 TTBR0，内核那 1GB 的映射完全不动。
  • 系统调用：从用户态进内核态不需要切页表，因为内核映射一直都在、地址都一样。
  • 数据传递：内核要用用户数据，只能通过 copy_from_user() 这类接口「跨边界拷贝」。
这条设计解释了三件事 ① 系统调用为什么快（不用刷 TLB、不换页表）；② 为什么内核代码在所有进程里地址相同（所以内核里可以用绝对地址）；③ 为什么内核拿到用户指针必须小心（那个地址在当前进程里也许有效，换个进程就无效，甚至可能是恶意伪造的）。

再往下一层：用户态指针交给内核时，内核不能用 try/catch 那套。它的做法是——用 copy_from_user()，内部会：检查地址范围是否落在用户空间（不能让你拿内核地址来读内核数据）、处理缺页（用户页可能还没分配，需要先触发分配）、拷贝失败时返回未拷贝的字节数而不是崩掉。这就是为什么驱动里「直接解引用用户指针」是严重错误：它不仅可能读错数据，还能被用来提权。

8. 宏内核：Linux 的选择与代价

操作系统有两种主流架构，差别可以用一句话概括：让各个子系统住在同一个地址空间里，还是各自住在独立进程里。

维度宏内核（Linux、FreeBSD）微内核（QNX、seL4）
文件系统、网络栈、驱动在哪全在内核地址空间各自是独立进程
模块间通信方式直接函数调用（纳秒级）进程间消息（两次上下文切换 + 拷贝）
一个驱动写坏了整机 panic / 重启该服务进程被杀，可重启
性能高（无通信开销）较低（通信开销显著）
典型场景通用、成本敏感、生态庞大安全关键、高可靠（车载仪表、医疗）

一个常见误解是「可加载模块（.ko）就相当于微内核的服务」。不是。加载模块只是把代码动态链接进内核地址空间：它和你写的内核代码用同一个栈、同一套全局变量、同样的绝对地址，可以互相直接调函数。insmod 的本质是「在运行时往内核里插一段代码」，不是「启动一个新进程」。

由此推出的三条硬约束 ① 驱动里的野指针、数组越界、栈溢出，后果是整机 oops 甚至 panic，不是「程序退出」；② 内核栈很小（ARM 上通常只有几 KB），递归和栈上大数组是禁忌；③ 内核里不能「随便睡眠」，因为你睡的可能是整个系统唯一在干活的那条流。

9. 内核源码树导览

不要求你现在读源码，但必须知道「出问题该去哪个目录找」。这张表是全书最实用的一张：

目录放什么你会来这里的场景
arch/arm/ARM 架构相关：head.S、异常向量、MMU 初始化、dts 目录看启动流程、找机器码检查、找板级 dts
mm/内存管理：页表、伙伴系统、slab、缺页处理研究 OOM、理解 vmalloc、查缺页路径
fs/VFS 与各文件系统：ext4、proc、sysfs、nfs看 open 的完整路径、查 fsync 语义
kernel/调度、中断管理、定时器、工作队列、printk看调度策略、理解上下半部
drivers/所有设备驱动，按总线分类（i2c、spi、mmc、net、gpio…）找同款外设驱动抄结构、看 probe 怎么写
include/linux/内核内部 API 头文件查函数原型、查结构体字段
init/start_kernel、initcall 机制看初始化顺序
net/协议栈理解收包路径、看 socket 状态
lib/内核自己的通用库（字符串、CRC、排序）别和用户态 libc 搞混
Documentation/官方文档：设备树绑定说明就在这查某个 dts 属性到底怎么写

看源码有个高效套路：从「我要找的东西」反向搜字符串。比如设备树里看到一个陌生的 compatible 值，直接在内核目录里 grep -rn "vendor,model" drivers/，五分钟就能定位到驱动文件，比从头读目录快十倍。

10. 版本号：别被数字骗了

Linux 的版本号格式是 主版本.次版本.修订号，外加后缀：

6.6.30 LTS 稳定版（长期维护，产品首选） 6.6.0-rc3 候选发布版（rc = release candidate，别用于产品） 4.1.15 常见于 i.MX 厂商 BSP（老，但外设驱动最全） 6.10 主线新版本（功能新，老芯片支持可能缺）

关于「次版本号是奇数还是偶数表示开发版」的老规矩：3.0 之后已经废除了，现在只看有没有 -rc 后缀。这是一个很常见的过时知识点。

uname -a 的输出逐段拆开看：

Linux myboard 6.6.30 #1 SMP PREEMPT Wed ... armv7l GNU/Linux ①系统名 ②主机名 ③内核版本 ④构建号与特性 ⑤构建时间 ⑥CPU架构 ⑦操作系统

第 ④ 段信息量最大：SMP 表示多核支持已编入，PREEMPT 表示内核可抢占（实时性更好），这两个词直接决定你系统的行为特征。看到 PREEMPT_RT 就说明这是实时内核。

11. 十个常见误解（照着自查）

误解真相
「内核态运行得更快」同一颗核、同一频率、同一条流水线。差别只有权限与地址可见性，不是性能档位。
「系统调用就是普通函数调用」多了三件事：模式切换、栈切换、现场保存恢复。一次空系统调用在 ARM 上也要几百纳秒。
「errno 是内核里的全局变量」errno 是 libc 提供的线程私有变量，内核只返回负的错误码，翻译在用户态完成。
「内核和用户共用一个栈」每个模式有自己的 SP。SVC 一进来用的就是内核栈，用户栈指针只是被存进 pt_regs 里等着恢复。
「加载模块等于启动一个内核进程」模块只是被链接进内核地址空间的代码段，没有独立进程、没有独立地址空间。
「虚拟地址是假的、不存在的」虚拟地址是逻辑地址，硬件每次访问都会翻译成物理地址。它比物理地址更"真实"，因为它是程序唯一认识的世界。
「内核数据在所有进程间共享」共享的是内核代码与映射。内核里的全局变量是全局唯一的一份，但进程私有的东西（页表、文件表）各是各的。
「32 位系统最多 4GB 物理内存」开了 LPAE 可以超出，但单个进程的虚拟地址空间仍是 4GB，这是虚拟地址位宽决定的。
「系统调用越少程序越快」真正的优化点是 vDSO（把 gettimeofday 之类放进用户态共享页）和批量接口，而不是硬减调用次数。
「Linux 就是 Unix」Linux 是「类 Unix」，未通过 Unix 商标认证。这个区别在文档里偶尔会咬你一口。

12. 自检：能答出来才算懂

1

执行 svc #0 那一条指令时，硬件自动保存了哪两个寄存器？软件还必须补保存什么？

看答案

硬件保存 CPSR → SPSR_svc 和 PC+4 → LR_svc，并把模式切到 SVC、切到 SVC 的栈。软件必须把 r0–r12、用户 SP、LR 压进内核栈组成 pt_regs，因为硬件没管这些通用寄存器——它们还带着用户态的值。

2

系统调用号放在哪个寄存器？参数放哪？返回值放哪？

看答案

号在 r7，参数在 r0–r6（最多 7 个），返回值回到 r0。这是 ARM EABI 的约定，写汇编或做 inline syscall 时必须遵守。

3

为什么内核返回错误要用负值，而不是返回 -1 再单独给个错误码？

看答案

因为合法的成功返回值恒为非负（字节数、fd、0）。用负值编码错误，一个寄存器就同时表达了「结果」和「成败」，不需要额外输出参数，也不破坏 ABI。libc 再把负值翻译成 -1 + errno。

4

copy_from_user() 到底在防什么？只说「查权限」为什么不完整？

看答案

防三件事：① 地址是否落在用户空间（否则可以拿内核地址骗内核读自己的数据，形成提权漏洞）；② 目标页是否已映射（用户页可能还没分配，需要触发缺页处理）；③ 拷贝过程中发生异常时必须安全返回而非崩溃。所以它的返回值是「还剩多少字节没拷成功」，不是布尔值。

5

进程切换时，页表基址寄存器换了几个？为什么可以只换一个？

看答案

只换 TTBR0（管低 3GB 用户空间）。TTBR1（管高 1GB 内核空间）保持不变，所以内核映射在所有进程里地址相同，系统调用不需要切页表、不需要刷 TLB。

6

驱动里写了个野指针，为什么可能整机重启，而不是只崩一个进程？

看答案

因为驱动代码运行在内核地址空间，用的是内核栈，访问的是共享的内核数据。它踩坏的东西可能是别的进程的页表、调度器链表、文件系统缓存——一旦这些被破坏，内核自己就站不住了，触发 oops 或 panic。

7

strace 输出里 openat(...) = 3，为什么不是 0？

看答案

0/1/2 已被 stdin/stdout/stderr 占用（进程启动时由 shell 或父进程继承）。fd 是按最小可用编号分配的，所以新文件拿到 3。

8

为什么说「系统调用不需要切页表」，但「进程切换需要」？

看答案

系统调用是从用户态进内核态，两者共用当前进程的页表（内核那半在所有进程都一样），所以不换。进程切换要换的是「用户那半」，即 TTBR0，让 CPU 看到另一个进程的 3GB 世界。

9

宏内核架构下，一个文件系统模块崩溃为什么能拖死整机？

看答案

因为它和内核共享地址空间与栈，没有进程边界保护。任何越界写都可能破坏内核数据结构；内核检测到不一致状态只能 panic。微内核把文件系统放到独立进程，就是为了把这类故障关在笼子里。

10

看到内核版本 6.6.30，你能判断它适合做产品吗？还要看什么？

看答案

6.6 是 LTS 分支，6.6.30 是稳定小版本，原则上适合产品。还要确认：① 你的 SoC 在该版本有没有成熟支持（尤其 GPU、VPU、PMIC 这类闭源或半开源模块）；② 厂商 BSP 是否基于该版本；③ 是否需要 PREEMPT_RT 等特殊配置。

13. 这一章要动手的命令

  1. strace -c ./demo —— 看系统调用的次数与耗时占比，建立「时间花在哪」的直觉。
  2. strace -e trace=openat,read,write ./demo —— 只盯关键调用，输出干净。
  3. ltrace ./demo —— 看库函数调用（和 strace 对照，理解「库函数 → 系统调用」的层级差）。
  4. cat /proc/self/maps —— 看一个进程的地址空间布局，找 3G/1G 分界线。
  5. lsmod / modinfo <模块名> —— 看清「模块」到底是什么形态的东西。
  6. objdump -d ./demo | head -40 —— 在反汇编里找到那条 svc，验证本章第 5 节。
  7. uname -a —— 按第 10 节逐段解读自己机器的那一行。
