CPU 是怎么执行一行代码的（详解）

这一章是「计算机组成原理」的实机版：从一串 0 和 1 开始，讲到一条指令怎么被取出来、译码、执行、访存、写回，再讲到 Linux 里一次系统调用、一次时钟中断、一次线程切换时，CPU 里那 16 个通用寄存器、CPSR、PC、SP、页表基址寄存器到底被谁改成了什么值。全程用 i.MX6ULL 的

★ 一读 纯读约 3 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 机器码里的 0/1 到底怎么划分成「指令」；② 一条 mov r0,#1 从内存到执行完，中间经过哪些硬件部件；③ 流水线为什么要「猜」；④ 为什么访问 DDR 那么慢、Cache 怎么救；⑤ Linux 切换线程时，究竟保存了哪几个寄存器、谁改的 PC、谁改的页表；⑥ 切一次线程为什么贵。

读完你应该能回答

  • 为什么 mov r0, #0x12345678 在 ARM 上编不出来，必须拆成 movw + movt？
  • 一条 ldr r0,[r1] 从发出到数据进 r0，最短几个周期、最长几个周期？
  • ARM 的 bl 和 b 差在哪一位？（提示：L 位）
  • 中断来时，硬件自动做了什么、软件还要补做什么？
  • switch_to 只保存 r4–r11 + sp + pc，为什么不保存 r0–r3？
  • 切线程时页表换了，TLB 一定要全刷吗？

1. 先给一张全局地图：CPU 一辈子只干五件事

不管多复杂的程序，落到硬件层面就是这五步在循环：取指（Fetch）→ 译码（Decode）→ 执行（Execute）→ 访存（Memory）→ 写回（Write back）。所谓「CPU 在工作」，就是 PC 指到哪里，这五步就在那里重复一次。

这里有一个非常关键的认知：CPU 内部没有「程序」这个概念。它不知道什么是循环、什么是函数、什么是线程。它只知道三样东西：

  • 一个叫 PC 的寄存器，里面存着「下一条要执行的指令的地址」；
  • 一堆寄存器（r0–r15 + CPSR），里面存着临时数据；
  • 一组按位段接线的组合逻辑，负责把读进来的 32 个比特解释成一个动作。

所谓「程序在运行」，就是内存里一段连续的 32 位字被 PC 一个个点过去。所谓线程切换，就是把 PC 和那堆寄存器换一套。后面所有内容都是这句话的展开。

2. 从二进制开始：一条指令就是 32 个比特

拿最简单的一句 C 代码开刀：

int add(int a, int b) { return a + b; }

交叉编译之后反汇编出来是这样（示意，寄存器分配随优化等级变化）：

00000000 <add>:
   0:  e0800001   add  r0, r0, r1
   4:  e12fff1e   bx   lr

左边那一列 e0800001 就是机器码，右边是它的人类可读形式。e0800001 写成 32 位二进制是：

1110 0000 1000 0000 0000 0000 0000 0001
cond 00 I opcode  S   Rn    Rd   shifter/Rm

按第 1 块图的分段表逐段读：

位段二进制含义
[31:28] cond1110AL，无条件执行（这是为什么普通指令不会被执行条件拦住）
[27:26]00数据类型指令
[25] I0第二操作数来自寄存器，不是立即数
[24:21] opcode0100ADD（0b0100）
[20] S0不更新 CPSR 标志位（所以 C 语句里的 if (a+b > 0) 会另生成一条带 S 的加法）
[19:16] Rn0000r0
[15:12] Rd0000r0
[11:0]0000 0000 0001移位类型与 Rm：Rm = 0001 即 r1

所以这三个名字说的完全是同一件事：

层次写法谁读它
比特流（内存里的样子）0xE0800001，小端存放为字节 01 00 80 E0CPU 取指单元
汇编助记符add r0, r0, r1人，以及汇编器/反汇编器
高级语言a + b编译器

注意小端这个细节：机器码本身按字（32 位）组织，但内存按字节编址，所以 0xE0800001 这四字节在内存里是低字节在前：01 00 80 E0。用十六进制编辑器看内核镜像时，指令是「反着」显示的，就是这个原因。

2.1 为什么 mov r0, #0x12345678 编不出来

看第 1 块图：立即数只有 8 位本体 + 4 位循环右移量（且移位量必须是偶数）。所以合法的立即数是一个 8 位值旋转偶数位的结果——一共只有 16×256 种。试图装 0x12345678 这种「散落在 32 位里」的数，编码位不够。

ARMv7 后来加了 movw/movt（16 位立即数进低半/高半），于是：

movw r0, #0x5678      @ 低 16 位
movt r0, #0x1234      @ 高 16 位
@ 两条指令拼出一个 32 位常量

这就是「指令编码决定语言能力」的真实案例：编译器不是随便定的，它受硬件的位段约束。学组成原理最大的收益，是看到任何一条汇编都能反推它在硬件里怎么走线。

2.2 三种你会天天见到的编码格式

指令机器码关键位段用在
ldr r0,[r1]0xE5910000[27:26]=01，I=0，P=1，U=1，B=0，W=0，L=1，Rn=r1，Rd=r0，offset=0读内存/读外设寄存器
str r0,[r1,#4]0xE5810004同上但 L=0，offset=4写内存/写外设寄存器
bl func0xEBxxxxxx[27:25]=101（分支），L=1（把返回地址存进 lr），imm24=相对偏移函数调用
b func0xEAxxxxxx同上但 L=0goto / 循环回跳
svc #00xEF000000[27:24]=1111，imm24=0系统调用（进内核）
push {r4,lr}0xE92D4010[27:25]=100（多寄存器），P=1,U=0,W=1,L=0，Rn=sp，reglist bit4=r4、bit14=lr保存现场

注意 bl 和 b 只差一位 L。L=1 时硬件顺手把「下一条指令的地址」写进 r14（lr），这就是函数调用能返回的全部秘密——不是什么软件栈魔法，是译码器看到这一位就多接了一条线。

EOF

arm-linux-gnueabihf-objdump -d t.o | head -20
arm-linux-gnueabihf-objcopy -O binary t.o t.bin

最后一行你会看到「指令在前，字节反着来」的真实二进制。对着第 1 块图的分段去拆，一路拆到 ALU 的控制脚，这一章就通了三分之一。

3. 寄存器堆：CPU 唯一能「立刻」摸到的东西

Cortex-A7 是 32 位核，通用寄存器 r0–r15 各 32 位，加一个 CPSR。数量少得可怜，所以编译器的核心工作就是「怎么把这 16 个格子用满」。

寄存器别名约定用途（AAPCS）切换线程时
r0–r3a1–a4函数参数 1–4、返回值不用保存（调用者已认为它们作废）
r4–r10v1–v7局部变量，被调用者负责保护必须保存
r11fp帧指针（可选）必须保存
r12ip过程间临时寄存器不保存
r13sp栈顶指针（每个模式各有一个）必须保存（换了栈就换了一切）
r14lr返回地址必须保存
r15pc下一条指令地址必须保存（否则回不到原处）
—cpsr模式位、中断开关、N/Z/C/V 标志必须保存（模式与标志都要恢复）

这张表看着平淡，但它直接决定了 Linux 的 switch_to 只存 r4–r11 + sp + pc（第 10 节会看到那 5 行汇编），也决定了为什么 r0–r3 在切换后是「不可信」的。所谓「上下文」，就是这张表里必须保存的那几格。

Cortex-A7 的流水线是 8 级、顺序双发射。8 级的大致划分（ARM 官方对 A7/A12 类核的经典划分）：

流水线带来的第一个反直觉结论：「一条指令几周期」和「流水线跑满时几周期一条指令」是两个不同的问题。前者叫延迟（latency），后者叫吞吐（throughput）。

动作典型延迟（A7 量级）说明
纯 ALU（add/mov/and）1 周期结果下个周期就能被下一条用（有前递）
L1 D-Cache 命中 load约 3–4 周期紧跟着用这个值，会插入 2–3 个停顿周期
L2 命中约 12–20 周期L2 是芯片内 128KB
DDR 命中（未缓存）约 100–200 周期这就是「内存墙」，第 6 节的主题
分支预测错误约 10+ 周期流水线被清空重填
乘法（32 位）1–2 周期发射，多周期完成取决于是否要等结果
CP15 协处理器访问（mcr/mrc）数十周期所以 dsb/isb 很贵，不能滥用

这些数字请当「量级」记，不同手册、不同编译器优化会差一点。重要的是差距的数量级：寄存器 1 周期 vs DDR 150 周期，差了两个数量级——这才是 Cache、预取、DMA 存在的理由。

4.1 流水线的三种冒险，以及硬件怎么救

① 数据冒险：下一条要用的寄存器，上一条还没写回。

add r0, r1, r2     @ r0 = r1+r2
sub r3, r0, r4     @ 立刻用 r0

硬件用「前递（forwarding/bypass）」解决：EX 阶段算出的结果不等 WB，直接旁路给下一条的 ALU 输入。救不了的情况（比如 load 后立刻用，值要到 WB 才出来）就插入停顿周期（stall）。编译器也会帮你排指令顺序，把不相关指令插进来填缝——这叫指令调度。

② 控制冒险：分支还没算出跳不跳，后面已经预取了指令。A7 有动态分支预测（BTB），猜错就清流水线。所以 if 分支在热循环里代价真实存在；这也是为什么内核里有大量 likely()/unlikely() 把「大概率走哪条」排成顺序执行。

③ 结构冒险：两条指令抢同一个部件（比如同时要 LSU、同时访问寄存器堆的同一端口）。A7 双发射但顺序提交，遇到冲突就只发一条。

把这三点记住，你再读内核里那些看起来「多此一举」的写法（提前算好、拆循环、__builtin_expect），就知道都有硬件层面的理由。

对应到 Linux 里的现象：

  • page fault：TLB 未命中不算错，但页表项无效（或者页不在内存）时，硬件抛 data abort，内核在异常处理里补页表、调页、再返回重试——这就是 T14 讲的缺页。
  • 段错误：权限位 AP 说「不许写」，你偏要写，同样走 data abort，内核发现是用户态越权，直接给你 SIGSEGV。
  • ioremap 必须用：外设寄存器地址在页表里要标成 Device 类型（强序、不缓存），否则 CPU 会把写入攒在写缓冲里、把读当成缓存命中，行为诡异。

这也解释了 T07 里那句「DMA 收完数据要 invalidate」：DMA 绕过 CPU 直接写 DDR，Cache 里还是旧副本，CPU 读到的就是旧值。

6. 为什么内存这么慢：Cache 与「内存墙」

CPU 主频 528MHz（一个周期约 1.9ns），而 DDR3 的一次随机访问要几十上百纳秒。两者差 50–100 倍。如果不做缓存，一颗 528MHz 的核实际表现会像 5MHz 的老机器。

Cache 的三个关键参数（写成工程语言）：

参数A7 实际值工程含义
行大小 cache line64 字节一次搬运 64B；DMA 缓冲要按 64B 对齐并独占，否则 invalidate 会误伤邻居变量
组相联4 路同一组只能放 4 条不同地址的 line，第 5 条会挤掉一条（冲突缺失）
写策略写回 + 写分配（数据 cache）写入先落在 cache 里标脏，之后才回写内存；所以「写完立刻给 DMA 用」必须 clean
地址类型VA 索引 / PA 标记（VIPT）切换进程换了页表，指令 cache 不一定要刷——这也是 ASID 能省 TLB 刷新的原因

在 Linux 上观察这些事最直接的工具是 perf：

perf stat -e cycles,instructions,cache-misses,cache-references ./your_app
perf stat -e L1-dcache-loads,L1-dcache-load-misses,branch-misses ./your_app

「cache-misses / cache-references」这个比值，就是你的代码到底有没有「顺着内存走」。数组按行遍历和按列遍历，在同一份数据上能差出 5–10 倍，原因全在这一节。

7. 函数调用：bl、lr 与栈帧，一次调用在硬件里怎么记账

先把「函数调用」这件事拆开看，因为线程切换和它长得极像，只是保存的东西更多。

main:
    ...
    bl   add          @ ①硬件：lr = 返回地址；pc = add
    mov  r3, r0       @ ④add 返回后从这里继续

add:
    push {r4, lr}     @ ②把用到的 callee-saved 寄存器押进栈
    ...
    pop  {r4, pc}     @ ③弹栈，pc 直接取回返回地址

8. 从用户态进内核：一条 svc 指令走完的路

Linux 里调用 read()，C 库最终会执行一条 svc #0（老叫法是 swi）。这条指令是唯一合法的「越权入口」：用户态代码不能直接改 CPSR 的模式位，只能靠这条指令触发异常，由硬件帮你切模式。

硬件在 svc 那一刻自动做的三件事，一定要背下来（这是组成原理的核心考点，也是读懂所有异常处理的前提）：

  1. 保存返回地址：把「svc 的下一条指令地址」写进 LR_svc（每个异常模式有自己的 LR）。
  2. 保存状态：把当前 CPSR 整份复制到 SPSR_svc。
  3. 切模式 + 关中断 + 跳向量：CPSR 的 M[4:0] 改成 0b10011（SVC），跳转到向量表偏移 0x08。

软件接着做的是：把 r0–r12 和 lr 压进内核栈（形成 pt_regs），这样内核 C 代码随便用寄存器都不会破坏用户现场；返回时反向弹栈，并用 movs pc, lr（或 ldm ..., {pc}^）把 SPSR 一次性写回 CPSR ——一条指令同时完成「跳回去」和「切回用户模式」。

确认一下你手上的板子：

[board] cat /proc/cpuinfo | head -3
[board] strace -c ls /          # 看每个系统调用被调用几次
[board] strace -f -e trace=read,write ls /

为什么要有这道门？ 因为如果用户态能直接改页表基址寄存器、直接改 CPSR，那么「进程隔离」就不存在了。特权级不是礼貌约定，是硬件层面的门锁：一般指令在 USR 模式下执行会直接触发未定义指令异常。

9. 时钟中断：内核怎么把 CPU 抢回来

如果只有 svc，一个死循环的进程会永远占着 CPU——因为它永远不会主动进内核。所以必须有一个不由程序控制的入口：定时器中断。

i.MX6ULL 上常见配置是内核 HZ=100（可以在 /proc/config.gz 或 defconfig 里确认），也就是每 10 毫秒，GPT 定时器把 IRQ 线拉高一次。IRQ 到来时，硬件做的是：

  • CPSR → SPSR_irq；
  • 返回地址 → LR_irq（IRQ 的返回地址是「被打断那条指令的地址 + 4」，所以返回时要减 4 修正）；
  • 模式切 IRQ、I 位置 1 屏蔽后续 IRQ（这就是为什么中断处理里不能睡眠，也是为什么要有「上半部/下半部」）；
  • PC ← VBAR + 0x18。

软件侧的关键几行（arch/arm/kernel/entry-armv.S 的 vector_irq 形态）：

vector_irq:
    sub   lr, lr, #4          @ 修正流水线超前造成的 +4
    srsdb sp!, #SVC_MODE      @ 把 LR_irq 与 SPSR_irq 一起压到 SVC 栈
    cpsid i                   @ 关中断（此时已在 SVC 模式）
    cps   #SVC_MODE           @ 正式切到内核使用的 SVC 模式
    stmdb sp!, {r0-r12, lr}   @ 补齐 r0–r12，形成 pt_regs
    ...
    bl    asm_do_IRQ          @ 进 C 世界：读 GIC、找 irq_desc、调 handler

srsdb 这条指令值得单独注意：它能「把当前模式的 LR 和 SPSR 一起存到另一个模式的栈上」。这是 ARMv6 之后专门为异常处理加的指令，省掉了「先切模式再想办法拿 SPSR」的麻烦。

进到 C 之后发生的事（与 T06、T12 呼应）：

  1. asm_do_IRQ 用 plar（或 GIC 的 IAR 寄存器）读出中断号；
  2. 查 irq_desc[irq]，调用驱动注册的 handler（比如 GPT 的定时器 handler）；
  3. 定时器 handler 做两件事：更新 jiffies、触发调度器检查（scheduler_tick）；
  4. 如果当前任务的 vruntime 已经落后太多，或者时间片用完，把 TIF_NEED_RESCHED 标志置上；
  5. 中断返回前，内核检查这个标志——一旦置位，就在返回用户态的路上做切换（而不是在中断上下文里切）。

这里有一个极其重要的设计：中断处理函数本身不切换线程，它只「打标记」。真正的切换发生在返回路径上（ret_to_user / preempt_schedule_irq）。原因是中断上下文没有「进程」的概念，在那里切栈会让收尾工作（EOI、恢复中断）变得无处安放。

10. 一次线程切换，CPU 到底动了哪些寄存器

现在把前面所有零件拼起来。假设你的板子上有两个进程在跑，tick 到来时内核决定从 A 切到 B。这 10 微秒里发生的事，按时间顺序是：

10.1 内核栈上到底存了什么

10.2 switch_to 那五行汇编，逐行读

Linux ARM 的 __switch_to(prev, next, last) 核心就是「存自己、换指针、跳对方」三步。下面是按结构简化的形态（真实源码还处理 TLS 寄存器、CPU 号、架构版本分支，寄存器顺序与偏移随版本略有差异）：

__switch_to:
    @ r0 = prev, r1 = next
    add   ip, r1, #TI_CPU_SAVE        @ ip = &next->thread.cpu_context
    stmia ip!, {r4-r11, sp, lr}       @ ① 把「当前正在跑的现场」存进槽位
    ...
    ldr   sp, [r0, #...]              @ ② 取回 prev 上次被切走时记下的 sp
    ldmia r0, {r4-r11, sp, pc}        @ ③ 弹回现场，pc 一写就跳回去了

三行注释就是全部秘密：

  1. 存：只存 r4–r11 + sp + lr。因为 r0–r3、r12 是「调用者保存」的，调用 switch_to 的那段 C 代码已经不指望它们了；而用户态的 r0–r15 早就躺在 pt_regs 里了，不用重复存。
  2. 换 sp：这一行是「换线程」的真正分界线。sp 一变，栈就变了，之后所有 push/pop、所有局部变量、所有返回地址都落到另一个任务的地盘。
  3. 跳：ldmia ..., {pc} 把对方上次存的 lr 装进 PC。于是函数「返回」到了 B 上次停在的地方——不是返回到调用 switch_to 的地方，而是返回到 B 自己的历史里。这是上下文切换与普通函数调用最本质的区别。

用普通函数调用切线程会怎样？想一下：普通 bl 只保存一个返回地址，栈还是同一个栈，函数返回时必然回到「调用的下一条」。要让 B 从它自己的旧位置继续，你必须能伪造一个返回地址并换掉栈 —— 那正是 switch_to 干的事。所以「线程切换不能用函数调用来实现」不是规定，是硬件语义决定的。

10.3 页表也要换，但 TLB 不一定全刷

每个进程有自己的地址空间，所以 switch_mm 会写 CP15 的 TTBR0（用户空间页表基址）。写完之后：

做法代价什么时候用
换 TTBR0 + 全刷 TLB几十到上百周期，且之后每次访存都 TLB miss 一阵内核线程 ↔ 用户进程、ASID 用尽时
换 TTBR0 + 换 ASID（8 位）几乎免费，老条目标成「非当前 ASID」自然失效常态，ARMv7 支持 ASID，Linux 默认用它

这也回答了第 6 节留下的问题：指令 Cache 不需要因为换页表而刷，因为 A7 的 L1 是 VIPT 并且带 ASID，同一个虚拟地址在不同进程下不会互相污染。

10.4 回来的时候：恢复用户现场

B 被恢复后，从它自己的 switch_to 返回点继续跑，一路返回到 ret_to_user，最后做：

ldmia sp!, {r0-r12}        @ 弹回用户寄存器
add   sp, sp, #...         @ 跳过 sp/lr 占位
ldmia sp!, {pc}^           @ ① pc 写回 ② 带 ^ 表示同时把 SPSR 恢复到 CPSR

那一条 ldmia ..., {pc}^ 同时干了两件事：把 PC 装成用户态被打断的地址、把 CPSR 装成用户态的模式与标志位。从这一刻起，CPU 又变回「用户态」——硬件上就是 CPSR 的 M[4:0] 从 0b10011 变回 0b10000。

再加一句对照：你现在在学的 FreeRTOS 跑在 Cortex-M 上，用的是 PendSV 异常 + vPortSVCHandler，思路完全一样——硬件自动压 8 个寄存器（xPSR、PC、LR、R12、R3–R0），软件再补压 r4–r11 到任务栈，然后改 PSP 换栈。区别只是 ARMv7-A 用 SVC/IRQ 模式加 CP15，ARMv7-M 用 PSP/MSP 双栈指针加 NVIC。**同一套「存现场 → 换栈 → 弹现场」的三段式，跨架构通用。**

11. 切换到底有多贵：把账算给你看

项目量级说明
进入中断 + 保存 pt_regs数百纳秒十几条 store，L1 命中
CFS 选下一个任务数百纳秒红黑树取最左节点，O(log n)
switch_to 本体百纳秒级20 条左右的指令
换页表 + ASID数十纳秒一次 CP15 写 + 屏障
冷启动（Cache/TLB 重填）几微秒到几十微秒这才是真正的成本，且难以直接测量

所以在 tick=10ms、切换开销几微秒的情况下，单看 CPU 时间，切换本身只占千分之一；但如果你的程序是「大量小任务 + 频繁 IPC」，那么每个任务真正干活的时间可能还没它冷启动长——这就是为什么服务端会做「线程池 + 批量处理」，嵌入式会做「事件驱动单线程」。

实测方法（板子上都能跑）：

[board] grep -E 'ctxt_switches' /proc/$$/status        # 自己这个 shell 被切了多少次
[board] cat /proc/stat | grep ctxt                      # 全系统累计上下文切换次数
[board] perf sched record -- sleep 5 ; perf sched latency   # 谁在等、等了多久
[board] cat /sys/kernel/debug/tracing/available_events | grep sched_switch

把 sched_switch 事件打开，你能看到每次切换的 prev/next 和 prev_state——这就是第 10 节那条时间轴的逐条实证。

12. 常见误解对照

13. 自检：十道题

1

把 0xE3A00001 拆成位段，说出它是什么指令、操作数是什么。

看答案

cond=1110(AL)、[27:26]=00、I=1（立即数）、opcode=1101(MOV)、S=0、Rd=0000(r0)、rotate=0、imm8=1 → mov r0, #1。

2

bl 和 b 差哪一位？这一位由谁解释？

看答案

差 L 位（bit24）。译码器看到 L=1 就把 PC+4 写进 lr，同时把 PC 改为目标地址；L=0 只改 PC。

3

为什么 ldr r0,[r1] 后紧接 add r2,r0,#1 会停顿？

看答案

load 的数据要到访存末尾才有，前递路径覆盖不到「EX 就要用」的场景，硬件插停顿；编译器通常会在这两条之间插一条无关指令填缝。

4

一条 ldr 走了哪些硬件环节？哪一步失败会变成 SIGSEGV？

看答案

算地址 → TLB → 页表遍历 → 权限检查 → L1/L2/DDR → 写回。权限检查失败抛 data abort，内核判定为用户越权后投递 SIGSEGV；页表项不存在则可能补页后重试。

5

svc 触发后，硬件自动做了哪三件事？

看答案

LR_svc ← 返回地址；SPSR_svc ← CPSR；CPSR 模式位切 SVC 并跳到向量表 0x08。

6

IRQ 返回时为什么要 sub lr, lr, #4？

看答案

因为流水线超前取指，硬件保存的 LR 指向「被打断指令的下一条 +4」，减去 4 才回到真正该重试的指令。

7

switch_to 为什么不保存 r0–r3 和 r12？

看答案

它们属于「调用者保存」，调用 switch_to 的 C 代码已把它们当临时值丢弃；用户态的 r0–r15 早已在 pt_regs 里保存过，不必重复。

8

切线程后不刷 TLB 为什么还能正确？

看答案

ARMv7 的 TLB 条目带 ASID（地址空间标识），换页表时同时换 ASID，老条目属于别的 ASID 自然不命中，不需要全刷。

9

中断处理函数里为什么不能睡眠？

看答案

它没有「当前进程」的合法上下文可切（用的是中断栈，不是任何任务的栈），也没有可调度的 task_struct；且 I 位已屏蔽，睡下去没人能唤醒这套栈。

10

同样是「换栈」，Cortex-M 的 PendSV 和 Cortex-A 的 switch_to 有什么共同点？

看答案

都是「保存 callee-saved 现场 → 把 SP 换成对方保存的值 → 弹现场并写 PC 返回对方历史位置」。区别只在硬件自动压栈的范围、用什么寄存器存页表基址（A 用 CP15 TTBR0，M 常靠 MPU 或不用）。

14. 这一章要动手的命令

  1. 反汇编你自己写的一个 C 函数：arm-linux-gnueabihf-gcc -O0 -c x.c && arm-linux-gnueabihf-objdump -d x.o，找出 push/pop、bl、ldr 三种指令。
  2. 用 xxd 看二进制，挑一条指令手工拆位段，和反汇编对一遍（验证第 2 节）。
  3. arm-linux-gnueabihf-objdump -d vmlinux | grep -A5 "<__switch_to>"，找到那几行 stmia/ldmia（需要内核镜像的符号）。
  4. [board] grep ctxt /proc/stat 连看两次，算出你这台板子每秒切多少次。
  5. [board] cat /proc/interrupts 找定时器那一行，看每秒涨多少（对照 HZ）。
  6. [board] perf stat -e cache-misses,instructions ./busybox true，感受 Cache 命中率。
  7. [board] strace -c ls /，看一次 ls 到底发了多少次 svc。
  8. 在 FreeRTOS 那个工程里找到 xPortPendSVHandler，把它的汇编和本文第 10.2 节并排看。
