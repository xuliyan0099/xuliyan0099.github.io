TCP 状态机与 sk_buff：一次数据往返的完整路径

★ 一读 纯读约 2 小时 左侧是本卷目录 理论为主 · 实作可跳

TCP 的全部智能，几乎都压缩在一个十一状态的状态机里。序号、确认、窗口、超时重传，都是这个状态机在不同状态下的动作。

而它每天搬运的东西叫 sk_buff。理解了 sk_buff 的四个指针，你就理解了「为什么内核给一个包加三层头几乎不花时间」。

先玩一下：把 TCP 状态机走一遍

点「按剧本巡演」，它会带你走一整圈：被动打开 → 建连 → 主动关闭 → TIME_WAIT → 回到 CLOSED。也可以手动点事件按钮，只有当前状态可达的边才亮。

这张图上有两个状态最值得死记：CLOSE_WAIT 和 TIME_WAIT。

  • CLOSE_WAIT 堆积，几乎总是代码问题：收到对端 FIN 之后你没有 close(fd)。半开连接、异常路径没释放——查你的业务代码，不要改内核参数。
  • TIME_WAIT 堆积，是主动关闭方的正常代价。它的作用有两个：让最后一个 ACK 丢失时能重发；让这条连接的旧重复包在网络里消失（2MSL 之后旧包不可能还活着）。
TIME_WAIT 多了要不要调先看是不是短连接太多（改用长连接/连接池）；再看 net.ipv4.tcp_tw_reuse=1（只对「连出去」的连接生效，且要求时间戳单调递增）。tcp_tw_recycle 在 NAT 环境下会误杀，新内核已经删掉了——别照旧教程抄。

一、一次数据往返，序号与窗口在动

下面这条时序只画了「发—确认」的骨架。注意每一次 ACK 里的 ack 是「我期望的下一个字节」，而不是「我收到了多少」——差一，是初学者最常错的地方。

这三个数字构成 TCP 的流控闭环：seq 定位置，ack 定进度，win 定节奏。丢包则由另一套机制处理：重复 ACK 触发快速重传，超时触发慢启动。

二、带宽×时延：窗口到底该多大

一条链路上能有多少「在途数据」，由带宽时延积（BDP）决定。窗口小于 BDP，链路就跑不满——这是跨地域传输慢的根本原因，不是「带宽不够」。

三、sk_buff：四个指针撑起一次封装

内核里没有一个「包」的实体对象，只有 struct sk_buff 加一块数据缓冲。缓冲被切成四段，由四个指针标出边界：

head缓冲起点，malloc 时定下，之后不动。用来算「还能往前推多少」。分片信息也挂在这里。
data当前第一个有效字节。加头 = skb_push 把 data 往前挪，并返回新头指针。
tail当前最后一个有效字节的下一个位置。加尾 = skb_put 把 tail 往后挪。
end缓冲终点，也不动。用 skb_headroom() / skb_tailroom() 判断还有没有空间。

所以「加一个 TCP 头」的真实动作是：data -= 20; tail 不变，然后把 20 个字节写进去。没有 memcpy，没有重新分配。TCP → IP → 以太，三层头依次往前推，一共 54 字节的 headroom 就够（这正是内核分配 skb 时会预留的量）。

操作改哪个指针典型用途
skb_reserve(n)data 与 tail 同向后移 n分配时预留头部空间
skb_push(n)data 前移 n压入协议头
skb_pull(n)data 后移 n接收时剥掉协议头
skb_put(n)tail 后移 n追加数据
skb_clone()新建 skb，共享数据区一份数据要发给多个目的地
skb_copy()连数据一起复制需要独立修改内容时
误解：skb 是「包」，改了它就改了网络上的包skb 只是内存里的描述。真正发出去要等驱动 DMA 读完。也正因如此，发送完成后驱动必须等 DMA 结束才能释放 skb，否则就是 use-after-free——这类 bug 在内核里非常典型。

四、Nagle 与延迟 ACK 的「40 毫秒之谜」

两个优化撞在一起会产生经典现象：Nagle 算法说「有未确认的小包就先攒着」，延迟 ACK 说「收到数据等 40 ms 再确认，也许能搭个便车」。结果是小包互相等，每次交互多出 40 ms。

判断方法：ss -i 看 rtt 很小但应用层延迟稳定在 40 ms 左右，基本就是这个组合。解决不是无脑开 TCP_NODELAY（那会增加小包数量），而是让应用一次写够一个 MSS，或者改用批量协议。

动手（可选）：让状态机在你眼前跑

只在 🔧 实作模式展开PC 上即可。
  1. 开两个终端，一个 nc -l 9000，一个 nc 127.0.0.1 9000。第三个终端 watch -n0.5 "ss -tan | grep 9000"。
  2. 在服务端终端 Ctrl-C，观察 CLOSE_WAIT / FIN_WAIT_2 / TIME_WAIT 的出现与消失。
  3. 用 ss -tan state time-wait | wc -l 数 TIME_WAIT；再写个循环建连的小脚本，看它涨。
  4. 抓包 tcpdump -i lo -n 'port 9000' -w t.pcap，用 Wireshark 看序号、窗口、重传，和上面的状态图对照。

离开这一篇，你应该能

  • 不看书画出十一状态图，并指出 CLOSE_WAIT 与 TIME_WAIT 各自意味着什么。
  • 解释 ack 的含义，以及为什么窗口会变成 0。
  • 用 BDP 算出「多少窗口才能跑满 100 Mbps / 40 ms」，并解释 skb 加头为什么是 O(1)。
