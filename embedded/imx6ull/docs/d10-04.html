卷 10·用户态·第 04 篇

进程间通信：管道、共享内存、消息队列、信号

★ 一读 纯读约 2 小时 左侧是本卷目录 理论为主 · 实作可跳

进程之间默认互相看不见：各有各的地址空间，各有各的 fd 表。要传数据，必须让内核在中间当一次「中间人」。

四种 IPC 的差别，其实只有四个维度：要不要拷贝、有没有同步、能不能跨机、谁负责生命周期。把这四个维度记住，选型就不用背表格。

先玩一下：共享内存为什么必须配信号量

共享内存是唯一「零拷贝」的 IPC：两个进程的页表指向同一块物理页。但也正因为没有内核参与，谁先写、谁后读，全靠你们自己约定。

「撕裂读」是共享内存最典型的问题：A 写了结构体的前 4 字节，还没来得及写后 4 字节，B 就读走了。解决要么用信号量/原子标志做发布，要么用双缓冲 + 原子切换。

一、四种机制，四个维度

机制拷贝次数同步跨机典型用途
pipe / FIFO2 次（写进内核 + 读出）内核自带（阻塞）不能（FIFO 同机）父子进程、shell 管道、日志流转
共享内存0 次需要自己加（信号量/原子）不能大块数据、帧缓冲、数据库缓冲池
消息队列2 次内核自带（优先级/阻塞）不能（POSIX mq 仅同机）离散消息、需要优先级、解耦生产消费
信号0 次（只传一个编号）异步，随时打断不能通知、终止、超时；不能用来传数据

另外两个值得知道的：unix domain socket（可双向、可传 fd，比 TCP 回环快）、eventfd（专用于事件通知，常配 epoll）。

二、pipe：最古老也最实用

匿名管道只能用于有亲缘关系的进程（fork 之后继承 fd），命名管道 FIFO 可以给任意进程用。它的内核实现是一个环形缓冲（默认 16 页左右），写满就阻塞，读空也阻塞——这就是它「自带同步」的来源。

int p[2]; pipe(p);
if (fork() == 0) { close(p[0]); write(p[1], buf, n); _exit(0); }
close(p[1]); read(p[0], buf, n);   /* 阻塞直到有数据或写端全关 */

注意「写端全关」这个细节：读端会读到 EOF（返回 0），而不是永远阻塞。这也是为什么父进程必须 close(p[1])——忘了关，读端就永远等不到 EOF。这类 bug 在守护进程里非常常见。

三、消息队列与信号：各自的边界

  • POSIX mq：mq_open/mq_send/mq_receive，有优先级、有消息边界（不会像 pipe 那样粘在一起）。适合「一条一条命令」的场景。
  • 信号：只传编号，不传数据。处理器里能安全调用的函数极少（async-signal-safe），printf、malloc 都不在其中。正确做法是「信号里只置一个标志或写 eventfd，真正的处理回到主循环」。
  • 不要用信号做同步：它会打断任意指令，可能在你持锁时到达，导致死锁。

上面这道题故意把「答案」写成顺序，因为真实的选型往往不是单选：共享内存通常还要配一个信号量或 eventfd，pipe 常常配一个线程。工具是组合用的。

误解：共享内存一定比 socket 快单次大数据传输它确实快；但如果每次只传几十字节、还高频，信号量/原子操作的开销会盖过省下的拷贝。小消息用 mq 或 unix socket 往往更省心。
一个立刻能用的检查ipcs -m 看 System V 共享内存有没有残留（进程崩了不会自动删）；lsof | grep FIFO 看谁还开着管道。这两条能解决一大半「资源莫名泄漏」。

动手（可选）：三种 IPC 各写一遍

只在 🔧 实作模式展开PC 上即可。
  1. pipe：父写子读 1 MB，计时；再把读端故意不读，观察写端阻塞。
  2. shm：shm_open + ftruncate + mmap，两个进程各映射同一名字，一个写一个读；再用 sem_open 加通知。
  3. mq：mq_send 三条不同优先级的消息，mq_receive 看取出的顺序。
  4. 信号：sigaction 注册 SIGUSR1，处理器里只 write(eventfd)，主循环 epoll_wait 收到后再打印——这是唯一安全的写法。

离开这一篇，你应该能

  • 用「拷贝/同步/跨机/生命周期」四个维度比较四种 IPC。
  • 解释共享内存为什么必须配同步，以及「撕裂读」是什么。
  • 说出信号处理器里为什么不能 printf，正确做法是什么。
