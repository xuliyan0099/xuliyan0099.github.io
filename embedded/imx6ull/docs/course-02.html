一个字节能装什么

一个字节 8 个比特，只有 256 种组合。可就是这么点空间，能装下 0 到 255、−128 到 127、一个 ASCII 字符、半条地址、甚至一小段指令。同一个 0xFF，在不同上下文里能是 255、−1、空白字符或者「全部位为 1 的掩码」。这一课把这件事彻底拆开，你会得到一把万能钥匙：字节没

★ 一读 纯读约 1 小时 左侧是本卷目录 理论为主 · 实作可跳

这一课要回答的问题

① 位、字节、字、半字、双字分别多大？② 0xFF 到底是 255 还是 −1？③ 为什么 −1 的全 1 表示让减法可以用加法器做？④ 一个 int 存进内存，四个字节是按什么顺序放的？⑤ 溢出发生在哪一位？

1. 直觉：一把尺子，四种刻度

拿一根 8 厘米的尺子，同样一根尺子可以标成：

  • 绝对长度：0 到 8（对应无符号 0–255）；
  • 相对于中点的位置：−4 到 +4（对应补码 −128~127）；
  • 温度计的刻度（对应 ASCII 里某个字符编码）；
  • 一排开关的图案（对应位掩码）。

尺子没变，只是你换了一种读法。类比的失效处：尺子的刻度是连续的，而字节只有 256 个离散取值；所以「解释」之间会互相冲突——同一个字节不可能同时是 255 和 −1，必须由代码（类型）决定用哪种。

2. 硬件上：一个字节就是 8 根线

从内存读一个字节，硬件上就是同时读 8 条数据线的高低电平，把它们锁存进 8 个触发器。没有「正负」「字符」的概念，只有 8 个电平。

算术单元（ALU）也不区分符号：它只做 8 位二进制加法，然后把结果的高位进位、是否为零、符号位这些「副作用」暴露出来。所以：

你以为是硬件实际做的
255 + 1 = 2560xFF + 1 = 0x00，进位位 C=1（结果被截断到 8 位）
−1 + 1 = 00xFF + 0x01 = 0x00，和「255+1」是同一次加法
−128 − 1 = −1290x80 + 0xFF = 0x7F，符号位从 1 变 0，即「溢出」

第二行是关键洞察：补码让减法和加法共用同一个电路。−1 存成 0xFF，加 1 自然变 0。如果当年选了「符号位 + 绝对值」的表示（原码），减 1 加 1 就得单独设计减法电路，还要处理「+0 和 −0」两个零。

3. 补码是怎么算出来的

规则简单到可以直接背：取反加一。

 5  = 0b0000_0101
~5  = 0b1111_1010   （按位取反）
+1  = 0b1111_1011   （0xFB = −5）

验证：0x05 + 0xFB = 0x100 → 8 位截断为 0x00 ✅

为什么这样就能成立？因为 8 位加法天然是「模 256」的运算：a + (256 − a) = 256 ≡ 0 (mod 256)。补码做的事，就是给每个负数找一个模 256 下的加法逆元。这不是技巧，是数学。

由此推出三个必知的结论：

  1. 范围不对称：8 位补码是 −128 ~ 127，负数比正数多一个（因为 0 占了一个位置）。
  2. 最小负数 −128 没有对应的正数，所以 abs(-128) 会溢出。
  3. 比较大小要看符号位：这就是为什么汇编里有「有符号比较」和「无符号比较」两套指令。

4. 字节序：四个字节进内存的顺序

一个 32 位整数 0x12345678，存进内存要占 4 个字节。哪个字节放低地址？

i.MX6ULL 的 Cortex-A7 支持两种字节序，但 Linux 运行在小端模式。判断自己机器：读一个 int x = 1 的第一个字节，是 0x01 就是小端。

5. 除了整数，字节还能装字符

ASCII 把 128 个字符映射到 0–127：'A'=65、'a'=97、'0'=48、换行=10。这个映射是人为约定，不是硬件规定——所以才有 GBK、UTF-8 这些编码。

UTF-8 的聪明之处：它用变长字节表示 Unicode，但保证 ASCII 部分（0–127）与老 ASCII 完全一致，且多字节字符的每个字节都有特征位（首字节 110xxxxx，续字节 10xxxxxx），所以能安全地和 ASCII 混排。

# 看一个中文字符到底占几个字节
echo -n "中" | xxd
# 输出 e4 b8 ad —— 3 个字节，每字节最高位都是 1
python3 -c "print(len('中'.encode('utf-8')))"   # 3
python3 -c "print(len('中'))"                    # 1（Python 的 str 是码点）

这条命令解释了一个经典困惑：「为什么 C 的 strlen 算出来是 3，而屏幕上只有一个字？」因为 strlen 数的是字节，不是字符。

6. 实验：把「解释」动手验证一遍

# ① 同一个字节，四种读法
python3 - <<'EOF'
b = 0xFF
print("无符号:", b)
print("有符号:", b - 256)                 # 255 - 256 = -1
print("十六进制:", hex(b), "二进制:", bin(b))
print("取反加一验证:", hex((~0x05 + 1) & 0xFF))
EOF

# ② 溢出的两个面
python3 -c "print((127+1))"                    # 128，Python 会扩展精度，不溢出
python3 -c "import ctypes; print(ctypes.c_int8(127).value + 1)"   # 仍会溢出成 -128

# ③ 字节序
python3 -c "import struct; print(struct.pack('<I', 0x12345678).hex()); print(struct.pack('>I', 0x12345678).hex())"

第三条输出 78563412 与 12345678：前者是小端在内存里的样子，后者是大端。以后看到 xxd 输出「反着」的整数，就知道不是 bug。

在板子上再看一眼内核实际使用的大小：

[board] getconf LONG_BIT          # 32，说明指针 4 字节
[board] python3 -c "import sys;print(sys.byteorder)"   # little
[board] cat /proc/cpuinfo | grep -i features

7. 三条常见误解

8. 自测与动手

1

写出 −3 的 8 位补码，并验证 5 + (−3) = 2。

看答案

3 = 0b00000011，取反 0b11111100，加一 0b11111101（0xFD）。0x05 + 0xFD = 0x102，截断 8 位得 0x02 ✅

2

为什么 8 位补码的范围是 −128~127 而不是 −127~127？

看答案

0 占掉一个编码（0x00），256 个编码里正数用 1–127（127 个），负数用 128 个编码（0x80–0xFF），对应 −128~−1。

3

如何用一条命令判断你的机器是小端还是大端？

看答案

python3 -c "import sys;print(sys.byteorder)"，或 lscpu | grep -i byte。

4

printf("%d", 0xFF) 与 printf("%d", (char)0xFF) 结果为何不同？

看答案

前者按 int 解释得 255；后者先截成 8 位有符号 char（−1），再提升为 int 时做符号扩展，仍是 −1。

5

一个 32 位地址最多能寻址多少内存？为什么？

看答案

2^32 字节 = 4GB。地址是 32 位无符号整数，每个地址指向一个字节。

  2. 把 −3 的补码在纸上算一遍，再用 hex((~3 + 1) & 0xFF) 验证。
  3. echo -n "中" | xxd，数清字节数，与 strlen 的结果对照。
