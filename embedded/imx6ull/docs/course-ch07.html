卷 02·编译与运行·第 02 篇

交叉编译与工程构建

板子上装不下编译器，所以必须在 x86 的 PC 上编出 ARM 能执行的程序。这一章解决「编得出、传得过去、跑得起来」三个问题。

★ 一读 纯读约 12 小时 左侧是本卷目录 理论为主 · 实作可跳

本章目标

① 说清为什么要交叉编译；② 看懂工具链名字每个字段；③ 编出第一个 ARM 程序并在板子上跑；④ 会写多文件 Makefile；⑤ 会远程调试。

7.1 为什么不能直接在板子上编

PCi.MX6ULL 板子
CPUx86_64，多核 GHzARM Cortex-A7，单核 528MHz
内存8–32GB256–512MB
编译器几百 MB 随便装塞不下，也跑不动
指令集x86ARM

x86 的机器读不懂 ARM 指令。可执行文件必须与运行它的 CPU 架构一致，这就是 ABI 兼容。交叉编译 = 在 x86 上跑一个「只产出 ARM 指令」的编译器。

7.2 工具链名字怎么读

arm-linux-gnueabihf-gcc
 │    │     │    │
 │    │     │    └── hf：hard float，硬件浮点（VFP）
 │    │     └─────── eabi：嵌入式 ABI
 │    └───────────── linux：目标是 Linux 系统
 └────────────────── arm：目标 CPU 架构

工具链不是一个程序，是一整套：gcc（编译器前端）、as/ld（汇编与链接，来自 binutils）、glibc（目标平台的 C 库）、gdb（调试器）。这四样必须来自同一套，混用版本会出现各种链接错误。

编译 U-Boot 和内核用厂商工具链 apt 装的 gcc-arm-linux-gnueabihf 版本较新，编 4.1.15 这种老内核常报错。厂商提供的 gcc-linaro-4.9.4 那套才是配套的，装到 /opt 下并配好 PATH。

7.3 第一个 ARM 程序

$ mkdir -p ~/lab/ch07 && cd ~/lab/ch07
$ vim hello.c
#include <stdio.h>
#include <unistd.h>
int main(void)
{
    printf("hello from ARM, pid=%d\n", getpid());
    return 0;
}
$ arm-linux-gnueabihf-gcc -Wall hello.c -o hello_arm
$ file hello_arm
hello_arm: ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV),
dynamically linked, interpreter /lib/ld-linux-armhf.so.3 ...

# 本地 x86 编一份对比
$ gcc hello.c -o hello_x86 && file hello_x86
hello_x86: ELF 64-bit LSB pie executable, x86-64 ...

# 传到板子（或 NFS 目录）运行
$ scp hello_arm root@192.168.1.101:/root/
# 板子上
# chmod +x hello_arm && ./hello_arm
file 是你的第一道验证 编完先 file，看到 ARM, EABI5 才说明编对了。如果显示 x86-64，说明你用错了编译器（多半是 PATH 里 arm 版没生效）。

板子上跑不起来？常见三种

报错原因解法
Permission denied没有执行权限chmod +x
not found（明明文件在）动态链接器或 libc 版本不匹配换 -static 静态编译，或换匹配的工具链
Illegal instruction编译器用了板子 CPU 不支持的指令集加 -march=armv7-a -mfpu=neon -mfloat-abi=hard

7.4 Makefile：工程化的第一步

一个文件可以手敲 gcc，十个文件就必须用 Makefile。核心规则只有一条：目标 : 依赖 → 制表符 + 命令。注意命令前面必须是 Tab，不能是空格，这是新手第一个坑。

CC      = arm-linux-gnueabihf-gcc
CFLAGS  = -Wall -O2 -I./inc
LDFLAGS =
TARGET  = app
OBJS    = main.o uart.o gpio.o

$(TARGET): $(OBJS)
	$(CC) $(OBJS) -o $@ $(LDFLAGS)

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f $(OBJS) $(TARGET)

.PHONY: clean
写法含义
$@当前目标名
$<第一个依赖
$^所有依赖
%.o: %.c模式规则：所有 .c 都能这样变成 .o
.PHONY声明 clean 是伪目标，防止目录里有同名文件导致不执行
 
$ make            # 只编译改动的文件
$ make clean
$ make -j4        # 并行编译
$ make V=1        # 看实际执行的完整命令（排查问题用）
改头文件不重新编译？ 因为 Makefile 没写头文件依赖。简单办法：CFLAGS += -MMD，然后 -include $(OBJS:.o=.d)，让 gcc 自动生成依赖文件。

7.5 静态库与动态库

静态库 .a动态库 .so
链接方式代码被拷进可执行文件运行时才加载
体积大小（多个程序共用一份）
部署单文件即可，最省心必须把 .so 也放到板子上
适用嵌入式首选多程序共享、需热更新
 
# 静态库
$ arm-linux-gnueabihf-gcc -c uart.c -o uart.o
$ arm-linux-gnueabihf-ar rcs libuart.a uart.o
$ arm-linux-gnueabihf-gcc main.c -L. -luart -o app_static

# 动态库
$ arm-linux-gnueabihf-gcc -shared -fPIC uart.c -o libuart.so
$ arm-linux-gnueabihf-gcc main.c -L. -luart -o app_dyn
# 板子上找不到 .so 时
# export LD_LIBRARY_PATH=/root/lib
$ ldd app_dyn        # 看依赖了哪些库、能不能找到

7.6 远程调试：gdbserver

板子上跑 gdbserver，PC 上用 gdb-multiarch 连过去，就能像本地一样设断点、看变量、单步。

# PC：编带调试信息的程序
$ arm-linux-gnueabihf-gcc -g -O0 hello.c -o hello_dbg
$ scp hello_dbg root@192.168.1.101:/root/

# 板子：启动 gdbserver
# gdbserver :1234 ./hello_dbg

# PC：连上去
$ gdb-multiarch hello_dbg
(gdb) target remote 192.168.1.101:1234
(gdb) break main
(gdb) continue
(gdb) next
(gdb) print pid
(gdb) quit
板子上没有 gdbserver？ 用交叉工具链里的 gdbserver 编译一份（./configure --host=arm-linux-gnueabihf && make），或者用 Buildroot 勾选 BR2_PACKAGE_GDB_SERVER。第 11 章会讲。

7.7 动手任务

  • 编 hello.c 的 ARM 版，用 file 确认架构，传到板子（或 QEMU）执行。
  • 分别用 -static 和动态链接编一次，对比体积和运行结果，用 ldd 看依赖。
  • 把 hello.c 拆成 main.c + uart.c + uart.h 三个文件，写 Makefile 编译，改一个文件确认 make 只重编那一个。
  • 用 make V=1 观察实际命令；故意把 Makefile 的命令行缩进改成空格，看报错。
  • 打一个 libuart.a 和 libuart.so，两种方式都链接一次，验证运行差别。
  • 用 gdbserver 调试一次，在 main 里设断点，打印一个局部变量。

7.8 验收标准

  • 能解释 arm-linux-gnueabihf 每个字段含义
  • 能编出 ARM 程序并用 file 验证架构
  • 能独立写多文件 Makefile（含变量、模式规则、clean、.PHONY）
  • 能说出 Makefile 命令行必须用 Tab 的原因
  • 能说清静态库和动态库在部署上的差别
  • 能用 gdbserver + gdb 在目标机上设断点并查看变量
