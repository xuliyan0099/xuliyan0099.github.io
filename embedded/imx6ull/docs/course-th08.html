卷 08·启动链·第 01 篇

从第一个字节开始：BootROM → SPL → U-Boot

上电那一瞬间，CPU 的 PC 指向一个你不能改的地址——片内 BootROM。这一章把从那里到内核第一条指令的完整路径拆开：BootROM 怎么选启动设备、IVT 里有什么、DCD 为什么能初始化 DDR、U-Boot 怎么把控制权交给 Linux。

★ 一读 纯读约 5 小时 左侧是本卷目录 理论为主 · 实作可跳

本章要解决的问题

① 上电后 CPU 从哪取第一条指令；② BootROM 凭什么知道该从 SD 卡还是 eMMC 启动；③ 镜像头部的 IVT 和 DCD 各是什么；④ 为什么必须有 SPL 这一级；⑤ U-Boot 交给内核时，寄存器和内存必须是什么状态。

读完你应该能回答

  • IVT 在 SD 卡的哪个偏移？为什么是这个偏移？
  • DCD 的内容本质是什么？它为什么不能在内核里做？
  • SPL 和 U-Boot 的分工边界在哪？
  • U-Boot 启动内核时，r0/r1/r2 分别约定是什么？
  • 为什么 U-Boot 启动内核前必须关 MMU 和 D cache？

1. 五个阶段，一张表看清

阶段在哪运行谁提供核心任务典型耗时
① BootROM片内 ROM（0x0000_0000）NXP 出厂固化，不可改选启动设备、读 IVT、执行 DCD、跳到用户代码几十毫秒
② SPL（可选）片内 OCRAM（0x0090_0000）你编译（U-Boot 的 SPL）初始化 DDR/时钟/串口，把完整 U-Boot 搬进 DDR十几毫秒
③ U-BootDDR你编译命令行、存储/网络/文件系统、加载内核与 dtb100ms 级
④ 内核DDR你编译解压自身、建页表、初始化子系统、挂根文件系统、启 init1–2 秒
⑤ 用户空间DDR你的 rootfsinit/systemd 启动服务数秒

这张表的价值在于定位：板子起不来时，先判断卡在哪一级。串口有 BootROM 的输出说明①过了；有 SPL 输出说明②在跑；出现 U-Boot 提示符说明③成功；打印内核日志说明④接管了。每一级的证据都在串口上。

2. BootROM：你不能改，但必须懂的那段代码

复位后，CPU 的 PC 被硬件强制设为 0x0000_0000（或由引脚决定的别名地址），那里是片内 ROM。这段代码由 NXP 在流片时烧死，你一辈子改不了它，但它的行为决定了你镜像必须长什么样。

2.1 它怎么知道从哪启动

BootROM 读两类信息：eFUSE 里烧死的启动配置（量产时定），和BOOT_MODE 引脚的电平（开发板上常用拨码开关）。由此得到「启动设备列表」，然后按顺序尝试：

  • SD/eMMC（通过 USDHC 接口读）
  • NAND / QSPI NOR
  • USB（进入下载模式，等主机传镜像——这就是「救砖」通道）
  • 串口（极老式的下载协议）

「按顺序尝试」这点很关键：如果 SD 卡里有合法镜像，它就用 SD 卡；SD 卡不合法就去试下一个设备。所以插一张写好镜像的卡，往往能盖过板载 eMMC——这是开发板调试的常用手段。

2.2 从 SD 卡读什么：偏移 0x400 的 IVT

BootROM 不会读整张卡，它只读固定位置的一小块：SD 卡的 0x400 偏移处（第 1 个扇区的第 1024 字节）。为什么是 0x400？因为 0x000–0x1FF 是 MBR（分区表），0x200–0x3FF 常留给引导扇区，i.MX 约定把镜像头放在 0x400。

它读的这 4KB 里最关键的是 IVT（Image Vector Table），一个固定格式的结构：

偏移字段含义
0x00header魔数 0x402000D1（校验用，不对就认为不是合法镜像）
0x04entry用户代码入口地址（BootROM 最后跳到这里）
0x08reserved保留
0x0Cdcd_ptrDCD 数据在内存中的地址（0 表示没有）
0x10boot_data_ptr指向 boot_data 结构（镜像在内存的起始与大小）
0x14self_ptrIVT 自身在内存中的地址（自校验）
0x18csf_ptr签名/HAB 安全启动数据（不开安全启动时为 0）

而 boot_data 只有三个字段：镜像在内存里的起始地址、总大小、是否 plugin 模式。BootROM 靠它知道「该把多少字节从卡搬到内存的哪里」。

所以流程是：读 0x400 的 IVT → 校验魔数 → 按 boot_data 把镜像从卡搬到内存 → 如果 dcd_ptr 非 0，执行 DCD → 跳到 entry。

2.3 DCD：一段「寄存器写脚本」

DCD（Device Configuration Data）不是代码，而是一串命令，BootROM 会逐条执行。命令就三种：

命令tag作用
写寄存器0xCC往指定地址写 4 字节值（可批量）
检查（poll）0xCF轮询某地址直到某位变化（等硬件就绪）
延时0xC0等若干微秒/毫秒（等电源稳定、等 PLL 锁定）

它的典型内容：初始化 DDR 控制器的几百个寄存器、配置 IOMUX、通过 I2C 设置 PMIC 电压、打开必要时钟。这些必须「在镜像能装进 DDR 之前」完成——这就是 DCD 存在的唯一理由。

为什么 DDR 参数这么麻烦 DDR 是模拟电路 + 严格时序的集合：每一颗 DDR 芯片的行列地址位宽、刷新周期、CAS 延迟都不同，必须按芯片手册逐项写寄存器。所以 DCD 通常由 NXP 的 DDR 配置工具生成，不要手抄别人的 DCD——你的板子颗粒型号不同，抄来的参数会跑飞或随机丢数据。

3. 为什么还要有 SPL 这一级

既然 DCD 已经能把 DDR 初始化好，BootROM 为什么不直接把几 MB 的 U-Boot 搬进 DDR 跑完事？因为现实里有两类麻烦：

  • 初始化太复杂：多路电源上电顺序、PMIC 通过 I2C 配电压、PLL 逐级锁定、DDR 训练。DCD 只能「写寄存器 + 延时 + 轮询」，做不了条件判断和循环。
  • 镜像要加密 / 校验 / 多备份：需要真正的代码来做选择与校验。

SPL（Secondary Program Loader）就是「BootROM 之后、U-Boot 之前」的一小段代码，被 BootROM 搬进片内 OCRAM（128KB）执行。它的任务是：初始化 DDR 与串口，然后把完整 U-Boot 从 SD/eMMC 搬进 DDR，跳过去。

方式谁初始化 DDR镜像大小限制灵活性典型场景
DCD 直启DCD 脚本（BootROM 执行）BootROM 一次搬完，受 RAM 限制低，只能顺序读写寄存器简单开发板、快速验证
SPL 两级SPL 代码SPL 本身要 < OCRAM（留余量约 64KB）高，可判断、可重试、可加密量产板、复杂电源、安全启动

编译产物上看得更清楚：u-boot-spl.bin 是第一阶段，u-boot.bin 是第二阶段，两者用工具打包成一个 u-boot-with-spl.imx，烧到卡的 0x400 偏移处。BootROM 只认这个格式。

4. U-Boot 自己的两阶段

U-Boot 内部也分两段，源码里极其显眼（board_init_f / board_init_r），因为它必须解决一个物理问题：刚启动时它跑在「只读、位置固定」的存储映射里，而它需要一块可写的大内存。

  1. board_init_f：在重定位前运行。这时不能写全局变量（还在 ROM/低地址），只能用一个专门的 gd 结构（放 RAM）保存状态。它算出「RAM 怎么分」：给 U-Boot 自己留多少、给内核/设备树/根文件系统留多少。
  2. relocate_code：把 U-Boot 自身整体搬到 DDR 高地址（gd->relocaddr），并修正所有绝对地址引用。
  3. board_init_r：在新位置运行，这时才能自由使用全局变量、初始化外设、扫描存储、跑命令行。
算一笔：为什么重定位地址放在内存顶端
DDR 512MB：0x8000_0000 – 0x9FFF_FFFF
U-Boot 通常放顶端往下：如 0x9FF0_0000 附近（给自己留几百 KB）
内核与根文件系统从低端往上放：内核常在 0x8000_8000，dtb 在 0x8300_0000
理由：U-Boot 尽量不占「将来要装内核」的区域，避免搬迁时压到内核

常用命令必须熟：printenv 看环境变量、setenv bootargs ... 设内核参数、saveenv 存到存储、mmc dev 0 选设备、fatload mmc 0:1 0x80800000 zImage 把文件读到内存、bootz 0x80800000 0x83000000 启动。其中 bootargs 里的 console=ttymxc0,115200、root=/dev/mmcblk1p2 直接决定内核行为。

5. U-Boot 交给内核的那一瞬间：ARM 启动协议

这一跳有严格约定，写错任何一条内核都会在启动早期静默死掉（串口什么都不打印）。ARM Linux 的启动要求：

项目要求为什么
r0必须是 0历史约定，内核会检查
r1machine id（老式 ATAGS）；用设备树时常为 0用于匹配板级代码
r2ATAGS 或 DTB 的物理地址内核对硬件描述的唯一来源
MMU必须关闭内核要自己建页表与映射，继承别人的映射必然冲突
D cache必须关闭（或至少已 clean）cache 里的脏数据会让内核看到「不一致的内存」
I cache可开可关不影响数据一致性
中断必须关闭内核还没装中断处理代码
CPU 模式SVC内核以特权态启动
PC内核入口（zImage 的自解压入口）U-Boot 用函数指针直接跳过去

注意 r2 是物理地址：此刻 MMU 关着，CPU 眼里没有虚拟地址。这也是为什么你会看到 bootz 0x80800000 0x83000000 这种写法——两个数都是物理地址，前者是 zImage，后者是 dtb。

6. zImage 为什么还要「自己解压自己」

你烧进板子的是 zImage，但内核代码是压缩的（gzip / lzo / lz4）。它的开头是一小段不压缩的解压代码，U-Boot 跳到的就是这个入口：

U-Boot 跳入口→解压代码跑起来→把自己解到 0x80008000→跳过去→head.S 第一条指令

三种镜像格式的区别必须清楚，否则你会拿着错误的文件去烧：

文件内容谁认它
Image未压缩的内核（几十 MB）U-Boot booti 直接启动
zImage压缩内核 + 自解压头U-Boot bootz
uImagezImage 再加 64 字节 U-Boot 头（含校验与加载地址）老式 bootm

还有一个容易混的点：内核的链接地址与运行地址不同。内核被链接到虚拟地址 0xC000_8000（即 PAGE_OFFSET + 0x8000），而 zImage 解压到物理 0x8000_8000。这两个数之所以「对得上」，是因为内核启动早期建好页表后，用「物理 0x8000_0000 ↔ 虚拟 0xC000_0000」的直接映射把两者对齐。这是 T03 那个换算在启动阶段的第一次实战。

7. 十个常见误解

误解真相
「上电后跑的第一段代码是我的 U-Boot」是片内 BootROM，出厂固化。你的镜像由它加载。
「U-Boot 是必需的」不是。内核可由 BootROM 直接加载，U-Boot 提供的是「方便调试与加载」。
「DCD 是代码」它是命令数据（写寄存器/轮询/延时三条命令），由 BootROM 解释执行。
「DCD 和 SPL 是一回事」DCD 是数据脚本，SPL 是真代码。简单板用前者，复杂板用后者。
「镜像可以放在 SD 卡任意位置」BootROM 只认固定偏移（SD 上 0x400），位置错了直接当无效镜像。
「U-Boot 直接把内核解压好再跳」U-Boot 只跳到自解压入口，解压由 zImage 自己的头完成。
「传给内核的是虚拟地址」MMU 此刻关闭，r2 必须是 DTB 的物理地址。
「U-Boot 里开着 MMU 也没关系」进内核前必须关，否则内核建页表时会踩到已有映射。
「串口没输出就是硬件坏了」更常见是：镜像格式不对、启动设备选错、DDR 参数错、控制台参数错。要按五阶段逐级定位。
「DDR 参数可以抄现成板子的」颗粒型号、位宽、时序都不同，抄来的参数会随机丢数据，极难查。

8. 自检：能答出来才算懂

1

上电后 CPU 的第一条指令从哪来？能不能改？

看答案

片内 BootROM（0x0000_0000 映射区），NXP 出厂固化，不可修改。它负责选启动设备、加载你的镜像。

2

IVT 在 SD 卡的哪个偏移？里面最关键的两个字段是什么？

看答案

0x400。最关键 entry（用户代码入口地址）与 boot_data_ptr（镜像在内存的起始地址和大小），另外 dcd_ptr 决定是否执行 DCD。

3

DCD 的三类命令是什么？为什么它必须在 BootROM 阶段执行？

看答案

写寄存器（0xCC）、轮询检查（0xCF）、延时（0xC0）。因为 DDR 还没初始化，镜像无法装进 DDR，必须先由它把 DDR 控制器配起来。

4

SPL 解决了 DCD 解决不了的什么问题？

看答案

复杂初始化（电源时序、PMIC、DDR 训练）、条件判断与重试、镜像校验与解密。DCD 只能顺序写寄存器，做不了这些。

5

U-Boot 为什么要重定位？重定位前后代码有什么本质差别？

看答案

因为启动初期它跑在只读、位置固定的存储映射里，不能写全局变量、也没有足够空间。重定位后搬到 DDR 高地址才能自由用内存与外设。差别：重定位前只能用 gd 结构保存状态。

6

U-Boot 交给内核时，r0/r1/r2 各是什么？

看答案

r0=0；r1=machine id（用 DT 时常为 0）；r2=DTB 或 ATAGS 的物理地址。

7

为什么进内核前必须关 MMU 和 D cache？

看答案

MMU：内核要自建页表，继承映射必然冲突。D cache：缓存里的脏数据会让内核看到不一致的内存。

8

zImage、Image、uImage 有什么区别？分别怎么启动？

看答案

Image 未压缩（booti）；zImage 压缩 + 自解压头（bootz）；uImage 是 zImage 再加 U-Boot 的 64 字节头（老式 bootm）。

9

内核被链接到 0xC000_8000，为什么能跑在物理 0x8000_8000？

看答案

启动早期建立的直接映射把物理 0x8000_0000 映射到虚拟 0xC000_0000，偏移 0x8000 后正好对齐。链接地址是虚拟视角，运行地址是物理视角。

10

板子串口完全没输出，怎么快速缩小范围？

看答案

按五阶段定位：启动设备选择（拨码/eFUSE）→ 镜像是否烧在正确偏移（0x400）→ IVT 魔数与 boot_data → DDR 参数（换已知可用的镜像对比）→ 串口引脚与波特率。每一步都可以用「换一张已知可启动的卡」来二分。

9. 这一章要动手的命令

  1. hexdump -C u-boot.imx | head -20 —— 看到 0x400 前的填充与 IVT 魔数 d1 00 20 40。
  2. hexdump -C zImage | head -5 —— 看 zImage 头部的魔数与自解压标识。
  3. U-Boot 里 printenv bootcmd bootargs —— 看它到底怎么启动内核。
  4. U-Boot 里 mmc dev 0; mmc info —— 确认设备与容量。
  5. U-Boot 里 bdinfo —— 看内存布局与重定位地址。
  6. 内核启动后 cat /proc/cmdline —— 确认 bootargs 真的传进来了。
  7. 内核启动后 dmesg | head -40 —— 看它早期打印的机器型号与内存大小。
