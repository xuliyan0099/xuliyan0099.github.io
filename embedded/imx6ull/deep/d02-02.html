静态库与动态链接：PLT / GOT / PIC 全链路

同一个 printf，静态链接把它抄进你的程序，动态链接只给你留一个「跳板」。跳板怎么跳、地址什么时候才知道，是这一篇要讲清的事。

上一篇的坑，是链接时填的。这一篇讲另一种坑：链接时只留一张「欠条」，等程序跑起来才还。动态链接的全部魔法——.so、PLT、GOT、-fPIC——都是为这件事服务的。

先给结论：动态链接不是「把库放进去」，而是「把库的名字写进去，并在代码里留一个能被改写的跳板」。跳板叫 PLT，欠条叫 GOT。

先玩一下：第一次调用 printf，走了五步

点「下一步」。注意第一步之后 GOT 里存的还不是 printf，而是「解析器」的地址——这就是懒绑定（lazy binding）。

关键的一步是「回填」。GOT 必须放在可写的数据段（.got.plt），而代码段保持只读——这既是安全设计，也是 -fPIC 存在的根本原因。

一、静态库：把 .o 打包，用多少抽多少

.a 文件本质是一个 ar 归档：里面是一堆 .o，外加一个符号索引。链接器遇到 -lfoo 时并不会把整个库塞进你的程序，而是按需抽取：哪个 .o 定义了当前未解析的符号，就把那个 .o 拉进来。

  • 好处：产出一个自包含的可执行文件，不依赖目标机上的库版本，调试时符号齐全。
  • 代价：体积随用量线性增长；库升级必须重新链接、重新发布。
  • 坑：库的顺序。链接器从左到右扫一遍，被依赖的库要放在依赖者后面（gcc main.o -lfoo，不要反过来），否则符号还没出现就扫过去了。

二、动态库：只写名字，运行时再找

.so 是 ELF 的 ET_DYN 类型——它没有固定加载地址，可以映射到进程地址空间的任意位置。你的可执行文件里只留下三样东西：

DT_NEEDED「我需要 libfoo.so.1」。注意是 SONAME，带主版本号，不是文件路径。
.dynsym导入/导出符号表：我用到哪些符号、我提供哪些符号。strip 不会删它。
.plt + .got.plt每个外部函数一个跳板项，每个跳板项对应 GOT 里的一个可写槽位。

运行时由 ld.so（动态链接器）接手：读 DT_NEEDED → 在 /etc/ld.so.cache 里查路径（这个缓存由 ldconfig 生成）→ mmap 库 → 处理它自己的依赖（递归）→ 执行初始化函数 → 最后跳到你的 _start。

所以在板子上遇到「error while loading shared libraries: libxxx.so.1: cannot open shared object file」，原因永远是这一条链上的某一环：库没拷进 rootfs、没跑 ldconfig、或者 SONAME 对不上。LD_LIBRARY_PATH 能救急，但不该出现在产品里。

三、PIC：为什么代码里不能写死地址

动态库要能被多个进程共享同一份物理页，前提是它的代码段在所有进程里长得一模一样。只要代码里出现一个绝对地址，这个前提就破了：进程 A 把库映射到 0xB6F00000，进程 B 映射到 0xB7A00000，同一份代码不可能同时满足两个地址。

解决方式是把所有「需要地址」的地方改成「相对于 GOT 的偏移」，GOT 是每进程私有的（写时复制），代码段保持只读共享。这就是 -fPIC（Position Independent Code）。

写法编译选项代码段能否共享典型用途
绝对地址默认（非 PIC）不能静态链接、固定地址的裸机程序
GOT 间接-fPIC能共享库 .so，必需
GOT + 可执行也随机化-fPIE -pie能现代发行版的默认主程序，配合 ASLR
常见误解：-fPIC 会让程序变慢很多一次额外的间接跳转、多占一个寄存器存 GOT 基址，在现代 CPU 上通常只有百分之几。真正的代价常来自「为了 PIC 而放弃某些内联/常量折叠」。对性能敏感的库，正确做法是测，而不是猜。

四、懒绑定、立刻绑定与 RELRO

懒绑定的好处是启动快：程序启动时不解析任何符号，用到才算。坏处是第一次调用的延迟不可预测，而且 GOT 必须一直可写。

反过来，-Wl,-z,now（立刻绑定）+ -Wl,-z,relro,-z,now（完全 RELRO）会在启动时解析所有符号，然后把 GOT 标记为只读。代价是启动变慢一点，收益是攻击者没法改写 GOT 来劫持控制流。产品固件通常选后者。

怎么验证你的库到底依赖了什么readelf -d ./app | grep NEEDED 看依赖；ldd ./app 看实际解析到哪个路径（交叉编译的程序在 PC 上跑 ldd 会报错，正常）；objdump -d -j .plt ./app 看跳板。三件事一起看，动态链接就没有黑箱了。

动手（可选）：亲手制造一次「找不到库」

只在 🔧 实作模式展开目标：不是修好它，而是看清报错从哪来。
  1. gcc -shared -fPIC -Wl,-soname,libhello.so.1 -o libhello.so.1.0 hello.c，再 ln -s libhello.so.1.0 libhello.so.1。
  2. 编译主程序 gcc main.c -L. -lhello（注意 -lhello 找的是 libhello.so，所以还要建一个 libhello.so 的软链或直接给全路径）。
  3. 直接运行，会报 cannot open shared object file；LD_LIBRARY_PATH=. 再跑就好了。readelf -d 里能看到 NEEDED: libhello.so.1——这就是 SONAME 的作用。
  4. 把 -soname 去掉重新编库，再链接主程序，你会发现 NEEDED 变成文件名本身。这解释了「为什么升级库必须保留 SONAME 链接」。

离开这一篇，你应该能

  • 说清 .a 与 .so 在「链接时」和「运行时」分别发生了什么。
  • 解释 GOT 里存的到底是什么，谁在什么时候填它。
  • 回答「为什么 .so 必须用 -fPIC 编译」，并说出不加会怎样。
