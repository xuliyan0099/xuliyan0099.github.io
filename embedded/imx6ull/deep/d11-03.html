ftrace / perf / eBPF：内核里的可观测四件套

不加一行 printk，也能知道谁调了谁、谁慢了 3 毫秒、谁在频繁分配内存。三种工具的分工，比会用命令更重要。

不加一行 printk，也能知道「谁调了谁、谁慢了 3 毫秒、谁在疯狂分配内存」。这就是可观测工具的用处：它们读的是内核本来就在维护的信息。

三种工具的分工可以用一句话记住：ftrace 看「路径」，perf 看「热点」，eBPF 看「任意问题」。

先玩一下：一次函数调用的耗时去哪了

把采样频率拖到 1000 Hz，看开销怎么涨。这就是 perf 的取舍：频率越高越准，但越贵。

一、ftrace：看调用路径

ftrace 挂在 /sys/kernel/debug/tracing（或 /sys/kernel/tracing）。最常用的三个开关：

cd /sys/kernel/debug/tracing
echo function_graph > current_tracer        # 记录每个函数的进出与耗时
echo 'my_driver_*' > set_ftrace_filter      # 只跟自己的函数，输出小得多
echo 1 > tracing_on; sleep 1; echo 0 > tracing_on
cat trace | head -50

function_graph 的输出是一棵树：缩进表示调用深度，右侧是耗时。它最适合回答「这个 ioctl 里到底调了哪些函数、哪一段慢」。

  • function：只记函数名，开销最小。
  • function_graph：记进出与耗时，开销较大但信息最全。
  • 事件（tracepoint）：events/ 下按子系统分类，如 sched/sched_switch、irq/irq_handler_entry。比函数级更语义化。
  • kprobe：在任意地址插探针，连没有 tracepoint 的地方也能看。
  • trace_printk：写进 trace 缓冲而不是串口，适合高频日志（但别留在产品里）。

输出里最值得看的是「耗时异常的那一层」：如果 my_read 总共 3 ms，而它调用的 msleep 占了 2.9 ms，那你不用再猜了。

二、perf：看热点

perf 是采样型工具：每隔一段时间中断一次，记录当前 PC 与调用栈，最后统计「哪些函数出现得多」。它的强项是不需要预先知道问题在哪。

perf stat -a sleep 5                      # 总览：IPC、cache miss、上下文切换
perf record -F 99 -g -a sleep 10          # 采样 10 秒，带调用栈
perf report --stdio | head -40            # 按函数聚合
perf top                                  # 实时看热点

-g 记录调用栈，才能生成火焰图（flamegraph）：横轴是占比，纵轴是调用深度，宽条就是热点。火焰图最有用的一点是它显示的是「谁调用导致的」，而不是「谁自己耗时」。

perf 在板子上的三个注意1）需要 CONFIG_PERF_EVENTS；2）硬件 PMU 计数在虚拟化/容器里可能不可用，用 -e cpu-clock 代替；3）符号解析需要 /proc/kallsyms 与对应的 vmlinux，否则全是地址。

三、eBPF：在内核里跑你的判断

eBPF 允许你把一小段程序挂到 kprobe/tracepoint 上，在内核里过滤、聚合，只把结果送回用户态。于是「抓一万次调用的延迟分布」不再需要把一万条记录拷出来。

# bpftrace 一行看 tcp_sendmsg 的返回值分布
bpftrace -e 'kretprobe:tcp_sendmsg { @bytes = hist(retval); }'

# 看谁在调用 kmalloc，按进程统计
bpftrace -e 'kprobe:kmalloc { @[comm] = count(); }'

但要注意版本：i.MX6ULL 常见的 4.19 内核里 eBPF 是可用的，但 CO-RE、BTF、部分 map 类型要 5.x 才成熟。在板子上跑 bpftrace 之前，先 uname -r 与 ls /sys/kernel/btf/vmlinux 确认，否则会花半天在编译依赖上。

误解：可观测工具可以随便开在生产上ftrace 的 function_graph 在高压下有可观开销；perf 采样频率过高会拉高 CPU；eBPF 程序写错循环会拖死内核（老内核没有循环上限检查）。生产上先小范围、短时间、明确预算。
误解：有火焰图就能定位 bug火焰图解决「哪里热」，不解决「为什么错」。逻辑错误仍然要靠 oops、日志与代码。工具只回答它能回答的问题。

动手（可选）：三板斧各跑一次

只在 🔧 实作模式展开PC 上即可；板子上需要内核配置支持。
  1. 挂载 tracefs，用 function_graph + filter 抓一次 read 的调用树。
  2. perf record -F 99 -g -a sleep 5，生成火焰图（perf script | flamegraph.pl）。
  3. 若有 bpftrace：bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm]=count(); }'，看谁在疯狂打开文件。
  4. 对比三者输出的「粒度」：ftrace 是全量、perf 是采样、eBPF 是自定义聚合——这就是选择依据。

离开这一篇，你应该能

  • 说出 ftrace / perf / eBPF 各自回答什么问题，以及为什么不能互相替代。
  • 用 function_graph + filter 定位一次慢调用。
  • 解释采样频率与开销的取舍，以及 99 Hz 的由来。
