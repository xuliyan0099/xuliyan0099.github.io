ext4 磁盘布局：超级块、块组、inode 表、目录项与日志

文件系统不是抽象概念，它是一张画在磁盘上的表格。把这张表摊开，你就知道「删了文件为什么空间没回来」。

文件系统不是「一个抽象层」，它是一张画在磁盘上的表。你在 shell 里敲 ls，内核做的第一件事是读这张表；你敲 rm，它做的最后一件事是改这张表里的一个计数。

把这张表摊开之后，几个长期困扰人的问题会立刻有答案：为什么 rm 一个大文件只要一瞬间？为什么「删了文件但 df 不降」？为什么掉电之后 ext4 能自己恢复？

先玩一下：一个块组里都放了什么

ext4 把磁盘切成一个个「块组」，每组自带一份账本。鼠标在条上移动，看每一块的分工。

注意超级块的位置：偏移 1024 字节，不是 0。前 1 KB 留给引导扇区（历史上的 x86 习惯），所以你在文件开头 dd 出来的东西可能是空的。0xEF53 这个魔数就在超级块里，file 命令靠它认出「这是一个 ext 文件系统」。

一、inode 才是文件，目录只是名字到号的映射

Linux 里一个文件由三样东西组成，分开存放：

inode这个文件的一切属性：类型、权限、大小、三个时间、链接数、数据块位置。没有文件名。
目录项（dentry）「名字 → inode 号」的一行记录，存在目录文件的数据块里。
数据块内容本体。可能不连续，由 inode 里的 extent 树描述。

所以「一个目录里有多少文件」不是查一张全局表，而是读那个目录自己的数据块。目录项结构大致是：inode(4B) + rec_len(2B) + name_len(1B) + file_type(1B) + 名字，最后按 4 字节对齐。删除一个文件，就是把这一项的 inode 置 0、把 rec_len 并给前一项——这就是 rm 为什么快。

硬链接的本质也随之清楚：两个目录项指向同一个 inode 号，inode 里那个 i_links_count 加一。只有计数归零、且没有进程还开着它，数据块才被真正释放。这就是「删了文件但空间没回来」的第一种原因。

二、extent：ext4 相对 ext3 最大的改动

ext2/ext3 的 inode 里有 12 个直接块指针 + 单/双/三重间接。文件一大，指针就变成一棵「指针的树」，读一个 100 MB 文件要追很多层。

ext4 默认用 extent：一段连续的块用一条记录表示「逻辑块号 + 物理起始块 + 长度」。一个 inode 内联 4 条 extent（在 i_block 的 60 字节里），不够就长成一棵 B 树。文件越连续，元数据越少——这也是为什么「顺序写」的文件系统开销更低。

三、日志：掉电之后靠什么恢复

一次写文件要改好几处元数据：分配数据块 → 置位图 → 更新 inode 大小 → 改目录项 → 更新时间戳。如果改到一半断电，磁盘上就是「半个状态」——这就是早期 ext2 需要 fsck 几十分钟的原因。

ext4 用 JBD2 日志：先把「要改什么」写进日志区（journal，通常是 inode 8），写完一整条事务并打上提交记录，再去改真正的位置。断电重启后，只需重放「已提交但未落地」的事务，或丢弃「未提交」的事务。

三种日志模式的取舍：

模式记录什么一致性性能
journal元数据 + 数据都进日志最强最慢（数据写两遍）
ordered（默认）只记元数据，但保证数据先落盘不会出现「指向垃圾数据的 inode」接近 writeback
writeback只记元数据，数据不管顺序元数据一致，但内容可能是旧的最快
fsync 到底保证了什么保证「这个文件的数据 + 让它可见的元数据」都已落盘。它不保证目录项也已落盘——所以「新建文件后 fsync 文件」在某些情况下仍会丢文件。要连目录一起保证，得 fsync 目录 fd（并确保文件系统支持）。

四、四个常见误解

误解一：rm 会把数据擦掉不会。它只改目录项和链接计数，数据块被标记为空闲。要真擦，得 shred 或往整盘写随机数。SSD 上更难，因为磨损均衡让你无法指定物理块。
误解二：df 和 du 应该相等du 数的是「目录树里文件占的块」，df 数的是「文件系统元数据认为的空闲」。差异来自：被删除但仍被进程打开的文件、预留块（默认 5% 给 root）、日志区、以及稀疏文件的空洞。
误解三：延迟分配（delalloc）很危险它把「分配块」推到最后写回时刻，从而能把零散的小写合并成连续大块——顺序写性能的巨大提升就来自这里。代价是进程崩溃时最近的写可能丢（这正是 fsync 存在的理由）。
误解四：ext4 目录里文件名是顺序查找小目录是线性的；大目录会启用 dir_index（htree，一种 B 树），所以「一个目录放十万个文件」虽然不推荐，但查找并不是 O(n) 到底。

动手（可选）：把一张表读出来

只在 🔧 实作模式展开PC 上做一个循环镜像，不需要板子，也不动你的真盘。
  1. dd if=/dev/zero of=fs.img bs=1M count=32 造一个 32 MB 的空文件。
  2. mkfs.ext4 -b 4096 -I 256 fs.img 格式化；dumpe2fs -h fs.img 看超级块摘要（块数、每块组块数、inode 数）。
  3. debugfs -R "stats" fs.img 看块组分布；debugfs -R "ls -l /" fs.img 看根目录的目录项。
  4. 挂上去（mount -o loop fs.img /mnt），建一个文件，stat 看 inode 号与块数，再 debugfs -R "stat <inode>" 看 extent 记录——你会发现「逻辑块 0 → 物理块 N，长度 M」这一行就是文件在盘上的位置。
  5. 删掉文件但保持一个进程打开它（tail -f），再 df 与 du 对比，亲眼看到那点差异。

离开这一篇，你应该能

  • 画出「路径 → 目录项 → inode → extent → 数据块」这条链，并指出每一步读的是磁盘上哪块。
  • 解释 rm 为什么是 O(1)，以及空间什么时候才真的回来。
  • 说清 ordered 模式保证了什么、不保证什么，以及 fsync 的正确用法。
