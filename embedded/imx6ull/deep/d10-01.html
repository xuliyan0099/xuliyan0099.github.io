文件 IO 与 mmap：从 read 到直接映射寄存器

read 是一次拷贝，mmap 是一次「把页表改了」。理解了这句，你就能明白为什么用户态可以不写驱动去点灯，也能明白它什么时候不该用。

read 是「把数据从内核拷到你的缓冲」；mmap 是「把你的页表改一下，让同一块物理页同时出现在内核和你的地址空间里」。一字之差，代价差一次拷贝。

理解了这句，两个看起来神奇的事就有解释了：为什么用户态可以不写驱动去点灯（映射 /dev/mem），以及为什么 mmap 用错会 SIGBUS。

先玩一下：read 与 mmap 的路径差

看这两条路径在第 3 步分叉。read 多了一次拷贝，mmap 多了一次缺页。

所以小文件、一次性读，用 read 更简单；大文件、随机访问、多次读同一段，mmap 明显更省。但 mmap 不是「更快」，它是「换一种代价」。

一、mmap 在内核里做了什么

驱动侧的核心是 remap_pfn_range：它把一段物理地址（或 IO 内存）映射进用户空间。这也是 /dev/mem 的原理——把物理地址空间整个暴露出去。代价是完全没有保护：写错一个地址就是总线错误或死机。

为什么现在 /dev/mem 常常用不了CONFIG_STRICT_DEVMEM 会禁止映射普通 RAM 区域，只允许 IO 区域。这是安全设计，不是 bug。产品里正确的做法是写一个小驱动，只映射你需要的那一段寄存器。

二、MAP_SHARED 与 MAP_PRIVATE

标志写时发生什么别人能看到吗典型用途
MAP_SHARED直接改页缓存/物理页能，且会回写文件共享内存、寄存器映射、帧缓冲
MAP_PRIVATE写时复制（COW），产生私有副本不能只读加载可执行文件、进程私有数据
MAP_ANONYMOUS不对应文件，映射零页看是否 shared大块内存分配、父子进程共享

文件 mmap 还有一个容易忽略的点：映射长度不必是页大小的整数倍，但内核按页映射，最后一页的尾部字节属于「同一页里的别人」——所以写超出文件末尾的部分不会立刻报错，直到你触碰了文件长度之外的整页，才收到 SIGBUS。这是 mmap 最经典的崩溃原因。

三、用 mmap 点灯：可行，但要克制

i.MX6ULL 的 GPIO1 数据寄存器在 0x0209C000 附近，方向寄存器在 0x0209C004。理论上：映射这一页，往方向寄存器写 1，往数据寄存器写 0/1，就能点亮 LED。

int fd = open("/dev/mem", O_RDWR|O_SYNC);
void *base = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0x0209C000);
*(volatile uint32_t *)(base + 0x00) = 1 << 3;   /* 方向：输出 */
*(volatile uint32_t *)(base + 0x04) ^= 1 << 3;   /* 翻转电平 */

能跑，但要知道代价：绕过了 pinctrl（引脚可能还没复用成 GPIO）、绕过了时钟门控（时钟没开就写不进去）、绕过了内核驱动（两个使用者会互相踩）。调试可以用，产品不要用。这也是为什么「用户态点灯」的教程在板子上常常第一步就失败。

什么时候 mmap 是正解大帧缓冲、共享内存、只读大文件、把一段预分配的 DMA 缓冲给用户态直接填。判断标准是「数据量大、访问频繁、生命周期长」。反之用 read/ioctl 更安全。

动手（可选）：量一次拷贝的代价

只在 🔧 实作模式展开PC 上即可。
  1. 造一个 512 MB 文件，用 read 全量读到内存，计时。
  2. 用 mmap 映射后逐页求和，计时；第二次再跑一遍（页缓存已热）。
  3. 用 /usr/bin/time -v 对比最大 RSS 与 page fault 次数——mmap 的缺页会计入 minor fault。
  4. 把映射长度设成「文件长度 + 1 页」，往最后一页写一个字节，观察 SIGBUS（这是故意制造，不是 bug）。
